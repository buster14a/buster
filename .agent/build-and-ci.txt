     1: # AGENTS.md
     2: 
     3: Instructions for coding agents working in this repository. When this document
     4: and the code disagree, the code wins — update this file in the same change.
     5: 
     6: ## Project
     7: 
     8: **buster** is a from-scratch C compiler and toolchain written in C. The C
     9: frontend is the sole source-language frontend. The `ide` executable is a
    10: headless compiler, test runner, benchmark driver, fuzz entrypoint, and metadata
    11: tool; the target name is retained for build-script compatibility. The `ide cc`
    12: driver also orchestrates optional external shader toolchains for SPIR-V,
    13: NVPTX/PTX, AMDGCN/HSA code objects, Metal AIR/metallib, and DXIL; these
    14: pipelines add no linked or vendored dependency to the executable.
    15: Native outputs include freestanding PE32+ UEFI applications for x86-64 and
    16: AArch64 alongside the hosted desktop and mobile targets.
    17: 
    18: The compiler pipeline is:
    19: 
    20: ```text
    21: C source -> preprocessing/parsing/semantic analysis -> canonical IR
    22:          -> native machine IR/code generation -> object writer -> linker
    23:          -> direct core Wasm64 emission for wasm64 targets
    24: ```
    25: 
    26: The experimental custom-language frontend, its semantic model, its
    27: source-level interpreter/JIT entrypoints, the editor model built around it,
    28: and their C implementation and test files are intentionally removed. The
    29: `.bbb` fixture corpus and detailed former guidance remain as preservation
    30: material for a future redesign, but are absent from the generated build graph,
    31: unity translation unit, test registration, benchmarks, packaging, and CI.
    32: Shared active facilities remain: the canonical IR, optimizers, machine
    33: selection and scheduling, register allocators, x86-64 and AArch64 encoders,
    34: debug emitters, object formats, linker, generic object JIT, assembler, and
    35: Wasm64 backend. See `DORMANT_CUSTOM_COMPILER.md` for the historical reference.
    36: 
    37: ## Current compiler priority
    38: 
    39: Prioritize compiler throughput and producing an artifact as soon as possible.
    40: Do not add optimization passes or spend compile time improving generated code
    41: unless that work is explicitly requested. Prefer direct, predictable lowering
    42: and code generation with minimal analysis overhead.
    43: 
    44: The long-term implementation direction is to make the compiler broadly
    45: SIMD-friendly: prefer compact contiguous data, batchable lane work, masks for
    46: tails and irregular active sets, branch-regular loops, and layouts that can
    47: evolve from scalar to vector processing. Reducing branch and cache misses is
    48: therefore an architectural goal as well as a present-day performance lever.
    49: Keep the measurement discipline explicit: record SIMD-readiness and miss-rate
    50: improvements, but do not describe a scalar throughput regression as a current
    51: speedup merely because a proxy improved.
    52: 
    53: ### Data-oriented compiler design
    54: 
    55: - Optimize the real workload, especially its common cases, rather than every
    56:   theoretically possible case. Organize and measure the data before optimizing
    57:   the code that transforms it.
    58: - Where there is one, look for many — including along the time axis. Before
    59:   designing a scalar one-off path, look for the population across instructions,
    60:   values, blocks, functions, modules, repeated queries, or successive compiler
    61:   phases, and preserve enough context to process that population together.
    62: - Put frequently processed values together and separate different states and
    63:   cold metadata. Maximize useful information per cache line; avoid large hot
    64:   objects, padding, scattered flags, and pointer graphs that spend bandwidth
    65:   carrying data the current operation does not use.
    66: - Replace per-object, last-minute decisions with explicit classification
    67:   followed by homogeneous batch processing. Prefer masks, compact indices,
    68:   active counts, command buffers, state-specific arrays, and other forms that
    69:   can evolve into SIMD lanes over repeatedly testing independent booleans.
    70: - Do not reread or recompute facts already available. Hoist invariant reads,
    71:   calls, and branches even when an optimizing compiler might discover the same
    72:   transformation. Make constraints explicit so hot interfaces retain the
    73:   context needed to avoid generic work.
    74: - Precompute offline or during serial prewarm whenever practical. The cheapest
    75:   runtime operation is one that no longer exists; keep cold malformed-input and
    76:   fallback handling outside regular hot loops where the public contract allows
    77:   it.
    78: - Estimate before implementing: organize the cases, rank them by
    79:   `probability * count`, calculate approximate memory and compute cost, then
    80:   measure. Track useful information per cache line and passes per item, not
    81:   merely time attributed to a function.
    82: - Apply the process recursively. After improving one hot data transformation,
    83:   inspect the next largest remaining source of waste. Preserve maintainability,
    84:   debuggability, determinism, concurrency, and portability while doing so;
    85:   good data organization should improve all of them.
    86: - For buster, favor SoA or compact projections for hot compiler facts, explicit
    87:   active-lane masks and counts instead of fixed-maximum scans, grouped machine
    88:   instruction states where ordering permits, and prewarmed compact plans rather
    89:   than repeated metadata interpretation. Treat AVX-512 as a consequence of a
    90:   sound data layout, not the starting point: a compiler can optimize the final
    91:   instruction sequence, but it cannot repair wasteful data movement or context
    92:   that the program discarded.
    93: 
    94: ### SIMD transformation rules
    95: 
    96: - Choose the data layout before choosing SIMD instructions. Prefer SoA for
    97:   homogeneous transforms, use hybrid/tiled layouts only when measurements show
    98:   a scalar/SIMD tradeoff, and locally project fixed external AoS input into the
    99:   compact form a hot transform needs. Public interfaces do not have to mirror
   100:   internal storage.
   101: - For small divergent operations, compute candidate results and select with a
   102:   mask. For larger or more expensive divergence, first partition or compact
   103:   stable indices, then run a dedicated homogeneous kernel over each set. A hot
   104:   data-dependent branch needs strong measured predictability; a predictable
   105:   loop branch is not a problem merely because it is a branch.
   106: - Treat compare masks as useful data. Prefer compare -> mask -> compact/select
   107:   pipelines, advance compact outputs by mask population count, and use
   108:   precomputed permutation controls when a direct compress instruction is not
   109:   available. Preserve stable order whenever output order is observable.
   110: - Do not add software prefetch to linear streams the hardware already handles.
   111:   Consider it only for measured, sufficiently distant irregular pointer/index
   112:   accesses, and validate every supported microarchitecture. Likewise, avoid
   113:   habitual unrolling beyond the natural SIMD width: inspect generated code,
   114:   register pressure, and spills first.
   115: - Use non-temporal loads or stores only to prevent demonstrated cache pollution,
   116:   after the ordinary kernel is correct. Their ordering and visibility require
   117:   an explicit fence and ownership proof; they are never a cosmetic replacement
   118:   for normal memory operations.
   119: - Inspect the generated instructions for every explicit SIMD kernel. Count
   120:   useful lanes, loads/stores, shuffles, dependencies, spills, and work per
   121:   iteration. Wider code is a win only when the measured bottleneck is compute
   122:   rather than memory bandwidth and the target hardware executes that width
   123:   economically.

   125: ## Self-hosting — reproduce first
   126: 
   127: All contributors—humans and coding agents—should reproduce the current
   128: self-hosting fixed point from the repository root before changing the compiler:
   129: 
   130: ```sh
   131: ./build.sh test_self_host --config Release
   132: ```
   133: 
   134: `test_self_host` builds the trusted bootstrap compiler, compiles the complete
   135: unity-build compiler executable twice with its own C compiler, requires both
   136: generations to be byte-identical, and runs the stage-2 benchmark. The same build.c-owned workflow
   137: is also exposed as the `test_self_host` Ninja target. On Linux x86-64, its
   138: expanded equivalent is:
   139: 
   140: ```sh
   141: ./build.sh build --config Release -t ide
   142: build/Release/ide cc -Isrc -Ibuild/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g -v -fsource-metrics=build/ide-self.metrics src/buster/apps/ide/ide.c -o build/ide-self
   143: build/ide-self cc -Isrc -Ibuild/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g -v -fsource-metrics=build/ide-self-stage2.metrics src/buster/apps/ide/ide.c -o build/ide-self-stage2
   144: cmp build/ide-self build/ide-self-stage2
   145: build/ide-self-stage2 bench
   146: ```
   147: 
   148: On macOS, both `ide cc` invocations additionally receive the SDK returned by
   149: `xcrun --sdk macosx --show-sdk-path` through `-isysroot`, plus `-framework`
   150: arguments for AppKit, Metal, QuartzCore, and Foundation.
   151: 
   152: The target and fixed point are currently available on Linux and Windows x86-64,
   153: and on macOS. Preserve them when changing preprocessing, C semantics, IR, code
   154: generation, object writing, or linking, and report both self-hosting failures and benchmark
   155: regressions.

   157: ## Build
   158: 
   159: Three layers: `./build.sh` bootstraps `build/build` from `build.c` using
   160: **tcc**, which then drives CMake + ninja (multi-config, outputs in
   161: `build/<Config>/`).
   162: 
   163: The GitHub-hosted workflows are the bootstrap exception: the supplementary
   164: privacy broker and `.github/workflows/ci.yml` both compile `build.c` with the
   165: Clang already on the hosted image, because those images ship no TCC and modern
   166: macOS cannot run it, and because the broker must not download an unpinned
   167: compiler before it receives source. Neither produces a trusted or reusable
   168: compiler artifact, and neither runs the multi-compiler combination matrix,
   169: which needs TCC, GCC and Zig together. Canonical local and Forgejo workflows
   170: continue to bootstrap with TCC.
   171: 
   172: Keep build orchestration and policy in `build.c`, with the least practical
   173: process-launch and scripting overhead. Shell and PowerShell scripts exist only
   174: to bootstrap `build/build`; do not grow them into build systems. Use CMake only
   175: to generate/cache the platform build graph and let Ninja execute that graph;
   176: do not implement workflows, iteration, comparison, parsing, timing, or other
   177: general scripting in the CMake language when `build.c` can do the work
   178: directly. Prefer one persistent native build-driver process over chains of
   179: shell, CMake, and utility subprocesses.
   180: 
   181: ```sh
   182: ./build.sh                          # configure + build (Debug, clang)
   183: ./build.sh build -t test_all        # build and run the full test suite
   184: ./build.sh build --config Release -t test_all
   185: ./build.sh generate --sanitize && ./build.sh build -t test_all   # sanitized run
   186: ./build.sh test_all_combinations    # the full local matrix CI runs
   187: ```

   303: The opt-in LZ4 compatibility harness takes an external, pristine LZ4 v1.10.0
   304: checkout; upstream sources are never copied into or patched in this
   305: repository:
   306: 
   307: ```sh
   308: ./build.sh build --config Release -t ide
   309: ./build/build test_lz4 --config Release /path/to/lz4-v1.10.0
   310: ```
   311: 
   312: The checkout must be tag `v1.10.0` at commit
   313: `ebb370ca83af193212df4dcbadcc5d87bc0de2f0` with no tracked or untracked
   314: changes. The harness owns an explicit 24-unit source manifest and does not
   315: drive upstream's make or CMake files — upstream build-system detection is a
   316: later driver milestone — so it compiles in named stages and fails at the
   317: first one that breaks: the portable block library (`lz4.c`, `lz4hc.c`,
   318: `xxhash.c`), then the frame library (`lz4frame.c`, `lz4file.c`), then the CLI
   319: (`programs/*.c`), which is linked through `ide cc` so the driver itself is
   320: covered across a multi-file library plus executable. Everything is built with
   321: one flag set (`-I lib -I programs -DXXH_NAMESPACE=LZ4_ -DNDEBUG -O2`) because
   322: upstream's three makefiles agree on it and objects that disagree would not
   323: link. The CLI is the upstream `lz4-nomt` shape, without `-DLZ4IO_MULTITHREAD`,
   324: which keeps the compressed bytes reproducible. `tests/freestanding.c` is the
   325: one upstream unit left out of the manifest: it declares named-register
   326: variables for a raw syscall, which the C frontend does not support, and it is
   327: excluded rather than patched.
   328: 
   329: It then compiles and runs the upstream unit, round-trip, corruption, and
   330: interoperability programs — `fuzzer`, `frametest`, `fullbench`,
   331: `roundTripTest`, `decompress-partial`, `decompress-partial-usingDict`,
   332: `checkFrame`, `abiTest`, `checkTag`, plus `datagen` as the corpus generator
   333: they are written against — in the bounded `-i` forms upstream's makefile uses,
   334: so a run is minutes rather than hours. `abiTest` links against the harness's
   335: own static archive rather than an installed shared `liblz4`, since the harness
   336: must not depend on a system-installed lz4; it therefore checks the
   337: same-version API/ABI surface rather than cross-version stability.
   338: 
   339: The harness raises its own `RLIMIT_STACK` soft limit to 128 MB before it spawns
   340: anything, and the reason is Buster's frame layout rather than an upstream
   341: quirk: Buster gives every sibling block in a function its own frame slot where
   342: Clang overlaps the ones whose live ranges cannot intersect, so the fuzzer's
   343: `FUZ_unitTests` — a long chain of sibling scopes each holding a multi-megabyte
   344: buffer — lands on a 10,0 MB frame under FAST, MIR_STACK and QUALITY and a
   345: 24,7 MB one under NONE, against the Clang build's 271 KB. Under the 8 MB a
   346: login shell hands out, the Buster-built fuzzer dies with SIGSEGV before it
   347: executes a single test; the NONE build still dies at 32 MB and passes at 40 MB,
   348: so 128 MB is about three times the worst measured requirement. The program is
   349: correct — every test passes once it has room — so this is a code-quality gap,
   350: not a miscompile, and shrinking the frame is optimization work that is not to
   351: be added unasked. The limit is raised rather than the manifest trimmed or the
   352: iteration count lowered, because `FUZ_unitTests` is the part of the fuzzer
   353: worth running. A soft limit is inherited at spawn, which is why it is set once
   354: up front; it is a finite value rather than `RLIM_INFINITY`, which would move
   355: the loader's mmap layout, and it is POSIX-only — a Windows thread's stack size
   356: lives in the PE header of the image being run, so a parent cannot grant a child
   357: more of it, and there the harness reports the limit unchanged.
   358: 
   359: Cross-checking runs both directions over a deterministic corpus: each frame
   360: shape is compressed by the Buster CLI and by the Clang CLI, the compressed
   361: bytes must be identical — LZ4 output is deterministic for a given level, so a
   362: round-trip alone would accept two compressors that merely agree on what they
   363: can each undo — and each side's output is then decompressed and integrity-
   364: tested by the other. The rows cover `-1`, `-9` with linked blocks, block
   365: checksums and content size, `-12`, an incompressible corpus, legacy frames,
   366: and 4 MB blocks over an 8 MiB input; `tests/goldenSamples/skip.bin` covers
   367: skippable frames alone and embedded in a concatenated stream.
   368: `tests/basic_lz4_roundtrip.c` is the deterministic probe both compilers build
   369: and whose output must match byte-for-byte: it drives the block, HC, and frame
   370: APIs over unaligned little-endian records, explicit endian assertions, and a
   371: 4 MiB input, and it is cross-linked in both directions (Buster probe over the
   372: Buster archive, Clang probe over the Buster archive, Buster probe over the
   373: Clang archive) so a codegen difference stays separable from a linkage one.
   374: 
   375: Every workload runs under FAST, NONE, MIR_STACK, and QUALITY. The CPU axis is
   376: ordered so it cannot mask a portable failure: the `portable` configuration
   377: runs first and carries the upstream test suite, and only then do the explicit
   378: `-march=baseline` and `-march=native` configurations repeat the three compile
   379: stages, the probe, the large-input workload, and the full cross-check for all
   380: four allocators. Compiler cost and generated-code quality are reported
   381: separately and must not be conflated: `LZ4_METRIC` lines carry per-unit
   382: compiler wall time with the `-fsource-metrics=` source metrics, while
   383: `LZ4_THROUGHPUT` reports compress and decompress MB/s for the compression
   384: workload and `LZ4_CODEGEN` reports instructions retired and instructions per
   385: byte for the same runs. Both quote the uncompressed byte count, which is the
   386: conventional denominator for a compression rate in either direction. The
   387: throughput is end-to-end for the whole CLI process, including its startup and
   388: its reads and writes, so it is indicative rather than a benchmark and drifts
   389: with whatever else the machine is doing. The instruction counts do not: they
   390: come from the same Linux hardware counter as `STEP_INSTRUCTIONS`, read either
   391: side of a child that runs alone, and the counter follows this process tree
   392: only, so they are contention-immune and are the number to trend. Where no
   393: counter is available the `LZ4_CODEGEN` line is simply absent, which is never an
   394: error. For scale, a full matrix takes about seven minutes and one recorded run
   395: put the probe's cost at 13,819 instructions/byte for the Clang reference
   396: against 94,005 for QUALITY, 97,552 for FAST, 181,586 for MIR_STACK and 313,577
   397: for NONE over the same 53,7 MB workload — the allocator ordering the names
   398: promise, with NONE 3,3x QUALITY. Two properties of that run are worth keeping
   399: as expectations. Each allocator's instructions/byte was identical to three
   400: decimals across all three CPU configurations, the raw counts differing by about
   401: 200 in 5,2 billion, which is what a working counter over a deterministic
   402: workload should look like; and that identity means `-march=baseline` and
   403: `-march=native` currently generate the same code as the default for LZ4, so a
   404: future run where they diverge is signal rather than noise. Generated objects,
   405: metrics, archives, corpora, and logs remain under
   406: `build/lz4-v1.10.0-<pid>/`, which is about 1,4 GB for a full matrix — twelve
   407: copies of every object plus the corpora — and is not cleaned up on the way out,
   408: so delete the directories of runs you are done with.

   779: The harness first runs musl's own three header recipes with `sed`
   780: (`bits/alltypes.h` through `tools/mkalltypes.sed`, `bits/syscall.h`, and
   781: `src/internal/version.h`), then enumerates the manifest from the checkout the
   782: way musl's makefile globs it — musl's `BASE_SRCS`, every `.c` under each
   783: immediate subdirectory of `src/`, plus `src/malloc/mallocng`, `crt/` and
   784: `ldso/`, and musl's `ARCH_SRCS`, every `.c`, `.s` and `.S` under those
   785: directories' `x86_64` subdirectory — rather than carrying a written-down source
   786: list, so a release that adds or removes a translation unit shows up as a
   787: manifest change instead of a silent omission. On x86-64 that is 1356 portable
   788: `.c` files and 50 architecture files, and because every architecture file
   789: replaces a portable one of the same name the manifest is 1356 units: 1306
   790: portable C, 18 architecture C and 32 assembly. The replacement rule and what
   791: Buster does with it are described with the archive below.
   792: 
   793: One flag set drives both compilers, and it is musl's own `CFLAGS_ALL` minus the
   794: flags musl's `configure` only offers a compiler that accepts them: `-std=c99
   795: -nostdinc -fno-builtin -fno-strict-aliasing -fno-stack-protector
   796: -D_XOPEN_SOURCE=700 -O2 -g0` plus musl's seven include paths.
   797: `-ffreestanding` is absent because musl's configure falls back to
   798: `-fno-builtin`, which is in the set; `-fexcess-precision=standard`,
   799: `-frounding-math`, `-ffunction-sections`, `-fdata-sections`,
   800: `-fomit-frame-pointer`, `-fno-unwind-tables`,
   801: `-fno-asynchronous-unwind-tables` and `-Wa,--noexecstack` are `tryflag`-only,
   802: so a compiler that rejects them gets a build without them, which is the shape
   803: here. `-fno-stack-protector` is on both sides because Buster emits no canary
   804: and the reference build must not either: its canary load reads the thread
   805: pointer, which a program with no thread-local storage does not have.
   806: 
   807: The inline-assembly vocabulary the harness needs is the one a libc's atomics
   808: and thread pointer are written in, and it is bounded by two rules rather than
   809: by a list of accepted templates. A memory constraint (`m`, `=m`) carries the
   810: operand's storage rather than its value: the register the emitter assigns
   811: holds the address, the template reference expands to a memory reference
   812: through it, and no value is loaded or stored around the assembly. A literal
   813: register in a template is still refused, because one the emitter can also hand
   814: to an operand could be overwritten under the template's feet; the two
   815: exceptions are registers it can never hand out, each allowed only where it
   816: cannot alias anything -- the stack pointer as a memory base, which is the
   817: `lock orl $0,(%rsp)` fence idiom, and `%fs`/`%gs` before a colon, which is how
   818: a thread-pointer read is spelled. GNU's semicolon separates statements while
   819: this assembler reads one as a comment, so the inline-assembly path rewrites
   820: the separators, folding `lock ; insn` into the single statement the assembler
   821: wants and splitting the rest onto their own lines. The operand classes are the
   822: fixed general registers, `r`, `m`, `x`, `t` and `u`, and `X` for an operand a
   823: template does not care about the placement of, which is how musl's `remquol`
   824: keeps the addresses of its arguments from being discarded. Every unit in the
   825: manifest below compiles.
   826: 
   827: A literal register a template names has a third exception beside those two, and
   828: it is the one that makes the reason above stop applying: a register the asm has
   829: *already* committed to -- pinned by a fixed-class operand, or in its clobber
   830: list -- is one the emitter cannot hand to anything else, so a template naming it
   831: cannot overwrite anything. musl's `fmodl` is the shape: `fnstsw %%ax` beside an
   832: `"=a"` output, where the literal register is that operand's own.
   833: 
   834: `x` is GNU's SSE register class, and it is a second register file rather than
   835: another name for a general register. An operand in it is allocated a vector
   836: register out of its own pool -- so a general and a vector operand in one
   837: template can never collide -- carried in and out of its frame slot by a scalar
   838: `MOVSS`/`MOVSD`, and spelled in the template by the register name alone,
   839: because the SSE file has one name per register rather than a name per access
   840: width and the instruction the template wrote is what says how much of it is
   841: read. It carries a `float` or a `double` and nothing else: an x87 `long double`
   842: is the other file, and an integer would need a move between files that no
   843: operand here performs; both halves -- the value's type and the target having
   844: the file at all -- are refused by the frontend with a source diagnostic rather
   845: than left to the emitter. The vector register names joined the general ones in
   846: the literal-register refusal for the same reason the general ones are there:
   847: an operand is allocated one, and a template that also wrote one by hand could
   848: overwrite it. `tests/basic_c_asm_sse_output.c` and
   849: `tests/basic_c_asm_sse_input.c` are musl's own `sqrt`, `fabs` and `lrint`
   850: reduced to their operands and run under every allocator, with their answers
   851: checked -- an operand carried into the wrong register still assembles and still
   852: hands back a number.
   853: 
   854: `t` and `u` are the top of the x87 register stack and the one below it, and
   855: `st` is the clobber a template that pops declares. That file is where an
   856: x86-64 `long double` already lives, so these operands need no conversion around
   857: them at all -- and it is a stack rather than a set of registers, which is the
   858: whole of the emitter's model: the operands are pushed deepest first, so `u`
   859: lands in ST(1) and `t` on top; the template runs; an output in ST(0) is stored
   860: and popped; and whatever is still standing is discarded. An `st` clobber says
   861: the template popped what it was handed, so the depth is one shallower than the
   862: pushes left it and nothing is read back -- musl's `llrintl` is `fistpll`, which
   863: pops. The unwind runs *after* the general-file stores rather than straight
   864: after the template, because the six padding bytes a stored eighty-bit value is
   865: followed by are zeroed through RAX and `fmodl` reads its status word back out
   866: of AX. What the frontend refuses is everything that model does not hold for: a
   867: position named twice, a `u` without a `t`, an `st` clobber that is not beside
   868: exactly one `t` input, an operand that is not the 80-bit spelling, an operand
   869: reached through a pointer rather than sitting in a frame slot, and the class on
   870: a target with no x87 file. A literal `%st` in a template stays refused whatever
   871: the operands are, because a template that moved the stack itself would leave
   872: that accounting wrong. `tests/basic_c_asm_x87_output.c` and
   873: `tests/basic_c_asm_x87_clobber.c` are the fixtures, and `remquol` is the reason
   874: their answers are checked rather than assembled: its quotient bits are decoded
   875: out of the x87 status word, so a `fprem1` against the wrong stack position
   876: returns a plausible remainder beside a wrong quotient.
   877: 
   878: Two more things a template may do, and they are what a libc's startup and its
   879: dynamic loader are written in rather than its atomics. It may **name a
   880: symbol**: a line beginning with a dot goes through the same directive table
   881: module-level assembly uses, and every other line reaches `assembly_encode`
   882: with the relocations it reports recorded against the module, so musl's
   883: `GETFUNCSYM` -- `.hidden sym` followed by `lea sym(%rip),%0` -- reaches the
   884: object as a PC-relative relocation against a hidden symbol the block may be
   885: the only thing that names. The name a new symbol record keeps is the one in
   886: the instruction's IR literal rather than the one in the substituted copy: the
   887: retry that grows the code buffer rewinds the attempt arena, and a record that
   888: outlives the attempt cannot point into it (`codegen_assembly_durable_name`).
   889: And it may **write the stack pointer**, on the one condition that its last
   890: statement is an unconditional `jmp`, which is musl's
   891: `CRTJMP` -- `mov %1,%%rsp ; jmp *%0`. The rule the exception hangs on is not
   892: where the name appears but that nothing the emitter puts after the block is
   893: reached: RSP is never handed to an operand, so writing it cannot land under
   894: one, and the frame it does move is never read again. The AT&T dereference star
   895: comes with it and only directly in front of an operand reference, so `*` can
   896: only ever dereference a value the C side computed.
   897: `tests/basic_c_inline_asm_symbol.c` carries all of it, run under every
   898: allocator: the three PC-relative references are checked against the addresses
   899: they should have produced, and the hand-off ends the process itself because
   900: nothing after it runs.
   901: 
   902: One flag the set does not carry is a dialect, and it used to make the two
   903: compilers read different source: `ide cc` predefined `__GNUC__` only in a GNU
   904: dialect while Clang predefines it in every one, so under `-std=c99` musl's
   905: `<stddef.h>` gave Clang `__builtin_offsetof` and gave Buster the portable
   906: `((size_t)((char *)&(((type *)0)->member) - (char *)0))`, and every `offsetof`
   907: in the archive was a different expression on the two sides. That is fixed —
   908: the macro describes which extensions the compiler implements, not which ones
   909: the dialect permits, and both reference compilers report it beside
   910: `__STRICT_ANSI__`; `__STRICT_ANSI__` is the switch that still flips. Both
   911: sides now take the same branch of every one of these headers. The habit the
   912: divergence taught is still worth keeping: a class that looks like a Buster gap
   913: can be a branch the reference never took, so check what the unit actually
   914: preprocessed to (`ide cc -E` with the same flags) before naming a construct.
   915: `tests/basic_c_null_pointer_offsetof.c` still pins that the two `offsetof`
   916: spellings agree for the single-member designator it covers; they did not agree
   917: for a nested one, which is what `pthread_exit` walking the robust list stopped
   918: reaching when the predefine changed and is fixed one commit later, and
   919: `tests/basic_c_type_generic_math.c` pins the predefines themselves.
   920: 
   921: `<math.h>` splits on the same macro, and there the two branches are not
   922: interchangeable, which is why the fold below outlived the divergence. `NAN` is
   923: `__builtin_nanf("")` for a compiler that advertises the builtins and
   924: `(0.0f/0.0f)` for one that does not; both sides take the first branch now, but
   925: the second is still what any freestanding or older header hands the frontend,
   926: and it is an operation that creates a NaN rather than a constant that already
   927: is one — and IEEE-754 leaves the sign of an invalid operation's NaN
   928: unspecified, which the two available answers use:
   929: x86 hardware produces the negative default NaN, Clang folds to the positive
   930: quiet one. The frontend therefore folds the four operations that create a NaN
   931: out of operands that are not NaN — `0/0` and `inf/inf`, `0*inf`, `inf-inf`
   932: and `inf+(-inf)` — to the positive quiet NaN at every width, in the
   933: in-function path and in the x87 static-initializer folder alike, and reads
   934: constant operands through a negate and through a conversion between float
   935: widths so a source-level `-0.0f` and a widened literal fold the same way.
   936: Ordinary constant arithmetic is still left to the backend: only the invalid
   937: operations fold, because only their answer is a compatibility choice rather
   938: than a value. `tests/basic_c_created_nan_sign.c` carries the created and the
   939: propagated signs, and the created NaN's bytes are in
   940: `tests/basic_c_long_double_static_initializer.c` beside the rest of the x87
   941: initializer bytes Clang writes. `INFINITY` splits the same way, and its
   942: non-GNU spelling is the overflowing literal `1e5000f`, which the x87 folder
   943: refused until it learned that an overflow is a value — the infinity C names —
   944: rather than a failure. Twenty-one `src/math` units and `functional/strtold`
   945: stopped on that literal, and `fpclassify`'s `1/0.0` on the division by zero
   946: beside it, which creates an infinity rather than a NaN. The same 21 units and
   947: the same `strtold` stopped a second time on the *other* spelling when
   948: `__GNUC__` started being predefined everywhere and the header began choosing
   949: `__builtin_inff()` and `__builtin_nanf("")`: the folder is a recursive descent
   950: over arithmetic and knew no calls at all, so the two constant-valued
   951: intrinsics fold there now the way they already folded in
   952: `c_ir_constant_evaluate`, with only the empty NaN payload accepted.
   953: `tests/basic_c_long_double_static_special.c` carries both spellings against one
   954: set of expected bytes, and the `long double` bullet under "Platform and backend
   955: boundaries" is where the folder's whole boundary is written down.
   956: 
   957: One flag the reference carries and Buster does not is
   958: `-fcomplex-arithmetic=improved`. Clang's default for C lowers a complex
   959: multiply or divide to the compiler-runtime helpers -- `__mulxc3`, `__divxc3`
   960: and their siblings -- which live in libgcc or compiler-rt, and this harness
   961: links neither, so a reference object that calls one cannot be linked at all;
   962: musl's `cpowl` is such an object. `improved` is the inline Smith form the
   963: Buster frontend emits, bit-identical to it over the operand matrix described
   964: under `_Complex` below, so the flag is the reference-side counterpart of the
   965: probe's `-mstackrealign`: it makes the comparison possible rather than
   966: changing what is compared. It is the one option in the set that dates the
   967: reference compiler -- Clang grew `-fcomplex-arithmetic=` in 20 -- and an
   968: older one rejects it as an unknown option rather than miscompiling, which the
   969: reference build reports before any Buster invocation runs.
   970: 
   971: The Clang reference build runs first and every unit must compile — a musl unit
   972: Clang cannot build under this flag set is a broken workspace, not a Buster
   973: defect, and finding that out before a thousand Buster invocations keeps the two
   974: apart. Buster then compiles the same manifest under FAST, and every unit that
   975: fails is printed as a `MUSL_UNSUPPORTED` line carrying the first line of its
   976: diagnostic. That list is the inventory: it names every component the archive
   977: below is missing and why.
   978: 
   979: The gate is the compiled-unit count together with a hash of the newline-joined
   980: sorted failing paths. The count alone would accept a change that fixed one unit
   981: and broke another, so both are pinned as `MUSL_EXPECTED_COMPILED_UNITS` and
   982: `MUSL_EXPECTED_FAILURE_HASH` in `build.c` and both are printed on the
   983: `MUSL_INVENTORY` line, which is what a deliberate rebaseline needs. A fix and a
   984: regression therefore both move a number that has to be updated on purpose.
   985: 
   986: Both object sets are archived with `ar` through a response file — a musl
   987: archive is a thousand members, which is past what a Windows command line takes
   988: — under musl's own `AOBJS` rule, which puts the `src/` units in `libc.a` and
   989: nothing else. The `crt/` units are excluded for the reason in the
   990: startup-object note below, and `ldso/` because a static libc that carries the
   991: dynamic loader hands the linker a `dlopen` that wants `setjmp`, which is
   992: architecture assembly this build does not have; both are still built, and
   993: `MUSL_ARCHIVE` counts them as `startup_emitted`/`startup_absent` and
   994: `loader_excluded`. That is what makes the archive linkable by an ordinary
   995: program rather than only by a program that defines its own entry.
   996: `MUSL_ARCHIVE` also carries the wall time both archives took. The freestanding
   997: probe is then linked against each, and every link in the harness reports its
   998: own `link_us`. The probe,
   999: `tests/basic_musl_freestanding.c`, is a project-owned program with no include
  1000: of any kind: it is compiled `-nostdinc` against musl's own headers, entered at
  1001: `_start`, and linked with `ld -static` and nothing else, so no compiler driver,
  1002: no startup file and no host libc are on the link line and everything it
  1003: resolves comes out of the musl archive. It exercises the string, memory,
  1004: search and character routines, the seventeen x87 `long double` units named
  1005: below -- sixteen of them called directly and `__rem_pio2l` through `sinl` --
  1006: and the twenty-two under `src/complex` that take or return a
  1007: `long double _Complex`, each wide result recorded as the sign, exponent and
  1008: significand fields of musl's own `union ldshape` so that a result one ulp off
  1009: cannot pass, and a complex one recorded as both of its halves that way. It
  1010: writes a transcript through raw `write` and `exit` system calls; the Clang-built and Buster-built transcripts must be
  1011: identical byte for byte, so a routine that computes a different answer fails
  1012: the run where a link-and-exit check would not. The probe runs under FAST, NONE,
  1013: MIR_STACK and QUALITY against the one Buster-built archive, because the four
  1014: allocators have to produce the same answers rather than each produce some
  1015: answer. The reference is compiled with `-mstackrealign`: at process entry the
  1016: stack pointer carries the alignment the kernel leaves rather than the one a
  1017: `call` leaves, and Clang's aligned vector spills need the realignment while
  1018: Buster's emitters, which spill through plain moves, do not.
  1019: 
  1020: Two more links follow, and they are the ABI report. Two separately compiled
  1021: object sets calling each other across musl's own declarations is a direct test
  1022: of the calling convention, the struct layouts and the return shapes the two
  1023: compilers agree on, and a disagreement surfaces as a wrong answer rather than
  1024: as a link error. The first link is the Clang-compiled probe against the
  1025: Buster-built archive: a Clang caller into Buster-built musl. The second is that
  1026: same probe against a mixed archive, built by taking Buster's object for every
  1027: second unit and Clang's for the rest, so musl's own internal calls — `strstr`
  1028: into `memchr`, the character tables, the search routines — cross the boundary
  1029: in both directions inside one program. Both must reproduce the reference
  1030: transcript, and each prints a `MUSL_ABI` line.
  1031: 
  1032: The Buster-compiled probe is deliberately not linked against the Clang
  1033: archive. That pair does crash, and the reason is not an ABI disagreement: the
  1034: probe is entered at `_start` with the alignment the kernel leaves rather than
  1035: the one a `call` leaves, which is why the reference is compiled with
  1036: `-mstackrealign`, and the Clang probe built without that flag crashes against
  1037: Clang's own archive in exactly the same way. The Buster driver has no such
  1038: flag, so that direction would measure the probe's entry rather than the two
  1039: compilers, and the mixed archive covers what it was meant to cover.
  1040: 
  1041: Everything above is linked `-static`, and a shared object is the other half of
  1042: what a libc is. `libc.so` is built from the same object set on both sides, with
  1043: the three differences musl's own `libc.so` recipe states. `ldso/dlstart` and
  1044: `ldso/dynlink` join it, because musl's `LDSO_OBJS` rule puts the loader in the
  1045: shared library and its `AOBJS` rule keeps it out of the archive.
  1046: Nothing is substituted into it: `src/thread/__set_thread_area` used to leave
  1047: it for a project-owned object, and six more names used to need one, and both
  1048: sets are musl's own assembly now.
  1049: 
  1050: The link is `ld -shared -Bsymbolic --no-undefined -e _dlstart`, and the first
  1051: three of those are musl's own.
  1052: 
  1053: - `-e _dlstart`, because musl's `libc.so` *is* its dynamic loader and that is
  1054:   the entry point the kernel jumps to when the file is a program's `PT_INTERP`.
  1055:   It is what makes a shared musl testable here at all: nothing else on the
  1056:   machine can load one.
  1057: - `--no-undefined`, because a shared object may carry unresolved names and
  1058:   musl's loader will not. It reports each one it cannot relocate and leaves at
  1059:   exit 127, before the program's first instruction; upstream's `configure` asks
  1060:   for the flag for exactly that reason, and here it turns a name the object set
  1061:   is missing from a silent runtime death into a link error naming the symbol.
  1062: - `-Bsymbolic`, because this library is linked from the one object set the
  1063:   rest of the harness already measured and that set is compiled without
  1064:   `-fPIC`. The flag is a code model now rather than an accepted no-op --
  1065:   described under machine selection below -- so what forces `-Bsymbolic` here
  1066:   is the single object set and not a missing flag: a second,
  1067:   position-independent set would retire it, at the cost of another two
  1068:   thousand compiles. What the non-PIC set does emit is PC-relative, so the only
  1069:   references `ld` refuses to place in a shared object are the ones to symbols
  1070:   another object could interpose. Binding those at link time is what musl's own
  1071:   build does for everything except its public data, through `--dynamic-list`;
  1072:   taking the whole set costs the copy relocations that list exists to preserve
  1073:   and buys a shared musl out of the object set that is already built. The probe
  1074:   below references no libc data object, so nothing it measures turns on the
  1075:   difference.
  1076: 
  1077: One object set rather than two is the other departure. musl compiles a second,
  1078: `-fPIC` copy of every unit for `libc.so`; this harness links the one set both
  1079: compilers already produced, which keeps the shared stage at two links instead
  1080: of another two thousand compiles, and it is what makes the shared link a
  1081: statement about the code generation the rest of the harness already measured.
  1082: 
  1083: `--no-undefined` is what used to need a project-owned file beside the object
  1084: set. A static link pulls only the archive members a program reaches, so the
  1085: seven assembly-only units cost nothing until something calls one; every object
  1086: handed to `ld -shared` is in the result and every relocation in it is resolved
  1087: when the library loads, and six names were left over -- `__syscall_cp_asm` with
  1088: the three labels `__cp_begin`, `__cp_end` and `__cp_cancel` that bound its
  1089: cancellation window, and `setjmp`/`longjmp`. Every one of them is musl's own
  1090: x86-64 assembly now, so the shared object set is the compiled one and nothing
  1091: else. `setjmp` and `longjmp` in particular used to trap -- neither is
  1092: expressible in C -- and musl's loader saves a jump buffer around `dlopen`, so
  1093: that substitution is what held every libc-test unit that opens a library out of
  1094: the comparison.
  1095: 
  1096: The dynamic probe is `tests/basic_musl_freestanding.c` again, resolved against
  1097: the shared musl instead of the archive and started by the loader inside it. The
  1098: interpreter is named by absolute path because there is no installed musl to
  1099: point at: upstream installs `libc.so` as `/lib/ld-musl-x86_64.so.1` and links
  1100: every program against that name. Its gate is the static probe's, and
  1101: deliberately so: producing a shared object that links says nothing, and the
  1102: transcript has to be the reference's byte for byte under all four allocators,
  1103: so a routine that computes a different answer once it has been relocated rather
  1104: than linked fails here. A `MUSL_SHARED` line reports each side's library and a
  1105: `MUSL_DYNAMIC` line each program. The Buster-built library is about three times
  1106: the size of the reference's, which is the archive's ratio and the same emitter
  1107: spilling through the frame rather than through registers.
  1108: 
  1109: One compiler change came out of this and it is the only one that did: a
  1110: read-only object that carries a relocation is laid out with the writable data
  1111: rather than in the read-only section, described with the rest of the C rules
  1112: below. Twenty-one musl units hold one -- `__ctype_b_loc`'s `ptable`, the
  1113: `FILE *const stdout` trio, the locale tables -- and each of them put a
  1114: write-when-relocated word on a page the loader maps read-only, which is a
  1115: `DT_TEXTREL` musl's loader does not undo for the file it was itself started
  1116: from. `-fPIC` does not retire this one: a relocation into a read-only object
  1117: still has to be applied when the image loads whatever the code model is, and
  1118: what would retire it is a relocated-read-only section of its own, which this
  1119: object writer does not have.
  1120: 
  1121: The manifest is musl's own x86-64 configuration, replacement rule included and
  1122: whole. Every `.c` in a source directory is collected, and so is every `.c`,
  1123: `.s` and `.S` in its architecture subdirectory: musl's `ARCH_SRCS` is
  1124: `src/*/$(ARCH)/*.[csS]`, not its assembly half. Where a portable file and an
  1125: architecture file name the same unit the architecture file wins and the
  1126: portable one is not built -- musl's `REPLACED_OBJS`. That is 1356 units, 32 of
  1127: them assembly and 18 of them architecture C. Each replacement is named, on a
  1128: `MUSL_ASSEMBLY` or a `MUSL_ARCHITECTURE` line, because which units the archive
  1129: holds musl's own x86-64 implementation for is inventory worth having rather
  1130: than an exclusion. One unit's `.c` is empty with no architecture file to
  1131: replace it -- `src/thread/tls`, which x86-64 does not need -- and it is the
  1132: empty translation unit musl itself compiles rather than a reported gap.

  1134: All 1356 build, so the failing set is empty and its hash is the hash of
  1135: nothing. The last class to go was the inline-assembly operand classes musl's

  1137: output (`"=x"`, `"+x"`: `sqrt`, `sqrtf`, `fabs`, `fabsf`) and as an input
  1138: (`"x"`: `llrint`, `llrintf`, `lrint`, `lrintf`), which was issue 765; and the

  1146: path. Clang compiles all eighteen, and so does Buster now, so the two archives

  1152: that regresses moves the musl count and one fixture together.

  1154: A refused architecture unit does not leave a hole in the archive, and the

  1165: what makes this archive musl's own rather than a portable stand-in for it.

  1168: Before the driver took assembly input this was three groups of reported

  1171: `architecture-assembly` files the harness replaced with the portable C, and
  1172: whatever else failed. The last of the third group to go was
  1173: `vfprintf`/`vfwprintf`, both on wide floating-point `va_arg`, described with
  1174: the type below.
  1175: 
  1176: Static initializers are no longer a class, and neither are the three
  1177: singletons that stood beside them: 1344 to 1347. `src/misc/ioctl`'s
  1178: `compat_map` sizes its entries with `sizeof(struct { ... })`, and the parser
  1179: registered an aggregate an expression defines only inside a function body, so
  1180: the same definition in a file-scope initializer had no type for the sizeof
  1181: fold to resolve and the whole initializer was refused. `res_msend` writes
  1182: `int qpos[nqueries], apos[nqueries];`, a variable-length array in a
  1183: comma-separated declarator list, which the list path could not lower --
  1184: its diagnostic named an alignment, which is what an unresolved layout leaves
  1185: behind, and not the over-aligned automatic that reads like. `lsearch` and
  1186: `lfind` walk their tables through `char (*p)[width]`, a pointer to a variably
  1187: modified array, which is the type `char p[][width]` adjusts to and now becomes
  1188: the same local an array parameter does. Fixing the third also fixed a
  1189: wrong-code defect the compile inventory could not see: indexing either shape
  1190: with fewer subscripts than it has dimensions leaves an array, and the decay
  1191: that turns one into the address of its first element keys on the IR array
  1192: type a variably modified array does not have, so `p[i]` loaded one element
  1193: where the row's address was meant. Inline assembly is no
  1194: longer a class: `crt/rcrt1`, `ldso/dlstart`, `ldso/dynlink` and
  1195: `src/thread/__unmapself` were the four units that reached code generation and
  1196: stopped on a template, and they compile now that the inline path relocates a
  1197: symbol reference and takes musl's two hand-off shapes. Neither is an
  1198: inline-assembly *operand* class: the sixteen architecture C units under
  1199: `src/math/x86_64` stopped on the SSE register class and on the x87 stack, and
  1200: both are implemented, which is what took the count to the whole manifest.
  1201: 
  1202: `src/complex` is no longer a class either. Eighteen units returned a
  1203: `long double _Complex` and were refused at the signature boundary until the
  1204: System V COMPLEX_X87 result class reached the canonical emitter, described
  1205: with the type below: 1326 to 1344, and `functional/tgmath` in libc-test moved
  1206: from `blocked-compile` to the `vfprintf` link blocker with it. Neither is
  1207: wide floating-point `va_arg` a class any more, which is what `vfprintf` and
  1208: `vfwprintf` stopped on until the read described with the type below was
  1209: implemented: 1344 to 1346. Conflicting
  1210: declarations are no longer a class: C11 6.2.7p3 makes an unprototyped
  1211: `long f();` compatible with a non-variadic prototype for the same function,
  1212: which is what musl's `pthread_cancel.c` and `__libc_start_main.c` write.
  1213: 
  1214: `_Complex` is a two-field aggregate of its real type, real part first. That is
  1215: the layout every psABI specifies and, with one exception, also the argument
  1216: and result shape each of them classifies a complex value into, so the existing
  1217: struct rules produce the right registers with nothing added to the backends --
  1218: cross-probed against Clang for System V x86-64, Win64, AAPCS64 and Darwin
  1219: AArch64, and differenced against a Clang build across the boundary on the
  1220: first three. The exception is System V x86-64's `long double _Complex`
  1221: *result*, which the psABI returns in ST(0)/ST(1) under its COMPLEX_X87 class
  1222: where the equivalent `struct { long double a, b; }` is returned in memory
  1223: through a hidden pointer. It is the one place the aggregate model is not the
  1224: ABI, and it is keyed on the type being complex rather than on its shape,
  1225: because the two spellings have identical layouts and different conventions --
  1226: which is what Clang compiles, and what `ir_classify_abi_value` now keys the
  1227: class on. The classifier gives that result four eightbyte parts, one
  1228: X87/X87_UP pair per half in layout order; `ir_abi_value_is_complex_x87_result`
  1229: is the predicate over that shape and the only thing the backends ask. The
  1230: canonical x86-64 emitter pushes the imaginary half and then the real one
  1231: before its `RET`, so the real half is on top, and pops them in that order into
  1232: the result slot after a call. Every other position is the two-field aggregate
  1233: unchanged: the argument is a thirty-two-byte memory slot under the same psABI,
  1234: which is why `cabsl`, `cargl`, `creall` and `cimagl` compiled before any of
  1235: this, and the loads, stores and copies move bytes.
  1236: `tests/basic_c_complex_x87_caller.c` and its callee are the pair compiled by
  1237: one compiler and linked against the other in both directions, which is the
  1238: only thing that pins the register order to the platform's; the single
  1239: translation unit in `tests/basic_c_complex_arithmetic.c` cannot see a
  1240: disagreement about it.
  1241: 
  1242: Multiplication and division are lowered inline -- the naive product and
  1243: Smith's algorithm, which is what Clang emits for
  1244: `-fcomplex-arithmetic=improved` -- rather than as the `__muldc3`/`__divdc3`
  1245: calls Clang emits by default, because this toolchain neither ships nor links a
  1246: compiler runtime to resolve them. Against `improved` the two agree bit for bit
  1247: over an operand matrix covering the signed zeroes, the subnormal and overflow
  1248: edges and the infinities, `long double` included;
  1249: `c_ir_emit_complex_divide` in `c_gen.c` records where the default's library
  1250: helpers differ. Smith's algorithm compares the magnitudes of the two
  1251: denominator halves, and there is no absolute-value opcode, so
  1252: `c_ir_emit_float_magnitude` clears the sign bit through a stack slot. The
  1253: 80-bit x87 spelling has no integer of its own width to pun through, so it is
  1254: punned one halfword at a time -- bit 15 of the sixteen-bit sign/exponent field
  1255: at byte eight, the `se` member of musl's own `union ldshape` -- rather than
  1256: whole, which is what lets `cpowl` compile with the other seventeen. GNU's imaginary literal suffix
  1257: comes with the type, in both orders and both letters, because it is the only
  1258: way a `<complex.h>` can define `I`: musl spells `_Complex_I` as
  1259: `(0.0f+1.0fi)` and glibc as `(1.0iF)`. Two shapes stay unsupported and
  1260: diagnosed: a complex global initializer, and a complex operand inside an
  1261: integer constant expression, which the parser's folder reduces to the
  1262: operand's real part rather than refusing -- C does not admit one there either
  1263: way.
  1264: 
  1265: `long double` is no longer among them. Seventeen units were static
  1266: initializers until the folder learned the two shapes musl writes -- `floorl`,
  1267: `ceill`, `roundl`, `truncl`, `rintl`, `modfl` and `__rem_pio2l` open with
  1268: `static const long double toint = 1/LDBL_EPSILON;`, and `atanl`, `expl`,
  1269: `logl`, `log2l`, `log10l`, `log1pl`, `powl`, `tgammal`, `erfl` and `exp10l`
  1270: carry `long double` coefficient tables -- and then stopped in the canonical
  1271: emitter instead, which rejected a whole function when one of its values had a
  1272: type that *contained* an x87 `long double` without *being* one, so an array of
  1273: them was refused whether or not it carried an initializer. Classifying those
  1274: aggregates by the ABI rather than by that shape test released them along with
  1275: every unit reaching a value through musl's `union ldshape`: 54 units, 1192 to
  1276: 1246, and the whole x87 code-generation class with them. The four left in
  1277: that class were inline assembly -- `crt/rcrt1` and `ldso/dlstart` on
  1278: `GETFUNCSYM`, `src/thread/__unmapself` and `ldso/dynlink` on `CRTJMP`, the
  1279: last of them having joined once the portable `offsetof` in its `MIN_TLS_ALIGN`
  1280: folded and it stopped failing earlier -- and they closed together, 1322 to
  1281: 1326, when the inline-assembly path learned to relocate a symbol reference and
  1282: to take a stack hand-off. Nothing in the inventory stops on an assembly
  1283: template now.
  1284: 
  1285: musl's startup objects are their own report now that module-level assembly
  1286: goes through the real assembler. `crt/crt1.c` and `crt/Scrt1.c` compile, and
  1287: the harness writes `crt1.o` and `Scrt1.o` beside the archive rather than into
  1288: it, the way musl's own build keeps startup objects out of `libc.a`; a
  1289: `MUSL_STARTUP` line names each object it produced, and each one it did not
  1290: with the reason. The produced `crt1.o` is a complete startup object:
  1291: `_start`'s bytes are Clang's, `_DYNAMIC` is weak and hidden, `_init` and
  1292: `_fini` are weak undefined, and `ld -static` links it into a program the
  1293: kernel enters and that exits cleanly.
  1294: 
  1295: `rcrt1.o` joined them once the inline-assembly arm learned the same
  1296: relocation plumbing: `crt/rcrt1.c` and `ldso/dlstart.c` stop on x86-64's
  1297: `GETFUNCSYM` in `arch/x86_64/reloc.h`, which is *inline* assembly carrying a
  1298: `.hidden` directive and a RIP-relative `lea` against a symbol with an output
  1299: operand, and that shape now reaches the object as a relocation like any other.
  1300: `crti.o` and `crtn.o` are there too, and they are the whole reason a section
  1301: keeps its own name through the assembler: each contributes one and two bytes
  1302: to `.init` and `.fini`, which the system linker concatenates in order.
  1303: `startup_absent` is zero.
  1304: 
  1305: `ldso/dlstart.c` and `ldso/dynlink.c` compile now too, and stay out of
  1306: `libc.a` under musl's own `AOBJS` rule rather than because of anything Buster
  1307: cannot build, for the reason the archive note above gives.
  1308: 
  1309: The archive is linkable, which it was not until `__attribute__((weak))` and
  1310: `__attribute__((alias))` reached the object writer. musl publishes `malloc`,
  1311: `free`, `errno` and most of its pthread surface as weak aliases of internal
  1312: names -- `weak_alias(old, new)` is
  1313: `extern __typeof(old) new __attribute__((__weak__, __alias__(#old)))`, which
  1314: also needs the `__typeof` spelling -- and while the attribute went
  1315: unimplemented every one of those names was absent from the objects even
  1316: though every unit holding them compiled. 250 weak symbols now come out of
  1317: `libc-buster.a`, `malloc` among them. The compiled-unit inventory did not
  1318: move by a single unit when they appeared, which is exactly why the probe
  1319: exists: the gap was invisible from the compile side and showed up only when
  1320: something linked. The probe therefore calls `stpcpy`, `stpncpy`, `strchrnul`
  1321: and `memrchr`, four names musl publishes *only* through `weak_alias`, so the
  1322: link that used to fail is now part of the gate. It does not call `malloc`:
  1323: musl's allocator takes a lock through the thread pointer, which a program
  1324: entered at `_start` with no startup object never established, and the
  1325: Clang-built archive faults in the same place.
  1326: 
  1327: ### libc-test
  1328: 
  1329: Given a second path, the harness then runs libc-test, musl's own test suite.
  1330: It carries no tags and no version file, so the pin is a bare commit on
  1331: upstream's master, `68edb8bd73dab8147ee54c8bec638f4d2b3cff37`, verified
  1332: pristine the same way musl's checkout is. Upstream's canonical remote is
  1333: `https://git.musl-libc.org/cgit/libc-test`; `https://repo.or.cz/libc-test.git`
  1334: is the same history and is what a clone usually resolves to. Upstream's own
  1335: makefile builds in-tree, which is exactly what the pin exists to prevent, so
  1336: the harness drives the sources from where they sit and writes every artefact
  1337: into `libc-test/` under the run directory.
  1338: 
  1339: One generated header stands between the suite and musl: `src/common/options.h`,
  1340: which upstream derives by preprocessing `options.h.in` against the libc under
  1341: test and turning what survives into defines. The harness runs that recipe --
  1342: the four `sed` expressions written at the top of `options.h.in` itself, which
  1343: upstream's makefile spells again in awk -- and both sides compile against the
  1344: one copy. The reference preprocessor generates it, and that is not a statement
  1345: about which compiler is trusted: `ide cc -E` emits a token stream with the line
  1346: structure removed, the whole file coming back as one line of space-separated
  1347: tokens, and this recipe like musl's own three is line-oriented. The header
  1348: describes the musl under test rather than either compiler, so one copy is also
  1349: the right shape for a comparison.
  1350: 
  1351: One flag set again drives both compilers, and it is upstream's own
  1352: `config.mak.def` `CFLAGS` minus what only one of them takes, plus the
  1353: `-nostdinc` and musl include set that makes a test see the musl under test
  1354: instead of the host libc: `-std=c99 -nostdinc -fno-builtin
  1355: -fno-strict-aliasing -fno-stack-protector -D_POSIX_C_SOURCE=200809L -O2 -g0`,
  1356: with `-D_XOPEN_SOURCE=700` added for `src/api` because that is what upstream's
  1357: own api rule adds. `-pedantic-errors` and `-frounding-math` are dropped
  1358: because Buster rejects both, which is the same `tryflag` reasoning musl's flag
  1359: set is built on; the warning flags and `-g` change nothing about what is
  1360: compiled; `-D_FILE_OFFSET_BITS=64` is marked glibc-specific by upstream and
  1361: musl has one `off_t`; and the `-lpthread -lm -lrt` link libraries have no
  1362: meaning where there is one archive and no compiler driver. Clang alone gets
  1363: `-Werror=implicit-function-declaration`, which is upstream's and is not a
  1364: divergence: Buster rejects an undeclared callee outright, so the flag is what
  1365: makes the two compilers agree about a missing declaration -- which is most of
  1366: what the api subset is testing.
  1367: 
  1368: Two objects sit on every static link line that neither archive supplies, and
  1369: each side uses its own. `crt1.o` is musl's startup object, which is not an archive
  1370: member on either side — a program links it explicitly and `libc.a` separately —
  1371: so a libc-test program is one compiler's code from `_start` down. If Buster
  1372: ever stops producing it the reference's copy stands in on both sides, and the
  1373: `LIBCTEST_MANIFEST` line says which of the two arrangements is in force rather
  1374: than leaving it to be inferred. That is the only such object now. A
  1375: project-owned `__set_thread_area` used to sit beside it, because the harness
  1376: substituted the portable C sibling for every architecture-assembly unit and
  1377: that sibling is written for architectures with a `SYS_set_thread_area` system
  1378: call -- x86-64 has none, so it returned `-ENOSYS`, `__init_tp` failed, and
  1379: `__init_tls` crashed the process before `main` in *both* archives. Both
  1380: archives now hold musl's own `arch_prctl(ARCH_SET_FS)`, and the replacement
  1381: is gone.
  1382: 
  1383: Nine units are built differently, and upstream's sibling `.mk` is what says so.
  1384: It is a make fragment of one to four lines, and the harness reads it for the
  1385: three facts it states rather than interpreting it: `$(N).LIBS:=$(B)/$(N).so`
  1386: means the unit is a shared object instead of a program, `-rdynamic` means its
  1387: program has to export its own symbols because the library it opens resolves
  1388: against them, and any other `name.so` in the file is a sibling its program
  1389: needs beside it. Each of the four shapes upstream writes states its fact in a
  1390: token, so the file is scanned for tokens; anything a later release adds that
  1391: this does not understand shows up as a unit that fails to build rather than as
  1392: one quietly held out, which is the trade this stage wants.
  1393: 
  1394: What comes out of that is three link shapes rather than one. A shared-object
  1395: unit is compiled `-fPIC -DSHARED`, which is upstream's own `.lo` rule, and
  1396: linked `-shared` against the shared musl; upstream never runs one, so both
  1397: sides building it is the pass. That flag is the same code model on both sides
  1398: now, and this stage is where it is measured against a real linker: what a
  1399: shared object demands of the code generator is a thread-local model the loader
  1400: can place and a GOT-indirect reference for every other symbol another object
  1401: could interpose, and `ld` says so by name for each one that is missing. A
  1402: program with a `.mk` is linked against the shared
  1403: musl rather than the archive, with that musl as its interpreter and its own
  1404: directory as its run path, which is upstream's `-rpath='$ORIGIN'` spelled as a
  1405: directory this harness knows. Every other program is linked `-static` exactly
  1406: as before. The thread-pointer replacement is on the static link lines only: the
  1407: shared musl already carries it, and a second definition would be a duplicate
  1408: symbol rather than a substitution. Each side's dynamic programs are laid out
  1409: under `src/<subset>/<stem>` in that side's own tree and run from its root,
  1410: because three of the nine find the library they open by a path rather than by a
  1411: name -- two spell it from the working directory and one derives it from
  1412: `argv[0]` -- and that layout is upstream's own.
  1413: 
  1414: Each unit is classified rather than merely passed or failed, because most of
  1415: the suite cannot be reached yet and a single total would hide which wall it is
  1416: behind. The classification is derived from the checkout and from what the two
  1417: sides do, not written down:
  1418: 
  1419: - `excluded-reference` — the Clang-built musl of this same configuration
  1420:   cannot compile, link or run it green. It says nothing about Buster, so it is
  1421:   held out of the comparison. This used to be most of the suite -- musl's
  1422:   x86-64 assembly was in neither archive nor either shared object, so `fenv`
  1423:   was a stub, `clone` was absent and the thread tests hung out their
  1424:   ten-second deadline, and `setjmp` was a trap so nothing that called `dlopen`
  1425:   could run -- and building the assembly is what released it: 144 of the 199
  1426:   `src/math` units and 34 of the 69 `regression` ones were in this state, 31
  1427:   and 1 remain, and the suite's run time fell from 53,6 seconds to 3,9.
  1428: - `blocked-compile` — Buster cannot compile the test itself.
  1429: - `blocked-link` — Buster compiled it and the link against the Buster-built
  1430:   libc could not be made. Every undefined symbol is recorded, not just the
  1431:   first: the link stops at the startup object every time, so a ranking built
  1432:   from first symbols would name one symbol and hide the rest. A link that
  1433:   failed for another reason — a relocation a shared object cannot carry, or a
  1434:   sibling shared object this side did not build — carries the linker's own
  1435:   words instead of claiming zero unresolved symbols, and `ld` reports its
  1436:   warnings before the error that stopped it, so the line kept is the first one
  1437:   that is not a warning.
  1438: - `fail` — it ran, and its transcript or exit status differs from the Clang
  1439:   reference. This is the only state that is a defect in generated code.
  1440: - `pass` — it ran and matched; in `src/api` it compiled; in a shared-object
  1441:   unit both sides built the library.
  1442: 
  1443: Five units were what building the assembly newly put in front of Buster, and
  1444: each was filed rather than absorbed. Three are closed: `functional/setjmp`
  1445: compiles once an aggregate can be assigned across a `volatile` qualifier
  1446: (issue 735), and `functional/pthread_robust` and
  1447: `regression/pthread-robust-detach` pass once a walked-through aggregate member
  1448: is not loaded (issue 737). The other two, `functional/tls_align_dlopen` and
  1449: `functional/tls_init_dlopen`, joined the shared-object group that was already
  1450: there rather than being anything new; `tls_init_dlopen` is closed with the
  1451: rest of that group and `tls_align_dlopen` was one of the two the dropped
  1452: constructor held until issue 771 closed it. 243 to 388, and nothing that
  1453: passed before stopped passing.
  1454: 
  1455: Applying `ARCH_SRCS` whole moved the reference and not the suite. The Clang
  1456: archive holds musl's own x86-64 `sqrt`, `fabs`, the `lrint` family and the x87
  1457: `long double` remainders now instead of the portable files, and Buster's holds
  1458: the portable files for the sixteen it cannot compile. `src/math` is the subset
  1459: that would show it -- these are its implementations -- and all 168 of its
  1460: passing units answer the same as before, which is what a correctly rounded
  1461: portable implementation standing in for a hardware one should do.
  1462: 
  1463: Buster compiles every unit first and unconditionally, before the reference
  1464: decides reach, because its diagnostic is inventory in its own right, and
  1465: `buster_compile_failed` on each `LIBCTEST_SUBSET` line reports that count
  1466: independently of the state. The `long double` test tables under `src/math`
  1467: are what that separation was for: 63 of the 199 units failed to compile while
  1468: only 21 of them were classified `blocked-compile`, the rest being
  1469: `excluded-reference` already, so the state counts alone would have hidden
  1470: two thirds of one compile gap.
  1471: 
  1472: The four subsets are reported separately rather than as one total.
  1473: `src/api` is compile-only by upstream's own design: its units are declaration
  1474: conformance checks with no runtime, and upstream links a single `main.exe`
  1475: from all of them, so there a successful compile is the pass. `src/functional`,
  1476: `src/math` and `src/regression` are compiled, linked and run, and a run is
  1477: green when the program exits zero and prints nothing, which is the protocol
  1478: upstream writes down in its README. Upstream's `src/common` becomes a support
  1479: archive on each side, minus `runtest.c`, which is the process supervisor the
  1480: harness performs itself; upstream gives each test five seconds there, and the
  1481: harness gives it ten so a loaded runner cannot turn a slow test into a
  1482: classified failure. `src/musl` is not a subset: its one unit tests musl
  1483: internals through a header this build does not publish.
  1484: 
  1485: The gate is the passing count together with a hash of the newline-joined
  1486: `state subset/unit` lines of everything that did not pass, taken in manifest
  1487: order — the four subsets in the order above, each sorted by unit name —
  1488: pinned as `LIBC_TEST_EXPECTED_PASSING` and `LIBC_TEST_EXPECTED_STATE_HASH`
  1489: in `build.c` and printed on the `LIBCTEST_INVENTORY` line, which is what a
  1490: deliberate rebaseline needs. The hash covers the excluded states as well as
  1491: the blocked ones, so a change in the reference's reach is a deliberate edit
  1492: too.
  1493: 
  1494: Every unit that is not passing prints a `LIBCTEST_UNIT` line carrying its
  1495: state and the reason — a compiler diagnostic, the count and the first of the
  1496: unresolved symbols, or the reference's own reason for being out of reach — and
  1497: each subset then prints one `LIBCTEST_SUBSET` line with its counts and its
  1498: compile, link and run time. `LIBCTEST_SUPPORT` reports upstream's support
  1499: library per side, including its archive time, and any support unit that did
  1500: not compile is named on a `LIBCTEST_SUPPORT_UNSUPPORTED` line. All nine
  1501: compile on both sides today, so the line is absent.
  1502: 
  1503: `LIBCTEST_BLOCKER` is the stage's most useful output while most of the suite
  1504: is out of reach: the symbols the Buster-built archive could not supply, ranked
  1505: by how many tests wanted each. It is the work list in the order that unblocks
  1506: the most tests, and it is why this stage grows by itself as the compiler
  1507: improves rather than needing to be extended by hand.
  1508: 
  1509: The suite is built twice, and the second time is the only coverage the NONE
  1510: register allocator has against a whole libc. Both compile inventories — musl's
  1511: 1356 units and libc-test's 424 — are compiled under FAST, and building either
  1512: of them four times over would produce four object sets and one answer. All
  1513: four allocators do run on the freestanding probe, each required to reproduce
  1514: the reference transcript byte for byte, but that is one program of about two
  1515: kilobytes against FAST's 424. So one subset is built and run a second time
  1516: under `-fregister-allocator=none`: `src/functional`, 77 units of ordinary C
  1517: whose programs run in a couple of seconds. Compiling the musl manifest a
  1518: second time under NONE and gating the unit count would have been cheaper and
  1519: could only ever have caught a refusal — the half of the compiler the register
  1520: allocator is not in — where this compiles, links, runs and compares generated
  1521: code.
  1522: 
  1523: Only the test's own object is rebuilt. It links against the same Buster-built
  1524: libc, startup object and support archive as the pass above, so a unit that
  1525: answers differently here answers differently because of the allocator and not
  1526: because of anything underneath it. Each unit is classified from scratch,
  1527: against the same reference transcript the first pass recorded, rather than by
  1528: comparing the two Buster passes: a unit FAST cannot compile says nothing about
  1529: NONE, and the reference's reach is the one thing the two passes do share. The
  1530: gate is its own count and its own hash — `LIBC_TEST_ALLOCATOR_EXPECTED_PASSING`
  1531: and `LIBC_TEST_ALLOCATOR_EXPECTED_STATE_HASH`, printed on

  1884: is then required to fail, so a regression and a silently landed fix are both
  1885: caught. Fixture runs are deliberately uncaptured — wine's background services
  1886: inherit captured pipe ends and stretch a 10 ms run to seconds — and every
  1887: child is bounded by `MODE_MATRIX_TIMEOUT_SECONDS`. The whole matrix costs
  1888: about four seconds on a warm tree; CI runs it on the dedicated Linux runner
  1889: and on macOS (where the Mach-O rows execute natively), and skips the Windows
  1890: runner because that box is the CI wall-time gate and its PE rows already run
  1891: under wine on Linux.
  1892: The combination matrix shares one multi-config build tree across configurations
  1893: when their configure-time policy matches. Clang omits unsanitized Debug because
  1894: sanitized Debug provides the stronger coverage; it builds and runs unsanitized
  1895: Release plus sanitized Debug and Release. Non-Apple Clang configurations use
  1896: dedicated trees because their fuzz-runtime policy differs, while AppleClang's
  1897: two sanitized configurations share one cross-config Ninja graph. GCC and Zig
  1898: compile unsanitized Debug only and do not execute it; MSVC does the same on
  1899: Windows. Only optimized, unsanitized Clang/AppleClang builds use the requested
  1900: unity build; every other build uses split translation units. TCC is retained
  1901: only as the bootstrap compiler for `build.c` and is omitted from all
  1902: application/compiler combinations.
  1903: The matrix configures its compiler trees in parallel, then uses
  1904: `cmake/superbuild/CMakeLists.txt` for one outer `cmake --build` invocation.
  1905: Each shared compiler tree builds Debug and Release through one cross-config
  1906: Ninja process, so concurrent builds never write the same `.ninja_deps` or
  1907: .ninja_log`. One shared CMake job pool admits the outer compiler and test
  1908: commands, so a completed tree can release its slot to its tests while other
  1909: trees continue compiling. On hosts with four or fewer logical CPUs, it admits
  1910: one tree per CPU and sets every inner Ninja and `BUSTER_TEST_JOBS` quota to
  1911: one; the six-tree Windows matrix therefore runs four one-job compiler trees
  1912: at a time without nested oversubscription. Larger hosts retain the weighted
  1913: allocator: split trees share at least two logical CPUs per admission slot while
  1914: unity trees use one job. Clang tests then run concurrently in the same bounded
  1915: pool, with each tree's quota passed through `BUSTER_TEST_JOBS`; future multithreaded test work
  1916: must honor that limit. Application builds are multithreaded by default;
  1917: `./build.sh generate -DBUSTER_SINGLE_THREADED=ON` is the explicit serial
  1918: fallback. A single compile is serial throughout: the compiler library starts no
  1919: lanes of its own, so build-level concurrency is the only thing that has to be
  1920: budgeted. Trees are declared longest-first — sanitized Debug,
  1921: sanitized Release, the unity Release tree that also runs `clang_analyze`, trees
  1922: covering two configurations, then the rest — because Ninja admits ready edges
  1923: from a shared pool in declaration order and a fresh CI checkout has no
  1924: `.ninja_log` for its critical-path scheduler to learn from. Set
  1925: `BUSTER_MATRIX_DIRECT=1` only to diagnose the retained legacy scheduler,
  1926: `BUSTER_MATRIX_NO_TREE_ORDER=1` to restore the previous declaration order, and
  1927: `BUSTER_MATRIX_THREADS=<n>` to state a CPU budget instead of the detected one
  1928: (`get_nprocs()` ignores CPU affinity, so `taskset` alone cannot reproduce a
  1929: small runner's admission behavior). The last two exist so the ordering can be
  1930: A/B measured on one host. When artifact fan-out is enabled on the supported
  1931: desktop CI platforms, the canonical trusted Clang Release tree also gets a
  1932: self-host worker in this same pool. The build-driver boundary is mandatory:
  1933: capture provenance, clean the canonical Release producer, then start the outer
  1934: superbuild. The clean preserves the configured CMake/Ninja graph and cache while
  1935: forcing producer objects and links to rebuild under the captured inputs. The worker depends only on the canonical compile target,
  1936: consumes the producer's one-shot integrity-checked compiler/tool/cache/graph/
  1937: environment provenance record before validating and snapshotting the artifact,
  1938: runs the existing direct fixed-point workflow without starting an inner Ninja
  1939: process, and remains disabled for the direct scheduler and unsupported platforms.
  1940: Each self-host stage and the stage-2 benchmark are bounded at ten minutes
  1941: (`SELF_HOST_TIMEOUT_SECONDS`): the work is fixed and costs seconds, so a stage
  1942: that does not finish is a compiler that never will, and waiting on one wedges
  1943: a serialized CI runner for hours while Ninja buffers the edge's output and the
  1944: log says nothing. On expiry the child is killed and the run fails naming the
  1945: stage and its command line. Every other run waits indefinitely, because their
  1946: cost scales with what they are given.
  1947: The fixed-point pair continues to use the default FAST allocator, and the
  1948: existing non-Windows machine stage continues to compile and run its benchmark
  1949: with `-fregister-allocator=mir-stack`. That stage is followed by a canonical
  1950: compile-only gate: the stage-2 compiler builds `ide-stage2-none` with
  1951: `-fregister-allocator=none`. It does not run that output because the regression
  1952: this gate protects against is a canonical argument-capture crash while
  1953: compiling `ide.c`; launching a second benchmark would add CI work without
  1954: covering that path. NONE is the only allocator stage here that reaches the
  1955: canonical emission path; QUALITY exercises the same machine path already
  1956: covered by FAST/MIR_STACK and is covered by focused/all-mode tests, so another
  1957: full unity compile would add CI cost without distinct self-host coverage.
  1958: CI Release builds use `-O2`; local Release builds retain the toolchain default.
  1959: Local builds make the optimized tree profilable, which CMake's defaults do not:
  1960: `BUSTER_DEBUG_INFO` emits debug information in the configurations that carry no
  1961: `-g` (`Release`, `MinSizeRel`) and `BUSTER_FRAME_POINTERS` adds
  1962: `-fno-omit-frame-pointer` to every optimized configuration. Both default to off
  1963: under `--ci` and on everywhere else, and both are overridable with
  1964: `./build.sh generate -DBUSTER_DEBUG_INFO=ON|OFF -DBUSTER_FRAME_POINTERS=ON|OFF`.
  1965: `Debug` and `RelWithDebInfo` already carry `-g` from the CMake defaults, `Debug`
  1966: is `-O0` and keeps frame pointers anyway, and sanitized trees keep their own
  1967: reduced `-gline-tables-only` mode, so neither option disturbs them. MSVC is
  1968: excluded from the frame-pointer option because `/Oy` has no x64 meaning.
  1969: Measured on Clang 22/Linux x86-64: debug information does not change code
  1970: generation and costs compile time and artifact size only (unity Release
  1971: `ide.c` 37.3 s -> 46.5 s, `ide` 11.4 MiB -> 19.1 MiB); frame pointers do change
  1972: code generation but cost 0.065% of instructions on a unity self-compile
  1973: (29.5037 G -> 29.5227 G) with no wall-clock difference above run-to-run noise
  1974: and no change to the parser benchmark. CI opts out of both because it profiles
  1975: nothing and pays the compile time.
  1976: Clang static analysis runs only against unsanitized Release. Every Clang matrix
  1977: configuration runs `test_all`; GCC, Zig, and MSVC are compile-only, and platform
  1978: packages use their native test runner.
  1979: The one carve-out inside `test_all` is a **whole-table audit**: a module whose
  1980: result is a function of the generated metadata tables and the repository's
  1981: source text alone, so no compiler, configuration or optimization level can
  1982: change its answer. Those modules run on the same single canonical tree per
  1983: platform that already owns `clang_analyze` — unsanitized optimized Clang —
  1984: because re-deriving one identical answer in eight to ten configurations cost
  1985: more than any other single thing in CI. Mark such a module with
  1986: `table_audit` in the `test_descriptors` table of `src/buster/tests/test.c`;
  1987: `x86_64_completion_census_tests` is the current one. The superbuild opts a
  1988: tree out with `BUSTER_TEST_TABLE_AUDITS=0`, and **the default is on**, so a
  1989: bare `ide test`, a single-tree build, or any runner that does not set the
  1990: variable keeps full coverage. Never mark a module whose result depends on
  1991: generated code, the host, or the sanitizer.
  1992: Flag scope matters: `--sanitize`, `--fuzz`, `--lto`, `--ci`, `--time-trace`,
  1993: `--instrument`, `--cc <clang|gcc|zig|cl>` are accepted **only by
  1994: `generate`** for public workflows; `build` rejects them with an explicit
  1995: diagnostic. The internal `self_host_from_existing` worker is the narrow
  1996: exception for build-driver-supplied `--ci/--no-ci` and
  1997: `--fuzz/--no-fuzz`, and requires the captured provenance record.
  1998: TCC is reserved for compiling `build.c` through `build.sh`/`build.ps1` and
  1999: `generate --cc tcc` is rejected as an application compiler.
  2000: `--optimize`/`--no-optimize` are configuration shorthands for
  2001: Release/Debug and never create separate cached optimization state. `build`
  2002: accepts `--config <name>`, `--optimize`, `--target/-t <ninja target>`, and
  2003: `--verbose/-v`. Booleans have `--no-` twins; `--` passes the rest through to
  2004: Ninja (`build`) or CMake (`generate`).
  2005: 
  2006: The Clang-like `ide cc` driver accepts `-march=<model>` and
  2007: `-mcpu=<model>` (or their separated forms), ordered target-feature overrides
  2008: through `-mattr=+feature,-feature`, and x86 assembly dialect selection through
  2009: `-masm=att|intel`. CPU and feature options also accept separated values. CPU names use the canonical
  2010: spellings printed by `cpu_model_to_string_os`, such as `baseline`, `native`,
  2011: `haswell`, `znver5`, and `apple-m4`; incompatible target/model pairs are
  2012: diagnosed. `-v` reports the selected CPU, the sorted effective feature set,
  2013: and maximum native vector width. `-target`/`--target` strings are
  2014: `arch[-vendor][-os][-environment]`: the vendor and environment components stay
  2015: free-form, but a CPU model there is rejected in favor of `-march=`, and so is
  2016: anything past the fourth component. Both used to be dropped silently, which
  2017: left baseline code generation and no hint that the request was ignored.
  2018: Native x86-64 and AArch64 compilation uses the FAST register allocator at
  2019: every optimization level, including the default and `-O0`, while
  2020: `-fno-register-allocator` selects the canonical stack emitter. Advanced and
  2021: diagnostic callers may select `none`, `mir-stack`, `fast`, or `quality` with
  2022: `-fregister-allocator=<mode>`; when several allocator-affecting options are
  2023: present, the last one wins.
  2024: The allocators run on x86-64 under both System V and Win64, and on AArch64
  2025: everywhere but the PE-unwind targets, which still take the canonical path
  2026: whole. Win64 differs from System V in the file it allocates — RSI and RDI are
  2027: callee-saved there, so the allocator has seven callee-saved registers instead
  2028: of five and the vector class keeps only the volatile ZMMs — and in how a call
  2029: is built: the outgoing arguments and the callee's shadow space are written
  2030: into a fixed area at the bottom of the frame instead of pushed, because the
  2031: stack pointer must not move inside the body of a function whose unwind data
  2032: can only carry a frame-pointer offset up to 240 bytes. Its prologue pushes the
  2033: callee-saved registers before establishing the frame pointer for the same
  2034: reason. Shapes the Win64 subset does not build yet — variadic definitions and
  2035: calls, 128-bit integers, vector signatures, indirect (non 1/2/4/8-byte)
  2036: aggregate arguments, and dynamic stack allocation — fall back per function,
  2037: which `-v`'s `fallback_functions` and `CODEGEN_FALLBACK` lines report.
  2038: A `.s` input, or any input under `-x assembler`, is an assembly translation
  2039: unit rather than a C one. `assembly_unit_encode` (`assembly_unit.c`) is the
  2040: layer above `assembly_encode`: it interprets the directive vocabulary, tracks
  2041: one offset per section, resolves labels, and hands each instruction line to
  2042: the instruction layer beneath, and the driver turns its sections, symbols and
  2043: relocations into an `ObjectFile` like any other. The vocabulary is `.text`,
  2044: `.data`, `.bss`, `.rodata` and `.section`; `.globl`/`.global`, `.weak`,
  2045: `.hidden`, `.type` and `.size`; `.align`, `.balign` and `.p2align`; `.byte`,
  2046: `.short`/`.word`/`.hword`/`.value`, `.long`/`.int`, `.quad`, `.ascii`,
  2047: `.asciz`/`.string`, and `.zero`/`.skip`/`.space`; `.intel_syntax noprefix` and
  2048: `.att_syntax prefix`; and the `.cfi_*` family, accepted and dropped because it
  2049: describes unwinding rather than bytes. Anything else -- a directive the table
  2050: does not claim, or an operand form one of these does not cover -- is a
  2051: diagnostic naming the directive and its line, the way every other unsupported
  2052: construct here is reported rather than silently dropped.
  2053: 
  2054: Three things that layer owns rather than the instruction layer. Local numeric
  2055: labels: `1:` becomes a generated name and `1f`/`1b` resolve to the nearest
  2056: following or preceding definition in source order, and those names leave the
  2057: symbol table again once every reference to one is folded, the way GNU as drops
  2058: its own `.L` locals. A repeat or lock prefix alone on a line joins the
  2059: instruction on the next one. And a same-section PC-relative reference to a
  2060: label defined in the file is written into the bytes; only a cross-section or
  2061: undefined name becomes a relocation. `@PLT` is dropped: a static link resolves
  2062: such a call the same way it resolves a plain one. Sections keep their own
  2063: names -- `.init` and `.fini` are neither `.text` nor absent -- and a
  2064: hand-written section gets alignment 1, because `crti.o` and `crtn.o`
  2065: contribute one and two bytes to `.init` and any padding between them would
  2066: run as code.
  2067: 
  2068: One deviation from GNU as, and one refusal. A forward branch to a label is
  2069: always the near form, because the instruction layer sizes a statement before
  2070: the label is known and this assembler does not relax; the bytes are correct
  2071: and a few longer than GNU as writes. And a `.S` -- assembly the C
  2072: preprocessor runs over first -- is refused by name: this frontend's
  2073: preprocessor hands back C tokens, and `%rax`, `$1` and `1f` do not survive
  2074: that round trip, so the input is reported rather than mis-assembled.
  2075: 
  2076: `-emit-llvm` emits binary LLVM bitcode directly from canonical typed IR for C
  2077: inputs. It writes `<input>.bc` by default, accepts `-o` for a single
  2078: input, and rejects native objects, archives, libraries, frameworks, linker
  2079: arguments, `-E`, `-S`, and `-fsyntax-only`. The writer has no LLVM dependency;
  2080: see `LLVM_BITCODE.md` for its target metadata, API, and supported boundary.
  2081: 
  2082: Every hosted ELF link reads the shared libraries' own dynamic symbol tables.
  2083: `compiler_driver_elf_library_exports` looks `libc.so.6` and each requested
  2084: library up where the loader would — the `-L` paths, then the sysroot or host
  2085: `lib`/`usr/lib` roots, multiarch first — and rejects a file whose ELF machine
  2086: disagrees with the target, so a cross link never reads the host's own libc.
  2087: `compiler_driver_elf_dynamic_symbols` walks that table once and produces two
  2088: things.
  2089: 
  2090: The first is the defined global and weak **objects** with their addresses and
  2091: sizes, as `NativeDynamicDataSymbol` arrays, which `link.c` uses to reserve
  2092: copy-relocation slots: a slot stands for the library's object rather than the
  2093: one name the program spelled, so it carries every name the library exports at
  2094: that address, takes the library's own size, and is shared by two imported names
  2095: for one object. The alias set is what makes `extern char **environ` work. A
  2096: definition in the executable takes precedence over the library's for every one
  2097: of its names, and glibc stores the environment through `__environ` after
  2098: startup; an executable that defined only `environ` left that store in libc's
  2099: own storage while the program read a copy taken before startup ran, which is to
  2100: say null. This half is still collected only for a link with an undefined data
  2101: symbol, since a link with none has nothing to copy, and a library that cannot
  2102: be found or parsed leaves the pointer-sized slots the writer reserved before
  2103: alias sets existed.
  2104: 
  2105: The second is the **symbol version** of every defined entry, functions
  2106: included, read from the library's `.gnu.version` and `.gnu.version_d` into
  2107: `NativeDynamicVersionedSymbol` arrays. That half is collected on every hosted
  2108: ELF link, because versioning applies to functions and there is no cheaper way
  2109: to know: reading `libc.so.6` where nothing did before costs about 0,65 M
  2110: instructions, a tenth of a percent of the smallest hosted compile. It buys two
  2111: things in the x86-64 dynamic writer, and the AArch64 one through it:
  2112: 
  2113: - **A reference records the version it bound to.** `.gnu.version` carries one
  2114:   index per dynamic symbol, `.gnu.version_r` names per library the versions
  2115:   the image needs, and `DT_VERSYM`/`DT_VERNEED`/`DT_VERNEEDNUM` publish both.
  2116:   The alias names a copy slot defines are versioned too, because each of them
  2117:   is a name the library publishes. Without this the image binds by name to
  2118:   whatever the running glibc calls default, which is the versioning
  2119:   mechanism's whole purpose: `readelf -W --version-info` on a Buster
  2120:   executable now agrees with GNU ld's for the same program, `stat@GLIBC_2.33`
  2121:   included. Both sections are omitted when nothing needed a version, and the
  2122:   layout then collapses to exactly what it was before, so an unversioned
  2123:   library's image is byte-for-byte unchanged.
  2124: - **A name with no default version is refused** rather than linked, as
  2125:   `LINK_ERROR_SYMBOL_VERSION`. glibc publishes `sys_errlist` four times, once
  2126:   per historical layout, and every one of them is a non-default `name@VER`; an
  2127:   unversioned reference has nothing to bind to, GNU ld reports it undefined,
  2128:   and Buster linked it and let the loader pick. **Do not use `sys_errlist` as a
  2129:   Clang-differential fixture** — a harness that reads "Clang refuses, Buster
  2130:   accepts" as a Buster success measures nothing (issue #660).

  2175: ## Benchmarking and diagnostics
  2176: 
  2177: - **`test_self_host` is the most trustworthy and complete compiler benchmark.**
  2178:   It exercises the full self-hosting IDE pipeline, including the trusted
  2179:   bootstrap, two complete unity-build IDE compilations, byte-identical stage
  2180:   verification, and the stage-2 benchmark. Use its end-to-end result as the
  2181:   primary completeness/fixed-point signal for compiler-throughput changes.
  2182:   For performance measurements, run the benchmark with the trusted
  2183:   Clang-compiled `ide` executable, whose generated host code has the best
  2184:   quality; self-compiled stage executables are useful for fixed-point
  2185:   validation, not as the default benchmark host.
  2186: - `ide bench` (also exposed through the `bench_all` target) reads
  2187:   `tests/basic_c_operations.c` and measures the complete C frontend path:
  2188:   preprocessing, syntax construction, semantic analysis, and canonical-IR
  2189:   lowering. It prints one `BENCH_C_FRONTEND` line with minimum and median
  2190:   latency plus source throughput. Run it from the repository root.
  2191: - **`STEP_INSTRUCTIONS` lines** report instructions retired for every build step
  2192:   that already reports wall time, printed straight after its `took ... seconds`
  2193:   line. The one to watch is `Self-host stage 1`, which is compile throughput on
  2194:   the complete unity translation unit: it is contention-immune and reproducible
  2195:   to a few thousand instructions, where wall time on an idle 16-thread desktop
  2196:   varies about 10% run to run. Compare it across commits — a change that only
  2197:   *adds* source can regress it sharply through a latent quadratic, which is
  2198:   invisible to test-time measurement. Linux-only: this needs hardware counters
  2199:   and there is no cheap portable equivalent, so nothing is printed elsewhere or
  2200:   when `perf_event_open` is unavailable, and its absence is never an error. One
  2201:   counter covers the process tree, so a step's number is exact only while it is
  2202:   the sole child running; that holds for the sequential self-host stages and
  2203:   CMake generation, but concurrent matrix steps overlap and must not be read as
  2204:   per-step totals.
  2205: - **The `SOURCE` table** gives `STEP_INSTRUCTIONS` a denominator: it reports
  2206:   what the C frontend read, in bytes, physical lines, sLOC, comments, blank
  2207:   lines, literals, and preprocessing tokens, each with its share of the whole.
  2208:   `ide cc -v` prints it, and the self-host stages pass `-v` so it lands in the
  2209:   log beside their instruction counts. The `unique` column covers the distinct
  2210:   files of the include closure, the `lexed` column every inclusion: a header
  2211:   with neither `#pragma once` nor a whole-file `#ifndef` include guard the
  2212:   preprocessor recognizes (see `CIncludeGuardTable` in `c_source.c`) is
  2213:   re-read and re-lexed at each `#include`, so the two columns' ratio is the
  2214:   unit's include amplification (currently 295 files/27,2 MB against
  2215:   326/27,3 MB; before the guard optimization the same tree read 448/29,4 MB).
  2216:   A `files lexed more than once` block under the table attributes the
  2217:   remainder per path — deliberately re-includable files like the builtin
  2218:   `stddef.h` and glibc's `bits/wordsize.h`, whose re-reads total 28 KB. `bytes on disk`/`physical lines` measure
  2219:   the files as written, `bytes scanned`/`lines scanned` what the lexer saw
  2220:   after carriage returns and line splices are folded out, and two partitions
  2221:   hold exactly: bytes are code plus comment plus whitespace, and lines are
  2222:   code plus comment plus blank once the `both` row is subtracted. A closing
  2223:   `preprocessed output` block measures the other side — the tokens actually
  2224:   handed to the parser, their spelling bytes, every spelling byte the run
  2225:   retained, macro expansions, and `#define` directives — because macro
  2226:   expansion multiplies the input by whatever factor the macros ask for, so
  2227:   parsing and lowering scale with those and not with the file sizes. The
  2228:   measurement is always on and costs 0.19% of stage-1 instructions (measured
  2229:   on Clang 22/Linux x86-64), because every source unit falls out of a branch
  2230:   the lexer already takes rather than a second pass over the bytes, and the
  2231:   output side is one linear sum over the finished token stream. The
  2232:   bootstrap's table does not match the self-hosted stages' and is not meant
  2233:   to: the bootstrap finds its host compiler's resource headers and the
  2234:   self-hosted stages fall back to the builtin ones, which is why the file
  2235:   table is populated lazily (see `map_entry` in `c_source.c`).
  2236: - **The `SELF_HOST stage <1|2> throughput` block** is the division done: its
  2237:   `workload` row reports bytes, LOC, SLOC and tokens; its `bandwidth` row
  2238:   reports MB/s, LOC/s and SLOC/s from the execution time shown immediately
  2239:   above it; and, where the platform exposes a hardware counter, its
  2240:   `instructions` row reports the total and the per-byte, per-SLOC and per-token
  2241:   ratios. These are the numbers to trend across commits, printed
  2242:   by `self_host_compare_action` beside the `SELF_HOST deterministic` line. `-v`
  2243:   prints the `SOURCE` table for a human;
  2244:   `ide cc -fsource-metrics=<path>` writes the same measurement as
  2245:   `<group>.<field>=<value>` lines for a program, each self-host stage writes
  2246:   one beside its executable, and build.c combines the relevant fields with
  2247:   the stage's own `STEP_INSTRUCTIONS` delta and wall time. A file rather than
  2248:   another stdout line, because capturing a compile step's output would stop its
  2249:   diagnostics from streaming as it runs. `bytes` is `lexed.translated_bytes`,
  2250:   `loc` is `lexed.translated_lines`, and `sloc` is `lexed.code_lines`; all
  2251:   three legitimately differ between the two stages for the resource-header
  2252:   reason above. The LOC/s and SLOC/s values divide those line counts by the
  2253:   stage's recorded wall time; MB/s uses decimal megabytes
  2254:   (1,000,000 bytes). `tokens` is `preprocessed.tokens`, which does not differ,
  2255:   and is the denominator to reach for when comparing the stages to each other.
  2256:   The ratios carry three
  2257:   decimals because a compile costs a few hundred instructions per byte, and
  2258:   whole units would quantize the series to about 0.3% — coarser than the
  2259:   regressions the counter exists to catch. Without a usable instruction
  2260:   counter the line still prints its units and omits the ratios. Only ever add
  2261:   keys to the metrics file: readers take the fields they know and must keep
  2262:   working against a newer compiler's file.
  2263: - **The stages' preprocessed token streams are a fixed point too**, gated
  2264:   beside the executable bytes. `test_self_host` fails when the two stages
  2265:   disagree on `preprocessed.tokens` or `preprocessed.bytes`, and when the
  2266:   executables differ it first says whether the token streams matched — which
  2267:   halves the search, since the parser and everything after it are a function
  2268:   of that stream alone. Nothing else is compared between the stages: bytes,
  2269:   sLOC, comments, `#define` directives and macro expansions all legitimately
  2270:   differ for the resource-header reason above (currently 6.088 vs 6.087
  2271:   `#define`s and 56.429 vs 56.426 expansions converging on the same 1.378.839
  2272:   tokens and 12.124.867 spelling bytes). Changing what the builtin resource
  2273:   headers declare can part the streams on purpose; that is the signal and not
  2274:   a false alarm, because the two stages are then no longer compiling the same
  2275:   program and byte-identical executables would be saying less than they
  2276:   appear to. Update the gate deliberately in that case — do not weaken it to
  2277:   the token count alone, since equal counts of differently spelled tokens are
  2278:   still different programs.
  2279: - **`ninja_log_summary <build-dir> [--limit N]`** and **`time_trace_summary
  2280:   <json-path>... [--limit N]`** (both new `build/build` commands, same
  2281:   shape as `cmake_profile_summary` — see `build.c`) are diagnostics for
  2282:   *where compile time goes*: the former reads `<build-dir>/.ninja_log`
  2283:   directly (only useful for multi-TU/Debug builds — Release is a single
  2284:   unity TU); the latter parses one or more clang `-ftime-trace` JSON files
  2285:   (enable via `--time-trace`) and reports the slowest `"Total *"` rollups
  2286:   clang itself pre-aggregates (`Total Frontend`, `Total Backend`,
  2287:   `Total InstantiateFunction`, ...), summed across every file given. These
  2288:   commands are diagnostics for humans to inspect when aggregate numbers
  2289:   suggest a regression, and can be run from CI or locally.
  2290: - **`test_timing_summary <test-log>... [--limit N] [--baseline <path>]
  2291:   [--update-baseline]`** answers *where test time goes*, the counterpart to
  2292:   the two commands above. It parses the `TEST_MODULE_TIMING` lines
  2293:   `library_tests()` already prints under `--verbose=1` (which every CI job
  2294:   passes) out of a saved matrix run or CI log, reports each module's total
  2295:   across the configurations in that run with its share of the whole, then the
  2296:   slowest individual (configuration, module) rows with their deltas against a
  2297:   stored baseline. `--update-baseline` records the current run.
  2298:   This exists because test cost accumulates silently: `x86_64_metadata_tests`
  2299:   reached 60% of all CI test CPU time before anyone noticed, and every number
  2300:   needed to catch it in week one was already printed on every run and
  2301:   discarded with the log.
  2302:   Two properties are deliberate and should be preserved. **It is a diagnostic,
  2303:   not a gate** — it has no thresholds and no CI failure condition, because
  2304:   wall-clock test time is far too noisy to gate on (identical code measured
  2305:   290.1 s and 319.8 s for the same matrix on an idle 16-thread desktop, a 10%
  2306:   spread); recording history first is the right order, and a gate would need a
  2307:   noise model that does not exist yet. **Series are per-runner and
  2308:   per-configuration and are never merged** — the same module measured 4.4 s in
  2309:   Linux Release, 138 s in sanitized Debug and 192 s on a sanitized Debug
  2310:   Windows runner, so a baseline records the runner it was taken on and refuses
  2311:   to be compared against another, every runner keys its own baseline (none is
  2312:   excluded, including shared or noisy ones), and rows are only compared within
  2313:   the same configuration. The runner name defaults to `<platform>-<arch>` and
  2314:   is overridable with `BUSTER_TEST_TIMING_RUNNER`; the default baseline path is
  2315:   `build/test-timing-baseline-<runner>.txt`. Configurations are recovered from
  2316:   the build commands the superbuild echoes ahead of each test block; timing
  2317:   rows with no command line in front of them are attributed to numbered
  2318:   `unknown:<n>` series rather than merged.
  2319: - **`tools/ci_time.py`** answers *what CI actually costs*, over a window rather
  2320:   than for one push. It reads the Forgejo Actions API and prints runner hours
  2321:   per runner (or per day, week, or branch) beside push latency — the two
  2322:   numbers that matter separately, since machine time is what the matrix burns
  2323:   and latency is what a push waits for:
  2324: 
  2325:   ```sh
  2326:   tools/ci_time.py --days 30
  2327:   tools/ci_time.py --days 30 --by week
  2328:   ```
  2329: 
  2330:   The 30 days to 2026-08-28 measured **403 runner-hours over 5,877 jobs** —
  2331:   `x86_64-windows-znver5` 131.0 h (median 5.7 min/job), `aarch64-macos-mini`
  2332:   113.9 h, `x86_64-linux` 102.1 h, `x86_64-linux-dedicated` 52.7 h, the gate
  2333:   3.3 h — and push latency over 1,435 runs of median 6.1 min, mean 8.1, p90
  2334:   17.0. Authentication reuses the git credential for the forge, so there is
  2335:   nothing to set up.
  2336: 
  2337:   The arithmetic is trivial and every trap is in the data, which is why this is
  2338:   a script and not a one-liner. **`task.updated_at` is not the end of the
  2339:   job**: Forgejo's log-retention sweep re-touches the row long afterwards in
  2340:   batches that share one end second (a whole day stamped `23:45:3x`), which
  2341:   makes a raw sum overstate a month by ~30x — a five-minute Windows job
  2342:   appearing to run for 33 hours. Two physical ceilings repair it: a job cannot
  2343:   outlive its run (clamp to the run's `stopped`, joined on `run_number ==
  2344:   index_in_repo`) and cannot outlive `ci.yml`'s `timeout-minutes`, which is why
  2345:   exact 7201-second rows are real timeout kills; the ~0.3% that survive both
  2346:   are imputed from the runner's median and counted in an `imputed` column
  2347:   rather than hidden. `actions/tasks` is the only per-job timing source —
  2348:   `actions/runs/{id}/jobs` returns `started_at` and `completed_at` as null
  2349:   here. And a paged walk must test the **head** of each id-descending page
  2350:   against the cutoff, never the tail: runs that never dispatched carry
  2351:   `0001-01-01`, which ends the walk hundreds of runs early and silently
  2352:   inflates every job whose run can no longer be found. `--self-test` covers the
  2353:   repair without touching the network.
  2354: 
  2355:   `limit` caps at 50 and the server ignores `Accept-Encoding: gzip`, so a cold
  2356:   month is 154 requests and 23 MB (~18 s); terminal rows are cached under
  2357:   `build/ci-time-cache.json`, which takes a repeat window to 2 requests and
  2358:   ~1 s. Do not raise `--jobs` past its default of 8 to go faster — 16 measured
  2359:   slower, the forge being the bottleneck while it is also serving runners.
  2360: - **`tools/cache_miss_survey.py`** answers *where the cache misses are*, the
  2361:   data-side counterpart to `tools/branch_miss_survey.py` below. It runs the
  2362:   stage-1 workload under `perf stat` for the hierarchy budget (L1d accesses
  2363:   and misses, how many fills L2 answers, the demand fills that reach DRAM,
  2364:   both TLBs, page faults), then takes one `perf record` per event and ranks
  2365:   symbols by miss share *beside their cycles share*, because the ratio is what
  2366:   separates a symbol that misses because it is big from one that is waiting on
  2367:   memory. Top symbols are broken down by source line through
  2368:   `llvm-symbolizer`, and `--dwarf` adds a sparser DWARF-unwound capture that
  2369:   names the exact `memcpy`/`memset` call sites — worth it here, where a fifth
  2370:   of every miss event has its leaf in libc. Three of its rules are the same
  2371:   ones this section states for `perf`, and the script encodes them so they do
  2372:   not have to be remembered: symbolize `sym+offset` rather than `-F srcline`,
  2373:   keep `--no-inline` on `perf script` (inline expansion costs 170 s against
  2374:   under a second here) and recover inline chains from `llvm-symbolizer`
  2375:   instead, and read a line table as a loop rather than an instruction, since
  2376:   AMD's precise sampling facility (IBS) is system-wide only and the script
  2377:   stays unprivileged. It also documents the trap that frame-pointer unwinding
  2378:   *skips* the caller of a `memcpy`, so an fp callchain names the call site one
  2379:   level out. Run it from the repository root on an idle machine after
  2380:   `./build.sh build --config Release -t ide`; a full `--dwarf` pass takes
  2381:   about 25 seconds and writes its captures and report under
  2382:   `build/cache-miss-survey/`.
  2383: - **The local Release tree is profilable as built.** `BUSTER_DEBUG_INFO` and
  2384:   `BUSTER_FRAME_POINTERS` are both on by default outside `--ci`, so
  2385:   `./build.sh build --config Release -t ide` produces a `-O3` binary that
  2386:   symbolizes to source lines and unwinds through `--call-graph fp`, the same
  2387:   cheap unwinding the sanitized Debug tree allows. Superluminal reads it
  2388:   directly. Record it like any other build:
  2389: 
  2390:   ```sh
  2391:   ./build.sh build --config Release -t ide
  2392:   perf record -F 999 -g --call-graph fp -o release.data — ./build/Release/ide bench
  2393:   ```
  2394: 
  2395:   The `perf script`/`llvm-symbolizer` rules below apply unchanged; the Release
  2396:   binary is a clang PIE like the Debug one. Pass
  2397:   `-DBUSTER_FRAME_POINTERS=OFF` when the point of the measurement is the
  2398:   frame-pointer cost itself, or when reproducing a CI Release number exactly.
  2399: - **Sampling the sanitized (ASan+UBSan) Debug tree with `perf` works.** It is
  2400:   the CI critical path, so it is the configuration most worth profiling. Record
  2401:   it exactly like any other build; there is no sanitizer-specific obstacle:
  2402: 
  2403:   ```sh
  2404:   ./build.sh generate --sanitize && ./build.sh build -t ide
  2405:   LD_PRELOAD= perf record -F 999 -g --call-graph fp -o asan.data \
  2406:       — ./build/Debug/ide test --verbose=1
  2407:   ```
  2408: 
  2409:   Four things must be right, and each one silently produces a *plausible but
  2410:   wrong* profile when it is not:
  2411:   - **Clear `LD_PRELOAD`.** With one inherited (NoMachine sets
  2412:     `LD_PRELOAD=/usr/NX/lib/libnxegl.so`), the shared ASan runtime is not first
  2413:     in the initial library list, the process aborts inside `ld.so` before
  2414:     `main`, and the capture is ~12 samples that are ~100% of *user-space* time
  2415:     in `ld-linux-x86-64.so.2` with no ASan symbols. That result is not a
  2416:     symbolization failure and not evidence that ASan defeats sampling — it is
  2417:     an empty profile of the dynamic loader. `CMakeLists.txt` already composes
  2418:     the runtime ahead of any inherited `LD_PRELOAD` for its own test targets;
  2419:     only ad-hoc command lines need the `LD_PRELOAD=` prefix.
  2420:   - **Run on a quiet machine.** A contended host produces the same visual
  2421:     signature — few samples, attribution smeared into the loader and the
  2422:     scheduler. Confirm the sample count and the `TEST_MODULE_TIMING` line agree
  2423:     with a serial run before reading anything into the histogram.
  2424:   - **`--call-graph fp` is correct and cheap here.** Debug is `-O0` and the
  2425:     sanitizer runtime keeps frame pointers, so frame-pointer unwinding resolves
  2426:     from inside `libclang_rt.asan` back into buster code. This matters because
  2427:     the sanitizer cost has to be charged to the buster function that provokes
  2428:     it; a leaf-only profile just says "memcpy".
  2429:   - **Do not use `perf script -F srcline` (or `-F ip,sym,srcline`) for line
  2430:     attribution.** It resolves the raw return address, which points *after* the
  2431:     call, so it reports the following line — measured on this tree it shifts
  2432:     call sites by 1–2 lines (real `c_test.c:7227` is reported as `7229`, real
  2433:     `7229` as `7230`) and prints `:0` for ~69% of frames. Extract
  2434:     `sym+offset` instead and symbolize the byte before the return address:
  2435: 
  2436:     ```sh
  2437:     perf script -i asan.data --no-demangle -F comm,ip,sym,symoff,dso
  2438:     # static vaddr = (readelf -sW addr of sym) + offset; then
  2439:     #   llvm-symbolizer --functions=linkage --demangle  <<< "CODE build/Debug/ide 0x<vaddr-1>"
  2440:     ```
  2441: 
  2442:     Use `sym+symoff`, not `-F dsoff`: `dsoff` is a **file** offset while
  2443:     `llvm-symbolizer` wants a **virtual** address, and for a clang PIE the two
  2444:     differ by `p_vaddr - p_offset` of the text segment (`0x1000` for
  2445:     `build/Debug/ide`). Feeding `dsoff` straight to `llvm-symbolizer` yields
  2446:     wrong-but-believable source lines. This is the same class of mistake as
  2447:     `perf report` mis-symbolizing buster-produced `ET_EXEC` images by
  2448:     `-0x400000`; clang-built binaries are PIE and symbolize normally once the
  2449:     right address space is used.
  2450: - **`tools/branch_miss_survey.py` ranks branch mispredictions by source line,
  2451:   not by symbol.** `perf record -e branch-misses` is not a precise event: the
  2452:   sample lands past the branch that caused it, so its histogram names the
  2453:   function and three audits (`2026-08-22b`, `2026-08-22d`) paid to discover
  2454:   that separately. Zen 3 and later carry the AMD Last Branch Record extension,
  2455:   so `perf record -j any,u` captures the last sixteen branches of every sample
  2456:   with a per-entry mispredict flag — the branch instruction's own address. The
  2457:   script records that over the stage-1 self-host compile by default, tallies
  2458:   the mispredicted records, symbolizes them through inline frames, and prints a
  2459:   ranking per function and per line with each row's estimated absolute misses:
  2460: 
  2461:   ```sh
  2462:   ./build.sh build --config Release -t ide
  2463:   tools/branch_miss_survey.py --repeat 3 --cross-check
  2464:   ```
  2465: 
  2466:   `--cross-check` re-profiles the same run with `branch-misses:u` and prints
  2467:   that share beside each function, which is the check that the address mapping
  2468:   is right: a branch record is a runtime address in a PIE and needs the
  2469:   `p_vaddr - p_offset` skew above, and dropping it silently reports the
  2470:   neighbouring functions. Profile any other workload by passing it after `--`.
  2471:   `--self-test` covers the address math without needing `perf`.
  2472: - **Validate any profiling method against a non-sampling ground truth before
  2473:   trusting it.** The cheap one here is direct timing: bracket the call sites
  2474:   under suspicion with `timestamp_take()`/`timestamp_ns_between()` and print
  2475:   through `arguments->show`, then compare against the sampled shares of the
  2476:   same process. Confirm the extracted return addresses too — each one must
  2477:   disassemble to the instruction immediately after a `call` to the callee the
  2478:   callchain names (`objdump -d --start-address=... --stop-address=...`).

  2480: ## Performance audit notes
  2481: 
  2482: Audit history lives in `PERFORMANCE_AUDITS.md`, newest first — it is kept out
  2483: of this file because it is a growing record rather than a rule. **Read its
  2484: newest entry before any performance work**: it holds the reference numbers a
  2485: new measurement is compared against (stage 1 instructions, sanitized and
  2486: Release `ide test`, `ide bench` medians), the finds that were deliberately
  2487: left untaken, and the traps an earlier audit already paid for. Record a new
  2488: audit there, not here; this file keeps the method, that file keeps the
  2489: history.
  2490: 
  2491: An audit is a **new file**, `docs/performance-audits/<id>.md`, plus one line at
  2492: the top of the index in `PERFORMANCE_AUDITS.md`. Never append an entry into an
  2493: existing audit file and never rewrite one: the split exists so that two audit
  2494: branches open at once touch disjoint files, which is what the single prepended
  2495: history could not do. The index line is the only shared text, and
  2496: `.gitattributes` marks `PERFORMANCE_AUDITS.md` `merge=union` so concurrent
  2497: inserts keep both lines rather than conflicting — after such a merge, check
  2498: that the newest id is on top, because union does not know which line is newer.
  2499: 
  2500: The id is the **UTC timestamp at which the audit is recorded**,
  2501: `2026-08-22T140351Z` — ISO 8601 with the colons dropped, because Windows
  2502: forbids them in filenames. `tools/new_audit.py` mints one, creates the file and
  2503: inserts the index line; use it rather than typing an id by hand, because the id
  2504: is the one field two concurrent sessions can independently choose the same
  2505: value for. Audits before 2026-08-22 are named by date plus a sequence letter
  2506: (`2026-08-08k`), and that is precisely what collided: the letter is picked by
  2507: counting the day's existing entries, so two sessions auditing the same day
  2508: always picked the same letter, and three of the four PRs open when the history
  2509: was split had done exactly that. Those older names are historical — entries
  2510: cross-reference each other by them — and stay as written.

  2512: ## Forge, issues, and pull requests
  2513: 
  2514: The forge and source of truth are Forgejo at
  2515: `https://code.buster14a.com/buster/buster`, not GitHub; CI lives under
  2516: `.forgejo/`. A private workflow-only GitHub broker may supply opt-in hosted
  2517: desktop runners as documented in `docs/ci-github-hosted-runners.md`, but it is
  2518: never a source mirror. Talk to Forgejo with **`fj`**, the Forgejo CLI. It reads
  2519: the repository from the git remote, so run it from inside a checkout (or pass
  2520: `-C <path>` / `-r buster/buster`).
  2521: 
  2522: The issues open on 2026-08-31 were copied to `buster14a/buster` on GitHub as
  2523: part of the migration under way there. Numbers did not survive the copy, so
  2524: every reference in this file, in code comments, and in commit messages names
  2525: the **Forgejo** number: resolve it through `docs/issue-migration-map.md`, or
  2526: through `docs/forgejo-issue-archive.md` for issues already closed by then.
  2527: 
  2528: `fj` needs a token once per machine. The password half of the
  2529: `code.buster14a.com` line in `~/.git-credentials` is a valid API token, so
  2530: authentication is a pipe, not a browser round trip:
  2531: 
  2532: ```sh
  2533: grep code.buster14a.com ~/.git-credentials \
  2534:   | sed 's|https://[^:]*:||; s|@code.buster14a.com.*||' \
  2535:   | fj auth add-token -H code.buster14a.com
  2536: fj whoami          # verify: <account>@code.buster14a.com
  2537: ```
  2538: 
  2539: `fj issue create "<title>" --body-file <path> --no-template`,
  2540: `fj issue search [-s open|closed|all]`, `fj issue view <n>`,
  2541: `fj issue comment <n>`, and `fj pr create --base main --head <branch>
  2542: --body-file <path>` are the whole working set; `fj pr search`, `fj pr status`
  2543: and `fj pr view` read the other side. Two things to know before scripting it:
  2544: the subcommand for listing issues is `search`, not `list`, and **omitting both
  2545: `--body` and `--body-file` opens `$EDITOR`**, which hangs a non-interactive
  2546: session — always pass a body file. Write the body as a file rather than a
  2547: shell string: backticks inside `$(cat <<EOF)` get command-substituted by zsh,
  2548: which has mangled a commit message before.
  2549: 
  2550: `fj` supersedes the older workarounds. `tea`'s login for this host has no
  2551: token, and the raw-`curl` recipe that went with it needed a browser
  2552: `User-Agent` to get past Cloudflare's `403 error code: 1010`; `fj` is not
  2553: subject to either problem.
  2554: 
  2555: **Issues are the task queue.** Work that is real but not being done right now
  2556: becomes an issue, not a paragraph in an audit that nobody will find — a chip
  2557: filed against a memory is invisible to the next agent, while an issue is
  2558: something a fresh session can pick up cold. Write the body as a **prompt**: what
  2559: is wrong and how it was diagnosed, the file and symbol names to start from,
  2560: the constraints and do-not-retries that earlier work already paid for, how to
  2561: validate the fix (which oracle, which harness, which counters), and a
  2562: definition of done. State what was measured and when, so a stale claim is
  2563: recognisable as stale; the tree moves fast enough that a count quoted without
  2564: a date is a trap. Issues #537-#549 are examples of the form.
  2565: 
  2566: **Push a rebase before you re-verify it.** A rebase onto a moved `main` is
  2567: followed by a full local pass — `test_all`, `test_self_host`, whichever compat
  2568: harness the change touches — and that pass takes longer than CI takes to start.
  2569: Push the rebased branch first, as long as the runners are not already saturated
  2570: with other work, so the matrix runs while the local pass runs; the two agree
  2571: almost always, and when they disagree you have both answers sooner. Force-push
  2572: with `--force-with-lease`, never a bare `--force`, so a branch someone else
  2573: advanced is not overwritten. This is a rebase rule, not a general one: a branch
  2574: whose content is still changing waits for the local pass, because a red CI run
  2575: on a commit you already know is incomplete tells nobody anything.

  2577: ## Core rules
  2578: 
  2579: - **Code must stay human-maintainable.** Every major file opens with an
  2580:   orientation header — what it owns, its entry points, and, for large files,
  2581:   a layout map anchored to greppable definition names, never line numbers.
  2582:   Update the header in the same change that moves what it describes. A value
  2583:   that must agree across several sites (a chunk size that a capacity
  2584:   computation and an emitter both depend on, a limit one file checks and
  2585:   another file exploits) is a named constant, not a respelled literal; a
  2586:   genuinely one-off format field keeps its literal with a comment naming it.
  2587:   Comments state constraints the code cannot show; a claim that has not been
  2588:   verified against the code does not get written down.
  2589: - **One return per function.** A function has a single exit: compute the
  2590:   answer into one result variable, let control flow converge, and `return` it
  2591:   once at the end. Guard clauses, mid-loop `return`s, and per-case `return`s in
  2592:   a `switch` all become assignments to that variable followed by ordinary
  2593:   structured flow — an `else`, a loop condition, a `break`. Prefer restructuring
  2594:   the condition over adding nesting; where an early exit skipped work that is
  2595:   now merely wasted, keep it skipped with a `done` flag or a loop guard rather
  2596:   than reintroducing a second `return`. A single exit is what makes an epilogue
  2597:   — a cleanup, a trace point, an arena reset — impossible to leak past. `goto`
  2598:   to a shared tail is a second exit spelled differently; it is allowed only for
  2599:   the error-unwind ladders that already exist, never as a way to keep an early
  2600:   return. Returns in mutually exclusive `#if`/`#elif`/`#else` arms are one
  2601:   return — every configuration compiles exactly one of them — so a
  2602:   platform-dispatch body already satisfies this rule and does not need a result
  2603:   variable threaded through the preprocessor. A `switch` that used to return a
  2604:   value per case becomes an undecorated `Type result;`, one `result = ...` per
  2605:   case, and `default: BUSTER_TODO();` for the impossible case: `BUSTER_TODO`
  2606:   never falls through, which is what leaves `result` definitely assigned without
  2607:   a placeholder initializer that a real bug could hide behind. Do not initialize
  2608:   the result variable when every path already assigns it: `clang_analyze` reports
  2609:   that store as dead and fails the Release tree, and the rule's whole point is
  2610:   that the paths, not an initializer, decide the answer.
  2611: - `BUSTER_F_DECL` belongs on header declarations only. In a `.c` file, a
  2612:   module-local function is `BUSTER_GLOBAL_LOCAL`, and a function that a header
  2613:   already declares carries no macro at all — the header declaration is what
  2614:   gives it internal linkage in the unity build.
  2615: 
  2616: ## Machine instruction selection and scheduling
  2617: 
  2618: - `MachineInstruction` is the 24-byte hot row. Keep static form, scheduling,
  2619:   memory, bundle, fixed-register, tie, early-clobber, implicit-physical, and
  2620:   implicit-resource facts in `MachineOpcodeInfo`, accessed through the
  2621:   `machine_opcode_*` helpers.
  2622: - `MachineFunction` owns CFG edges, block parameters, and incoming edge
  2623:   parallel-copy sources. Edge source `i` maps to destination block parameter
  2624:   `i`; keep these copies parallel through allocation so cycles are resolved as
  2625:   copies rather than serialized selector moves. Replay files include all three
  2626:   arrays and use the current replay version.
  2627: - An ordinary machine virtual register has exactly one definition and every
  2628:   use, including an edge-copy source, is dominated by it. The temporary
  2629:   `MACHINE_VIRTUAL_REGISTER_FLAG_MUTABLE` exception is explicit and counted;
  2630:   FAST/QUALITY liveness scans all textual touches, the scheduler preserves
  2631:   their source order, and SSA-only consumers must reject mutable values.
  2632: - Shared canonical-IR facts and the generated FAST/QUALITY rule decision tree
  2633:   live in `machine_select.{c,h}`, `machine_select_rules.h`, and
  2634:   `machine_select_generated.c`. Target selectors may retain custom ABI and
  2635:   complex lowering, but must consume shared facts instead of introducing a
  2636:   third permanent graph IR.
  2637: - x86 ADD/SUB/AND/OR/XOR/IMUL rows are three-operand machine SSA with operand
  2638:   0 tied to operand 1. Allocators satisfy the physical two-address constraint;
  2639:   selectors must not reintroduce a MOV plus mutable USE_DEFINE result.
  2640: - QUALITY scheduling remains pressure-first and deterministic. Pressure is
  2641:   counted per register class; metadata supplies barriers, memory membership,
  2642:   and vector scheduling membership while compatibility opcode classifiers
  2643:   cover legacy rows during migration.
  2644: - `-fPIC` is a code model, not an accepted flag. It reaches code generation as
  2645:   `CodegenModuleOptions.position_independent`, and generation resolves it for
  2646:   the target: x86-64 ELF, where the relocations it changes are the ones `ld`
  2647:   refuses in a shared object. A symbol another object could interpose --
  2648:   `ir_symbol_is_interposable`, which is external or imported linkage without
  2649:   hidden visibility -- has its address loaded out of its GOT slot
  2650:   (`R_X86_64_GOTPCREL`) instead of computed rip-relative, and a direct call to
  2651:   one is relocated `R_X86_64_PLT32` so the linker may route it through a
  2652:   procedure linkage entry. Internal and hidden symbols keep the rip-relative
  2653:   form, and a thread-local address is the thread-local model's to pick --
  2654:   `codegen_thread_local_model` reads the same flag and answers general-dynamic
  2655:   under it. The canonical emitter and the machine path make
  2656:   the same decision from the same predicate: the selector writes a
  2657:   `MachineSymbolReference` beside each call-target row and the module
  2658:   relocation is derived from it, so the four allocators cannot disagree. One
  2659:   object-writer decision follows from the model rather than from a relocation:
  2660:   an unwind record's function pointer is relocated against a local text symbol
  2661:   with the function's own offset, because an FDE naming a preemptible function
  2662:   is the same PC-relative reference to an interposable symbol that `ld`
  2663:   refuses in the body.
  2664: - `-fPIE`/`-fpie` stay accepted and inert, and that is a statement rather than
  2665:   an omission: every reference this compiler emits is already rip-relative, an
  2666:   executable's own definitions are not interposable, its references to another
  2667:   image's data are what the linker's copy relocation is for, and its own
  2668:   thread-local block is still the initial one -- so the
  2669:   position-independent-executable model asks for no code this compiler does not
  2670:   already produce. `-fno-pic` clears the model; `-fno-pie` clears nothing
  2671:   because nothing was set.
  2672: - The built-in linker resolves both forms for the image it writes, which binds
  2673:   every name in it: `PLT32` patches the same rel32 `PC32` does, and a GOT load
  2674:   is relaxed back into the `lea` it would have been (`link_x86_relax_got_load`),
  2675:   the same relaxation `ld` performs for a `GOTPCRELX` it can resolve. The ELF
  2676:   reader takes `R_X86_64_GOTPCREL`, `GOTPCRELX` and `REX_GOTPCRELX` as one
  2677:   kind for that reason, so a `-fPIC` object -- this compiler's or clang's --
  2678:   links here. An instruction shape the relaxation does not recognize fails the
  2679:   link by name rather than being rewritten. It relaxes the two indirect
  2680:   thread-local models back to local-exec for the same reason
  2681:   (`link_elf_relax_thread_local`).
  2682: 
  2683: - **C only.** No C++, no exceptions. `-fwrapv`, `-fno-strict-aliasing`,
  2684:   `-funsigned-char`.
  2685: - **No third-party code.** External code was deliberately removed from the
  2686:   tree. Do not add dependencies or vendor libraries.
  2687: - **Recursion is forbidden unless it is trivial and statically bounded.**
  2688:   Recursive algorithms must represent recursion in data, using an explicit
  2689:   stack, queue, or worklist rather than the C call stack. Never use recursive
  2690:   calls when the depth depends on source input, runtime data, or another
  2691:   unbounded structure.
  2692: - **Compiler control flow must not use callbacks or function-pointer dispatch.**
  2693:   Use direct calls, loops, switches, and explicit work structures. Function
  2694:   pointer values may model the program being compiled, but the compiler itself
  2695:   must not execute through them. The one infrastructure exception is the
  2696:   uniform SPMD entry passed to `lane_run`; work inside that entry still uses
  2697:   direct control flow and an explicit index or range.
  2698: - **Parallelism target: SPMD across threads, SIMD within each thread.**
  2699:   Implementation code is written multi-core-by-default in the lane model of
  2700:   Ryan Fleury's raddebugger (`lane_run`, `lane_index`/`lane_count`,
  2701:   `lane_range`, `lane_sync`, `lane_broadcast` in `<buster/lib/os.h>`): every
  2702:   lane of a gang runs the same code, narrows serial work with
  2703:   `if (lane_index() == 0)`, and splits parallel work by `lane_range` or an
  2704:   atomic take-index — not through job systems, task queues, or callbacks.
  2705:   Lane-style code must degrade to serial: `BUSTER_SINGLE_THREADED` builds and
  2706:   one-lane gangs run the identical path with no threads and no separate serial
  2707:   variant. Within a lane, prefer wide data parallelism in the style of Daniel
  2708:   Lemire's simdjson kernels — process data in blocks, classify with tables and
  2709:   bitmasks, iterate set bits — over per-element branching, and shape data the
  2710:   way Casey Muratori advocates: flat index-linked arrays in arenas transformed
  2711:   by batch passes, not pointer graphs walked element-at-a-time. Wojciech
  2712:   Muła's notes (`http://0x80.pl/notesen.html`; fetch over plain HTTP — the
  2713:   host's HTTPS certificate is broken) are the project-endorsed catalogue of
  2714:   these kernel shapes: before writing a byte- or word-granularity loop, check
  2715:   whether one of his notes already solves it branchless with masks, `vpshufb`
  2716:   or `vpermb` lookups, `vpternlogd`, or compaction. Start from "Modern
  2717:   perfect hashing for strings", "SIMD-ized check which bytes are in a set",
  2718:   "AVX512VBMI — remove spaces from text", "AVX512VBMI2 and packed varuint
  2719:   format", "Parsing decimal numbers" parts 1–2, "SIMD-friendly algorithms
  2720:   for substring searching", and "AVX-512 conflict detection". Parallel
  2721:   stages must stay deterministic — write results into slots indexed by work
  2722:   item, never by completion order — so the self-hosting fixed point stays
  2723:   byte-identical at any lane count. `lane_run` keeps a persistent worker gang
  2724:   on the calling thread context and reuses it across phases; do not add phase-
  2725:   local thread creation. Variable-duration work uses an atomic take-index,
  2726:   writes function- or item-local fragments into stable source-indexed slots,
  2727:   and merges them only after a lane barrier.
  2728: - **A global built on first use is prewarmed, never raced.** Several hot
  2729:   tables are derived once and read forever after through plain loads — the C
  2730:   frontend's character classes, compact lexer tables, punctuator dispatch and
  2731:   declaration keywords, the codegen ABI target cache, the font provider's
  2732:   resolved paths, and the x86 metadata decode plus the three caches over it.
  2733:   That shape is sound only while no other thread can be reading, so every such
  2734:   build states `BUSTER_CHECK_SERIAL_INITIALIZATION()` (`<buster/lib/os.h>`,
  2735:   always compiled in, over `os_is_only_live_thread()`), and every owning
  2736:   module publishes a prewarm entry point that fills it on the calling thread:
  2737:   `c_prewarm`, `codegen_prewarm`, `font_provider_prewarm`,
  2738:   `buster_x86_metadata_prewarm`, and `compiler_prewarm` for the compile
  2739:   pipeline as a whole. **Call the prewarm
  2740:   before `lane_run`** — x86 metadata separately, since its prewarm costs a
  2741:   full table decode. That decode is on the compile path:
  2742:   `codegen_prewarm_for_target` runs it for every x86-64 module, and the
  2743:   encoder's fallback rows still query forms per row, so the cost is the
  2744:   per-invocation floor of every `ide cc`, not an optional extra. Its per-form
  2745:   caches — the normalized row, the parsed pattern, the operand views, the
  2746:   derived facts and each record's validity — fill on the first *serial* touch
  2747:   of each form, so a caller about to hand the tables to a gang must call
  2748:   `buster_x86_metadata_prewarm_all_forms()` first, which fills every one of
  2749:   them. A new lazily built global adds both the check and a line in its
  2750:   module's prewarm.
  2751:   Publish the flag *after* the state, never before: the x86 metadata decode
  2752:   needs two flags for this, one guarding re-entry from the reads its own
  2753:   layout checks make through the accessors and one, set last, that every
  2754:   accessor tests. Spelling the character-class
  2755:   tables as constant initializers over a predicate macro would remove four of
  2756:   these outright, and was measured at **+178.8 M stage-1 instructions
  2757:   (+3.5%)** for 112 k extra preprocessed tokens — one predicate expansion per
  2758:   byte value per table. A real generator writing the bytes into source would
  2759:   not cost that; the preprocessor doing it at every compile does.
  2760: - **Microarchitecture tuning target: design for Zen 5's native 512-bit
  2761:   width; Zen 4 must break even, Zen 5 collects the upside.** The main
  2762:   development machine is a Ryzen 9 7940HS (Zen 4) and the CI x86-64 runners
  2763:   cover both generations (the Windows runner is a Zen 5 box), so
  2764:   single-thread throughput decisions — SIMD width, table sizes,
  2765:   branch-vs-cmov trades — are made for and measured on these cores.
  2766:   GNU-family builds compile with `-march=native`, so clang-built binaries on
  2767:   these hosts already have AVX-512 (VL/BW/DQ/VBMI/VBMI2) available. Write
  2768:   kernels at full 512-bit width: Zen 4 executes them double-pumped over its
  2769:   256-bit datapaths at AVX2-equivalent bytes per cycle with fewer
  2770:   instructions retired — no downclocking, no penalty, just no width upside —
  2771:   while Zen 5's native 512-bit units roughly double the same code's
  2772:   throughput. A kernel therefore has to justify itself at Zen 4's effective
  2773:   width and is validated there, but its shape (masks, compaction, permutes)
  2774:   is chosen for Zen 5. Watch the exceptions on Zen 4: the few instructions
  2775:   whose 512-bit form costs more than 2x the 256-bit form (check uops.info
  2776:   before leaning on exotic two-source permutes; `vpcompressb` is safe at
  2777:   ~9 cycles Zen 4 / ~5 cycles Zen 5), store-throughput-bound kernels (one
  2778:   256-bit store per cycle on Zen 4), and unaligned 64-byte loads — keep hot
  2779:   streamed buffers 64-byte aligned. Explicit intrinsics must stay behind
  2780:   feature/compiler guards with a scalar or SWAR fallback: MSVC builds carry
  2781:   no `-march`, aarch64 (macOS/Android/iOS) must keep building, and the
  2782:   self-hosted `ide cc` stages compile the same tree without vendor headers —
  2783:   performance is only ever quoted from clang-built binaries, so fallback
  2784:   paths need correctness, not speed.
  2785: - **Write 512-bit kernels in the vocabulary of `<buster/lib/simd.h>`, not in
  2786:   `<immintrin.h>`.** That header is a target-fixed list of AVX-512 operations
  2787:   — masked 512-bit loads and stores, byte comparisons producing a `Mask64`,
  2788:   `vpermt2b`, `vpcompressb` and its compacting store, byte-to-word widening,
  2789:   `vpternlogd`, lanewise arithmetic — with three implementations behind one
  2790:   spelling: `__builtin_buster_simd_*` for the self-hosted stages, host
  2791:   intrinsics for clang and gcc, and a scalar fallback for MSVC, AArch64 and
  2792:   pre-AVX-512 x86. `BUSTER_SIMD_512` says which one is in play; guard on it
  2793:   only where a *different algorithm* is worth writing, never merely to keep
  2794:   the tree building. It is deliberately not a portability layer — every
  2795:   operation names one instruction, and an abstraction wide enough to also
  2796:   describe NEON would lose exactly the operations that make these kernels
  2797:   fast. Adding to it means adding an `IrSimdOperation`, its arity in
  2798:   `ir_simd_operation_shape`, its validation, its EVEX lowering in
  2799:   `codegen_canonical_x64_simd_operation`, the builtin in `c_ir_simd_builtins`,
  2800:   its spelling in `c_symbol_predefined` (`c_source.c` — without it the
  2801:   self-hosted stages fail with "could not lower unbound identifier"),
  2802:   a fallback, and a case in `tests/basic_c_simd.c`; the shape table is the
  2803:   single source of truth that keeps a new operation from being half-taught to
  2804:   the pipeline. Two consequences are worth knowing before writing a kernel.
  2805:   **Everything in the header is a macro**, because `ide cc` lowers directly
  2806:   and runs no inliner — not even for `always_inline` — so a function wrapper
  2807:   would be a real call per SIMD operation in the self-hosted stages;
  2808:   arguments must therefore be free of side effects. A `Simd512` may still
  2809:   cross a call boundary by value where that is what the code wants: SystemV
  2810:   passes and returns it in a vector register and spills past the eighth, and
  2811:   a target whose vector registers are narrower than the value says so with
  2812:   `CODEGEN_ERROR_UNSUPPORTED_ABI` rather than encoding a register it does not
  2813:   have. And **masks are `u64`, not an opaque k-register handle**: the
  2814:   canonical backend allocates no registers, so a mask spills to its frame slot
  2815:   either way, the vector instructions pick it back up with a single `kmovq`,
  2816:   and mask shifts, Boolean combinations, `mask64_count` and `mask64_first_set`
  2817:   stay on the general-purpose ALUs, which retire more of them per cycle on
  2818:   Zen 4/5 than the k unit does.
  2819: - **SIMD C lexing method: the Validark lineage.** `c_lex_compact` in
  2820:   `frontend/c/c_source.c` draws on Niles Salter's (Validark's) Accelerated Zig
  2821:   Parser — local checkout `~/dev/Accelerated-Zig-Parser`, upstream
  2822:   `github.com/Validark/Accelerated-Zig-Parser` — plus validark.dev (start with
  2823:   `posts/deus-lex-machina` and
  2824:   `posts/eine-kleine-vectorized-classification`) and the three Utah Zig talks
  2825:   (YouTube `oN8LDpWuPWw`, `FDiUKafPs0U`, `NM1FNB5nagk`). When accelerating the
  2826:   C lexer, reach for these techniques first and keep new code compatible with
  2827:   their shapes. The core vocabulary: (1) per-64-byte-chunk classification —
  2828:   every class (whitespace, newline/CR, alpha/digit/underscore, quotes,
  2829:   backslash, slash, operator chars) becomes one comparison into a `k`-mask
  2830:   bitstring, all classes over the same chunk in lockstep sharing one load; (2)
  2831:   token extents by mask arithmetic — starts `x & ~(x << 1)`, ends
  2832:   `x & ~(x >> 1)`, then either cursor queries (shift by cursor, count trailing
  2833:   ones — one tzcnt replaces an unpredictable byte loop) or full vector
  2834:   compaction: `vpcompressb` an iota vector through the starts and ends masks,
  2835:   subtract, and every token length in the chunk materializes at once; kinds
  2836:   come from masked broadcasts into a kinds vector compressed by the same
  2837:   starts mask, interleaved with lengths on store; (3) charset membership via
  2838:   nibble-decomposed `vpshufb`/`vpermb` tables —
  2839:   `table[c & 0xF] & (1 << (c >> 4))` per lane, the upper-nibble powers-of-two
  2840:   vector shared across charsets, `vptestmb` folding the AND and test on
  2841:   AVX-512; (4) multi-character operators as a bit-channel `vpshufb` NFA: three
  2842:   per-position tables whose looked-up bytes AND together so each of the 8
  2843:   bit-channels legalizes one family of 2-/3-char sequences, plus a short
  2844:   effectively-branchless reconciliation of overlaps; (5) keyword and builtin
  2845:   recognition by perfect hash, never a memcmp ladder —
  2846:   `((len << 14) ^ first_two_bytes) * last_two_bytes >> 8` to 7 bits, Bagwell
  2847:   array-mapped compression (two u64 bitmaps + popcount rank) into a dense table
  2848:   of length-padded entries validated by a single wide compare, with
  2849:   compile/startup-time collision checks so editing the keyword set stays safe;
  2850:   (6) sentinels instead of bounds checks — a leading newline, trailing
  2851:   quote/NUL sentinels, and chunk-aligned overallocation let the hot loops drop
  2852:   every length test; (7) upper-bound allocation plus post-scan shrink instead
  2853:   of grow-and-check (the `2026-08-08k` tokenizer change is this trick alone,
  2854:   `-21.6%` bench instructions); (8) length-based token streams — kind + length
  2855:   with a 0-length escape to a wide length, no per-token start offsets or
  2856:   eagerly materialized line/column, offsets rebuilt by a running cursor and
  2857:   line numbers recovered by popcount over retained newline bitmasks.
  2858:   Escape-run parity uses the simdjson backslash algorithm (simdjson PR #2042
  2859:   has the current best form). All of it sits behind the guard rules of the
  2860:   tuning target above; scalar fallbacks keep the exact current semantics.
  2861:   `c_lex_compact` walks source in **item-aligned 64-byte windows** so no lexer
  2862:   state crosses a window: the item touching a window's last byte is deferred
  2863:   and rescanned by the next one, and shapes the masks do not model escape to
  2864:   the scalar single-item scanner `c_lex_scan_one`. C skips whitespace and
  2865:   comments instead of tokenizing them, so token ends need an explicit boundary
  2866:   mask rather than `starts >> 1`; lookahead loads are masked by the **file**
  2867:   bounds rather than the window's because a delimiter near the window end can
  2868:   be spelled from bytes the next window owns. Every SIMD lexer change must keep
  2869:   the differential gate asserting byte-identical agreement with the scalar
  2870:   reference over construct cases slid across the window boundary, items longer
  2871:   than a window, the real corpus at every window phase, and fuzz blobs over the
  2872:   full alphabet.
  2873: - **Warnings are errors** under a very large warning set (see
  2874:   `GNU_FAMILY_WARNINGS` in `CMakeLists.txt`), and code must stay clean under
  2875:   Clang, GCC, Zig cc, and MSVC. TCC is required only to compile/bootstrap the
  2876:   native `build.c` driver through `build.sh`/`build.ps1`; application code is
  2877:   not promised to compile with TCC. Avoid compiler-specific extensions unless
  2878:   guarded.
  2879: - **Idioms**: arena allocation (`<buster/lib/arena.h>`) — no malloc/free churn;
  2880:   `String8`/`S8("...")` (defined in `<buster/lib/base.h>`) — no C strings; `STRUCT(Name)`
  2881:   declarations; `BUSTER_`-prefixed macros; 4-space indent, snake_case, braces
  2882:   on their own line. Prefer function headers, declarations, statements, and
  2883:   similar constructs on one line; split them only when doing so is clearer.
  2884:   Match the surrounding file.
  2885: - Test implementations are not registered as modules; add new test pairs under
  2886:   `src/buster/tests/`, add
  2887:   the implementation to `BUSTER_TEST_SOURCES` and the header to
  2888:   `BUSTER_TEST_HEADERS` in `CMakeLists.txt`, and include both from
  2889:   `src/buster/tests/test.c` in the existing registration order (the
  2890:   implementation only in the `BUSTER_UNITY_BUILD` block).
  2891: - **Adding a module** (`foo.c`/`foo.h` under `src/buster/lib/`) takes three
  2892:   edits: (1) `buster_register_module(foo ...)` in `CMakeLists.txt`;
  2893:   (2) add `foo` to the `MODULES` list of `buster_add_executable(ide ...)`;
  2894:   (3) add `#include <buster/lib/foo.c>` to the `BUSTER_UNITY_BUILD` block at
  2895:   the top of `src/buster/apps/ide/ide.c` — optimized non-sanitized configs compile as
  2896:   unity builds, so forgetting this breaks ordinary Release builds.
  2897: - Headers are included as `<buster/lib/...>` or `<buster/tests/...>` (include
  2898:   root is `src/`).
  2899:   `compile_commands.json` is exported to `build/` by default.

  2901: ## Platform and backend boundaries
  2902: 
  2903: - In rendering and windowing, keep platform-neutral policy and data flow in
  2904:   the module front door (`rendering.c`, `window.c`). Native API calls
  2905:   belong in the selected backend implementation.
  2906: - Rendering backends live in `src/buster/lib/rendering/*.c`; window backends
  2907:   live in `src/buster/lib/window/*.c`. These are implementation files
  2908:   included by their owning module, not standalone CMake modules, so do not
  2909:   register them or add them to the unity-build include list.
  2910: - Every backend `.c` includes its directory's `internal.h` before its
  2911:   implementation declarations. Those private headers own the shared types,
  2912:   helper declarations, and native headers needed for clangd to parse a backend
  2913:   independently; do not depend on declarations only earlier in the owning `.c`.
  2914: - Share CPU-side draw generation, font/texture orchestration, event-list
  2915:   ownership, and lifecycle policy. Keep device resources, synchronization,
  2916:   swapchains, native event translation, and native handles backend-specific.
  2917: - Renderers consume window-system handles through `WmNativeSurface`; do not
  2918:   reach into `WmHandle` or `WmWindowHandle` from a rendering backend.

  2920: ## C frontend and canonical IR rules
  2921: 
  2922: - The public frontend API is `compiler/frontend/c/c.h`. In non-unity builds the
  2923:   implementation is split across `c_source.c`, `c_parse.c`, and `c_gen.c`;
  2924:   `c.c` preserves the unity include order and diagnostic mapping.
  2925: - Keep the frontend pipeline explicit: source loading and preprocessing,
  2926:   parsing and semantic construction, then canonical-IR lowering. Do not add a
  2927:   parallel frontend-specific IR or route code generation around canonical IR.
  2928: - Invalid user input must produce structured C diagnostics and a failed driver
  2929:   result. Assertions and `BUSTER_TODO()` are for violated internal invariants,
  2930:   never ordinary syntax or semantic errors.
  2931: - Arena ownership is part of the API contract. Returned source, syntax,
  2932:   semantic, and IR structures may reference earlier-stage storage; callers must
  2933:   retain the translation-unit arena until every downstream consumer finishes.
  2934: - Zero-initialize aggregate tables before publishing a partially resolved type.
  2935:   Recursive and mutually dependent declarations can expose an aggregate while
  2936:   later members are still unresolved; an uninitialized `IrField` must never be
  2937:   mistaken for a valid type or source reference.
  2938: - Canonical IR owns format-neutral functions, blocks, instructions, values,
  2939:   symbols, source ranges, types, and relocations. Shared layers must not contain
  2940:   frontend entity IDs, parser AST pointers, or language-specific invalid
  2941:   sentinels.
  2942: - Validate IR before machine selection or Wasm emission. A diagnosed frontend
  2943:   failure must not publish an apparently valid partial function to codegen.
  2944: - **GNU's `__alignof__` takes an expression; `_Alignof` takes only a type
  2945:   name.** Both spellings reach the same fold in `c_gen.c`, and it resolved an
  2946:   expression operand only for a compound literal until libc-test's
  2947:   `tls_align_dso.c` reached it: the file fills a table with `__alignof__(x)`
  2948:   over four `__thread` objects, and every other shape refused with "could not
  2949:   lower logical expression core". The operand now goes through the resolver
  2950:   `sizeof v` already used, which answers the alignment of the operand's **own
  2951:   type** -- `__alignof__(arr)` over a `char[7]` is 1, not the 8 the expression
  2952:   type prediction would give the pointer it decays to in any other context.
  2953:   The prediction is still the last resort for both words, under the same
  2954:   guards: an inline aggregate definition and an object whose array type never
  2955:   mapped are refused rather than guessed at. `tests/basic_c_alignof_expression.c`
  2956:   is the fixture, and every value in it was compared against clang.
  2957: - **`void` is one byte, and an object of it is still refused.** GNU gives
  2958:   `void` a size and an alignment of one so that arithmetic on a `void *` steps
  2959:   by bytes, and clang and gcc both fold `sizeof(void)`, `sizeof(const void)`
  2960:   and `_Alignof(void)` to 1. This compiler folded 0, and the index that `p + 3`
  2961:   becomes is scaled by the pointee's layout size, so the pointer did not move
  2962:   at all -- a silently wrong address rather than a diagnostic, and `q - p` was
  2963:   refused outright because the divide by the element size would have been a
  2964:   divide by zero (#743). The answer lives in `c_parse_builtin_type_layout`,
  2965:   which is the one table **both layout engines** read: `c_parse_type_layout`
  2966:   folds `sizeof` through it during the parse and `c_ir_scalar_type` builds the
  2967:   `IrType` from it, so there is no second place to keep in step. Nothing
  2968:   downstream had to change, because every backend already scales an
  2969:   `IR_OPCODE_INDEX` by the element type's size and every question about `void`
  2970:   that is *not* its size is asked of `IR_TYPE_VOID` rather than of a zero.
  2971:   The size is an extension for that arithmetic and for `sizeof`, **not a
  2972:   licence to declare a `void` object**: C 6.7p7 wants a complete type and both
  2973:   reference compilers refuse `void v;`, `void a[4];` and a `void` member. Those
  2974:   refusals used to fall out of the zero size -- an aggregate whose layout never
  2975:   resolved, a local whose alignment was zero, a file-scope object that reached
  2976:   code generation and failed there naming `main` rather than the object -- so
  2977:   they are asked of the kind now, through `c_ir_type_is_void_object` in
  2978:   `c_gen.c`, at the two local-declaration sites, the global definition walk,
  2979:   and the aggregate member layout, which reports through the same
  2980:   one-per-type slot a rejected alignment specifier uses. The predicate
  2981:   descends array elements alone: a qualified copy keeps the base's kind, so
  2982:   `const void` answers the same, and a `void *` is a pointer and answers no.
  2983:   `tests/basic_c_void_size.c` pins every runtime answer under all four
  2984:   register allocators -- both orders of the addition, the two subtractions,
  2985:   `++`/`--`/`+=`/`-=`, and the qualified pointees -- reading each stepped
  2986:   pointer back through a live object so an address that folds correctly and
  2987:   lowers wrongly still fails; `c_test_void_object_refusals` pins both layout
  2988:   engines' number and the four refusals.
  2989: - An integer converted to a pointer reaches pointer width in the frontend,
  2990:   before `IR_CONVERSION_INTEGER_TO_POINTER`, sign-extending when the operand is
  2991:   signed. All four backends lower that conversion as a plain register copy and
  2992:   LLVM's own `inttoptr` zero-extends, so a narrower operand that arrives
  2993:   un-widened silently loses its top half: `(void *)-1` — musl's `MAP_FAILED` —
  2994:   came out as `0x00000000ffffffff` and hung four libc-test units for as long as
  2995:   it was expressible. `c_ir_emit_integer_to_pointer` is the one place that
  2996:   performs it, a null pointer constant is built at pointer width so it costs no
  2997:   instruction there, and `ir_canonical_conversion_valid` rejects a
  2998:   non-pointer-width operand outright. `tests/basic_c_integer_to_pointer.c`
  2999:   pins the answers under every allocator.
  3000: - `main` is the one function whose fall-off is defined: reaching the `}` that
  3001:   terminates it returns 0 (C 5.1.2.2.3), where every other non-void function's
  3002:   is undefined (C 6.9.1p12) and terminates with `IR_OPCODE_UNREACHABLE` — the
  3003:   `ud2` Clang and GCC also emit. `CIrSignature.returns_zero_at_end` decides it
  3004:   once, with the signature, from a file-scope declaration named `main` whose
  3005:   return type is `int`; the terminator does not match a name. Getting it wrong
  3006:   is silent until the program ends: `regression/sem_close-unmap` and
  3007:   `functional/mntent` in libc-test have no return statement anywhere and both
  3008:   ran correctly to their last statement before dying on the brace with SIGILL.
  3009:   `tests/basic_c_main_implicit_return.c` pins it under every allocator, and
  3010:   exit zero is reachable there only through the closing brace.
  3011: - `builder->size_type` and `builder->ptrdiff_type` are chosen against the width
  3012:   of the scalar type the lowering built, not against `program->data_layout`'s
  3013:   own `unsigned long` entry. The two can disagree: the layout comes from the
  3014:   *preprocess* result and the scalar types come from `c_lower_to_ir`'s `target`
  3015:   argument, so a caller that preprocesses with one target and lowers with
  3016:   another — every frontend test does, preprocessing with a default target —
  3017:   otherwise gets a `size_t` narrower than a pointer on an LLP64 host. Nothing
  3018:   noticed while that only reached arithmetic; the widening above notices
  3019:   immediately, which is how a platform-independent defect first showed up as
  3020:   one platform's CI failure.
  3021:   `c_test_pointer_width_integer_conversion` lowers the same source for an LLP64
  3022:   target and an LP64 one and checks both.
  3023: - `IrFunction.opcode_summary` answers *may this function contain opcode X*
  3024:   without a scan, and it answers only for the `IR_OPCODE_SUMMARY_TRACKED`
  3025:   list: an opcode outside that list is never recorded, so
  3026:   `ir_function_may_contain_opcodes` rejects a query naming one rather than
  3027:   reporting a confident absence. Adding a query means adding its opcode to
  3028:   the list in the same change. The summary is exact only for functions
  3029:   created by `ir_module_add_function` and filled by
  3030:   `ir_function_add_instruction`; IR whose rows were written straight into
  3031:   `instructions` reads as unknown and every consumer keeps a scan for it.
  3032: - Source diagnostics in shared layers use canonical `IrSourceRange` and
  3033:   `IrSourcePosition`. Do not reintroduce parser-specific source-range APIs into
  3034:   codegen, debug information, object writing, or the linker.
  3035: - A value defined by `IR_OPCODE_GLOBAL` is a *place*: its frame slot holds the
  3036:   object's address, so it is an eightbyte whether or not the object's type has
  3037:   a resolved layout. That is what lets C's `extern struct opaque object;` be
  3038:   addressed without ever being completed, and musl's `src/include/stdio.h`
  3039:   depends on it — it suppresses the definition of `struct _IO_FILE` and then
  3040:   declares `extern FILE __stderr_FILE`, so every `stderr` in the tree takes
  3041:   the address of an incomplete object. Codegen's two value-sizing loops
  3042:   therefore require a resolved layout of every value *except* a global place;
  3043:   requiring it of all of them cost eight musl units with an
  3044:   `INVALID_IR` blamed on whichever function happened to be first in the
  3045:   module.
  3046: - **An array lvalue is never loaded**, whichever expression names it. A named
  3047:   array keeps its place, and so does `*p` on a pointer to an array: C 6.5.3.2p4
  3048:   says the dereference designates the array object, and what follows either
  3049:   decays it or indexes it in place, neither of which reads anything. Loading
  3050:   one instead emits an `IR_OPCODE_LOAD` of the array type, which the code
  3051:   generator honours by copying the whole object into a frame temporary — so
  3052:   `(*p)[1] = v` indexed the copy and the store was dropped with no diagnostic
  3053:   (#719), while `p[0][1] = v` next to it worked. The expression walk in
  3054:   `c_gen.c` returns the place from its dereference arm for the same reason its
  3055:   address-of arm accepts one; `tests/basic_c_packed_layout.c` runs all three
  3056:   spellings of the store and `c_test_frontend_global_types` pins that no lowered
  3057:   function holds a load of array type. The decay is the half a libc trips
  3058:   over: musl's strftime writes into `*s` through `snprintf` and returns it from
  3059:   a `char (*s)[100]` parameter, so the copy took every formatted specifier with
  3060:   it and libc-test's `functional/strftime` failed all 64 of its checks.
  3061:   `tests/basic_c_pointer_to_array_place.c` pins that shape under all four
  3062:   register allocators.
  3063: - **An aggregate member the next `.` walks through is a place, not a value.**
  3064:   `((T *)p)->a.b` names b, and C 6.5.2.3 gives the route to it no read of its
  3065:   own. The expression walk in `c_gen.c` loaded `a` anyway and then recovered
  3066:   the place it needed from that load's own operand, so every answer was right
  3067:   and the copy was dead — but a dead copy is still a read of memory, and
  3068:   offsetof is written on the null pointer. A compiler that does not advertise
  3069:   `__builtin_offsetof` gets musl's other spelling,
  3070:   `((size_t)( (char *)&(((type *)0)->member) - (char *)0 ))`, so a member named
  3071:   through two accesses copied a whole object out of address zero. musl's
  3072:   `__pthread_exit` takes exactly that offset for every mutex on the robust list
  3073:   — `_m_next` is `__u.__p[4]` — and died there with SIGSEGV, which is what
  3074:   libc-test's `functional/pthread_robust` and `regression/pthread-robust-detach`
  3075:   reported as #737. Predefining `__GNUC__` in every dialect moved musl to
  3076:   `__builtin_offsetof` and closed both units before this rule landed, so the
  3077:   spelling that reaches the walk is now a program's own rather than a libc's:
  3078:   measured 2026-08-30, the libc-test classification is identical with and
  3079:   without this rule. The member arm keeps the place when the following token
  3080:   is a `.`, which is the same rule as the array arm beside it; a chain that
  3081:   ends at the aggregate still loads it, so a by-value read is unchanged.
  3082:   `tests/basic_c_member_chain_place.c` pins the offsets against a live object
  3083:   under all four register allocators, spelling the pointer form directly so it
  3084:   does not depend on which offsetof a header picks, and faults the way musl did
  3085:   if the copy comes back. The peek only sees the token after the member
  3086:   identifier, so a group hides the `.` that follows from it — `(*o).a.b` and
  3087:   `&(((T *)0)->a).b[i]` reach the next access with the load already emitted,
  3088:   the dereference arm having emitted the first one and the member arm the
  3089:   second (#741). The place `c_ir_emit_field_place_from_value` recovers from
  3090:   such a load therefore *drops* it, through the same
  3091:   `c_ir_recover_place_from_value` the address-of arm of `c_ir_apply_operation`
  3092:   uses for `&E`: the load must still be the last instruction emitted, which it
  3093:   is because the access that recovers from it is the next thing the walk does.
  3094:   A group is not a frame of its own — an ordinary one is a `C_CONDITIONAL_OPEN`
  3095:   marker on the same expression frame's operator stack — so nothing about this
  3096:   needs a place-or-value request threaded through the lowering machines.
  3097:   `c_test_frontend_global_types` pins that no lowered function holds a load of
  3098:   a struct or union type nothing reads, and that the by-value read beside it
  3099:   keeps the one it needs.
  3100: - **A value never carries a qualifier.** The frontend builds a qualified copy
  3101:   of a type wherever a qualifier is written, because a place, a pointee or a
  3102:   member has to carry it, and that copy keeps the base's kind and layout: it is
  3103:   one representation under two ids. Both load emitters and the store emitter
  3104:   therefore unqualify a `volatile` place the way they already unqualified
  3105:   `_Atomic` -- an lvalue conversion yields the unqualified type of the object
  3106:   (C 6.3.2.1p2) and an assignment converts to the unqualified type of the left
  3107:   operand (C 6.5.16.1p2) -- and `c_ir_emit_cast` treats a difference of only
  3108:   `volatile` as no conversion at all. The value ladder there spans the scalar
  3109:   kinds, so while a struct crossing the qualifier had to find an arm in it,
  3110:   `volatile sigset_t oldset = set2` was refused outright and every unit written
  3111:   around `setjmp` failed to compile (#735). Volatility itself never travelled on
  3112:   the type: a load and a store carry `volatile_access`, taken from the place's
  3113:   own flag, which is why none of this changes which accesses are volatile.
  3114:   `ir_types_differ_only_in_volatile` is the one predicate, and
  3115:   `ir_validate_canonical_module` admits exactly that difference between a plain
  3116:   `IR_OPCODE_LOAD` or `IR_OPCODE_STORE` and its place -- the pairing the atomic
  3117:   opcodes were always validated with. `tests/basic_c_volatile_aggregate.c` pins
  3118:   both directions of the qualifier under all four register allocators.
  3119: - Native lowering is `canonical IR -> machine IR -> scheduling/register
  3120:   allocation -> encoding`. Selection patterns and scheduling classes remain
  3121:   separate metadata domains even when they share instruction-form IDs.
  3122: - **A read-only object that carries a relocation is laid out with the writable
  3123:   data.** `const` is the frontend's answer and the object writer's read-only
  3124:   section is where it usually goes, but those bytes are written when the
  3125:   program is relocated, and in a shared object that write lands on a page the
  3126:   loader mapped read-only — a `DT_TEXTREL` the loader has to undo before it can
  3127:   process the relocation, and one musl's loader does not undo for the file it
  3128:   was itself started from. Clang answers the same question with a fourth data
  3129:   section, `.data.rel.ro`; this writer has three, so
  3130:   `codegen_global_is_read_only` in `codegen.c` folds "has a relocation" into
  3131:   the placement instead. Nothing in the C object model moves with it — writing
  3132:   through a `const` lvalue is undefined either way — and a static link, whose
  3133:   relocations are all resolved before the program runs, cannot tell the
  3134:   difference. `static const unsigned short *const ptable = table+128;` in
  3135:   musl's `__ctype_b_loc.c` is the shape, and `FILE *const stdout` is the one
  3136:   every program has.
  3137: - **`__attribute__((weak))` and `__attribute__((alias("target")))`** reach the
  3138:   object file, because musl publishes `malloc`, `free`, `errno` and most of
  3139:   its pthread surface as weak aliases of internal names. Weak is
  3140:   `IrSymbol.is_weak` and becomes `ObjectSymbol.weak`, which ELF writes as
  3141:   `STB_WEAK` and Mach-O as `N_WEAK_DEF`. COFF spells a weak definition as a
  3142:   selectany COMDAT, which needs a section per symbol while this model merges
  3143:   sections by kind, so a COFF object reads `weak` back but cannot write it and
  3144:   carries such a symbol as an ordinary external. That is the one gap of the
  3145:   three formats, and it predates aliases: `object.c`'s header states it. An
  3146:   alias is a pair in `IrModule.aliases` rather than a field on every symbol:
  3147:   it is a relation between two symbols rather than a property of one, and
  3148:   nearly every module has none. The object writer gives
  3149:   the alias its target's section, offset, size and kind and only its own
  3150:   binding, which is what Clang produces for the same source, and
  3151:   `ir_validate_canonical_module` requires the target to be a definition in
  3152:   that same module. The frontend keeps a static alias target alive -- an
  3153:   attribute names it, no identifier use does -- and diagnoses an alias whose
  3154:   target this translation unit does not define rather than emitting an
  3155:   import. Both attributes are read inside the declaration's
  3156:   `__attribute__((...))` list by `c_declaration_binding` in `c_gen.c`, never
  3157:   anywhere in its token range the way `section` and `asm` are matched: a
  3158:   marker attribute has no argument shape to recognise it by, and `weak` and
  3159:   `alias` are ordinary identifiers, so `int weak;` must stay a strong
  3160:   definition.
  3161: - **`__attribute__((constructor))` and `__attribute__((destructor))`** run a
  3162:   function before and after `main`. They are read out of the declaration's
  3163:   attribute list by the same `c_declaration_binding` walk as `weak` and
  3164:   `alias`, with the reserved `__constructor__`/`__destructor__` spellings
  3165:   beside the plain ones and the optional `constructor(101)` priority; the
  3166:   attribute may be written on any declaration of the function, so the flag is
  3167:   collected per entity the way `noreturn` is. Three consequences follow, and
  3168:   each was a separate hole before issue 771 closed them. A registered function
  3169:   is **reachable by definition** -- no expression names it -- so it is a root
  3170:   of the unused-static elimination in `c_gen.c`, without which a translation
  3171:   unit whose only function is a static constructor came out with an empty
  3172:   `.text`. The registration is a module-level list, `IrModule.initializers`,
  3173:   for the reason aliases are: it is a relation, not a property of a symbol,
  3174:   and nearly every module has none. And the two targets with no initializer
  3175:   array at all -- core Wasm, which starts one function of its own, and eBPF,
  3176:   which has no startup -- **diagnose** the attribute rather than dropping it.
  3177: - **`.init_array` and `.fini_array` are section kinds**,
  3178:   `OBJECT_SECTION_INIT_ARRAY` and `OBJECT_SECTION_FINI_ARRAY`, holding one
  3179:   pointer-wide slot per initializer with an `ABSOLUTE64` relocation against
  3180:   the function. ELF writes them `SHT_INIT_ARRAY`/`SHT_FINI_ARRAY`, Mach-O
  3181:   `__DATA,__mod_init_func`/`__mod_term_func` with the `S_MOD_*_FUNC_POINTERS`
  3182:   types, and COFF the `.CRT$XC*`/`.CRT$XT*` group MSVC's C runtime walks.
  3183:   **Priority orders the whole program**, and the priority travels beside the
  3184:   array rather than in it. A linker gets that order off the *section name* --
  3185:   `ld` places every `.init_array.NNNNN` ahead of the unsuffixed
  3186:   `.init_array`, ascending, and a PE linker concatenates a `$` group in
  3187:   lexicographic order of the whole name -- and this model has one section per
  3188:   kind, so a translation unit's whole array is one section, its entries sorted
  3189:   into that order by `object_from_canonical_codegen_module` (ascending
  3190:   priority, an attribute that named none last, equal priorities in declaration
  3191:   order) and each entry's priority recorded beside it in
  3192:   `ObjectFile.initializer_priorities`, one `u32` per slot. Three places carry
  3193:   that array, and they are the same fact from different sides.
  3194:   `object_split_initializer_priorities` splits it back into one section per
  3195:   priority group for the ELF and COFF writers, so an external linker orders
  3196:   two Buster objects exactly as it orders Clang's (issue #782).
  3197:   `object_read_elf64` and `object_read_coff` recover it from those section
  3198:   names -- the padded `.init_array.00101` written here and the unpadded
  3199:   `.init_array.101` Clang writes are both read -- and
  3200:   `object_reader_merge_initializer_arrays` merges the sections of a kind in
  3201:   that order rather than in section header order. And
  3202:   `link_initializer_arrays_order` sorts the *merged* array, stably, after
  3203:   `link_objects` has concatenated its inputs: without it a `constructor(101)`
  3204:   in the second object ran after an unprioritized constructor in the first,
  3205:   for Clang's objects as much as for this compiler's, which was issue #789.
  3206:   That sort moves each entry's relocation and any symbol defined at its slot
  3207:   with the entry, and it runs on the merged object rather than in
  3208:   `link_initializer_plan_build` so the Mach-O writer -- which keeps the
  3209:   initializer array for dyld to walk instead of reading a plan for it -- gets
  3210:   the same order the entry-stub writers do. An input that states no priorities
  3211:   (the Mach-O reader, the assembler's objects) has every entry unprioritized,
  3212:   which leaves it in link order.
  3213: - **A relocatable object keeps its arrays in all three formats; ELF and COFF
  3214:   can also state a priority, Mach-O cannot.** The COFF spelling is
  3215:   `.CRT$XCA00101` for a group, `.CRT$XCU` for what named none, and
  3216:   `.CRT$XTA00101`/`.CRT$XTX` for the terminators, which is what Clang emits
  3217:   and what `link.exe` and `lld-link` order lexicographically -- `A` sorts
  3218:   before `U`, so it says exactly what `ld`'s suffix says. Taking the
  3219:   platform's convention rather than a private `.init_array.NNNNN` suffix is
  3220:   what makes an object written here order correctly under a PE linker as well,
  3221:   and what lets `object_read_coff` recover the priorities out of an object
  3222:   Clang wrote; `object_coff_initializer_section_kind` reads the group back,
  3223:   and only that `A`-plus-five-digits spelling is a priority (`.CRT$XCU` and
  3224:   the runtime's marker sections are unprioritized, and a marker's null slot is
  3225:   dropped because no relocation fills it). The Mach-O reader classifies by the
  3226:   `S_MOD_INIT_FUNC_POINTERS`/`S_MOD_TERM_FUNC_POINTERS` section types, the way
  3227:   `SHT_INIT_ARRAY` names `.init_array` in ELF. Without those the arrays came
  3228:   back as `.data` and read-only data, and a program linked from an object ran
  3229:   **no constructor at all** on Windows and macOS -- the entries reached no
  3230:   initializer plan, and nothing diagnosed it. **Mach-O states no priority and
  3231:   is not going to**: `__mod_init_func` is 15 of a section name's 16 bytes, and
  3232:   the platform has no carrier elsewhere -- Clang emits one unsuffixed
  3233:   `__mod_init_func` per translation unit with the priorities sorted only
  3234:   inside it, so ld64 orders two objects by link order. A private carrier there
  3235:   would make `ide cc a.o b.o` disagree with `clang a.o b.o` on the same
  3236:   objects, so `ide cc a.o b.o` concatenates in link order on macOS, as the
  3237:   platform toolchain does (issue #795). That is why `driver_test`'s
  3238:   cross-translation-unit object route is gated off Apple hosts alone, while
  3239:   its source route -- where the priorities never touch a format -- runs on
  3240:   every host.
  3241: - **An image this linker produces calls its initializers from the entry
  3242:   stub.** There is no libc startup object in it -- the stub *is* the startup,
  3243:   which is why `link_x86_build_elf_entry_stub` exists at all -- so nothing
  3244:   would walk the arrays, and the linker already knows every entry's target at
  3245:   layout time. `link_initializer_plan_build` reads the two sections into a
  3246:   plan and hands back the object with them removed; each writer then emits one
  3247:   direct call per constructor before `main`, patched exactly like the call to
  3248:   `main` beside them. ELF passes argc, argv and envp to each constructor as
  3249:   GNU does; PE passes nothing, which is MSVC's `.CRT$XCU` contract and all
  3250:   that is available before the argv machinery runs. The **destructors** are
  3251:   not called where `main` came back: a program that reaches `exit` from inside
  3252:   `main` never comes back, and GNU runs a destructor either way, so the hosted
  3253:   stubs synthesize a **runner** past the trap that ends the stub -- one call
  3254:   per destructor and a return -- and register it with the C runtime before the
  3255:   constructors run. That is the position `__libc_start_main` hands `_dl_fini`
  3256:   to `__cxa_atexit` from, and it is what leaves the runner behind every
  3257:   handler the program registered itself (issue 781). The registration is
  3258:   `__cxa_atexit` on ELF and `_crt_atexit` on PE, because glibc's `libc.so.6`
  3259:   and Windows' `ucrtbase.dll` both keep plain `atexit` in a static library
  3260:   this linker does not read; `link_elf_hosted_exit_symbol` appends the ELF
  3261:   import beside `exit`, and both ELF dynamic writers have to agree on whether
  3262:   it is there because the AArch64 one re-derives the x86-64 one's import
  3263:   numbering. The freestanding ELF shape keeps its destructors inline after
  3264:   `main`: it has no `exit` to call and no runtime to register with, and a
  3265:   `-nostdlib` program that reaches the raw exit syscall runs no handler
  3266:   either. Two writers synthesize no entry point of their own, and they answer
  3267:   differently. **Mach-O** needs none for its constructors: LC_MAIN hands
  3268:   `main` straight to dyld, which runs the main executable's
  3269:   `__DATA,__mod_init_func` before it enters `main`, so that writer keeps that
  3270:   array, gives it the section type dyld dispatches on, and lets the loader
  3271:   call it (issue 779) -- which is why the merged array has to be in GNU's
  3272:   order before any writer sees it (issue 789), rather than only in the plan
  3273:   the other writers read. **dyld does not run a main executable's
  3274:   `__mod_term_func`**, which was measured rather than assumed (issue 798): on
  3275:   macOS 26.3.2 a pointer placed by hand in a `__mod_term_func` of an image
  3276:   *ld64* wrote never ran while the `__mod_init_func` slot beside it did, and
  3277:   Clang emits no terminator array on Darwin at all -- it registers every
  3278:   `__attribute__((destructor))` with `__cxa_atexit` from a
  3279:   `__GLOBAL_init_65535` initializer it synthesizes. So the Mach-O writer emits
  3280:   no `__mod_term_func` either. `link_mach_initializer_prepare` takes that
  3281:   array off the object -- the one half of this writer that does read a plan,
  3282:   built from the same merged array issue 789 ordered -- the writer synthesizes
  3283:   a **runner** over its entries past the import stubs, and a **registrar**
  3284:   prepended as the *first* `__mod_init_func` slot hands the runner to `atexit`
  3285:   before any constructor of the program runs. Registering first is what leaves
  3286:   the walk behind every handler the program registered itself, so Apple gets
  3287:   the same order the two entry stubs produce and
  3288:   `tests/basic_c_destructor_exit.c` runs there; Clang's own Darwin shape does
  3289:   not have that property, because it registers each destructor as its
  3290:   initializer is reached and a handler registered by a constructor therefore
  3291:   runs *after* the destructors. The prepended slot carries no relocation --
  3292:   its value is an address this writer chooses -- so it is written directly and
  3293:   named directly in the rebase stream, and the registrar reaches `atexit`
  3294:   through the import stub, appending that import when the program never named
  3295:   it. **UEFI** has no such third party -- a
  3296:   firmware image has no C runtime, and its entry is the firmware's call with
  3297:   the image handle and the system table -- so it still **refuses** a program
  3298:   with initializers, naming the first one, rather than placing an array
  3299:   nothing will call; `link_initializer_plan_empty` is that refusal. The
  3300:   objects it produces are correct and link through the system linker.
  3301: - **Every blob in a Mach-O image's `__LINKEDIT` starts on an eight-byte
  3302:   boundary.** dyld runs a layout check over the whole segment before it reads
  3303:   any of it, and a blob that starts mid-word makes it refuse the image with
  3304:   `mis-aligned LINKEDIT content '<name>'` -- which `dyld_info` prints in place
  3305:   of the fixup table while dyld itself still loads and runs the image, so
  3306:   nothing but a tool, a signing pass or a notarisation pass ever notices
  3307:   (issue 800). The rebase stream opens the segment at a page boundary, but its
  3308:   length is one uleb128 run per rebased address, so `bind_offset`,
  3309:   `symbol_table_offset` and the code signature are each aligned rather than
  3310:   laid straight after the blob before them. Anything added to that chain --
  3311:   export info, function starts, data in code -- has to be aligned the same
  3312:   way; the gap bytes are already zero because the image buffer is memset
  3313:   before anything is written, and every blob carries its own size, so the
  3314:   padding is read by nothing. `link_test.c` walks LC_DYLD_INFO_ONLY, LC_SYMTAB
  3315:   and LC_CODE_SIGNATURE of five images and requires one fixture to keep ending
  3316:   its rebase stream mid-word, without which the alignment would hold by
  3317:   accident; on macOS the same image goes through `dyld_info -fixups`.
  3318: - **An undefined weak symbol resolves to address zero**, which is what a
  3319:   program asks for by declaring one: musl's startup takes the address of a
  3320:   weak hidden `_DYNAMIC` and reads zero to learn it is static. Which party
  3321:   answers is the question of whether the reference can be preempted, and the
  3322:   ELF writers decide it with `link_elf_symbol_resolves_to_zero` in `link.c`:
  3323:   a hidden reference, and any reference in a static image, is relocated
  3324:   against zero here, while a default-visibility one in a dynamic image stays
  3325:   an import entered in `.dynsym` as `STB_WEAK`, so the loader binds it when a
  3326:   shared library defines it and leaves it zero rather than refusing the image
  3327:   when none does. `link_elf_symbol_needs_dynamic_import` is the same question
  3328:   asked by the three places that choose between the static and dynamic
  3329:   writers and by the two that number imports; they must not disagree, because
  3330:   the AArch64 dynamic writer re-derives the x86-64 writer's import numbering.
  3331:   Merging inputs follows ELF: a symbol only references name is weak while
  3332:   every one of them is, and one hidden occurrence makes it hidden.
  3333:   A default-visibility reference is promoted to an import **only when a
  3334:   library the image names is known to define the name** with a default
  3335:   version, which is the same question `link_elf_symbol_version` answers for
  3336:   the version to record; asking the loader for a name nothing has is how such
  3337:   a reference came back as its own PLT thunk or copy slot. What knows is
  3338:   `compiler_driver_elf_dynamic_symbols`, which records every defined global
  3339:   and weak entry of every shared library on every hosted ELF link, functions
  3340:   included, and sets `exports_known`: `versioned_symbols` is the ELF export
  3341:   list, `exported_symbols` stays PE's. Absence is evidence only when **every**
  3342:   library was read — `link_elf_exports_complete` — because a library the
  3343:   driver could not open exports whatever it happens to export; a link missing
  3344:   one of them keeps the import it made before, which is also why a target
  3345:   whose libraries are never read, Android today, is unchanged.
  3346: - **A C library keeps some of its own names out of its shared object**, and
  3347:   this linker imports from the shared object alone, so it has to supply the
  3348:   rest itself. glibc puts `atexit` and `at_quick_exit` in libc_nonshared.a as
  3349:   one call apiece to `__cxa_atexit` and `__cxa_at_quick_exit`; UCRT puts the
  3350:   same two names in its import library as one call apiece to `_crt_atexit` and
  3351:   `_crt_at_quick_exit`. `link_elf_libc_runtime_object` and
  3352:   `link_windows_libc_runtime_object` build those stubs — weak, so a program's
  3353:   own definition wins, and a bare tail branch, so the C ABI hands the
  3354:   arguments through — over the shared `link_forwarding_runtime_object`. The
  3355:   driver adds either one **the way it selects an archive member**
  3356:   (`compiler_driver_archive_member_needed`): only when something references a
  3357:   stub and nothing defines it. That selection is the contract, not a
  3358:   refinement of it. The stub carries an undefined `__cxa_`/`_crt_` reference,
  3359:   so adding it unconditionally would put that import in every executable, and
  3360:   on a host with no readable `ucrtbase.dll` it would fail every Windows link
  3361:   outright. `link_windows_runtime_object` is the counterexample that has to
  3362:   stay separate: `_fltused` is a four-byte marker with no reference of its
  3363:   own, so it is added to every hosted Windows link unconditionally.
  3364:   `_onexit` is deliberately absent — it answers with the handler rather than
  3365:   with a status, so it cannot be a tail branch, and a stub that called and
  3366:   then chose would need Windows unwind data of its own.
  3367: - **`__attribute__((packed))` and `__attribute__((aligned(N)))`** decide object
  3368:   representation, so ignoring them is an ABI divergence rather than a missing
  3369:   optimization: a Buster-only program agrees with itself whatever it agrees on,
  3370:   and the disagreement only appears against another compiler's object or an
  3371:   offset a program computes by hand. `packed` and the aggregate's own
  3372:   `aligned` live in `CParseResult.aggregate_attributes`, a side table keyed by
  3373:   type index rather than a field on every `CType`: the population is a handful
  3374:   of aggregates against tens of thousands of types. A member's `packed` is a
  3375:   bit on `CMember`; an object declarator's `aligned` joins the specifier-level
  3376:   alignment specifiers in the one contiguous run `alignment_start`/
  3377:   `alignment_count` names, which is why the trailing scan runs immediately
  3378:   after the specifier one. `#pragma pack(N)` asks the same question -- the
  3379:   ceiling a member's alignment is clamped to -- and `packed` is that ceiling at
  3380:   one byte, so both feed one knob. **Two layout engines read it and must agree**:
  3381:   `c_parse_type_layout` in `c_parse.c` folds `sizeof`/`_Alignof` during the
  3382:   parse and `c_lower_to_ir` in `c_gen.c` builds the `IrType`. They disagreed
  3383:   about `#pragma pack` before this: the fold packed and the IR did not, so a
  3384:   folded size contradicted the object it sized.
  3385:   A packed bit-field takes the next bit rather than the next storage unit of
  3386:   its declared type, which is what Clang and GCC do and what makes
  3387:   `struct __attribute__((packed)) { int a : 3; int b : 30; }` five bytes. The
  3388:   unit such a field is *read* through is chosen after the aggregate's size is
  3389:   known, by sliding it back until it lies inside the object -- a
  3390:   read-modify-write through a unit hanging off the end would clobber the next
  3391:   object -- and where the object is too small for the declared type to sit
  3392:   anywhere, by narrowing the unit to the smallest power of two that covers the
  3393:   field: `struct __attribute__((packed)) { char c; int b : 5; char t; }` is
  3394:   three bytes, so `b` is read through the byte at offset one, which is again
  3395:   what Clang and GCC do. **The narrowed width lives on `IrField.access_size`**,
  3396:   zero meaning the declared type's size, and `ir_field_access_size` is what
  3397:   every reader asks: the load and the read-modify-write in `c_gen.c`, the four
  3398:   constant-initializer folds there, the `IR_OPCODE_AGGREGATE` selectors in
  3399:   `machine_x86_64.c` and `machine_aarch64.c`, and the two canonical emitters in
  3400:   `codegen.c`. It is also the one place a `LOAD` or `STORE` may disagree with
  3401:   its place's type, which `ir_place_narrow_bit_field_access` is what validation
  3402:   admits it through. **A field whose bits cross every unit that fits has no
  3403:   single-unit access even then**, which is every width whose byte count is not
  3404:   a power of two: `union __attribute__((packed)) { long long b : 40; }` is five
  3405:   bytes and there is no five-byte load. `access_size` then carries the *span*
  3406:   rather than a unit, and `ir_field_access_pieces` decomposes it into the
  3407:   descending powers of two that cover it -- five is four plus one, seven is
  3408:   four plus two plus one, and nine, the widest span there is, is eight plus
  3409:   one. Clang writes the same access as `i40` and lowers it to the same
  3410:   sequence. Every reader walks the pieces: the frontend assembles a load out of
  3411:   them and read-modify-writes each one in turn, reaching the bytes past the
  3412:   first through a `unsigned char*` taken from the member place, and the
  3413:   constant folds deposit the bits one byte at a time because no integer is nine
  3414:   bytes wide. The `IR_OPCODE_AGGREGATE` selectors decline a span that is not a
  3415:   single unit and the canonical emitters take it, which is a per-function
  3416:   fallback the statistics already count. **A `_Bool` bit-field is extracted
  3417:   like any other**: its declared type is not an integer, so it used to skip the
  3418:   extraction and hand back the whole `_Bool` unit -- every neighbour's bits with
  3419:   it, normalized to one, which is why a `_Bool` that was the only set bit still
  3420:   read correctly -- and the write clobbered them. The unit it is read and
  3421:   written through is the unsigned integer of the same width, because the shift
  3422:   has to see the raw byte. A zero-width bit-field keeps aligning to its declared
  3423:   type even inside a packed aggregate, which is also what Clang and GCC do.
  3424:   **A zero width belongs to the *unnamed* bit-field alone**: C requires a named
  3425:   one to be at least one bit wide (C23 6.7.3.2p4) and both reference compilers
  3426:   refuse `int b : 0;`, where accepting it laid out a member that occupies no
  3427:   bits and can still be assigned and read back (issue #710). The width is
  3428:   checked in `c_lower_to_ir` where the constant expression is folded, so the
  3429:   expression spelling `int b : 1 - 1;` is refused with the literal one rather
  3430:   than only the spelling the parse fast path folds. The report shares the
  3431:   one-diagnostic-per-type budget with the rejected alignment specifier -- they
  3432:   are one `definition_rejection` slot whose kind travels with the message --
  3433:   and the definition still lays out, the way a rejected alignment specifier
  3434:   still hands back an alignment, so the program hears about the member it wrote
  3435:   rather than about a type that never got a layout.
  3436:   On AArch64 the accesses this reaches land at whatever byte offset packing
  3437:   chose, and the scaled unsigned-immediate load/store addresses only multiples
  3438:   of its own width, so `codegen_canonical_a64_memory_operation_base` falls back
  3439:   to the unscaled form -- `LDUR`/`STUR`, any byte offset in a nine-bit field --
  3440:   and materializes the address beyond that. It used to fail the whole
  3441:   compilation instead, which `struct __attribute__((packed)) { char a; int v :
  3442:   32; }` already reached before any of this.
  3443:   **A bit-field is not a field for System V's unaligned-field rule.** Its
  3444:   declared type is not what it occupies -- `int value : 20` at bit eight of a
  3445:   packed record occupies twenty bits inside the first eightbyte, not four
  3446:   bytes at an offset no `int` would sit at -- so
  3447:   `ir_system_v_abi_classify_bit_field` merges INTEGER into each eightbyte the
  3448:   field's *bits* fall in and leaves the declared type out of it, which is what
  3449:   the psABI writes and what clang and GCC compile. Asking the declared type
  3450:   instead sent every such record to memory, so the five bytes of
  3451:   `struct __attribute__((packed)) { char lead; int value : 20; char tail; }`
  3452:   came back through a hidden pointer where System V returns them in `rax`
  3453:   (issue #721); a program agreed with itself and disagreed with the object
  3454:   next to it. An *unnamed* bit-field is padding for this and contributes no
  3455:   class at all, which is observable beside a float: clang returns
  3456:   `struct { float f; int : 20; }` in `xmm0` and the same record with the field
  3457:   named in `rax`. The class is always INTEGER, since C admits no bit-field of
  3458:   floating type. AArch64 never asked: its aggregates up to sixteen bytes take
  3459:   INTEGER parts by size once `ir_homogeneous_float_abi` declines them.
  3460:   **A union member starts at bit zero whichever kind it is**, so a union sizes
  3461:   to the bits its widest member *occupies* rather than to that member's
  3462:   declared type: `union __attribute__((packed)) { char c; int b : 5; }` is one
  3463:   byte. The unpacked spelling needs no arm of its own -- rounding the size up
  3464:   to the alignment its declared type asks for is what gives it its four bytes
  3465:   back -- and the unit the field is read through is chosen by the same slide a
  3466:   struct's is, so the one-byte union reads its five bits through a byte
  3467:   (issue #706). Sizing it from the declared type is also what hid the
  3468:   single-unit refusal above from unions: a widest bit-field of 17 to 24 or 33
  3469:   to 56 bits sizes the union to a width no power-of-two unit fits inside --
  3470:   three bytes hold no unit covering 24 bits -- and is diagnosed for the same
  3471:   reason the struct spelling of those widths is.
  3472:   **A unit is never written whole.** Sliding and narrowing are what make a unit
  3473:   reach bytes it does not own: it can cover an ordinary member -- the four-byte
  3474:   unit of `struct __attribute__((packed)) { char c; int a : 5; int b : 7; char
  3475:   t; }` starts at offset zero, where `c` is -- and two units can share a byte,
  3476:   because packing narrows one field's unit and not the next one's. So every
  3477:   writer of a bit-field is a read-modify-write, including the one inside an
  3478:   aggregate initializer, where the members are materialized into a zero-filled
  3479:   slot and it is tempting to treat the accumulated word as the whole unit: the
  3480:   canonical emitters spell it `OR mem, reg` and the two `IR_OPCODE_AGGREGATE`
  3481:   selectors seed the accumulator with a load of the unit rather than with zero.
  3482:   Ordering the members differently does not substitute for it -- a whole-unit
  3483:   store loses whichever neighbour ran first, and two overlapping units lose one
  3484:   of themselves whatever the order (issue #705).
  3485:   A bit-field declarator carries a list of its own in exactly one place, *after*
  3486:   the width -- Clang rejects `int b __attribute__((packed)) : 5` -- so
  3487:   `c_type_parse_aggregate_segment_step` trims the width's token range with
  3488:   `c_parse_trailing_attribute_start`, the helper the parenthesized-declarator
  3489:   path already uses. Left untrimmed the list is part of the constant expression
  3490:   and the width never folds, which loses the aggregate's whole layout while
  3491:   `sizeof` still answers (issue #693). It is the third spelling of the packed
  3492:   bit-field layout above, and reaches the same narrowed unit as the other two. The trimmed tokens stay inside
  3493:   `[declarator_start, declarator_end)`, which is the range the per-declarator
  3494:   `packed` and `aligned` scans read, so the attribute reaches the layout with no
  3495:   second pass.
  3496:   **`aligned` written on a typedef is a different question**: it sets the
  3497:   alignment of the type the name declares rather than raising a declaration's,
  3498:   which makes it the one spelling that *lowers* an alignment without `packed`
  3499:   -- `typedef int pair __attribute__((aligned(2)))` is two-byte aligned in
  3500:   Clang and GCC alike. The request lives in `CParseResult.type_alignments`, a
  3501:   side table keyed by type index for the reason `noreturn_function_types` is
  3502:   one, and it keys on a *copy* of the type the declarator arrived at:
  3503:   `typedef int cache_line __attribute__((aligned(64)))` names the one builtin
  3504:   `int`, so marking that would realign every `int` in the translation unit.
  3505:   The copy carries `has_unqualified_type`, which is what gives both layout
  3506:   engines one place to read the natural alignment from and keeps the alias
  3507:   compatible with what it aliases. **Which of the two positions it is written
  3508:   in decides how many names it reaches**: after the declarator it belongs to
  3509:   that declarator alone, and among the specifiers it belongs to the
  3510:   declaration's type, so `typedef int __attribute__((aligned(16))) t5, t6;`
  3511:   aligns both names. That position is also where `_Alignas` is a constraint
  3512:   violation rather than a request -- a typedef declares no object for a
  3513:   declaration's alignment to apply to, and Clang and GCC both refuse
  3514:   `typedef _Alignas(16) int t;` -- so the run is *partitioned* by spelling
  3515:   rather than rejected by position, which had dropped the whole declaration
  3516:   (issue #715). `c_parse_typedef_alignment_run` in `c_parse.c` does that for
  3517:   both the file-scope and the block-scope parser, reading the spelling back
  3518:   out of the token stream with `c_alignment_specifier_is_standard`, and it
  3519:   rewinds the specifier table with the records it drops so the
  3520:   declarator-position ones each parser appends next stay contiguous with what
  3521:   survives. A **function** keeps the position rejection whole: neither
  3522:   reference compiler raises a function's alignment through it.
  3523:   **A qualifier cannot take the request away**, and a qualified copy points
  3524:   *past* the alias at the type it strips to, so `c_parse_add_qualified_type`
  3525:   gives the copy its own record rather than
  3526:   leaving the layout engines to walk a chain that no longer names the alias --
  3527:   `const cache_line` folded `_Alignof` 4 where Clang and GCC answer 64, in
  3528:   every position and with no diagnostic (issue #714). `_Atomic` applied to an
  3529:   aligned alias is the exception, and it is the one place the two references
  3530:   disagree: Clang gives `_Atomic cache_line` the alignment an atomic of that
  3531:   width gets and GCC keeps the alias's, so the record is inherited only when
  3532:   the step does not add `_Atomic`. **Two places build that type and one rule
  3533:   answers for both**, `c_parse_atomic_drops_type_alignment`: the copy a
  3534:   declaration makes goes through `c_parse_add_qualified_type`, while a type
  3535:   name in an expression is resolved during lowering by
  3536:   `c_ir_type_name_prefix` in `c_gen.c`, which builds no `CType` at all and so
  3537:   reached the aligned alias's own `IrType` and kept the request the typedef
  3538:   spelling had already dropped -- one type answering `_Alignof` 64 written
  3539:   inline and 4 written through a typedef of it, which is two layouts for one
  3540:   object across two translation units (issue #726).
  3541:   `c_ir_atomic_over_aligned_alias` is the lowering half, and both of that
  3542:   resolver's spellings ask it: `_Atomic` as a qualifier before or after the
  3543:   name, and the `_Atomic ( T )` operator, whose branch reads its operand's
  3544:   typedef out of the tokens because an alias and the type it aliases can map
  3545:   to one `IrType`. It rebuilds from the alias's *unqualified* type exactly as
  3546:   the type-mapping pass builds the typedef spelling, so
  3547:   `c_ir_add_qualified_type`'s dedup hands back the very `IrType` that spelling
  3548:   mapped to; the qualifier spelling runs before the pointer run because
  3549:   `_Atomic cache_line *` qualifies the pointee. The `_Atomic` shapes in
  3550:   `tests/basic_c_packed_layout.c` are written twice, once each way, and pin
  3551:   the pair rather than only the number; they stay out of the cross-linked
  3552:   `basic_c_packed_layout_shapes.h`, whose other half is whichever host
  3553:   compiler the platform has and where a GCC host answers the alias's number.
  3554:   A *qualified* copy is built where the qualifier
  3555:   is written, which is after the aggregate that embeds it, so the
  3556:   scalar seed in `c_lower_to_ir` is cleared for every recorded type: the
  3557:   mapping round that lays the aggregate out would otherwise read the seed's
  3558:   natural alignment before the alias branch replaced it.
  3559:   On the System V side one more rule follows:
  3560:   "contains unaligned fields" there means unaligned for the field's *natural*
  3561:   alignment, so `struct { char tag; pair value; }` is passed in memory even
  3562:   though `value` sits where its type asked. `IrTypeLayout::natural_alignment`
  3563:   carries that, and it is zero for every type nothing lowered.
  3564:   It is also the only way an **array element can end up over-aligned**, which
  3565:   Clang and GCC both refuse and so does this: an element has to be addressable
  3566:   at its own alignment in every slot, so its size has to be a multiple of that
  3567:   alignment, and `cache_line a[2]` puts the second element four bytes into a
  3568:   sixty-four-byte alignment. The scan is at the end of the type-mapping rounds
  3569:   in `c_lower_to_ir`, over a settled table, which is what makes one report per
  3570:   array type automatic and reaches a typedef no object ever names; it is
  3571:   skipped whole on an empty `type_alignments`, because every other type is
  3572:   sized at a multiple of its alignment by construction -- an aggregate's own
  3573:   `aligned` rounds its size *up*, so `struct __attribute__((aligned(16))) { char c; } a[2]`
  3574:   is thirty-two bytes and stays well-formed (issue #703). The report is counted
  3575:   on the *bound record* rather than on the type, because a qualified array and
  3576:   a typedef of an array are copies carrying the same bound, and one report per
  3577:   written `[N]` is what Clang produces; two identical declarations that intern
  3578:   to one array type therefore report once where Clang reports twice. Two
  3579:   spellings reach that report down a different road (issue #713), because
  3580:   neither reaches the type table as a `C_TYPE_ARRAY`. A parenthesized
  3581:   declarator's `cache_line (*p)[2]` builds one only once the syntax scan stops
  3582:   reading a top-level `(` after an identifier as the parameter list of a
  3583:   function that identifier names -- see the declarator note below. An array
  3584:   type name in an expression, `sizeof(cache_line[2])` and the compound literal,
  3585:   is resolved during lowering and never reaches the table at all, so
  3586:   `c_ir_type_name_suffix` records the earliest offending bracket on the builder
  3587:   and `c_lower_to_ir` makes one report from it at the very end, after every
  3588:   declaration has been lowered: that resolver runs inside speculative attempts
  3589:   that are rolled back and revisits the same tokens many times, so keying on
  3590:   the token index is what makes the report independent of the order the
  3591:   attempts run in, and it has no bound record to count on. It records without
  3592:   refusing the type, the way the settled-table scan reports without refusing
  3593:   one: the report is what refuses the translation unit.
  3594: - **`_Atomic T` is a type built from T, not a qualified T, and its layout says
  3595:   so.** Clang pads it up to the next power of two and aligns it there, so a
  3596:   value the `__atomic` builtins could reach lock-free has an instruction that
  3597:   covers it: there is no three-byte atomic access and there is a four-byte one.
  3598:   `_Atomic` of a three-byte record is four bytes aligned four, of a five-byte
  3599:   one eight aligned eight, of a twelve-byte one sixteen aligned sixteen, and a
  3600:   zero-sized aggregate still takes a byte; every atomic scalar ends up aligned
  3601:   to its size, which is the same sentence that answers `_Alignof(_Atomic
  3602:   cache_line)` above and what moves `_Atomic _Complex double` from eight-byte
  3603:   alignment to sixteen. The ceiling is the target's maximum lock-free width,
  3604:   `TargetDataLayout::atomic_max_width` -- 128 bits everywhere here but wasm64
  3605:   and BPF, where it is 64 -- and a type wider than that keeps T's own layout,
  3606:   so the rule is not "round every aggregate up": `_Atomic` of a seventeen-byte
  3607:   record is seventeen bytes aligned one in Clang too. GCC pads nothing and
  3608:   raises the alignment only where the size is already a power of two, so this
  3609:   is the second place the two references disagree and Clang is the oracle for
  3610:   both (#731). `c_atomic_promoted_layout` in `c_parse.c` is the one rule and
  3611:   both engines ask it: `c_parse_type_layout` at the seed, at the exit that
  3612:   answers a builtin kind outright, and at an atomic branch of the solve that
  3613:   answers for every kind a qualified copy can carry -- ahead of the branches
  3614:   that would lay that copy out from its own kind -- and
  3615:   `c_ir_add_qualified_type` for the copy the mapping pass builds. An **alias
  3616:   over an atomic type** replaces the alignment and keeps the padding, so the
  3617:   aligned-alias branch runs first and takes only the promoted size from the
  3618:   rule: `typedef at3 t __attribute__((aligned(32)))` is four bytes aligned
  3619:   thirty-two. A **type name** builds the atomic type as well, in each of the
  3620:   three spellings that reach one: `c_ir_type_name_prefix` qualified only an
  3621:   aligned alias before, which was invisible while `_Atomic T` was laid out like
  3622:   T and became `sizeof` 3 written inline against 4 through a typedef the moment
  3623:   it was not. The fourth spelling is `_Atomic` written in
  3624:   front of a `struct`, `union` or `enum` keyword, and it reaches the type
  3625:   through the declaration-specifier run rather than through a resolver of its
  3626:   own: `c_parse_atomic_type_specifier_at` is what tells the qualifier apart
  3627:   from the `_Atomic ( T )` specifier, a `(` right after the keyword being the
  3628:   only difference, and the prefix scans stop only at the specifier. Stopping
  3629:   at both left the qualifier uncollected, so the aggregate branch handed back
  3630:   the tag's own type and `_Atomic struct three` was `sizeof` 3 against the
  3631:   other three spellings' 4 -- and, worse than a number, an assignment to such
  3632:   an object was an ordinary aggregate copy where the program asked for an
  3633:   atomic store (#761). `const struct S` and `volatile struct S` ride that same
  3634:   run and always reached the type through it. Two scans ask the question: the
  3635:   declaration-specifier run in `c_type_parse_scalar_step`, whose existing
  3636:   completion applies whatever the run collected, and
  3637:   `c_parse_machineless_base_type`, the operand walk the enum-constant
  3638:   evaluator uses because the type-parse machine is already running the body it
  3639:   is folding for -- that walk dropped the leading run before the tag and the
  3640:   trailing run after it alike, which failed a `const struct S` operand outright
  3641:   rather than mis-sizing it. That walk had no branch for the `_Atomic ( T )`
  3642:   spelling either, so it resolved nothing for a tag, a typedef name and `int`
  3643:   equally, and the enumerator that spelled it failed -- which fails the enum
  3644:   type and leaves every enumerator beside it undeclared for the rest of the
  3645:   file (#784). The specifier's operand is a whole type name rather than a base
  3646:   type, so the walk resolves it the way it resolves the outer one -- base type,
  3647:   then `c_parse_machineless_declarator_suffixes`, the pointer/qualifier/array
  3648:   chain shared with the sizeof operand walk -- and then applies the refusals
  3649:   `c_type_parse_scalar_step` diagnoses at `C_DIAGNOSTIC_INVALID_ATOMIC_TYPE`:
  3650:   an array, a function, `void`, or an already-qualified operand. It refuses
  3651:   silently, because the walk has a fallback -- the caller tries the operand as
  3652:   an expression next -- and a diagnostic would land in the caller's throwaway
  3653:   copy of the parse result; an enum constant that does not fold reports the way
  3654:   every other one does. `_Atomic(_Atomic(int) *)` is legal C, so the nesting
  3655:   follows the source and the levels go on an explicit stack
  3656:   (`C_PARSE_MACHINELESS_ATOMIC_LEVELS`, eight) rather than on the C call stack;
  3657:   past it the operand does not fold, which is where every depth of it stood
  3658:   before, and the machine-bearing path folds it at any depth either way. On
  3659:   the argument side the promotion moves nothing *on System V*: a promoted
  3660:   four-byte record is one INTEGER eightbyte where the three-byte one already
  3661:   was. It does move something on Win64, where the class is a function of the
  3662:   size alone -- four bytes ride a register and three are passed indirectly --
  3663:   so the classification is made from the promoted type rather than from the
  3664:   record on every convention, and that is what makes an argument position
  3665:   carry the atomic type; see the parameter bullet below.
  3666:   The **LLVM bitcode writer** maps an atomic type onto its
  3667:   operand's LLVM type, which is exact for every atomic scalar -- `_Atomic int`
  3668:   and `int` are one type -- and short by the padding for an aggregate, so an
  3669:   atomic type whose `layout.size` exceeds its operand's gets a record of its
  3670:   own instead: the operand followed by a byte array of the padding, which is
  3671:   what Clang writes as `{ %struct.three, [1 x i8] }` (#767). The operand is
  3672:   then the atomic type's only dependency, so `llvm_bc_type_dependencies_ready`
  3673:   answers for it directly rather than from the fields the qualified copy shares
  3674:   with it -- otherwise the table walk builds the copy as a plain struct before
  3675:   the operand it is meant to wrap has an id, and the padding is lost.
  3676:   `tests/basic_c_atomic_bitcode.c` holds the three positions a type is built
  3677:   for, and the native object it also runs pins the sizes the bitcode has to
  3678:   agree with.  `tests/basic_c_packed_layout.c` pins the promoted sizes
  3679:   next to the one-byte aggregate that agrees without them, once for each
  3680:   engine, and they stay out of the cross-linked
  3681:   `basic_c_packed_layout_shapes.h` for the same reason the shapes above do.
  3682: - **A qualifier decides nothing about how a value is passed.** `_Atomic T` and
  3683:   `volatile T` take T's argument class on every convention: the qualified copy
  3684:   carries T's kind and T's fields, `_Atomic` changes only the size and the
  3685:   alignment, and neither qualifier introduces a class of its own. So a record
  3686:   holding an `_Atomic int` is the INTEGER eightbyte its `int` spelling is, a
  3687:   record holding an `_Atomic float` beside a plain one is still two floats --
  3688:   SSE on System V, a homogeneous float aggregate on AAPCS64 -- and an atomic
  3689:   record passed by value is classified from the record it is built from, which
  3690:   no fixture can pin yet: an atomic aggregate parameter fails code generation
  3691:   in every spelling (#786), and the one spelling that compiles does so only
  3692:   because it is not reaching the type at all (#761), so a fixture written that
  3693:   way would pass while testing nothing. The wrapped shape --
  3694:   `struct { char c; _Atomic(struct pair) v; }` -- reaches the same walk and is
  3695:   in the pair. `ir_abi_unqualified_type` in `ir.c` is the one step that says
  3696:   so, and the AAPCS64 homogeneity walk is its only caller: System V already
  3697:   reads the leaf kind, which a qualified copy keeps.
  3698:   **This is the one place the oracle is not followed, and it is a decision
  3699:   rather than an oversight** (#763). Measured 2026-08-30 against Clang 22.1.8
  3700:   and GCC 16.2.1: GCC classifies every one of these shapes exactly as the
  3701:   unqualified spelling on x86-64 (its AArch64 answer was not measurable on the
  3702:   machine that measured this -- no cross-GCC). Clang sends any record
  3703:   *containing* an atomic member, and any atomic record, to MEMORY -- but only
  3704:   on System V x86-64; the same Clang passes a record *containing* an atomic
  3705:   member in registers on Win64, on AAPCS64 and on Darwin AArch64. An atomic
  3706:   *record* passed by value shows the fallthrough in a third shape on Win64
  3707:   (measured 2026-08-30): Clang expands it into one argument per member, the
  3708:   padding byte among them, and returns it through `sret`, where the four-byte
  3709:   record it is built from would ride one register both ways. Its AArch64
  3710:   homogeneity test declines separately, so `struct { _Atomic float a, b; }`
  3711:   rides X0 there where `struct { float a, b; }` rides S0/S1. Both refusals are
  3712:   the same accident: `X86_64ABIInfo::classify` asks `Ty->getAs<RecordType>()`
  3713:   and `isHomogeneousAggregate` asks for a builtin type, an `AtomicType` is sugar
  3714:   over nothing, and each walk falls through to its "everything else" tail. The
  3715:   psABI and AAPCS state no such rule, `volatile` reaches neither refusal, and
  3716:   Clang contradicts itself across three of its own conventions, so following
  3717:   it would mean writing a rule neither document states and disagreeing with
  3718:   GCC everywhere and with Clang on every convention but one. The cost is real
  3719:   and is recorded rather than hidden: a `struct { char c; _Atomic int v; }`
  3720:   argument sits in a register on this side of a System V x86-64
  3721:   translation-unit boundary and in memory on Clang's.
  3722:   The same reading fixed a divergence from *both* references: identity in the
  3723:   homogeneity walk was a type id, so `struct { float a; volatile float b; }`
  3724:   was an integer pair where Clang and GCC both keep the two-register
  3725:   aggregate. `tests/basic_c_atomic_abi_shapes.h` and the callee/caller pair
  3726:   around it pin all of it -- both halves through this compiler under every
  3727:   allocator, mixed with a real GCC on System V x86-64 (the host compiler
  3728:   cannot stand in: on that convention Clang is the half that disagrees), and
  3729:   mixed with Clang on AArch64 under qemu, where the one shape Clang answers
  3730:   differently leaves through `ATOMIC_ABI_REFERENCE_DECLINES_ATOMIC_HFA` and its
  3731:   `volatile` twin stays behind to pin the same mechanism. Both directions were
  3732:   verified to fail when the rule is taken away: the Clang-paired System V link
  3733:   fails at the first record, and restoring the type-id identity fails the
  3734:   Clang-paired AArch64 link at the `volatile` shape.
  3735: - **An atomic aggregate is loaded and stored as one integer access of its
  3736:   promoted width**, which is what the promotion above exists for: a three-byte
  3737:   record is read and written through four bytes, and the padding the promotion
  3738:   added is written as zero, because Clang copies the value through a zeroed
  3739:   temporary and that is the oracle. The widths the canonical emitters lower
  3740:   that access at are one, two, four and eight bytes on both targets, plus
  3741:   sixteen on x86-64 where `cx16` gives them `CMPXCHG16B` -- the sequence
  3742:   `_Atomic __int128` already used, which now also takes any aggregate the
  3743:   promotion padded into the same width. The machine selectors decline the
  3744:   aggregate shapes and the function falls back to the canonical emitter, which
  3745:   the fallback statistics already count, so all four allocators answer the same
  3746:   bytes. Anything wider would need a `libatomic` lock and there is none here,
  3747:   so lowering refuses it with a diagnostic naming the width rather than leaving
  3748:   code generation to fail internally (#762). The refusal is
  3749:   `c_ir_atomic_aggregate_accesses_lowerable` in `c_gen.c`, and it runs over the
  3750:   *finished* body rather than where the access is built, because an operand is
  3751:   lowered as a value before an expression that only wanted its address recovers
  3752:   the place and drops the load again: refusing at the emit site rejects
  3753:   `&object.atomic_member`, which performs no atomic access at all and is what
  3754:   `tests/basic_c_packed_layout.c` writes over its seventeen-byte atomic
  3755:   member. AArch64 has no 128-bit lock-free access
  3756:   here -- `_Atomic __int128` does not lower there either -- so a sixteen-byte
  3757:   atomic aggregate is one of the shapes that refusal covers, and the refusal is
  3758:   therefore target-dependent where the layout rule above is not.
  3759:   `tests/basic_c_atomic_aggregate.c` runs the bytes under every allocator with
  3760:   Clang's answers baked in, including the padding.
  3761: - **A parameter and a return value of an atomic aggregate carry the atomic type
  3762:   itself, and what converts between it and the record is an object rather than
  3763:   an instruction.** Every access in between carries the unqualified type -- a
  3764:   load of an atomic place yields the record and a store takes one, which the IR
  3765:   validates rather than merely allows -- but an ABI position cannot: the
  3766:   `IR_OPCODE_ARGUMENT` type is validated against the signature's parameter type,
  3767:   and code generation classifies an argument from the type the instruction
  3768:   carries, so a record-typed value there would be classified from three bytes
  3769:   where the object is four. The two are therefore two aggregates of two sizes
  3770:   meeting in one expression, which no ladder in `c_ir_emit_cast` spans, and
  3771:   every spelling of the type failed code generation with an internal message
  3772:   rather than a diagnostic (#786). `c_ir_atomic_aggregate_pair` in `c_gen.c`
  3773:   recognizes the pair and `c_ir_emit_atomic_aggregate_conversion` converts
  3774:   through a slot of the atomic type, written through one view and read back
  3775:   through the other: widening is the settled atomic store -- one integer access
  3776:   of the promoted width, which is what zeroes the padding -- followed by a
  3777:   plain read of the whole slot, private storage nothing else can observe, and
  3778:   narrowing is that pair reversed. Both accesses are the settled ones above, so
  3779:   a promoted width past the target's lock-free ceiling is refused by the same
  3780:   walk over the finished body rather than failing inside code generation, and
  3781:   nothing in the IR, in validation or in code generation had to change. The
  3782:   parameter and return round trips are in `tests/basic_c_atomic_aggregate.c`
  3783:   in all four spellings and in both positions, with Clang's bytes -- the
  3784:   padding the promotion added among them -- baked in the way the rest of that
  3785:   fixture bakes them.
  3786: - **A top-level `(` right after an identifier** is the parameter list of a
  3787:   function that identifier names in `T f(int)`, and a parenthesized declarator
  3788:   in `T (*p)[2]`, whose `T` is the last word of the declaration specifiers.
  3789:   The syntax scan that finds a declaration's name has no typedef table to tell
  3790:   those two identifiers apart, and does not need one: a parameter is a
  3791:   declaration, so a parameter list can never begin with a `*`, and a group that
  3792:   does is a declarator group whatever precedes it. Without that,
  3793:   `T (*p)[2]` and `struct s (*p)[2]` were read as functions named `T` and `s`
  3794:   and the declaration each really makes was dropped whole -- no definition
  3795:   emitted, no diagnostic, and a `sizeof(*p)` that folded nothing. The redundant
  3796:   `T (p);` is the one shape still left: it needs the typedef table, since
  3797:   `int f(x);` with `x` a typedef name is a real function declaration.
  3798: - `__typeof` is accepted alongside `__typeof__` and `typeof`, because musl's
  3799:   `weak_alias` macro is written with it. **A function declared through a type
  3800:   name rather than a parameter-list declarator** -- `extern __typeof(f) g;`,
  3801:   or the same through a typedef -- has no function-name token, and that token
  3802:   is what the declaration kind is otherwise decided by. `c_analyze_semantics`
  3803:   in `c_parse.c` therefore reclassifies on the resolved type: a declarator
  3804:   whose type is a function is filed `C_DECLARATION_FUNCTION` with the
  3805:   parameter range taken from the `CType`, because the declarator has no
  3806:   parameter list and only the type knows the parameters. Everything
  3807:   downstream reads the declaration -- `c_ir_build_function_name_index` indexes
  3808:   it, `c_ir_function_signature` gives it an arity, and the entity is a
  3809:   `C_ENTITY_FUNCTION` -- so the name is callable and not merely addressable
  3810:   (issue #641). The same handoff from type to declaration is what the
  3811:   parenthesized declarator path and the block-scope function declarator in
  3812:   `c_parse_declaration_type` already do.
  3813:   `c_parse_entity_kind_redeclares` in `c_parse.c` is what keeps this spelling
  3814:   and an ordinary prototype one entity, which in musl every published name
  3815:   has.
  3816: - **A `typeof` operand is typed twice, by two engines, and both have to
  3817:   answer.** `c_ir_sizeof_operand_type_attempt` in `c_gen.c` types the operand
  3818:   of a `typeof` written in an *expression* -- a cast, a compound literal --
  3819:   and `c_type_parse_sizeof_step` in `c_parse.c` types the one written as a
  3820:   *declaration's specifier*, because the parse is what decides a declaration
  3821:   exists at all. A specifier that resolves to nothing declares no name, so the
  3822:   reported error is "use of undeclared identifier" at the first *use*, naming
  3823:   neither the `typeof` nor its operand; a `typeof` bug reads as a missing
  3824:   declaration (issue #760). The parse-side walk carried two gaps that the
  3825:   gen-side one did not: no unary `*` or `&` at all -- so `__typeof__(*(double
  3826:   *)0)` resolved to nothing, prefixes over a plain identifier chain being the
  3827:   only ones `c_parse_direct_expression_type` handles -- and a conditional
  3828:   merge that compared type ids, so two pointer arms of different types
  3829:   resolved to nothing either. `c_parse_conditional_pointer_type` now applies
  3830:   C11 6.5.15p6 in its own order, and both engines agree: a *null pointer
  3831:   constant* on either side yields the other operand's type, and only if
  3832:   neither is one does a `void *` operand pull an object pointer to `void *`.
  3833:   Two object pointers with incompatible elements are what clang reports as
  3834:   `-Wpointer-type-mismatch` and still types as `void *`, so
  3835:   `*(0 ? (double *)0 : (char *)0)` is `void` and the declaration on it is
  3836:   refused for an incomplete type -- clang's own diagnostic -- rather than
  3837:   never being seen. `c_parse_range_is_null_pointer_constant` answers the
  3838:   spelling half: it gates on the arm's type (integer, or pointer to `void` --
  3839:   the constant walk strips casts, so without the gate `(double *)0` would
  3840:   answer yes), strips leading pointer casts by shape, since a parenthesized
  3841:   group whose last token is `*` is never a parenthesized expression, and folds
  3842:   the rest through `c_parse_integer_constant_range` *machineless*, the caller
  3843:   already being inside a type-parse frame. That composition is exactly musl's
  3844:   `__type1(c,t)`/`__type2(c,t1,t2)`, whose outer cast is
  3845:   `(__typeof__(...) *)` and whose machineless base-type reader cannot resolve
  3846:   it -- hence the by-shape strip. `tests/basic_c_typeof_conditional.c` runs
  3847:   both macros under all four allocators and
  3848:   `c_test_typeof_conditional_type` pins the resolved types themselves.
  3849: - **A failed call blames the call, not the declaration.** A direct call's
  3850:   callee token is not an identifier *use*: it resolves through the
  3851:   call-target index, so the parser records no binding for it and
  3852:   `c_ir_identifier_entity` misses. The lowering failure in
  3853:   `c_ir_lower_expression_core_step` looks the name up before reporting, and
  3854:   keeps the identifier's own token index rather than the one the call arm
  3855:   advanced to the closing parenthesis, so an object called as a function is
  3856:   reported as one instead of as an unbound identifier. A name nothing
  3857:   declares still reports as unbound, which is what a SIMD builtin missing
  3858:   from `c_symbol_predefined` looks like.
  3859: - **A call to a function declared `()` supplies the parameters itself.**
  3860:   Before C23 an empty parameter list is no prototype at all, so the arguments
  3861:   take the default argument promotions and the *call site* is the signature.
  3862:   `IrType.is_unprototyped` marks such a declaration's type, and
  3863:   `c_ir_unprototyped_call_type` in `c_gen.c` gives the `IR_OPCODE_FUNCTION`
  3864:   reference the call's own parameter types plus a trailing `...` -- Clang's
  3865:   model, which declares `void die()` as `void (...)` and types each call site
  3866:   `void (i32, ...)`. The `...` reaches only System V x86-64, where it sets the
  3867:   AL vector count that a callee which really is variadic reads;
  3868:   `int printf(); printf("%f", x);` is that program. Every argument stays
  3869:   *named*, so Darwin AArch64 passes them in registers rather than on its
  3870:   variadic stack, and a definition is untouched: `int main()` is still an
  3871:   ordinary zero-parameter body with no register save area.
  3872:   `ir_validate_instruction` therefore lets a function reference disagree with
  3873:   its symbol's type when that type is the unprototyped one and the return
  3874:   types agree, and Wasm64 refuses such a call, because it types every call by
  3875:   the callee's declared signature. C23 made `()` mean `(void)`, so the marker
  3876:   is never set in that dialect and the call is refused as an arity error --
  3877:   which every dialect now reports by naming the callee and its parameter
  3878:   count rather than as "could not prepare C calls" (issue #666).
  3879: - The generic JIT loads already-produced host-native objects and resolves
  3880:   explicit bindings. It is not a second source-language compiler and must stay
  3881:   independent of frontend semantic structures.
  3882: - The command-line driver accepts C source/preprocessed C plus native
  3883:   objects/archives where the selected action permits them. Unknown languages,
  3884:   retired module-root options, and unsupported source extensions must fail
  3885:   explicitly rather than being forwarded or guessed.
  3886: - **`long double` is 80-bit x87 on System V x86-64, and it is memory-only.**
  3887:   Transport, the four arithmetic operators, negation, the six comparisons,
  3888:   truth conversion, and the conversions to and from the narrower floats and
  3889:   every integer width all lower, and a variadic argument takes the sixteen-
  3890:   byte, sixteen-aligned overflow slot the ABI requires. Every one of those is
  3891:   a *closed* x87 transaction: it loads its operands from frame slots, operates,
  3892:   stores the result back, and leaves the x87 stack as empty as it found it, so
  3893:   no value is ever live in an ST register across a machine instruction and the
  3894:   register allocators need no x87 class. Machine selection therefore refuses an
  3895:   f80 function outright and it falls back per function to the canonical
  3896:   emitter, which is where the whole vocabulary lives
  3897:   (`codegen_canonical_x64_emit_f80_*` in `codegen.c`). Do not touch the x87
  3898:   control word outside `codegen_canonical_x64_x87_truncate_begin/end`: its
  3899:   default extended precision is exactly what `long double` wants, and only a
  3900:   float-to-integer conversion may switch the rounding field, for one store.
  3901:   An **aggregate** carrying an f80 payload takes one of two paths, and which
  3902:   one is the ABI classification's answer, never a walk of the fields. System
  3903:   V's merger algorithm orders its rules equal, NO_CLASS, MEMORY, INTEGER, x87,
  3904:   SSE — **INTEGER beats x87** — so musl's `union ldshape`, an f80 overlaid
  3905:   with `struct { uint64_t m; uint16_t se; }`, classifies as two INTEGER
  3906:   eightbytes and rides two general-purpose registers, which is what clang
  3907:   compiles it to (`{ i64, i64 }`) and is not what a literal "an x87 class
  3908:   makes the value MEMORY" reading produces. A shape the merger cannot
  3909:   reconcile — `union { long double; unsigned long; }`, whose X87_UP tail is
  3910:   then unaccompanied, or `union { long double; double; }`, or anything past
  3911:   two eightbytes — goes to memory whole, byval in and sret out. Neither asks
  3912:   anything of the x87 stack: their bytes are copied. Only a classification
  3913:   that really carries an X87/X87_UP part needs the x87 vocabulary, and
  3914:   `ir_abi_value_has_x87_part` is the predicate every gate asks. Objects of
  3915:   more than one `long double` — `long double v[2]`, local or global — lower
  3916:   the same way, because the array is memory-class and its elements are reached
  3917:   one f80 at a time. `tests/basic_c_long_double_aggregate.c` covers the
  3918:   semantics under all four allocators; the ABI itself is only pinned by
  3919:   `tests/basic_c_long_double_aggregate_{caller,callee}.c`, linked against the
  3920:   host compiler in both directions, because a caller and a callee this
  3921:   compiler produced agree with each other whatever they agree on.
  3922:   Reading one back out of a `va_list` admits exactly the two shapes the
  3923:   argument side does, and for the same reason. The X87/X87_UP pair classifies
  3924:   into memory, so a variadic `long double` is never in the register save area
  3925:   whatever the argument counters hold: `va_arg` realigns the overflow cursor
  3926:   to sixteen, takes the slot, advances past all of it, and copies the payload
  3927:   through the x87 stack, which is what leaves the destination's six padding
  3928:   bytes zeroed. An opaque aggregate reads back through the ordinary eightbyte
  3929:   path. `tests/basic_c_va_arg_long_double.c` pins both under all four
  3930:   allocators, including a read through a `va_list *` and one past a `va_copy`
  3931:   — the spellings musl's `pop_arg` uses, and the ones the canonical emitter
  3932:   alone has the x87 vocabulary for.
  3933:   A *static* x87 initializer is folded rather than emitted:
  3934:   `c_ir_ext80_fold_initializer` in `c_gen.c` evaluates a constant expression
  3935:   over numeric literals — `+ - * /`, unary sign, parentheses — straight into
  3936:   the 64-bit significand and sign/exponent pair the object writer stores, for a
  3937:   scalar global, a function-local static, and each x87 element of an aggregate.
  3938:   Every leaf rounds in its own declared type and every operation rounds in the
  3939:   common real type the usual arithmetic conversions pick, which is what
  3940:   reproduces C's per-operation rounding and makes the bytes Clang-identical; a
  3941:   decimal fold would not, because `1/LDBL_EPSILON` is exactly 2^63 only once
  3942:   musl's spelling of the epsilon has rounded to 2^-63 first. Overflow becomes
  3943:   an infinity, underflow a signed zero, and the invalid operations — infinity
  3944:   minus infinity, infinity times zero, infinity over infinity, zero over zero —
  3945:   the default *positive* quiet NaN whatever the operand signs were, which is
  3946:   the answer Clang's own folder gives and the one
  3947:   `c_ir_fold_float_invalid_operation` gives the same expression inside a
  3948:   function; the two have to stay together, because a disagreement prints `nan`
  3949:   from one and `-nan` from the other. Those last two matter because musl spells
  3950:   `INFINITY` as `1e5000f` and `NAN` as `(0.0f/0.0f)` for a compiler that does
  3951:   not advertise the GNU builtins, so they are what a `long double` table in
  3952:   libc-test is made of. An operation between two *integer* operands is refused
  3953:   on purpose: it does not round at all, and `1/3` would need its own truncating
  3954:   semantics rather than 0.5 — which is also why `0/0` between two integer
  3955:   literals is a diagnostic here rather than the NaN its floating spellings fold
  3956:   to, Clang rejecting that initializer outright. So is an addition that aligns
  3957:   a genuine subnormal against a near-maximum operand, which spans more of the
  3958:   x87 exponent range than the folder's bignum holds — a zero operand is taken
  3959:   as the exact identity instead of aligned, so only a real subnormal reaches
  3960:   that edge. `tests/basic_c_long_double_static_initializer.c` pins the finite
  3961:   arithmetic and `tests/basic_c_long_double_static_special.c` everything from
  3962:   the infinities out, both against bytes read out of Clang's own object.
  3963:   Still refused with a source diagnostic: a fixed wide-float parameter of a
  3964:   variadic *definition* (the SysV `va_start`
  3965:   register-save area does not account for it), an aggregate whose
  3966:   classification carries an X87 class without being the ABI-proven single-f80
  3967:   shape, and every wide float on a target whose `long double` is not this
  3968:   format.
  3969: - **A module-level `__asm__` block emits into the module's text through
  3970:   `codegen_emit_global_assembly` in `codegen.c`.** It interprets the
  3971:   directives itself — `.text`, `.byte`, `.p2align`, and the symbol directives
  3972:   `.globl`/`.global`, `.weak`, `.hidden`, `.type` and `.size` — and hands
  3973:   every instruction it does not have a fixed encoding for to `assembly_encode`,
  3974:   the same assembler the inline-assembly path uses, one line at a time. That
  3975:   is where relocation support comes from: a `call sym` or a
  3976:   `lea sym(%rip),%reg` against a name the block does not define becomes a
  3977:   `CodegenModuleRelocation`. The assembler's PC-relative addend already carries
  3978:   the distance from the relocated field to the end of its instruction, and the
  3979:   module vocabulary's does not — the object writer subtracts four on the way
  3980:   out — so the emitter adds those four back rather than restricting the shapes
  3981:   it accepts. A symbol the block names does not need a C declaration: the
  3982:   emitter adds one to `IrProgram.symbols` when the search misses, which is what
  3983:   lets a startup object define `_start`. Two things follow from the AT&T/Intel
  3984:   dialect being x86-only: the emitter passes `ASSEMBLY_SYNTAX_DEFAULT` for
  3985:   every other target, and the assembler's AArch64 vocabulary is the bootstrap
  3986:   control-flow set, so an AArch64 block gets `bl`, `brk`, `ret` and `nop` and
  3987:   not an ADRP/ADD page pair. A block that fails reports through
  3988:   `CodegenModule.failed_in_assembly` and the block/line beside it, which is what
  3989:   keeps the driver's diagnostic off the next C function in the file. The
  3990:   *inline*-assembly arm of `codegen_generate_canonical_module_attempt` shares
  3991:   the last two of those: once its template is substituted,
  3992:   `codegen_emit_inline_assembly` walks the result a line at a time and hands a
  3993:   leading-dot line to the same directive table and everything else to the same
  3994:   `codegen_global_assembly_encode_instruction`, so a `lea sym(%rip),%0` in a
  3995:   GNU asm template becomes the same relocation. What the two do not share is
  3996:   where a new symbol's name may point: an inline template is a copy the
  3997:   code-generation attempt owns and the retry rewinds, so the name recorded is
  3998:   the one in the instruction's IR literal (`codegen_assembly_durable_name`).
  3999:   Labels are refused inside a template rather than defined, because a template
  4000:   is emitted once per instruction rather than once per file.
  4001: - The Wasm64 backend consumes canonical IR directly. Unsupported ABI or
  4002:   instruction shapes must be diagnosed; never silently fall back to a native
  4003:   backend.
