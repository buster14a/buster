## The census build

The patch (not committed) changes no answer. It adds three things:
- **The refusal reason, at the decline or miss.** `c_ast_types_answer` works
  out why the node was refused.
  - An accepted node that is not vouched for is charged to its gate: a
    pending enumerator list, a `_Generic` or type-identity site, or a lookup
    that disagrees. None occurred.
  - Otherwise the census descends from the query's node to the operand that
    refused first. A step goes to the first operand the machine types for that
    node which is unaccepted, or, in checked mode, accepted but not safe. The
    descent ends at a node whose own rule refused, and that node's kind and
    sub-reason name the shape.
  - So a query of `operands[count++]` is charged to `++`. Its index node is
    only the query's kind, which the log records separately.
- **The machine run, behind one wrapper per shape.** The query's machine
  branch moves into `census_machine`, and each shape reaches it through its
  own no-inline `census_run_<shape>`. `c_parse_expression_type_query` is made
  no-inline, so Callgrind sees the caller. A machine run nested inside another
  is charged to the outer run's shape. None of the census's own work runs
  inside a wrapper.
- **What the machine run left behind.** Per shape, the census counts the
  checked queries, the valid answers, the rows appended and the string-leaf
  calls (`c_parse_string_literal_expression_type`). With `CENSUS_LOG` set, it
  writes one line per decline or miss: the shape, the query and root kinds,
  whether the query was checked, the caller and the first 24 tokens.

Cross-checks:
- The log has 29,982 lines, equal to 24,759 declines plus 5,223 misses.
- 27,877 queries reach the machine branch. In arm B,
  `c_parse_expression_type_query` calls `c_type_parse_machine_run` 27,803
  times. The 74 difference is probably the 74 `,`-started misses, but that
  was not confirmed.
- The wrappers' inclusive Ir sums to 135,572,733. The toggle-collect run
  collected exactly 135,572,733.
- The census binary runs 9,451.72 M Ir, against 9,394.32 M for arm B. The
  extra 57.4 M is the census's classification and the calls it keeps out of
  line, all outside the wrappers.

Two shapes were relabelled after reading the log:
- **`cast_other`** is a cast whose type name re-types at query time, so its
  pointer row was interned after the eager pass. It belongs to the late-row
  family below.
- **`cond_other`** is mostly the member-tail width rule. In 178 of the 189
  complete logged ranges, an arm ends in `. name` or `-> name` but is not a
  member node, the same cause as `binary_width`.

## Reconciling the 42,239 figure

The issue cites 42,239 declines. That count is the C arm of #3374's own audit
(`2026-10-10T190424Z`). On `main` after #3381, #3374 and #3382, the typer
declines 24,759 queries and misses 5,223. #3381's string-literal replay answers
most of the difference (42,239 − 24,759 = 17,480, against the 17,765 string
queries #3381 found). A further 1,829 machine runs come from queries made
outside any typed body or initializer (`no_region`), which the typer never
sees.

## Per-shape census

The **floor** is the work an exact tree answer would still do. It assumes
200 Ir per answered query on the tree path. That is the measured
`c_ast_types_locate` (36.49 M over 869,832 calls, 42 Ir), the answer and the
memo publish. A node with a lookup mark would add `c_ast_types_lookups_agree`

- every appended row, if replayed through `c_parse_add_qualified_type`: 392 Ir

### What the top shapes are

- **Qualified member.** Most of these are `p->field` where `p` is a pointer to
  a const struct, such as `preprocess->tokens`, `instruction->operands` and
  `symbol->name`.
  - The postfix rule (`c_parse_direct_expression_postfix`) ends each such step
    with `c_parse_add_qualified_type`. That appends a qualified copy of the
    member row, with a copy of the base row's alignment record. It appends one
    on every run, so 9,710 queries leave 13,429 rows.
  - 3,442 queries are the member node itself. The rest are parents whose
    refusal starts there: `[]` 1,097, `&&` 1,032, `?:` 665, `=` 660 and `.`
    647.
  - Two things make an exact answer harder than for primitive or pointer rows.
    The appended row has a side-table record keyed by its index, and a machine
    run's sub-range memo entries decide how many copies a run appends.
- **Member-tail width.** For example `prefix.length + 1 + modrm.length`, or
  `x ? a.y + a.z : 0`.
  - `c_ast_types_operand_width` returns `C_AST_TYPE_NONE` for an operand that
    ends in `. name` without being a member node. That is because the machine's
    `c_parse_expression_bit_field_width` then re-types the prefix before the
    final `.`, through `c_parse_direct_expression_type`.
  - These runs are the most expensive per query, at 13,800 Ir for binary
    operators and 15,843 for `?:`. They are long expressions, each split at
    every operator.
- **`++` and `--`.** `c_ast_types_type_node` has no case for the four update
  kinds.
  - The machine keeps the operand's own row (`C_PARSE_EXPRESSION_TYPE_UPDATE`)
    and, checked, tests a modifiable place. It appended only 7 rows over 4,299
    runs.
  - 1,407 queries are `x++` itself. Most of the rest are parents: `a[i++]`
    1,382 and `x = y++` 1,311.

## Reading

- What remains is small. Every machine run from a query together is
  135.57 M Ir (1.44%) of the pilot's 9,394 M. The three largest shapes are 69%
  of it.
- The ranking of the slices is not the ranking of the shapes:
  - The largest shape, the qualified member at about 50 M, is the riskiest. An
    exact answer must append the same qualified copies, with their alignment
    records, in the order the machine's memo-dependent sub-runs would. Or it
    must intern them, which is new, observable interning: alignment records
    are keyed by row index, and earlier interning reordered `-g` output.
  - The member-tail width rule (about 18.6 M) and `++`/`--` (about 14.2 M)
    append almost nothing. Both are rules over operand types the pass already
    holds, plus one probe each: the width of the prefix before the final
    `.`, and the modifiable-place test.
- The late-row family (about 10 M, rank 4) was tried in #3384 and lost to
  code layout. At about 2,750 Ir per run it is the cheapest machine work in
  the table, and it should not be revisited.
- Misses are no longer a target: 1.35 M in all, now that the designator probes
  are gone.
- These are ceilings, before any eager-pass cost. #3384 showed that code
  layout can erase a few million instructions. A slice under about 10 M
  should expect to measure close to zero, so only the top three shapes are
  worth a slice.

Performance validation is incomplete (#2761): these are hosted Callgrind
counts, and no 9700X evidence exists for them.
