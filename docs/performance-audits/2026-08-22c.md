`2026-08-22c` (Linux x86_64, Zen 4 7940HS; **classify the IR delimiter index
from the punctuator id, and keep the two delimiter walks apart**).  Hotspot #5
of the stage-1 branch-miss survey.  Two passes build a bracket-matching index
over the same token stream: `c_parse_position_index_build` classifies from
`token.punctuator`, while `c_ir_build_delimiter_index` did the identical job by
materializing each token's spelling and loading its first byte —
`c_token_spelling(...).pointer[0]` — then comparing that byte against
`(`/`[`/`{`, guarded by a `kind == C_TOKEN_PUNCTUATOR && length == 1` test.
The survey put the two at 0.37% and 0.41% of all stage-1 branch misses.

The second pass now classifies from the punctuator id, the same way the first
one does and the same way `c_ir_scan_delimiter_group` two functions below it
already did.  The kind test goes away because only a `C_TOKEN_PUNCTUATOR`
token ever carries an id (`c_token_is_punctuator`), and the length test goes
away because the digraph spellings carry distinct ids, so `<%` stays excluded
exactly as the one-byte-spelling test excluded it — verified by compiling a
digraph-bodied function, which the parser rejects before lowering in both
trees.  The stack entry's `char8 opening` plus three reserved bytes becomes a
`CPunctuator`, matching the parse pass's entry and leaving the struct 8 bytes.
What is removed per scanned body token is the whole-`CToken` copy, the length
compare, and the spelling materialization with its dependent byte load; what
replaces it is one byte read through the token pointer.

**The two walks were then measured against each other and deliberately left
separate.**  `CTokenPositionIndex.matching_delimiters` already spans the whole
token stream across all three delimiter kinds, so the IR pass looked like pure
duplication, and the function body's own brace makes the verdict derivable:
`body_start - 1` is the `{` and `body_start + body_token_count` its `}`, so
`parse_index[body_start - 1] == body_end` is exactly "this body is well
nested".  An instrumented `ide` that built both indexes and compared them
entry-by-entry found **zero** disagreements over 3,000+ bodies of the unity
translation unit and 2,000+ more across the whole test corpus — and then
disagreed on the first malformed body it was shown.  On
`int m(int a) { int b[3]; b[0) = 1; return b[0]; }` the parse index still
records a match past the mismatch (offset 15: parse 24, IR `UINT32_MAX`), and
on `int f2(int a) { int b[2]; b[0) = 1; b[1] = 2; return (a); }` it records two.
The cause is the difference the header comment already documents: the parse
walk resets its stack and continues, the IR walk stops at the first mismatch.
The verdicts agreed in every case; the contents did not.  Since lowering
continues after `builder.failure_message` is set and keeps consuming
`c_ir_matching_delimiter_cached`, sharing the index would feed
plausible-but-wrong matches into real lowering work over exactly the malformed
regions the comment reserves for exact scalar walks.  So this entry takes the
classification change alone.  Anyone revisiting the merge has to reconcile the
two recovery policies first, not just the indexes.  The index-comparison probe
ran on the pre-rebase tree; the nine malformed-body reproducers were rerun
afterwards and diagnose identically, and the divergence is a property of the
two recovery policies rather than of any one revision.
