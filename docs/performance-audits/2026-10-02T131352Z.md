## Why Clang debug is already better in some kernels

Fresh disassembly shows excess Buster address construction, temporary/home copies and stack traffic, **before** any ClangO2 comparison:

| Inner loop | Instructions Buster/ClangO0 | RBP memory operands Buster/ClangO0 | Moves Buster/ClangO0 |
|---|---:|---:|---:|
| reduction | 27/10 | 12/6 | 19/5 |
| invariant-heavy | 64/23 | 32/12 | 46/11 |
| helper-call | 55/21 | 24/11 | 40/12 |

Both debug helper loops still call the helper twice; the2.56× debug gap is **not** evidence ClangO0 inlined. Buster uses explicit index*8 IMUL plus LEA/ADD and home chains, while ClangO0 uses scaled addressing/shorter selection. These are static loop receipts, not dynamic PMU counts or isolated causal shares.

Prioritize debug code quality through #1928 home/copy coalescing, #1929 scaled-address selection and #49 bounded local selection cleanup. Preserve correct variable lifetimes; dropping metadata or silently enabling aggressive transformations is not a debug improvement. #47 owns explicit effort-level policy.

For the separate optimized-output gap, actual ClangO2 artifacts use SSE2 packed/unrolled reductions, inlined/vectorized helpers, loop-invariant integer calculations and high-multiply/shift constant division. Existing remedy owners: #2299 reductions, #48 inlining, #1949 LICM, #1943 division, #1944 SLP, #1927 FP placement. Validate semantics and measure isolated changes before predicting a patch's gain. Do not assign the whole17.80× reduction gain to a single feature.
