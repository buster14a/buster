## The machine paths the rule copies

Read in `c_parse.c` at the base before writing the rule:
- **Prefix.** The operator scan turns a leading `++` or `--` into a
  `C_PARSE_EXPRESSION_TYPE_UPDATE` task over the rest of the range. When the
  operand's task returns, the operation leaves `last`, the operand's answer,
  unchanged: no promotion, and pointers allowed. Checked, it raises
  "increment or decrement operand is not a modifiable place" when
  `c_parse_update_operand_modifiable` fails over the operand's tokens or the
  operand is a struct, union or `nullptr`.
- **Postfix, checked.** The leaf's `postfix_update` test sees the trailing
  `++` or `--` and pushes a nested run over the operand's tokens
  (`c_type_parse_postfix_update_push`). Its `POSTFIX` stage completes with that
  run's type, unchanged, after the same modifiable test.
- **Postfix, unchecked.** `postfix_update` is false, so the leaf calls
  `c_parse_expression_leaf_without_cast`. That falls to the direct reader,
  which drops a trailing update (`c_parse_direct_expression_type_core`) and
  reads the operand's postfix chain.

So every path answers with the operand's own row, and none of them appends a
row of its own. The rule accepts an update node over an accepted operand with
that operand's type. Checked, the node is safe only when the operand is safe,
the operand is not a struct, union or `nullptr`, and the modifiable test holds.
The test is the machine's own function, now shared through `c_internal.h`.
For a lone identifier the binder bound, the function reduces to the binding
and the row: the place shape of one identifier holds, and it reads the same
identifier use. The pass reads those directly and runs the function only for
other operands and for array rows (an adjusted array parameter).

The unchecked direct reader is a different reader from the operator machine.
Exactness there rests on the corpus verify gate below, which compares every
tree answer with a machine run in both modes.

## The rows these runs append

The census attributed 7 appended rows to `++`/`--` in 4,299 runs. Its
attribution descends to the operand whose own rule refused, so it does not
say which shape appended them. A throwaway patch (not committed) built over
both the base and the candidate logs every machine run from a query whose
range holds a `++` or `--` token, with the rows the run left behind:

| Binary (pilot) | Such runs | Runs that append | Rows appended |
| --- | ---: | ---: | ---: |
| base | 4,325 | 17 | 23 |
| candidate | 31 | 17 | 23 |

The 17 appending runs are the same queries in both. So none of the 4,294 runs
the rule removed appended a row, as the verify gate also requires. The 17 are
still declined, because an operand inside them appends a row the typer does
not intern:
- a member through a pointer to a qualified aggregate, which appends a
  qualified copy of the member row, census shape 1. Examples are
  `cfg->edges + block->successor_offset + successor++` and
  `cfg->blocks + pending[--pending_count]` in `ebpf.c`, where `cfg` is
  `IrPublishedCfg const*`, and `variant->operand_slots[...]` in
  `machine_x86_64.c`;
- an array operand of `+` that decays, census shape 11, such as
  `digits + --digit_count` in `object.c`, where `digits` is a local
  `char8[32]`.

The other 14 runs left are larger expressions that decline for other reasons,
mostly shifts and casts on the right of `words[count++] = …`. They append
nothing.
