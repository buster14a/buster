`2026-09-07T231146Z` (Linux x86_64, AMD Zen 4, Clang 21.1.8; **proven disjoint
stack-slot scheduling and conservative unknown-memory ordering (#41)**).

The QUALITY scheduler can now move bounded accesses to distinct stack-slot
objects independently. One conservative chain previously ordered every memory
unit, including independent locals under high register pressure. The useful
result is less spill traffic on the pressure fixture; these measurements do
not establish a compiler-throughput improvement.

## Scope and invariants

`machine_schedule_stack_alias` identifies existing stack-slot objects only for
fixed-width x64/AArch64 frame loads and stores whose byte range fits the slot.
All accesses to the same slot remain ordered, including overlapping ranges.
Pointer, incoming-argument, aggregate, multirow, out-of-range, and unrecognized
forms stay UNKNOWN. Each UNKNOWN unit follows all pending slot tails and
precedes each subsequent slot chain. Calls, physical-register staging, atomics,
fences, and other existing barriers retain their full ordering.

The native selectors already walk canonical rows to build their selection
index. That walk now also certifies that the entire function contains no
`volatile_access` row. Uncertified functions retain the old all-memory chain.
This proof is necessary because selection does not preserve per-row volatile
provenance. Manual MIR starts uncertified; structural replay deliberately
drops the proof. Consumers introducing volatile memory must clear it. Existing
CFG, SSA, and scheduling rewrites preserve it because they do not introduce
volatile semantics. Unsupported inline assembly still uses canonical fallback.

This is a conservative whole-object first implementation, not pointer alias
analysis or byte-range disambiguation within an object. Mutable-vreg touch
chains remain: native selection still explicitly produces mutable promotion
rows, so removing those dependencies is not justified by canonical promotion
alone. The documented mutable fallback contract remains valid.

For N block rows, the dependency bound becomes `9N+8`: four operand edges,
two barrier edges, one vector edge, and at most two memory edges per row.
Each pending slot tail is flushed once. The ready queue remains `10N+16`;
blocks whose count would overflow its u32 count keep the source schedule.
The added scheduler scratch is at most `16N+8S` bytes for S slots in a
pressure-gated certified function. `MachineFunction` and its embedded selection
result grow by eight bytes. FAST never constructs this alias graph; its
selector does perform the additional boolean accumulation in the existing walk.

## Reproduction and method

Baseline source/compiler: `ebfdd11705bc470564e726857e498f1c82aa746c`.
Candidate: this change, built independently from that baseline. Both trusted
hosts were Clang 21.1.8 native Release unity builds, O3 with debug information
and frame pointers. Genuine TCC bootstrapped the build driver. Configure with
`./build.sh generate --linker DEFAULT`, then build Release.

The [comparison script](2026-09-07T231146Z-compare.py) takes baseline compiler,
candidate compiler, frozen baseline source root, and output directory. It
generates 128 identical-shape functions with 64 distinct locals, external
one-pointer initializer calls, and a bit-reversed balanced sum. The external
calls keep the locals addressable without a huge unsupported argument list.
The other inputs are frozen `machine.c` and the complete frozen unity IDE.
All comparisons use the same input, flags, cwd, and output path. The script
records raw samples, output sizes and streaming SHA-256 digests in
`results.json`; timings exclude hashing. The measured
[raw samples](2026-09-07T231146Z-samples.json) are retained with this audit.

There is one warmup per case/compiler, then eight alternating A/B pairs for
the object cases and six for unity. Python `perf_counter_ns` measures wall
time; `wait4` records per-child user/system CPU and peak RSS. The process is
not core pinned (affinity CPUs 0–8), on a shared Zen 4 host with other local
builds idle. Paired wall-ratio intervals below are percentile bootstrap 95%
intervals from 10,000 resamples, seed 41. Hardware PMU access is unavailable;
there are no retired-instruction, branch, cache, or Zen 5 claims.

## Useful generated work

The single pressure function has 705 canonical instructions and 576 values
for both hosts, with no fallback. QUALITY attempts and retains one schedule.

| Counter | Before | After |
|---|---:|---:|
| Reloads | 140 | 91 |
| Spills | 205 | 157 |
| Spills + reloads | 345 | 248 |
| Copies | 177 | 226 |
| Stack frame bytes | 2,160 | 1,776 |

This is 28.1% less spill/reload traffic, 17.8% less frame space, and 8.5% less
code, with 49 additional copies. The 128-function corpus confirms the same
traffic change at scale: 44,160 → 31,744 spills plus reloads, 22,656 → 28,928
copies, and 276,480 → 227,328 total frame bytes. Both hosts retain all 128
schedules and have zero fallback functions.

Frozen `machine.c` is a counterexample to a universal code-quality claim:
450 functions, 129,516 instructions, 112,414 values, 19 fallback functions,
and 39 retained schedules stay constant, while spill/reload traffic increases
38,818 → 38,822, copies 13,914 → 13,916, total frame space 696,440 → 696,456
bytes, and code 1,770,208 → 1,770,240 bytes. The existing pressure and final
placement acceptance gates remain in force; they compare each candidate to
its unscheduled input, not to the previous scheduler's chosen output.
