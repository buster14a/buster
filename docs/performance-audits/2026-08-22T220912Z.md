The question this audit was opened to answer: the buster C parser began life as
a scalar port of Niles Salter's (Validark's) Accelerated Zig Parser
(`~/dev/Accelerated-Zig-Parser`), the lexer side has since become the Validark
window pipeline (`2026-08-22T140940Z`), and nobody had gone back to ask what
the *parser* side of that lineage still owes. Census first, per the standing
rule; no code was touched before the table below existed.

**The premise is void: there are no upstream parser kernels.** The repository's
own to-do list still reads "Actually implement the AST parser", `RUN_LEGACY_AST`
and `RUN_NEW_AST` are both `false` at the top of `src/main.zig`, and the only
`parse` outside the tokenizer in its 4.825 lines is a disabled benchmark
harness that calls **stock** `std.zig.Ast.Parse` (line 3021) to time the
unaccelerated parser as a baseline. The `multi_char_symbol_parser` at line 2220
is the `vpshufb` NFA for operators — a tokenizer component. So the accelerated
half of that project is entirely the tokenizer, which this tree has already
drawn on and then some. Nothing can be "ported" from it into `c_parse.c`,
and `reference_original_parser`'s standing claim that the parser's SIMD kernels
are still waiting to be ported is retired here as historical: it was true of
the lexer, it was never true of the parser, because upstream never wrote one.

That leaves the useful question, which is the one the ranked table answers:
which parser-side loops in *this* tree have the shape the Validark lexer
vocabulary applies to — per-item classification, mask arithmetic, batch
validation — and are hot enough to be worth a kernel.

**What the table is really measuring, and the finding under it.** All five
loops re-derive the same facts from the same rows: `CToken` is a 12-byte AoS
row (`offset` u32, `symbol` u32, `length` u16, `kind` u8, `punctuator` u8) and
every one of these passes reads **two** of those twelve bytes — `kind` and
`punctuator`, which are adjacent at offsets 10 and 11 — to ask what shape the
token is. The stream is walked end to end four times in the parse phase
(`c_parse_ast`, `c_parse_position_index_build`, the census, and the per-body
walk), each time reloading 12 bytes per token to look at 2. That is the layout
finding, and it is what AGENTS.md's "choose the data layout before choosing
SIMD instructions" points at here: the instruction count is a symptom.

**Instructions per element, which decides the kernel's shape.** The census
costs 58,8 M / 2.959.183 = **19,9 instructions per token** today. Two kernel
forms were priced before writing either:

- *Compare in place.* `lcm(12, 64) = 192`, so the byte lanes holding
  `punctuator` repeat with period three across 64-byte chunks and a compare
  against a splatted punctuator value can be ANDed with a constant lane mask
  per phase. No projection, but each 64-byte chunk carries only 5,33 tokens
  and every class needs its own compare over the full chunk: ~30 operations
  per 5,33 tokens = **5,6 instructions per token**. A 3,5x win, and the AoS
  tax is the whole of what is left.
- *Project, then count.* Two `vpermt2b` passes gather the `kind` and
  `punctuator` bytes of 64 tokens into two contiguous 64-byte registers
  (~34 operations per 64 tokens including the twelve loads), after which each
  class is one compare, one popcount and one add over **64** tokens rather
  than 5,33 (~28 operations per 64 tokens). Together ~**1,0 instruction per
  token**, a ~20x reduction, and the projected stream is reusable by the other
  three passes.

The second form wins by five times and is the one this audit implements. The
two counters that carry state across tokens — `maximum_delimiter_depth` and
the brace-depth-0 comma count — do not vectorize as counts and are computed by
iterating the set bits of the delimiter and comma masks the same pass already
produces, which is ~44% of tokens instead of 100%.
