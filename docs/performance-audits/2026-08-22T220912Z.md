`2026-08-22T220912Z` (Linux x86_64, Zen 4 7940HS; **census the parser side
against the Accelerated Zig Parser: the upstream parser kernels do not exist,
and the ranked token-walk ceilings say the token census is the one that
pays**).

The question this audit was opened to answer: the buster C parser began life as
a scalar port of Niles Salter's (Validark's) Accelerated Zig Parser
(`~/dev/Accelerated-Zig-Parser`), the lexer side has since become the Validark
window pipeline (`2026-08-22T140940Z`), and nobody had gone back to ask what
the *parser* side of that lineage still owes. Census first, per the standing
rule; no code was touched before the table below existed.

**The premise is void: there are no upstream parser kernels.** The repository's
own to-do list still reads "Actually implement the AST parser", `RUN_LEGACY_AST`
and `RUN_NEW_AST` are both `false` at the top of `src/main.zig`, and the only
`parse` outside the tokenizer in its 4.825 lines is a disabled benchmark
harness that calls **stock** `std.zig.Ast.Parse` (line 3021) to time the
unaccelerated parser as a baseline. The `multi_char_symbol_parser` at line 2220
is the `vpshufb` NFA for operators — a tokenizer component. So the accelerated
half of that project is entirely the tokenizer, which this tree has already
drawn on and then some. Nothing can be "ported" from it into `c_parse.c`,
and `reference_original_parser`'s standing claim that the parser's SIMD kernels
are still waiting to be ported is retired here as historical: it was true of
the lexer, it was never true of the parser, because upstream never wrote one.

That leaves the useful question, which is the one the ranked table answers:
which parser-side loops in *this* tree have the shape the Validark lexer
vocabulary applies to — per-item classification, mask arithmetic, batch
validation — and are hot enough to be worth a kernel.

Ranked by raw ceiling `c_parse_bind_function_body` leads, and that is the
misleading order: three quarters of it is the entity binding it exists to do.
Ranked by *addressable* ceiling the token census is #1, and it is also the
cleanest shape in the table — nine counters over a linear stream, no output
order to preserve, no stack, no early exit, and a correctness check that is
nine integer equalities against the scalar loop.

**What the table is really measuring, and the finding under it.** All five
loops re-derive the same facts from the same rows: `CToken` is a 12-byte AoS
row (`offset` u32, `symbol` u32, `length` u16, `kind` u8, `punctuator` u8) and
every one of these passes reads **two** of those twelve bytes — `kind` and
`punctuator`, which are adjacent at offsets 10 and 11 — to ask what shape the
token is. The stream is walked end to end four times in the parse phase
(`c_parse_ast`, `c_parse_position_index_build`, the census, and the per-body
walk), each time reloading 12 bytes per token to look at 2. That is the layout
finding, and it is what AGENTS.md's "choose the data layout before choosing
SIMD instructions" points at here: the instruction count is a symptom.

**Instructions per element, which decides the kernel's shape.** The census
costs 58,8 M / 2.959.183 = **19,9 instructions per token** today. Two kernel
forms were priced before writing either:

- *Compare in place.* `lcm(12, 64) = 192`, so the byte lanes holding
  `punctuator` repeat with period three across 64-byte chunks and a compare
  against a splatted punctuator value can be ANDed with a constant lane mask
  per phase. No projection, but each 64-byte chunk carries only 5,33 tokens
  and every class needs its own compare over the full chunk: ~30 operations
  per 5,33 tokens = **5,6 instructions per token**. A 3,5x win, and the AoS
  tax is the whole of what is left.
- *Project, then count.* Two `vpermt2b` passes gather the `kind` and
  `punctuator` bytes of 64 tokens into two contiguous 64-byte registers
  (~34 operations per 64 tokens including the twelve loads), after which each
  class is one compare, one popcount and one add over **64** tokens rather
  than 5,33 (~28 operations per 64 tokens). Together ~**1,0 instruction per
  token**, a ~20x reduction, and the projected stream is reusable by the other
  three passes.

The second form wins by five times and is the one this audit implements. The
two counters that carry state across tokens — `maximum_delimiter_depth` and
the brace-depth-0 comma count — do not vectorize as counts and are computed by
iterating the set bits of the delimiter and comma masks the same pass already
produces, which is ~44% of tokens instead of 100%.

## What landed

`c_parse_token_census` in `c_parse.c`, with `c_parse_token_census_reference`
beside it as the definition of the answer. The projection runs on 192-byte
groups: three `simd512_load`s, two maskz `vpermt2b` per stream against fixed
index vectors, an OR, and a 16-lane masked store into per-tile `kind`,
`punctuator` and `symbol`-low-byte arrays of 2.048 tokens. The counting pass
then reads those tiles in whole 64-lane windows -- one `vpcmpeqb` and one
`popcnt` per class -- and the tail is padded with zero, which is
`C_TOKEN_INVALID` and `C_PUNCTUATOR_NONE` and so matches no class, removing
every tail mask.

Three details are worth keeping:

- **`for` is found by its low symbol byte.** Counting `for` exactly would
  otherwise mean visiting all 571.884 identifiers. The candidate mask is
  `identifiers & (symbol_byte == FOR | symbol_byte == 0)` -- the second term
  admits the uninterned tokens whose answer is the spelling fallback -- which
  leaves a few thousand candidates, each then answered by the same
  `c_token_is_well_known` the reference calls. Exact, not approximate.
- **The two stateful counters replay the reference.** `maximum_delimiter_depth`
  and the brace-depth-0 comma count iterate the set bits of the delimiter
  masks (23% of tokens), applying the reference's clamps verbatim, so no
  "properly nested" assumption is made. The commas inside a depth-0 span are a
  popcount of the comma mask between two brace events rather than a visit per
  comma.
- **The scalar fallback is the reference, not this kernel through simd.h's
  fallback.** Without 512-bit lanes every `simd512_load` would be a
  64-iteration byte loop, which is the case AGENTS.md means by a different
  algorithm being worth writing.

**Against the prediction.** The loop was profiled again on the candidate:
`c_parse.c` lines 11.307-11.357's successor costs **15,2 M instructions**
against the 58,8 M the census measured, so the loop itself lost 43,6 M and the
whole-process figure of 44,2 M is that same win with nothing hiding behind it.
Per token the census went from **19,9 to 5,1 instructions**. The estimate
written before implementing was ~3,5, and the gap is the delimiter event loop,
which costs more per event than budgeted; the projection and counting halves
landed where predicted.

Generated code was inspected: the inlined kernel carries 6 `vpermt2b` (two per
projected stream), 9 `vpcmpeqb` and 8 `popcnt` per group, which is the
intended shape.

**Gates.** `-march=x86-64` compiles clean under the full warning set, as does
`-march=native`; `test_self_host` reaches its byte-identical fixed point
(`SELF_HOST deterministic`); the local CI matrix is green, which is what
caught the one configuration-specific defect in this change: an optimized
non-unity build calls `c_parse_token_census_reference` from neither arm, so it
needs `BUSTER_UNUSED_DECL`. A Release-only build never sees that.

## The differential gate, and the compiler bug it found

The gate is `#if !BUSTER_OPTIMIZE` inside `c_parse_token_census`: unoptimized
builds recompute the census the reference way and require all nine counters to
agree. That puts the check on **every translation unit the suite compiles**
rather than on a hand-written list of token streams, and -- because the
self-hosted stages are built without `-DBUSTER_OPTIMIZE` -- it also runs
inside the stage-1 and stage-2 compilers over the whole unity unit. It was
proved load-bearing by perturbing the kernel to miscount a single token in one
window, which failed the suite.

It immediately earned its keep. With the gate in, `test_self_host` failed
while `ide test` and an eleven-pair byte-identical A/B both passed: the
clang-built compiler computed the census correctly and the **buster-built**
one did not. Splitting the check per counter named
`declarator_list_comma_count`, the only one using `mask64_prefix` with a
runtime count, and the fault reduces to five lines with no SIMD in them:

```c
u32 lane = 32;                 /* opaque */
u64 value = lane >= 64 ? ~(u64)0 : (((u64)1 << lane) - 1);
/* clang: 0x00000000ffffffff.  ide cc: 0xffffffffffffffff. */
```

That is `mask64_prefix` from `<buster/lib/simd.h>` expanded. `-emit-llvm` on
the same function shows the cause: the conditional's result slot is allocated
**i32**, both arms are computed correctly in 64 bits, then `trunc`ed into it
and `sext`ed back on the reload, so every count in [32, 64) returns `~0`. The
predicted type, not the resolved one, sizes the slot -- and the misprediction
needs both arms to be what they are: `cond ? ~(u64)0 : x` and
`cond ? y : ((u64)1 << lane) - 1` are each fine, and only the pair fails. All
four allocator modes fail identically, so it is upstream of code generation.

The bug is **pre-existing**: the binary built from the parent commit
miscompiles the same five lines. The only other runtime-count user in the tree
is `ir_source_search_vector` (`ir.c:92-93`), where `mask64_prefix(lanes * 4)`
covers [32, 64) for 8 to 15 lanes; there the wrong mask over-reads the loaded
vector and the extra lanes are masked out of `covered` immediately after, so
it is latent rather than visible -- but it is a real over-read in the
self-hosted stages. The existing coverage misses it because
`simd_test.c` and `tests/basic_c_simd.c` only ever ask for
`mask64_prefix(0)`, `(1)` and `(64)`, all compile-time constants.

This audit does not fix it: the fault is in the C frontend's expression-type
prediction, a separate subsystem from anything the census touches, and a
speculative change there risks the fixed point. The census avoids it instead
by spelling the mask `c_parse_census_lanes_below(lane)`, a bare
`((Mask64)1 << lane) - 1` -- `lane` always comes from `mask64_first_set` of a
non-zero mask, so `mask64_prefix`'s `count >= 64` arm was dead weight here
anyway. **The next task on this thread is the prediction bug itself**, with
the five-line case above as its fixture and `ir.c:92` as its second caller.

## Untaken, in the order this census leaves them

- `c_parse_position_index_build`'s classification half, 43,6 M addressable.
  The same projection this kernel builds would serve it, and the tiles could
  be produced once and read by both -- the census runs first, so the arrays
  are already warm. The serial delimiter stack and the ordered appends stay.
- Making the projection a **property of the token stream** rather than of this
  one pass. All four parser walks read the same two bytes out of the 12-byte
  rows; a `kind|punctuator` sidecar written where the preprocessor already
  writes each `CToken` would cost one store per token and turn every one of
  those walks into a contiguous scan. That is the layout change this census
  argues for, and it is bigger than one kernel.
- `c_parse_bind_function_body`'s 25 M of token-shape tests, which only becomes
  worth it once the sidecar above exists.
