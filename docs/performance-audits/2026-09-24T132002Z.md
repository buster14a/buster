`2026-09-24T132002Z` (Linux x86_64, Devin VM (Emerald Rapids), not benchpress;

## Decision

Issue #124 slice: x86-64 frame spill/reload chunks (`machine_x64_emit_exact_frame_chunk`)
now copy one prewarmed, metadata-derived record per
`(direction, width slot, data register)` and patch its disp32, instead of
re-entering `machine_x64_emit_variable_memory_encoding` for every chunk. The
change is **kept on instruction-count evidence only**. It removes 51.4 M
Callgrind instruction references (-7.8%) from `machine_encode_x86_64` on the
frozen stage-1 self-compile and 60.5 M (-0.246%) from the whole compile.
Ordinary scalar hoisting (an inlined wrapper around the unchanged helper plus
an out-of-line metadata fallback) achieves about 69% of the encoder reduction
by itself; the prepared record accounts for the remaining 16.1 M references
(-0.065% of the compile) at 2 KiB BSS and roughly 12 K prewarm references, and
it has less code growth than hoisting alone.

**No wall-clock improvement is claimed.** Wall time and cycles on the Devin VM
did not resolve differences of this size, and the authorized benchpress 9700X
route was **NOT RUN** from this session. The generated artifact is
byte-identical. #124 stays open.

## Hypothesis, invariants and the falsifying experiment

Hypothesis: spill/reload chunk emission is a closed emission shape — load or
store, one of four widths, sixteen GPRs, base RBP, forced disp32 — whose
encoding bytes depend on nothing else. The per-call work in
`machine_x64_emit_variable_memory_encoding` (table-index validation, RBP
check, displacement-class choice, `reg + (base << 4)` row selection) is
therefore repeated interpretation that can be resolved once at prewarm. The
only dynamic inputs left are the frame offset, the per-function
`frame_base_offset`, and the destination capacity.

Cheapest disproof: if an inlined wrapper around the unchanged helper (letting
Clang constant-fold `base == RBP` and `force_disp32`) removes the same work,
the prepared record adds nothing and is rejected.

Invariants the record must preserve:

- **Single encoding authority.** Records are copied, never written by hand,
  from `machine_x64_variable_memory_encoding_tables[...].encodings[2][reg + (RBP << 4)]`,
  which prewarm already derives from the metadata tokens of
  `LOAD_PTR{8,16,32,64}` / `STORE_PTR{8,16,32,64}` through
  `machine_x64_chunk_memory_tables`. Prefixes (REX.W, REX.R, the bare `0x40`
  for SPL/BPL/SIL/DIL byte stores, `0x66`), operand widths (MOVZX r64 for one-
  and two-byte loads) and the `[rbp + disp32]` ModRM form are those rows'
  bytes.
- **Key publication and lifetime.** `machine_x64_frame_chunk_encodings` is
  filled inside `machine_x64_exact_prepare_chunk_memory_tables`, during the
  serial `machine_x86_64_exact_prewarm`, before `machine_x64_exact_opcode_map_ready`
  is published and before any `lane_run` worker encodes. It is immutable
  afterwards and process-lifetime, like the tables it copies. The key is
  target-wide only in facts that are target-wide: opcode row, width and
  register. Frame facts are not in it.
- **Displacement arithmetic.** The patched value is
  `(0u - offset) + encoder->frame_base_offset`, the same wrapping `u32`
  arithmetic as the old `(s32)((u32)(s32)(0u - offset) + frame_base_offset)`.
  `frame_base_offset` is set per function after the Win64 dynamic-stack
  `MOV RBP, RSP` and before block traversal, and is read at emission time.
- **Capacity and wide stores.** Before copying, the same
  `count > capacity || byte_count > capacity - count` check sets `overflow`,
  counts one attempt and one fallback, and emits nothing, as the old helper
  did. `machine_x64_encoder_copy_encoding` issues a 16-byte store only when
  16 bytes of capacity remain, otherwise an exact-length copy; the disp32
  patch lies inside `byte_count`.
- **Fallback and accounting.** A zero-length record (unprepared table) or
  `reg >= 16` goes to `machine_x64_emit_exact_frame_chunk_metadata`, the
  previous metadata body unchanged. Success counts one attempt and one
  success; output offsets advance by `byte_count`.
- **Machine representation unchanged.** No `MachineInstruction`,
  `MachineX64Encoder` or IR field changed.

The generic metadata packer (`buster_x86_metadata_emit_form_to_scratch`) is
therefore already bypassed almost everywhere; frame chunks are the largest
remaining population that still re-derives a fixed shape per call.

## Optimized trusted-compiler code

In the base Release `ide`, `machine_x64_emit_exact_frame_chunk` (937 bytes)
is out of line and calls `machine_x64_emit_variable_memory_encoding` (350
bytes), which re-validates `table_plus_one` against the table count, tests
`base == RBP`, selects the displacement class, forms the row index, checks
capacity, copies and patches. Clang does not specialize that call for the
constant RBP/forced-disp32 arguments. `machine_encode_x86_64` contains 26
frame-chunk call sites. With `p`, the fast path is inlined into those sites,
the metadata body (703 bytes) stays out of line, and each chunk becomes:
load record, capacity check, copy, one 32-bit patch, count updates.

## Limitations

- The kept result is an instruction-count reduction; paired wall-clock
  measurement on the dedicated host is still required before calling it a
  speedup.
- The prepared path's disp32 patch wraps offsets whose negation is not
  representable in `s32` (e.g. `offset == 0x80000000`), exactly as the old
  helper did; the metadata path rejects those. Frames that large do not occur
  (the workload's largest frame is 892,936 bytes); the test covers offsets up
  to `0x7fffffff` and `0xfffffff8`.
- Pointer chunks and `LEA_OFFSET` variable-memory emissions (≈ 247 K per
  compile) still use the generic helper; their base register is dynamic, so
  they are not the same closed shape.
