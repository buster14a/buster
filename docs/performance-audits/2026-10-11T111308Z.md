## Workload

Lowering runs only when an object is produced, so the measured compile is
`-c`. Every arm compiles the same input, the base revision's unity self-host
source, from the base checkout:

```sh
ide cc -Isrc -I<base build>/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 \
  -target x86_64-unknown-linux -march=znver5 -g0 -c -o <arm>.o \
  [-fc-ast-pilot] src/buster/apps/ide/ide.c
```

Four arms:
- A: base, default flags;
- B: base with `-fc-ast-pilot`;
- C: candidate with `-fc-ast-pilot`;
- D: candidate, default flags.

C − B is the slice's effect on the pilot. D − A is the default path, measured
on `-c` and on `-fsyntax-only` (the same input with `-fsyntax-only` in place of
`-c -o`). Every arm also wrote a `-g` object natively for comparison. Callgrind
ran with `--cache-sim=no --branch-sim=no`.

Before any code, a Callgrind run of arm A on the first base charged 6.07 G of

## The change

Under the pilot the driver passes the tree to lowering in
`CIRLowerOptions.syntax_tree`, which is null otherwise.
- `c_ir_tree_conditionals_build` runs once per lowering, in an arena of its
  own that `c_lower_to_ir_run` sizes, creates and destroys.
  - It runs only when the stream has a matching-delimiter array.
  - It indexes every top-level function body's `CONDITIONAL` and
    `CONDITIONAL_OMITTED` nodes.
  - For each body it keeps the `?` tokens in order.
  - For each node it keeps a record of the condition's first token, the `?`
    and the `:`.
  - First-token walks stop at an already indexed conditional
    (`CIrTreeFirstMemo`), and widening over parentheses resumes from that
    conditional's start. That keeps the build linear.
- `c_ir_tree_root_conditional` answers in one of three ways:
  - **False**, when no `?` lies in the range;
  - **True**, when a record starts at the range's start once outer parentheses
    are stripped;
  - **The scan** otherwise.

  Debug and sanitized builds check every true and false answer against the
  scan.

1. **Version 1 failed the function budget.**
   - `c_ir_root_conditional` fell only 34%, against a budget of 50%.
   - The tree answer stripped the range's outer parentheses before its `?`
     test. Stripping only narrows a range, and the `?` test decides 93% of
     the queries.
   - The index build also walked every body's nodes twice.
2. **Version 2 failed the default-path budget.** It ran the `?` test first and
   counted each body's conditionals with one branch-free compare per kind
   byte. Its out-of-line dispatcher cost the default path about 21 Ir per
   call.
3. **Version 3 passed every budget.** The dispatcher became inline.
   - The function fell from 154,126,101 to 72,455,085 (−52.99%).
   - Its objects were `-g0` `78583e834c3526ef…` and `-g` `27cf0b3c575e0256…`.
   - Its index build was the quadratic one above. On the self-host its line
     counts charged the build about 15 M.
   - An earlier copy of this audit gave version 3's full SHA as `1585bc84`
     followed by a wrong suffix. The SHA in the table above is the measured
     checkout, and its tree matches the one recorded then.

## Follow-ups

These items stay with the next lowering slices; none is claimed here.
- **The build's collecting walk.** It reads every node up to a body's last
  conditional. A chunked skip, using the same branch-free count per chunk,
  would remove most of it.
- **The per-query cost.** Bodies without a conditional (`question_count == 0`)
  could be answered in the inline dispatcher, before the out-of-line call.
- **The next slices.** The plan on #3102 orders them: root comma, assignment
  and control facts first, then the statement walker.
