`2026-09-25T215313Z` (Linux x86_64, shared 4-vCPU Xeon container; **FAST slot
liveness closes over every fixed frame slot; 99.56% of self-compile live bits
are never read**).

## Decision

`machine_fast_close_live_ranges` is the largest self-cost entry of the
self-compile (3.23% of 9700X `cycles:u` in the
[current-main census](2026-09-23T144607Z.md); 3.73% self and 5.2% inclusive of
a matched callgrind count here). Its work is a product: dense read/write and
live-in/live-out planes of `blocks × ⌈slots/64⌉` words, plus one
`trailing_zeroes_u64` per live bit. The slot population it closes over is
every frame slot, but its only consumer, `machine_fast_color_slots`, reads the
range of a slot that is **neither fixed nor untouched** and nothing else. On
the frozen self-compile **87,996,696 of 88,383,940 materialized live bits
(99.56%) belong to fixed slots** whose ranges are dropped, and one function —
`codegen_generate_canonical_module_attempt`, 8,393 machine blocks and 9,524
slots — produces 72,189,995 of them.

The prototype on branch `claude/laughing-noether-meufke` closes only the
shareable slots through a dense index, the idiom `machine_fast_close_home_ranges`
already uses for homes. It is **byte-identical** on every input checked and
removes the work structurally:

| Frozen self-compile (`-g0 -c`) | Baseline | Prototype | Ratio |
|---|---:|---:|---:|
| Live bits materialized | 88,383,940 | 387,244 | 228× |
| Plane words (`Σ blocks × ⌈objects/64⌉`) | 1,773,101 | 105,107 | 16.9× |
| Worklist block visits | 391,619 | 175,418 | 2.2× |
| Slot closures run | 5,206 | 1,417 | 3.7× |
| Largest single function, live bits | 72,189,995 | 47,232 | 1,528× |
| `machine_fast_close_live_ranges` inclusive Ir | 1,653,108,040 | 25,850,345 | 64× |
| `machine_fast_placement_build_prepassed` inclusive Ir | 3,472,441,489 | 1,756,205,738 | 2.0× |
| Whole compile Ir (counting build) | 31,710,581,013 | 29,994,589,536 | −5.41% |

These are exact operation and instruction counts, **not timings**. No
elapsed-time, cycle or 9700X claim is made; the approved leased 9700X path is
required before any speedup statement (see "Runnable 9700X experiment").

## How the lead was found

A callgrind screen compiled 27 deterministic geometric C families at
1k/2k/4k/8k (`screen_gen.py`, `screen_run.py`, `screen_analyze.py`) and ranked
functions by the share of instruction growth whose exponent between the two
largest sizes is ≥ 1.3. The complete table is `screen_summary.txt`. Families
whose growth is dominated by exponent-2.0 functions:

| Family (N varied) | Exponent-2 functions | Disposition |
|---|---|---|
| `structs`: N aggregate locals in N blocks | `machine_fast_close_live_ranges`, `trailing_zeroes_u64`; `c_type_parse_core_step` | **This audit**; frontend part below |
| `members`: N members, N accesses | `c_parse_member_type`, `string_equal`, `c_ir_emit_field_place_from_value` | bounded by struct size on real code |
| `ifchain`: N-arm `else if` | `c_ir_statement_span`/`_end`/`_labels_end` | real self-compile share ≈0.3% (85.7 M Ir) |
| `gotos`: N labels | `c_ir_label_find` | self-compile 0.5 M Ir |
| `switch`: N cases | `c_ir_switch_integer_less_equal`, `c_parse_validate_one_switch` | tracked by #954 |
| `longexpr`: N-operand sum | `c_type_parse_sizeof_step` | left-spine rescans; real exposure is generated code |
| `ptr_init`/`struct_init` | `ir_validate_global` | per-global R², 820,549 pairs on the self-compile |
| `includes` | `c_preprocess_file_index` | self-compile 2.2 M Ir |
| `compound_lits` | `c_ir_type_name_prefix` | K × T tag scan, frontend family below |

Three read-only scouts (frontend, IR/codegen, object/link) then modelled each
screen hit in source, and a real-source census ranked them. The FAST closure
won on every axis: largest real-source share, an exact product law, 99.56% of
its work provably unread, and a byte-identical structural repair.

## Cost model and geometric evidence

For one function with `B` machine blocks and `S = S_fixed + S_shareable` frame
slots, the baseline builds four planes of `B × ⌈S/64⌉` words (two in the
caller, two in the closure), runs the worklist over them, and materializes one
bit per (slot, block) pair in which the slot is live in or out. A slot whose
first touch is a partial store or a load is upward-exposed — the planes treat a
non-covering store as a read — so it is live from entry to its last touch. An
escaping aggregate that is later written field by field is exactly that: fixed
and live across almost the whole function.

`fast_gen_fixed.py F B` builds F escaping `struct P` locals, B conditional arms,
and then for each local a partial store and an address escape. The observed law
is exact, `bits = F × (2·B_m − 1)` and `words = B_m × ⌈F/64⌉` with `B_m`
machine blocks; the prototype does no closure work at all, and every object is
identical (`fast_grid_fixed.tsv`):

| F | B | Machine blocks | Baseline bits | Baseline words | Prototype bits / words | Object |
|---:|---:|---:|---:|---:|---:|---|
| 64 | 64 | 193 | 24,640 | 193 | 0 / 0 | identical |
| 64 | 1024 | 3,073 | 393,280 | 3,073 | 0 / 0 | identical |
| 1024 | 64 | 193 | 394,240 | 3,088 | 0 / 0 | identical |
| 1024 | 1024 | 3,073 | 6,292,480 | 49,168 | 0 / 0 | identical |

`fast_gen_fixed_shareable.py F B C` adds C arms of `__int128` arithmetic, whose
selector temporaries are shareable slots. The prototype's work is then a
function of (B, C) only, independent of F, while the baseline grows with F
(`fast_grid_fixed_shareable.tsv`, all 12 points identical objects):

| B | C | F = 64 baseline | F = 256 baseline | F = 1024 baseline | Prototype (any F) |
|---:|---:|---:|---:|---:|---:|
| 1024 | 16 | 923,635 bits | 2,140,339 | 7,007,155 | 518,067 bits |
| 1024 | 64 | 2,551,555 | 3,878,851 | 9,188,035 | 2,109,123 |

The remaining prototype bits are shareable temporaries that are themselves
upward-exposed. In this family every frame store is an 8-byte move (2,724 of
them in a 32-arm sample, none wider), so no single store covers a 16-byte
`__int128` slot and each half reads. Removing those bits needs a
lifetime-start or per-block coverage fact (see "Not done").

The screen's own `structs` family (N aggregate locals, one per block) shows the
same split: at N = 8,000 the baseline materializes 127,999,996 bits over
2,000,250 plane words and the prototype 63,999,996 over 1,000,125, with
identical objects. The fixed-slot half disappears; the remaining half is the
allocator's own home liveness on that straight-line CFG, which
`machine_fast_color_homes` does consume.

**Crossover.** The prototype adds one O(S) census pass and a dense map of
`4·S + 12·S_shareable` bytes per function with a slot closure, and it skips the
instruction scan entirely when no slot is shareable. It saves `B × (⌈S/64⌉ −
⌈S_shareable/64⌉)` words in each of four planes plus every fixed slot's live
bits. There is no input on which it does more plane or bit work; the only added
work is the linear census, which is below one plane word per slot per block.
Savings begin at the first fixed slot that makes a second word or carries a
live bit, and on the self-compile the modeled and measured bit reductions agree
exactly (`bits_total` = shareable bits + 620 home bits in both builds).

## Why the result cannot change

- `machine_fast_color_slots` selects `!slot_fixed[slot] && slot_starts[slot] !=
  UINT32_MAX` in both of its loops and reads `slot_starts`/`slot_ends` only for
  those slots; nothing after the closure reads them for any other slot.
- Every plane operation is bitwise per object (`reads | (out & ~writes)`, OR
  merges into predecessors, single-bit read/cover masks in the backward scan).
  Liveness over loops has more than one fixed point; the worklist climbs from
  empty sets to the least one, and each object's bits evolve independently on
  the way, so dropping other objects only removes requeues (391,619 → 175,418
  visits) and cannot change a shareable object's live-in/live-out or its
  materialized range. The counts agree: the baseline's shareable bits plus its
  620 home bits equal the prototype's 387,244 exactly.
- `slot_fixed` is complete before the closure (address rows, unproven access,
  inline assembly, variadic fetches, memory flags, the outgoing area) and is not
  modified afterwards.

## Limits of the counts

- **One workload, one dominant function.** 72.2 M of the 88.4 M bits (82%) come
  from `codegen_generate_canonical_module_attempt`, a 12,459-line function. The
  fixed share is broad in this translation unit (117,409 fixed, 3,023
  shareable and 35 untouched slots across 5,206 closures), but Buster's own
  style — aggregate temporaries passed by address, aggregate copies, `&local` —
  maximizes fixed slots. SQLite's `sqlite3VdbeExec` and CPython's eval loop are
  unmeasured; the repair never adds plane or bit work there, but the 228× and
  5.41% figures do not transfer.
- **Instructions are not cycles.** The counting build makes `trailing_zeroes_u64`
  an out-of-line call per bit and does not vectorize the word loops, so its
  instruction share overstates the Release cost. The right upper-bound anchor
  is the census's 3.23% self share for the closure. The caller's own 2.92% —
  its per-row `machine_schedule_frame_access` scans — mostly remains.

## Secondary finding: whole-type-table work per C semantic query

Also measured with exact counters (`frontend_grid.txt`, `unity_probe_counts.txt`)
and filed separately because it is a different subsystem. In
`src/buster/lib/compiler/frontend/c/c_parse.c`, three per-query helpers cost
`O(T)` in the parse type-table size `T`, which is 137,911 rows on the
self-compile and grows with every included header:

| Site | Frozen self-compile | Two-dimensional law (filler rows T, queries Q) |
|---|---|---|
| `c_type_parse_core_step` aggregate-definition scan | 1,160 scans, 18,725,775 row visits, **all misses** | visits = Q × (2T + Q − 1) |
| `c_parse_member_type` promoted-member `visited` memset | 2,767 calls, 296,975,457 bytes cleared | bytes = 3Q × (type_count + 1) |
| `c_parse_constant_offsetof` → `c_parse_type_layout_core` with `offset_out` (cache bypassed) | 23 queries, 16.4 M Ir each, 376.8 M Ir total | seeded rows = Q × type_count |

Each is quadratic in translation-unit size because both factors grow with it.
The frontend scout also located two siblings: `c_ir_type_name_prefix` (K tag
type names × T rows, no early exit; screen exponent 1.98) and
`c_ir_predeclare_labeled_automatic_locals` (functions with labels × all
entities). Repairs are an index from `definition_start` to the lowest type id,
generation-stamped visited arrays (the parse side already has one for
`c_parse_promoted_member_type`), and seeding offset queries from the committed
layout cache while forcing only the requested aggregate back into the solve.

## Related pre-existing defect: inverted volatile certificate

Found by the adversary review and reproduced at the pinned base; the prototype
neither causes nor fixes it. `MACHINE_STACK_SLOT_MEMORY_NONVOLATILE` is `1u` and
zero means unknown (`machine.h`); the selector sets every slot to 1 and clears
volatile-tainted ones (`machine_select.c`). The FAST placement census fixes
`stack_slot_memory_flags[slot] != 0`, which is the *certified* slots, so in any
function with a volatile access every certified slot loses sharing while the
tainted ones stay shareable. That is the opposite of the comment beside it and
of `docs/agents/machine.md` ("volatile-tainted … objects keep storage of their
own"); `machine_schedule_memory_access` tests the flag the right way. Witness:
a function with two `__int128` arms has 20 shareable slots and 0 fixed; adding
`volatile long g = a; x += g;` makes it 20 fixed and 2 shareable. No layout
difference was observed in the small witnesses because their shareable ranges
already overlap. The correction changes layout, so it is a separate change with
its own regression; it also moves slots back into this closure.
