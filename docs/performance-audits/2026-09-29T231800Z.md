## Answer and decision

Choose optimization effort by its incremental compilation cost, conservative
lifetime benefit, and hard resource limits. Traditional `-O` membership is not
evidence of profitability. Cheap static facts can identify legal opportunities
and bound work; they cannot establish execution frequency. Unknown frequency
therefore remains unknown. Keep the existing throughput default.

The first useful candidate is narrower than a profitability predictor: **never
run the current QUALITY pin-planning tail when its valid FAST core baseline has
zero spills and reloads**. The existing implementation must return that same
baseline later because it cannot create a candidate. This does not mean never
optimize spill-free functions using other transformations. The isolated pilot
tests this exact implication, not a collection of speculative passes.

General added-cost generated-code policies are a **no-go for adoption** without
held-out compile/runtime evidence and a declared deployment horizon. The narrow
gate is a **go for diagnostic validation**; production adoption additionally
needs an uninstrumented measured compiler-cost result. No production behavior,
default flags, CI admission requirement, retirement binding, or live benchmark
service policy was changed.

## Break-even model

For one build and N executions under a fixed input distribution:

`T(p) = C(p) + N * R(p)`.

Against baseline b, define `dC=C(p)-C(b)` and `D=R(b)-R(p)`. The strict
improvement condition is `dC - N*D < 0`; ties retain baseline.

| Incremental costs | Economic result before resource/correctness guards |
| --- | --- |
| dC > 0, D > 0 | N > dC/D; minimum integer reuse is floor(dC/D)+1 |
| dC > 0, D <= 0 | No finite beneficial reuse count |
| dC < 0, D >= 0 | Candidate dominates on this time objective |
| dC < 0, D < 0 | Candidate wins only N < abs(dC)/abs(D) |
| dC = 0 | Positive D wins only when N>0; negative D loses when N>0 |
| D = 0 | Generated-code reuse cannot repay extra compiler cost |
| N unknown | Report the frontier; abstain on a positive-cost runtime decision |

C includes fact extraction, mandatory preparation affected by the change,
analysis construction, cleanup, verification, allocation and emission. A feature
that costs more than the work it skips is a losing gate. Static linking belongs to C; R includes per-execution startup/dynamic loading,
all called functions and layout/cache effects;
an instruction-count or code-byte reduction is not a measured D.

For uncertainty with positive saving lower bound, require
`dC_upper - N_lower*D_lower < 0`. If the runtime-saving lower bound is nonpositive,
there is no certified finite break-even for an added-cost candidate. Other sign
cases need interval endpoints checked explicitly. Use simultaneous uncertainty
over the frozen policy family, and scope empirical intervals to the measured
domain. An unknown is not a zero or a fabricated mean.

For varying lifetimes/inputs the model becomes
`E[C + sum_i R(p,input_i)]`; the incremental saving is `E[N*D]`, not necessarily
`E[N]*E[D]`. Reuse count and input-dependent benefit can be correlated. At the
function level, expected calls and loop iterations must come from a declared
workload/profile envelope. Static loop depth is not that envelope.

| Deployment | Changes to the objective |
| --- | --- |
| Interactive builds | Charge every compilation, including discarded artifacts with N=0. Minimize edit-to-artifact latency and its tail separately from additive CPU work; parallel wall time follows the critical path. Optional effort needs a latency budget even when a final release could amortize it. |
| One-shot tool | Begin with N=1 and include process startup/input work. A single invocation can still execute a large loop, so one-shot does not prove every optimization unprofitable. |
| Long-running program | Evaluate the declared horizon/input mix and service throughput or latency goal. Long lifetime alone says nothing about a particular cold function. Code growth, I-cache effects and memory/SLA constraints can override a positive average. |
| Self-hosted generations | Count the trusted producer's first build once, then the emitted compiler's executions for later generations. Once the relevant source/headers/options fixed point is established, repeated generations use the same binary; savings are recurring, not geometrically compounding. |

Eight exact rational arithmetic controls were executed locally with Python
`fractions.Fraction` to check the sign/equality cases. These are illustrative
inputs, not compiler or runtime measurements:

| Control (dC ms, D us) | N | Decision |
| --- | ---: | --- |
| +0.2, +0.4 | unknown | Abstain; frontier N>500 |
| +0.2, +0.4 | 500 | Baseline at equality |
| +0.2, +0.4 | 1000 | Candidate before other guards |
| +0.2, 0 | 10^12 | Baseline |
| -0.2, -0.4 | 100 | Candidate before other guards |
| -0.2, -0.4 | 1000 | Baseline |
| 0.7 extraction minus 0.5 avoided, 0 | 1 | Baseline |
| +0.2, -0.4 | 1 | Baseline |

All 8/8 expected decisions matched. Known N=0 evaluates compilation alone;
work/scratch/growth violations always retain baseline even at huge N.

Code growth, scratch, retained storage and process RSS are explicit constraints
or additional Pareto objectives. Do not invent milliseconds per code byte, or
double-count cache costs already included in measured R.

## Cheap facts and errors

| Existing fact | Appropriate use | What it cannot predict |
| --- | --- | --- |
| IR/MIR row, value, block and edge counts | Cost/storage scale and cap refusal | Runtime frequency or quality gain |
| Valid cached operand totals and published CFG populations | Bound work/reopening without building an analysis first | Freshness after mutation unless invalidated |
| Existing opcode summaries, type/effect/call constraints | Pass legality and some zero-opportunity exclusions | General arithmetic opportunities: only tracked rare classes are queryable |
| Baseline spill/reload edits and register classes | Current pin-planner opportunity | Dynamic memory cost or useful hotness |
| Existing loop spans/static frequency classes | Structural prioritization | Whether a loop runs, its trip count or invocations |
| Already required pressure/live-range facts | Scheduling/allocator opportunity | A guaranteed whole-program runtime benefit |

Do not allocate a dependency graph, alias model, use CSR or second IR merely to
decide whether to build it. New facts require a concrete consumer and charged
collection/invalidation cost. Direct-call table counts exclude indirect calls;
reuse the actual prepass CALL facts when needed.

A false positive wastes compile work and can increase runtime/code/RSS. A false
negative misses a measured improvement but saves compilation. Report both
time-weighted regret and per-workload harm, abstention rate, cap-hit counts and
prediction coverage, not just classifier accuracy. Project/family-level holdout
prevents near-duplicate functions leaking between tuning and validation. A
different target, register class, call/effect shape or scale is outside the
admitted domain until validated; use baseline rather than extrapolating.

## Deterministic bounded candidate policy

This is a research candidate, not a new default or a new `-O` mapping:

1. Retain the current baseline and every mandatory semantics/validation/ABI
   boundary. Preserve explicit allocator-option ordering.
2. Apply exact no-op proofs using facts already paid for. The sole new pilot is
   valid QUALITY core FAST baseline with spill_count=reload_count=0.
3. For any later optional positive-cost recipe, check legality, feature-cost,
   function work/scratch/retained/code-growth caps **before** constructing its
   analyses. Reuse current canonical limits; QUALITY needs a complete work bound
   in addition to its existing candidate/retry caps. No new QUALITY cap is
   adopted by this probe.
4. Choose baseline or one fixed, reviewed recipe in a fixed order. An offline
   admission record must bind source/target/feature class, measured cost and
   benefit bounds, holdouts and declared minimum lifetime. Unknown lifetime,
   missing record, nonpositive benefit lower bound, out-of-domain input or
   exceeded cap selects baseline. The current admission set for an additional
   generated-code recipe is empty.
5. Future module budgets use deterministic per-function allotments or stable
   canonical/source-order assignment. Never choose the first lane to claim a
   shared budget; never use elapsed wall time as fuel. Peak scratch accounts for
   concurrent lanes, shared data and retained TU storage. Merge counters by
   stable work index through the existing persistent lanes.

The pilot bounds its incremental decision work to two count comparisons and adds
no scratch. It does not establish a new whole-pipeline QUALITY bound: the
existing regions-times-values closure remains paid. It adds no learned model, no runtime optimizer
search, no speculative compile-and-run loop and no extra permanent data
structure. Every nonzero-traffic invocation keeps the existing policy. The
current 4096-candidate cap, eight spans/register and three retries bound some
QUALITY populations, but not all loop-closure work (`regions * values`).

## Counterargument and smallest useful packet

The same function and static facts can be called once or billions of times;
nonlocal layout changes can reverse a local benefit. Conservative abstention
therefore leaves real long-lived benefits unclaimed. This cannot be solved by
renaming an opportunity score hotness. The pilot avoids the issue only because
the current tail provably returns identical placement. Every nonzero-traffic QUALITY invocation pays the additional branch. Zero-traffic
incidence may be low, and changing trusted-producer source can alter host-code
layout systematically even when emitted object bytes match. Avoided per-function
work therefore does not establish an end-to-end saving.

The smallest implementation packet, if uninstrumented acceptance succeeds, is
one condition at the existing QUALITY baseline return, preservation of
`empty_candidate_functions`, focused copy/rematerialization/pressure/predicate
controls and guide updates. Retain wrapper/scheduler behavior. No pass manager,
allocator economics rewrite, hotness predictor or new optimizer is part of that
packet. Charge the gate and measure real workload incidence first under #125;
compare same-root trusted binaries with A/A, frozen counts and generated-byte
parity on the dedicated benchpress 9700X. Self-built performance is a separate
subject, not an alternative throughput host.
