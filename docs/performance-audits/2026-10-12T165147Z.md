## Why publication moves rows

Publication lays each block's rows out as one span, in block-ID order. Rows are
written in emission order. A row is out of place for one of two reasons:

1. **Block IDs follow creation, not emission.** A join block is created before
   the nested blocks of its arms, so its rows are emitted after theirs while
   its ID is lower. The whole block is contiguous, just in the wrong place.
2. **A block's rows are split.** At `-g`, `c_ir_ssa_restore_memory` splices
   LOCAL, LOAD and STORE rows back for the locals that stay in memory. They are
   appended to the end of the array and linked into the middle of a chain.

The counts below come from temporary counters added to
`ir_cfg_publish_instruction_rows` at the base revision, after its ownership
walk succeeded. They were not committed. At that point `inverse[k]` holds the
original ID of the row that publication places at `k`, and `blocks[b]` holds
block `b`'s published span. The definitions:

- **Moved:** functions where some row's ID changes (`moved`).
- **Split block:** a nonempty block whose span does not hold consecutive
  original IDs.
- **Pieces:** maximal runs of consecutive original IDs inside one block,
  summed over split blocks only.
- **Runs:** maximal runs of consecutive original IDs over a function's whole
  published order. A run can cross a block boundary, when a block's first
  original ID follows the previous block's last one.
- **Out-of-order block:** a nonempty block whose first original ID is below
  that of the previous nonempty block.

On SQLite `-c -g0 -O0`:

Runs and pieces count different things, and the totals reconcile. A function
has one run, plus one per break between adjacent published rows. Breaks
inside blocks number 22,172 − 4,857 = 17,315. The remaining 40,751 − 2,549
− 17,315 = 20,887 breaks fall at block boundaries. The other 40,208 − 2,549
− 20,887 = 16,772 block boundaries continue a run. The 8,400 out-of-order
blocks are a subset of the boundary breaks.

## Measured changes

1. **The reopen test is inline.** `ir_function_add_value`,
   `ir_function_add_block`, `ir_function_add_instruction` and the protocol
   edits called `ir_function_invalidate_cfg` out of line on every append. Only
   a published function needs any work. The test now lives in `ir.h`, and
   `ir_function_reopen_cfg` holds the reopen.
2. **Clearing `next` joins the permutation.** The permutation's index loop now
   also clears each row's `next` once the row is final. Every cycle starts at
   its lowest index, so a row is final when its index is visited. This removes
   one pass over every row.
