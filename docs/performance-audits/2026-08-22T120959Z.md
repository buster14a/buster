`2026-08-22T120959Z` (Linux x86_64, Zen 4 7940HS; **attribute the include
amplification per header, then drop guard-shaped re-includes unread**).
The SOURCE table has always carried the include amplification as a ratio —
this tree opened at 295 unique files / 27,23 MB against 448 lexed / 29,39 MB,
2,16 MB re-read across 153 re-inclusions — without saying which headers the
re-read bytes belong to. This audit adds the attribution to the compiler,
uses it, and closes what it names. Baseline reproduced first:
`test_self_host` at the byte-identical fixed point, stage 1 at
10.172.846.827 instructions.

**The attribution lives in the tree, not in a script.** The metrics file set
that already decides unique-vs-lexed (`c_source_metrics_file_row` in
`c_source.c`) now keeps one row per distinct path — lex count and one lex's
scanned bytes — and `-v` prints every file lexed more than once with the
bytes its re-reads added, largest first, plus a total that equals the two
aggregates' scanned-byte difference exactly. It is deliberately not the
token-carrying file table beside `map_entry`: that one is populated lazily so
token-free headers never enter the program's source map across hosts, while
attribution needs precisely the files that contribute nothing twice.

**What it said.** One in-tree file owned 47,9% of the re-read bytes: the
1.034.723-byte `aarch64-canonical-decoder.generated.h`, included by both
`aarch64_encoding.c` and `aarch64_semantic_vm.c`, lexed twice. Nearly all
the rest was glibc — `features.h` 31 lexes / 593.580 bytes, `bits/types.h`
35 / 299.404, `string.h`, `unistd.h`, thirty smaller `bits/*` files. And
every one of these, the generated header included, already carries a classic
whole-file `#ifndef` guard; the preprocessor just only recognized
`#pragma once`, so the guard kept the tokens out while the bytes were
re-read, re-translated, re-lexed and re-interned at every inclusion. That
settled the close: guarding in-tree headers with `#pragma once` would have
covered 48% and left glibc untouched, so the fix is the multiple-include
optimization, which covers both from one mechanism.

**The estimate, before the measurement.** Re-read material: 2.160.707
scanned bytes, 511.240 tokens (16,1% of all lexed tokens), 65.824 lines. At
the SIMD lexer's few instructions per byte plus per-token interning and the
inactive-line walk, the guess was 25–40 M instructions, ~0,3% of stage 1.

**The mechanism.** While walking an include frame the preprocessor proves
the guard shape: SEARCHING until the file's first top-level directive, which
must be `#ifndef NAME`; GUARDED inside that conditional; CLOSED when its
`#endif` returns to the frame's base; DISQUALIFIED by any token or directive
at the frame's top level outside it, an `#elif`/`#else` arm on it, or end of
file inside it. A CLOSED frame records path → interned guard symbol
(`CIncludeGuardTable`), and a later `#include` of a recorded path is dropped
unread while the symbol is a defined macro — one macro-table lookup, the
same suppression `#pragma once` takes, testable at every inclusion so an
`#undef` of the guard re-arms the header. Deliberately multi-section files —
the builtin `stddef.h`, glibc's `bits/wordsize.h`,
`bits/libc-header-start.h` — disqualify themselves by construction and keep
their re-reads, now 28.182 bytes in total where 2.160.707 stood. New
fixtures cover suppression, `#undef` re-arming, and a token after the
guard's `#endif`.

**Measured** on the same input (the patched unity `ide.c`) with the
clang-built Release `ide` before and after, eleven order-alternated
CPU-pinned pairs, outputs byte-identical on every pair and the preprocessed
token stream unchanged (2.938.453 tokens, 22.904.208 spelling bytes, both

    cycles                 +24.275.129  median       2/11   (not a demonstrated win; wall-clock noise dominates)
