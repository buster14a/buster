## Decision

Land the bounded producer/consumer fusion that the `2026-09-13T125911Z` audit
named opportunity 2 for #51. The paste-free, stringify-free, non-builtin arm of
`c_macro_replacement_tokens` staged a `CPpToken` array only for
`c_macro_materialize` to hand it to `c_macro_expansion_tasks_push`, which
reserved the batch and copied the same rows in reverse. The new
`c_macro_produce_plain_tasks` reserves that batch once and writes the rows in
place. Nothing else in the expansion engine changed: same task rows, same
LIFO order, same ENABLE marker, same context floors, same output nodes.

- **Preprocess-only (`cc -E`, measured).** Full-profile macro workload
  (16,384 definitions): base median 71.72 ms, candidate 62.64 ms, paired
  median **-9.01 ms (-12.7 %)**, candidate faster in **40/40** pairs.
  CI-profile macro workload: 9.58 -> 8.81 ms, **-0.90 ms**, 51/60.
  Tiny control: 1.754 -> 1.805 ms, paired median +0.012 ms, 48/100 (noise).
  The `-E` output was byte-identical for every input.
- **Whole compilation (harness, measured, guard disabled).** Full-profile
  `macros/none`: 442.64 -> 429.85 ms, **-2.83 %**, paired median -9.68 ms,
  IQR [-30.5, +6.5] ms, 28/40; peak RSS **388.38 -> 367.38 MiB**.
  CI-profile `macros/none`: 66.88 -> 66.02 ms (-1.81 %), 26/40,
  73.38 -> 70.75 MiB. `tiny_startup/none` +0.83 %/+1.16 % and
  `many_functions/none` -0.49 % are inside their IQRs (16-20/40).
  Every paired object was byte-identical (`--require-identical-output`).
- The whole-compile saving equals the preprocess-only saving (about 9 ms on
  the full workload); the rest of the pipeline is untouched. The wide
  whole-compile IQR is this VM's noise, not the change.

The RSS drop is the staging arrays: one `16 * N` byte arena block per plain
expansion, which lived until the translation unit's arena was released.

## Eligibility boundary and state model

`c_macro_materialize` now branches once:

1. `definition.pragma_like`: one pragma marker output node, no task batch.
   Its definition is empty and has neither operator, so the old plain arm
   produced a zero-length list and never diagnosed; skipping it is identical.
2. `!macro->builtin && !has_paste && !has_stringify`: set `macro->disabled`,
   then `c_macro_produce_plain_tasks`.
3. Otherwise (builtins, `#`, `##`, and every invalid replacement diagnostic):
   the unchanged `c_macro_replacement_tokens` then `c_macro_expansion_tasks_push`.

The direct producer is the old plain arm with the array replaced by the batch:

- **Size.** `plain_count + sum(parameter_use_count[i] * expanded_token_count[i])`,
  the same dot product the old arm allocated; empty replacements and empty
  arguments contribute zero rows. `c_macro_expansion_tasks_reserve` (the
  growth half of the old push, now shared) reserves that plus one ENABLE row
  before any write, so a batch is never split by a reallocation.
- **Order.** ENABLE at the batch base; substituted token `i` of `N` at
  `base + 1 + (N - 1 - i)`, written downward from the batch end. This is
  exactly what `c_macro_expansion_tasks_push` stores for the staged list, so
  the popping consumer, ENABLE processing and `macro->disabled` clearing are
  unchanged.
- **Fields.** Same stamp (`invocation.stamp & C_PP_STAMP_MASK`), `foreign`
  set, `no_expand` carried from the expanded argument token, argument spacing
  kept except the first token taking the parameter's spacing; definition
  tokens take `replacement_space`.
- **Lifetimes.** Arguments are already fully expanded (their child contexts
  and floors completed before materialization), so the producer reads only
  the definition and `argument->expanded_tokens`, never task storage. The
  batch pointer is taken after the single reservation and dies with the
  function; `tasks->count` is published after the last row. No other
  operation runs between reservation and publication.

## Limitations

- The paste path still stages `CMacroReplacementToken` rows and the
  stringify path still builds spellings; both remain candidates only if a
  later census shows they matter. Builtins stay staged (one row).
- The whole-compile gate was run with `--no-guard` because the workload
  selection is custom; the table above is diagnostic, not a guard verdict.
- No SIMD was added: the remaining producer work is a per-token copy with
  field updates and reversal, and the census does not justify vectorizing it.
