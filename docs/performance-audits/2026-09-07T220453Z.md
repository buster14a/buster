## Changes

### Scheduler macro hides repeated scans (#87)

`machine_schedule_queue_push` supplied `machine_schedule_queue_growth(...)`
directly to nested `BUSTER_MIN` / `BUSTER_MAX` macros. Their conditional
expressions can evaluate an operand repeatedly. The scan reads the same
unchanged unit, opcode roles and demand epochs each time; no mutation occurs
until after bucket selection. Cache its `s32` result once, then apply the
unchanged clamp and bucket offset. Capacity/overflow handling, sequence
numbers, list links, tie-breaking and queue ownership are unchanged.

This adds no API, callback, allocation, cache lifetime, or alternative
implementation. It removes redundant work rather than introducing a more
generic abstraction. The existing fixed 33-bucket queue is retained.

### Uninstantiated machine records (#45, partial)

Whole-source reference searches found `MachineAddress`, `MachineSegment`,
`MachineUse`, and `MachineLocationSegment` only in their declarations and
size assertions. There were no producers, consumers, allocations or
serialization of these records. Remove the four declarations and their
corresponding assertions; retain all checks for live machine/IR records.

Keep the numeric `MACHINE_REF_ADDRESS` tag reserved and explicitly documented.
Deleting it would renumber encoded references, an unrelated compatibility
change. `MachineEdit` and actual allocator storage remain untouched. The
benefit is a smaller, less misleading internal representation surface, not
an asserted RSS or allocation reduction. No external source-compatibility
promise is made for consumers of these removed internal declarations.

## Abstractions deliberately retained

- Compiler-source callback/vtable searches found no compiler dispatch
  framework to remove. The apparent cleanup callbacks and PE TLS callback
  fields describe the compiled program, not callbacks executed by the
  compiler. Test dispatch and platform entry points were not confused with
  compiler hot-loop indirection.
- Metadata-only scheduling is **not equivalent** at this revision. A census
  over all 236 machine opcodes found seven legacy memory classifications,
  five legacy barriers, and all 33 legacy vector classifications not covered
  by the corresponding metadata predicate. Copy/frame operations are among
  the gaps. Removing the compatibility switches would change ordering and
  membership constraints. No such switch was deleted.
- The declarative rule-context/selection entry points have test callers but
  no production target-selector callers. This is evidence for existing #42,
  not permission to delete shared canonical facts or activate an unvalidated
  new selection path in a small cleanup.
- Canonical and machine target paths still provide distinct allocator-mode
  coverage and differential oracles. Wholesale consolidation remains outside
  this patch. Packed `MachineRef` values, opcode accessors and scratch-arena
  boundaries express real invariants and ownership; none was replaced with
  raw pointers or generic containers.
- Other nontrivial MIN/MAX operands in preprocessor line scanning and object
  symbol/label lookup were inventoried, not automatically rewritten. Actual
  optimizing-compiler behavior and workload cost require separate evidence.

## Measurements and interpretation

Host: Intel Xeon Platinum 8573C VM, Linux x86-64, Clang 17.0.0; **not Zen 5**.
Five vCPUs are visible, with a four-CPU cgroup quota. Production Release uses
the repository's `-O2 -march=native -fwrapv -fno-strict-aliasing
-funsigned-char` policy. The isolated queue benchmark has no counter
instrumentation and does not force `noinline` on the growth scan.

In the **actual Release compiler**, `nm -S` reports queue-push text shrinking
from `0x13df` (5,087 bytes) to `0x5c1` (1,473 bytes). The isolated default-target
Clang object shrinks from 989 to 401 bytes. GCC 14.2 at `-O2` already reduces
the old helper to one growth scan, so the Clang result is not generalized to
all host compilers.

For timings, warm each executable, pin it to one vCPU, alternate A/B then
B/A pairs, and retain every sample. Workloads, cwd, flags and output paths are
identical between compilers. Report paired median after/before ratios with a
10,000-resample paired bootstrap interval, not a percentage inferred from
unpaired medians. Initial CPU-0 results were noisy; the larger workload,
CPU-2 real-source series and FAST control are separately named series, not
silent replacements or discarded outliers. Builds/tests had completed
before timing.

**The component result is credible; an attributable whole-compiler speedup
is not established.** The queue microbenchmark's paired ratio is about
0.342, or 65.8% less time. The QUALITY intervals include 1.0, and the FAST
control moves even though the edited scheduling path is QUALITY-only.
FAST's timing improvement must not be credited to this queue change; binary
layout and this VM's execution variability are possible confounders. The
patch is justified by removal of demonstrably repeated work and dead
representation surface, not a claim of an end-to-end compiler speedup.

All measured full-compilation outputs are byte-identical before/after.
The 256-function pressure corpus schedules and keeps all 256 functions;
real `machine.c` schedules and keeps 43 of 446. Both have zero backend
fallbacks. Checksums, sizes, CPU time, individual timings and commands are
in the raw JSON/log evidence.

GNU time measurements in the CPU-2 series avoid the inherited Python-fork
RSS floor present in the initial wait4-only pilot. Median peak RSS is
230,978 versus 231,072 KiB for 2,048 pressure functions, 106,616 versus
106,612 KiB for machine.c, and 894,938 versus 895,040 KiB for frozen unity.
There is no meaningful RSS improvement. No dynamic allocation-count change
was measured or claimed. `perf_event_open` for hardware cycles returns
ENOENT in this VM, so cycles, retired instructions and cache/branch events
are unavailable, not zero.

## Reproduction

All commands below are single lines, run from the corresponding checkout.
The bootstrap executable is outside `build/` because `generate` recreates
that directory. The PATH wrapper is an audit-host tool, not a source patch.

```sh
./build.sh test_self_host --config Release
clang -Isrc -Wall -Werror -Wno-unused-function -Wno-unused-variable -g build.c -o /tmp/buster-audit-build
/tmp/buster-audit-build generate --cc clang --ci --linker DEFAULT
cp /tmp/buster-audit-build build/build && /tmp/buster-audit-build build --config Release -t ide
PATH=/path/to/evidence/host-tools:$PATH BUSTER_TEST_JOBS=2 /tmp/buster-audit-build build --config Release -t test_all
/tmp/buster-audit-build test_self_host --config Release
/tmp/buster-audit-build test_mode_matrix --config Release
python /path/to/evidence/queue_probe.py . /tmp/queue-probe.c
clang -Isrc -O1 -g -fwrapv -fno-strict-aliasing -funsigned-char -ffunction-sections -fdata-sections -DAUDIT_COUNT=1 -fsanitize=address,undefined /tmp/queue-probe.c -Wl,--gc-sections -o /tmp/queue-probe
ASAN_OPTIONS=detect_leaks=0 UBSAN_OPTIONS=halt_on_error=1 /tmp/queue-probe
python tools/new_audit.py --check
```

The evidence bundle contains the extraction scripts, the uninstrumented
benchmark C sources, pinned A/B runner, raw JSON, output hashes, host facts,
source inventory, disassembly and test logs. Its README gives commands using
explicit baseline/candidate binary paths. No timing threshold or flaky CI
performance gate is added by this focused patch.
