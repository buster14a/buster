then spent their audits discovering that a symbol's share names the function and
not the line (`2026-08-22b`, `2026-08-22d`).  Zen 3 and later expose the AMD Last
Branch Record extension, so `perf record -j any,u` records the last sixteen
branches of every sample **with a per-entry mispredict flag** — the branch
instruction's own address, not a skidded sample landing somewhere after it.
`tools/branch_miss_survey.py` is that measurement, kept in the tree so the next
survey is a command rather than a method.

**Method.**  `tools/branch_miss_survey.py --repeat 3 --cross-check` over the
stage-1 self-host compile (`build/Release/ide cc … src/buster/apps/ide/ide.c`,

**The one trap this instrument has, and it is silent.**  A branch record is a
runtime address in a PIE.  Converting it needs the mapping's file offset *and*
the text segment's `p_vaddr - p_offset` skew, `0x1000` for a clang-built `ide` —
the same class of mistake AGENTS.md already records for `perf script -F dsoff`.
Dropping the skew shifts every address by one page and reports the neighbouring
functions with complete confidence: the first run of this survey put 3,08% of
all mispredictions in `c_parse_aggregate_lookup`, a function holding 0,01% of
cycles, which is arithmetically impossible at 13 cycles a miss and is what
exposed the bug.  Cross-checking the function ranking against a plain
`branch-misses:u` profile catches it; so does `--self-test`.

Four groups come out of that table, in the order their evidence supports.

**1. Two indirect dispatches are the largest single instructions in the
compile.**  `machine_x86_64.c:3977` is `switch (instruction->opcode)` in
`machine_x64_select_instruction`, and it compiles to one `jmp *%rdx` off a jump
table at `0x13613f3` — **429 K misses, 1,73% of the whole run's, from one
instruction**.  `c_gen.c:17651` is the same shape one layer up: `switch
(active->kind)` at the top of `c_ir_lower_frame_fallback`, 182 K.  Both are
BTB-limited indirect branches over a dense small enum, and both dispatch per row
of an input whose opcode mix is known before the loop runs — the
sortable-by-opcode / homogeneous-lane treatment the `2026-08-18` series applied
to the encoder is the shape that removes an indirect branch, not a cheaper
switch.  Neither has been tried.  Both functions carry more than their dispatch:
`machine_select_canonical_function_x86_64` is the largest single mispredictor in
the compile at 11,84%, and `machine_x86_64.c:4300`/`:4313` — the candidate-opcode
test and the operand loop of the prepass `2026-08-22e` built — hold another 1,5%
between them, which is that entry's own recorded lead ("pass A's per-row operand
scatter is now the function's largest mispredictor") measured from the outside.

**3. Three source-map binary searches mispredict by construction.**
`ir_source_region_position` (1,93%), `ir_source_map_position` (1,72%) and
`c_ir_token_source_range` (1,42%, whose own hot line is `ir_source_map_find`
inlined) together hold **5,07% of all misses, ~1,25 M**.  The hot lines are
`ir.c:160` and `ir.c:72`, both the `low`/`high` update of a bisection, and clang
emitted a real branch for them (`cmp %edx,(%rcx,%r8,4); jbe` at `0x126b50c`), not
a `cmov`.  A bisection step is a coin flip: this is the textbook branchless
rewrite, it is local, and it is the cheapest lead in this list.  Size the
population first as `2026-08-22e` insists — how many probes per lookup, and
whether the page bracketing above each loop already bounds most searches to one
or two steps.

`c_symbol_intern` 2,86% (its own probe line `c_source.c:2382` 1,25%, plus
