# Scope and disposition

Issue [#103](https://github.com/buster14a/buster/issues/103) found that the
scheduler remapped source line marks and then repaired their order with one
global stable insertion sort. A large arbitrarily reordered block could move
quadratically many marks. PR
[#385](https://github.com/buster14a/buster/pull/385), merged as
`48207b860c69921f5a88166918c9b8e70f05524a`, replaced that repair with:

- a single remap pass that returns immediately when the marks remain ordered;
- stable insertion sorting only inside bounded sixteen-mark runs; and
- an iterative stable merge of those runs using one temporary mark array that
  is rewound before the scheduler returns.

This audit closes the missing acceptance evidence rather than changing that
algorithm. Final publication is
`97f522fa58a3633a1b38d835b6b480c0d22180cd`, tree
`d2190c99b79f14e806a146808e702a91dd783cc3`. It adds a registered regression
through the real `machine_schedule_function` gate and a permanent diagnostic
at `tools/machine_line_mark_scaling.c`.

The exact historical baseline is #385's first parent,
`464774d8e88cb3c97c182685474fbab3fcfcfc00`, tree
`cf36816e3ed4f6ba0f624eb42086c53bffd2289e`. That revision still contains the
quadratic insertion sort. The current production scheduler is the one already
present on main `b7a0f87cb881e44298a77e956e38ccc821d6e93b`; the acceptance PR
does not modify it.

# Workload and correctness contract

For a requested power-of-two leaf count, the probe constructs one x86-64
machine block containing independent `MOV_RI` leaves followed by a balanced
`ADD64` reduction, a result move and `RET`. It publishes one source line mark
per machine instruction. Scheduling the consumers close to their producers is
strictly cheaper than retaining input order, so the accepted result heavily
permutes the block and necessarily executes line-mark remapping and repair.

Every timed iteration checks all of the following before its sample is
accepted:

- `machine_schedule_function` reports that it moved the block;
- every repaired mark has row `i` at output position `i`;
- the mark's original instruction id names bytes identical to the scheduled
  instruction at that output row;
- the borrowed input marks remain byte-for-byte in source order;
- more than half the rows moved; and
- every repetition produces the same 64-bit schedule hash.

The same benchmark source, SHA-256
`1a404075d3bd99633473f4e05145101dd4a42afb9ce57315ebbc3cd92eb36cc3`,
was compiled against each scheduler. Across every baseline/candidate sample,
row count, retained bytes, number of permuted marks, aggregate displacement and
the schedule hash matched exactly. Thus the timing comparison is between the
same scheduling decisions and stable source-location result, not merely two
runs that both exited successfully.

The registered 256-leaf regression exercises the same production entry. It
also schedules the same input twice, verifies deterministic instructions and
marks, verifies the input was not mutated, and computes the exact arena
position of the three retained output arrays. The test requires that any merge
scratch be fully rewound. A focused split Release execution passed 11/11
assertions. The pre-existing bounded helper differential retains duplicate-row,
terminal-row, ordered-input and aliasing cases against the former stable
insertion-sort oracle.

# Scaling result

Medians below are raw scheduler-call time. `ns/mark` is shown because a
non-quadratic repair should stop becoming more expensive per mark as the block
grows.

| Leaves | Marks | Pairs | Historical median | Current median | Speedup | Historical ns/mark | Current ns/mark |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 32 | 65 | 21 | 13,916 ns | 14,207 ns | 0.98x | 214.09 | 218.57 |
| 256 | 513 | 15 | 103,724 ns | 92,012 ns | 1.13x | 202.19 | 179.36 |
| 1,024 | 2,049 | 11 | 585,403 ns | 407,270 ns | 1.44x | 285.70 | 198.77 |
| 4,096 | 8,193 | 7 | 5,047,135 ns | 1,348,077 ns | 3.74x | 616.03 | 164.54 |
| 16,384 | 32,769 | 5 | 68,672,210 ns | 4,864,975 ns | 14.12x | 2,095.65 | 148.46 |
| 65,536 | 131,073 | 3 | 1,056,953,848 ns | 19,590,497 ns | 53.95x | 8,063.86 | 149.46 |

The 65-mark row is effectively neutral on this shared VM: the absolute median
difference is 291 ns and is not treated as a regression verdict. From 8,193
through 131,073 marks, current cost stays between 148 and 165 ns per mark while
the historical cost per mark grows from 616 to 8,064 ns. Quadrupling the large
workload therefore keeps current cost approximately proportional to input size
while the old repair approaches the expected sixteenfold growth.

The largest schedule moved 131,067 of 131,073 marks, with aggregate displacement
4,695,005,894 and hash `cc11d3be7cf5f7b7`. Both revisions produced those exact
values. End-to-end probe elapsed time, including its warmup and measured run,
was 2.12 seconds historically and 0.07 seconds currently.

# Memory and sanitizer result

At 131,073 marks, the scheduler retained 6,291,472 arena bytes in both
revisions. That is exactly the scheduled instruction array, scheduled virtual
register array and repaired line-mark array. The current merge requires one
additional temporary `MachineLineMark[131073]`, 1,048,584 bytes, only while the
marks are disordered; the registered test proves that storage is rewound before
return.

`/usr/bin/time -v` reported maximum RSS of 37,956 KiB historically and 38,888
KiB currently, a 932 KiB increase. Hosted-process RSS is page-granular and
noisy, but the increase is consistent with the one bounded temporary array and
there is no retained per-row auxiliary structure beyond the result already
required by the scheduler.

The complete 131,073-mark candidate probe also passed Clang ASan+UBSan with the
same permutation, displacement and hash:


# Conclusion

The real scheduler now has a permanent one-mark-per-instruction, heavily
permuted workload and a registered semantic regression. The repaired marks are
stable and deterministic, the production result retains no merge scratch, the
largest measured block preserves exactly the historical schedule, and current
large-workload cost is approximately constant per mark instead of growing
quadratically. Ordinary repository CI and Release self-host remain independent
merge gates for the final pull-request head; this audit does not relabel them as
part of the microbenchmark.
