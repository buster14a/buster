# Scope and source identities

Issue [#103](https://github.com/buster14a/buster/issues/103) identified a
quadratic worst case after accepted machine scheduling: source line marks were
remapped to their new rows and then globally repaired with stable insertion
sort. A large arbitrarily permuted block could therefore move `O(M^2)` marks.

PR [#385](https://github.com/buster14a/buster/pull/385), merged as
`48207b860c69921f5a88166918c9b8e70f05524a`, replaced that repair with:

- one remap pass and an immediate return when marks remain ordered;
- stable insertion sorting only inside bounded sixteen-mark runs; and
- iterative stable merging of those runs with one temporary mark array.

The exact quadratic baseline is merge parent
`464774d8e88cb3c97c182685474fbab3fcfcfc00`, tree
`cf36816e3ed4f6ba0f624eb42086c53bffd2289e`. The exact bounded-repair
candidate is the other parent,
`f4d7562fb20d7cdc587b68970435e28ec6c9c9da`, tree
`85f537869198a11f1787f74a635246ffacb5ba33`. Comparing the two parents avoids
attributing later scheduler or compiler work to this repair.

PR [#814](https://github.com/buster14a/buster/pull/814) does not change the
production algorithm. It adds a registered regression through the real
`machine_schedule_function` gate, the permanent diagnostic
`tools/machine_line_mark_scaling.c`, and this acceptance record. The isolated
evidence run used workflow head
`64ab1bbbd609d3efbb15874db7c559628b206eb4`, tree
`104b24afb29c8bd8f6b3f65901ecc811717fc589`. The temporary evidence workflow
removed itself after publishing its artifact and is not part of the submitted
diff.

# Correctness and path-coverage contract

The production-path workload constructs one x86-64 machine block containing a
power-of-two population of independent `MOV_RI` leaves, a balanced `ADD64`
reduction, a result move and `RET`. It publishes one source line mark per
instruction. The pressure-aware scheduler accepts a substantially cheaper
order, so the workload necessarily reaches accepted scheduling, heavily
permutes the block and executes line-mark remapping and repair.

Every measured schedule must satisfy all of these conditions before its sample
is retained:

- `machine_schedule_function` reports that it moved the block;
- every output mark has row `i` at output position `i`;
- the mark's original instruction id names bytes identical to the scheduled
  instruction at that row;
- the borrowed input instructions and marks remain unchanged;
- more than half of the instructions move; and
- every repetition produces the same 64-bit schedule hash.

The same benchmark source, SHA-256
`5b88f6bb256c35da09f676d3261df76b4c219daf6010be759ac98a2e7d747599`,
was compiled against the exact baseline, exact candidate and current PR head.
At every measured size, all three produced identical row count, retained arena
bytes, permutation count, aggregate displacement and schedule hash. Timing is
therefore compared only after proving the selected and emitted schedule is
unchanged.

The registered 256-leaf regression exercises the same production entry twice.
It verifies deterministic instructions and marks, exact mark-to-instruction
mapping, input immutability and the exact retained footprint of the three
result arrays. Its focused split Release execution passed 11/11 assertions.
The pre-existing helper differential independently compares the bounded repair
with the former stable insertion-sort oracle for empty, tiny, ordered,
reverse, nearly ordered, duplicate-row, terminal/out-of-range and partial-tail
populations. It also exercises output/scratch arena aliasing and verifies that
temporary scratch position is restored.

# Memory and production text

At 131,073 marks, both scheduler revisions retain 6,291,472 arena bytes: the
scheduled instruction array, remapped virtual-register array and repaired
line-mark array. A disordered bounded repair temporarily requires one
`MachineLineMark[131073]`, or 1,048,584 bytes (eight bytes per mark). Production
`scratch_end` releases the scheduler scope, the helper alias regression checks
its own scratch rewind directly, and the registered production-path test
requires the output arena to retain only the three result arrays.

`/usr/bin/time -v` reported maximum RSS of 37,956 KiB for the quadratic probe
and 38,800 KiB for the bounded probe, an 844 KiB increase. Process RSS is
page-granular and noisy on a hosted VM; the observed increase is consistent
with one approximately 1 MiB temporary array and does not show retained
per-mark state beyond the required result.

The exact parent sources were also compiled as separate `machine.c` production
objects with identical flags. Summing every `.text*` section produced 369,707
bytes for the quadratic baseline and 354,850 bytes for the bounded candidate:
-14,857 bytes (-4.02%). The candidate's extracted
`machine_schedule_remap_line_marks` symbol is 1,661 bytes. The
`machine_schedule_function` symbol changes from 13,605 to 13,692 bytes (+87).
Extraction can change compiler outlining and section layout, so the total
translation-unit reduction is reported as the measured object result rather
than attributed instruction by instruction. There is no production-text
increase in this exact build.

# Disposition

The representative workload reaches accepted scheduling with one mark per
instruction and heavily permuted rows. Stable source-location semantics,
selected instruction order and retained output are identical across the exact
quadratic parent, exact bounded parent and current head. The ordered fast path
stays inexpensive, the merge crossover is measured, scratch is bounded to one
eight-byte-per-mark temporary array, production object text does not grow, and
large-workload cost no longer exhibits quadratic scaling.

Ordinary repository CI, the end-to-end compiler throughput guard and Release
self-host remain independent merge gates for the final PR head. They are not
relabelled as part of this isolated microbenchmark; PR #814 must pass them
before merge.
