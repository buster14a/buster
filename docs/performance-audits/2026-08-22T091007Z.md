**Sizing first, as `2026-08-22e` insists.**  Probe counters on both walks over
one self-host compile:

So the spans reaching the loop are short: a mean of 13,7 keys for the region
search and 4,24 checkpoints for the other.  **That is what makes a 16-lane
compare the right shape** — one vector answers the whole span, and the count of
lanes whose key is `<= probe` is the distance from `low` to the answer, because
a non-decreasing array puts those lanes in the low run of the mask.  A masked
load supplies the short spans so nothing is read past the array, and the region
keys are `{start, source}` pairs, so their compare uses every other lane
(`0x5555`) instead of a permute — 8 useful lanes of 16, which the measurement
still pays for.

**The scalar branchless bisection was measured first, and is not the answer by
itself.**  Rewriting both loops so the step is a masked add rather than a
branch: **+5.434.636 instructions (+0,0531%, 0/15)**, branches -1.764.422,
branch misses **-581.252 (-2,30%, 13/15)**.  Real, and it buys about half of
what the vector answers, but it pays for it in retired instructions.  It stays
in the tree as the tail of the vector path (spans above one vector) and as the
whole search where `BUSTER_SIMD_512` is off, so no target regresses to the
branchy form.  Two things about writing it are worth keeping:

- **Clang refuses to leave a bisection branchless if the select is spelled as a
  select.**  Both `low = keys[probe].start <= offset ? probe : low` and
  `low += half & (u32)-(s32)(keys[probe].start <= offset)` if-convert straight
  back into a `ja` over a `mov`.  The mask has to come out of the *sign bit of a
  subtraction* — `half & (u32)(((s64)keys[probe].start - (s64)offset - 1) >> 63)`
  — before the branch stays gone.  The subtraction is done in 64 bits so two
  `u32` operands cannot wrap into the sign.  Check the disassembly for `ja`
  after touching either loop.
- Stepping `low` forward by half the remaining span, instead of moving `low` or
  `high` to the midpoint, is what leaves one assignment to predicate.  The two
  forms return the same index for every non-decreasing array, verified
  exhaustively over every array of up to nine keys and every entry bracket.

**What the two operations cost to add.**  The checklist in
`2026-08-20a`/`project_simd_dword_vocabulary` is right as far as it goes — IR op
plus shape/name/validation, builtin table, `c_symbol_predefined`, canonical
lowering, machine selector and exact form, `simd.h` ×3 plus fallback,
`simd_test.c` and `tests/basic_c_simd.c` — and it misses the same class of spot
twice more.  A new *exact-form family* also needs, all hand-maintained and all
fail-closed rather than loud:

- `MACHINE_X86_64_EMIT_REGISTRY_COUNT`, `_FAMILY_COUNT` and
  `_EXACT_FORM_COUNT` in `machine.h`, and the two census counts in
  `machine_test.c` that mirror them;
- **a plan id**: `MachineX64ExactPlanId` plus its row in
  `machine_x64_family_exact_plan_id_by_recipe`.  Without it the new family index
  silently maps to plan 0, whose key belongs to another recipe, and the row
  fails the exact-map audit with `plan_valid=0` and no indication of why.  That
  was the one failure in this work that needed a temporary print inside
  `machine_x86_64_exact_map_audit` to locate.

`vpcmpud` also needed a new operand kind.  The vpcmp family selects its variant
with the machine payload, and `MACHINE_X64_EXACT_OPERAND_IMMEDIATE_CONSTANT`
emits that same payload as the immediate — which works for `vpcmpub` only
because its variant index (1) happens to equal the unsigned-less predicate.  The
dword compare is variant 4, so `MACHINE_X64_EXACT_OPERAND_IMMEDIATE_LESS`
carries the predicate instead.

Form keys were derived with the recipe the memory records — a temporary
`buster_x86_metadata_select_form` call at the end of the shape-cache prewarm,
printing `{status, form_id, stable_hash}`: `VPBROADCASTD zmm, r32` =
`{7534, 0xf65793e9357098c7}` and `VPCMPUD k, zmm, zmm, imm8` =
`{7550, 0xbd651626b11cf5bf}`, both status 19.  **Declare the family entry's
features exactly as the probe queried them** (`avx512f`+`avx512bw` here); the
prepared plan is matched on the key the features select.

**One number left on the table.**  A throwaway version of the same kernel
written directly on `_mm512_maskz_loadu_epi32` + `_mm512_mask_cmple_epu32_mask`
measured **-16,8 M instructions** against the same baseline, 5,6 M better than
the vocabulary version, because a masked compare does in one operation what
`simd512_less_word` plus a mask AND plus the strict-to-inclusive complement do
in three.  A `less_equal_word` taking a lane mask would recover it; it is not
worth a third operation for this call site alone, and the note is here so the
next dword-vocabulary consumer can decide with the number rather than without
it.
