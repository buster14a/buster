`2026-09-27T155317Z` (Linux x86_64, 4-vCPU KVM Xeon (Emerald Rapids) @ 2.1
GHz, Clang 18.1.3; **whole-project cost structure: per-process floor, repeated
headers and generated-code volume dominate real multi-file builds; one
prototype shape silently disables FAST for a whole TU**).

## Decision

No production change. This is a diagnostic census of workload *shapes* that
the stage-1 unity self-compile cannot see, taken to rank architecture-scale
opportunities. The synthesis and ranked proposals are in
[`docs/quantum-leap-research-2026-09-27.md`](../quantum-leap-research-2026-09-27.md).
Four results carry the ranking:

1. **In a per-file build of a real project, most time is not spent on the
   file's own code.** Lua 5.4.8 compiled one `ide cc -c` process per file:
   57% fixed per-process floor, 21% re-processing shared headers, 7% the
   file's own frontend work, 15% backend and object writing. One process
   compiling the same 33 files is 2.7x faster serially; a header-heavy
   five-line Python extension spends ~97% of its time on headers and table
   preparation and is no faster than Clang -O0.
2. **The in-process multi-TU path does not yet scale.** `-fcompile-jobs=4`
   (0.44-0.50 s) is no faster than four independent processes (0.43 s),
   with 2.1-2.4x the RSS and ~3x the system time of `-fcompile-jobs=1`.
3. **The backend emits ~2.6x the machine instructions of Clang -O0 and its
   code runs ~1.8x slower than Clang -O0** on an SQLite workload. Every
   downstream stage (allocation, encoding, line tables, relocations, object
   bytes) processes that volume.
4. **One declarator shape disables the FAST canonical pipeline for an entire
   translation unit.** A function returning a function pointer that also has
   a prior prototype fails canonical `RETURN_TYPE` validation; the
   `ir_prepare_canonical_module` "decline as a unit" policy then skips FAST for
   all 2,548 SQLite functions. Removing the shape restores FAST: -10.5%
   canonical instructions and -7.6% `.text`, compile time unchanged.
5. **A one-pass compiler is ~5x faster on the same inputs and its code runs
   faster.** TinyCC 0.9.27 compiles the same SQLite amalgamation in
   0.17-0.19 s with 18 MB peak RSS (Buster: 0.89-1.07 s, 257 MB at `-g0`),
   the 33 Lua files one process each in 0.30-0.31 s (Buster: 1.39-1.55 s),
   and its SQLite build runs the workload in 1.31-1.37 s (Buster: 2.12-2.24
   s). TinyCC validates far less and emits no DWARF, so this bounds what the
   current pass structure costs rather than setting a target to copy.

## FAST declined for a whole TU

`-v` on SQLite prints `IR_FAST functions=0 validation_skips=1`, while the
self-compile prints `IR_FAST functions=5205 validation_skips=0`.
`-fverify-codegen` names the cause: `canonical C IR validation failed:
boundary canonical input, error 7, function 671 ('sqlite3OsDlSym')` (error 7
is `IR_VALIDATION_RETURN_TYPE`); `memdbDlSym` has the same shape. Minimal
reproducer, rejected under `-fverify-codegen`:

```c
static int (*pick(int))(int);
static int twice(int x) { return 2 * x; }
static int (*pick(int which))(int)
{
    return which ? twice : 0;
}
int run(int v) { return pick(1)(v); }
```

Removing the prototype, or spelling the return type through a typedef,
validates. Rewriting SQLite's five such declarators through a typedef (on the
preprocessed text) makes `-fverify-codegen` pass and FAST run on all 2,548
functions:

| SQLite `-c -g0` | FAST declined (as shipped) | FAST applied |
|---|---:|---:|
| Canonical instructions into codegen | 353,699 | 316,675 |
| `.text` bytes | 2,611,486 | 2,412,378 |
| Allocator spills / reloads | 64,226 / 54,697 | 60,144 / 52,806 |
| Wall, three runs | 0.77-0.89 s | 0.79-0.91 s |

No open issue matched a search for this validation shape or for the
module-wide decline; they were filed afterwards as
[#1601](https://github.com/buster14a/buster/issues/1601) and
[#1602](https://github.com/buster14a/buster/issues/1602).

## Reference compiler: TinyCC 0.9.27

No TinyCC source or Linux binary was reachable, but the `pytcc`
0.9.27.1.1 manylinux wheel (CPython 3.10 extension) exports the whole
`libtcc` API. A 41-line C harness, retained as
[`tccdrv.c`](evidence/2026-09-27T155317Z/tccdrv.c), loads
`libpython3.10.so.1` for the extension's unresolved Python data symbols, then
drives `tcc_new`, `tcc_add_sysinclude_path` (the wheel's `tcc-rtlib/include`,
then `/usr/local/include`, `/usr/include/x86_64-linux-gnu`,
`/usr/include`), `tcc_define_symbol`, `tcc_set_output_type(TCC_OUTPUT_OBJ)`,
`tcc_add_file` and `tcc_output_file`. The harness's own cost is inside the
3 ms empty-file time below. TinyCC objects were linked by GCC with the
wheel's `libtcc1.o`, `alloca86_64.o` and `va_list.o`.

| Same input and flags | TinyCC 0.9.27 | Buster |
|---|---:|---:|
| Empty file to object | 2.8-3.0 ms | 20.8-23.2 ms (one run 40.6 ms) |
| SQLite `sqlite3.c`, `-g0` | 0.17-0.19 s, 18 MB | 0.89-1.07 s, 257 MB |
| SQLite `sqlite3.c`, `-g` (TinyCC: stabs) | 0.17-0.20 s, 20 MB | 0.96-1.23 s, 287 MB |

All four SQLite CLIs (Buster, TinyCC, Clang -O0/-O2) printed the same
workload output (MD5 prefix `5b562d33cef7`). TinyCC does much less semantic
validation, has no SSA or verifier, and its `-g` is stabs; the comparison
sizes the cost of Buster's pass structure and memory footprint, not a
like-for-like feature set. The attribution question is tracked in
[#1605](https://github.com/buster14a/buster/issues/1605).

## Reachability

`clang -O0 -ffunction-sections -fdata-sections` of the self-host unity TU
linked with `lld --gc-sections --print-gc-sections` removes 12 of 4,447
functions. Whole-program pruning before code generation has essentially
nothing to remove on this workload; the existing internal-function
reachability pass already covers the rest.

## Compatibility observations on `ade6ac4`

Hit while preparing inputs, all already tracked:

- SQLite 3.50.4 with `-DSQLITE_ENABLE_MATH_FUNCTIONS`: `could not lower
  initializer expression for local 'aBuiltinFunc'` from function pointers
  stored in `void *` fields (`MFUNCTION(ceil, 1, xCeil, ceilingFunc)`), and
  sqlean's `sqlite3_auto_extension((void*)f)` is rejected — #1397 / #1414.
- Lua 5.4.8 `ltablib.c:304`: `could not lower call to 'sort_comp'`. The
  shape is any call as the right operand of a comma used as an `if`,
  `while`, `for` or `do` condition (`if (g(i), h(i))`) — the #1421 family.
  Lua 5.4.8 is the version the Lua harness pins.
- Buster ELF objects carry no `.note.GNU-stack`, so a GNU ld link of them
  produces an `RWE` `GNU_STACK` — #1237.

## Limits

No acceptance host, no A/B pair of compilers, no PMU counters. The sampler
cannot see time outside `ITIMER_PROF` accounting, and its shares carry
sampling error. Lua's preamble extraction failed for four files, which are
excluded from the split table only. The SQLite and Lua versions differ from
the harness pins for SQLite (3.53.4) and match for Lua. No sanitizer,
self-host fixed-point, mode-matrix or harness gate was run; the tree was not
modified.
