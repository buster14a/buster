## Census method

The census build changes no answer. Its `-c` objects are byte-identical to
the base's in both arms (`-g0` `7102b68d95125e0e…`, 30,581,312 bytes). It:
- counts every `c_ir_group_type_name` and `c_ir_query_group_type_name` call by
  outcome: memo hit, gate refusal (`c_ir_group_may_be_type_name`), probe
  positive, probe negative;
- counts every `TYPE_NAME` frame attempt (`c_ir_type_name_internal_attempt`)
  by outcome, by its first token's class and by the frame that requested it;
- checks each answer against the tree, which the driver hands to the census
  through a global: is there a `TYPE_NAME` node whose anchor is the probe's
  first token?
- routes every probe and attempt through a `noinline` wrapper chosen by the
  outcome, so Callgrind's inclusive cost splits the work by outcome. Outcomes
  are deterministic, so a recording run writes them in call order and a
  replay run under Callgrind picks the wrapper before the call. The replay's
  counters equal the recording's.

## What a tree answer could still remove

A tree answer is "negative when no `TYPE_NAME` node is anchored at the probe's
first token; otherwise run the probe". Without the gate above it covers every
negative row: about 49 M of attempts, plus request and resume overhead. After
the gate, the token test has already answered the literal, `sizeof`,
punctuator and number rows, and the tree adds only the identifier rows:
- unbound identifiers: 16.8 M of attempts, plus about 240 Ir per request
  (the gate probe's saving less its attempts, over 53,653 requests), so about
  18 M;
- bound identifiers whose start has no `TYPE_NAME` node: at most 7.1 M;
- group probes that the gate keeps: 1.0 M.

That is a ceiling of about 26 M (0.11% of B) before the tree index is paid
for. A per-unit bitmap of `TYPE_NAME` anchors costs a scan of the kinds
column (2.78 M bytes) and 523 KB. Positive answers stay with the probe: the
probe parses the type, and a tree answer would have to produce the same IR
type.

## Typer facts: retain or recompute

The typer's per-node arrays are body scratch in analysis and are gone before
lowering. On this input:

| Quantity | Value |
| --- | ---: |
| tree retained bytes (`C_AST retained_bytes`) | 36,095,358 (8.63 B per token) |
| nodes typed / accepted (`C_AST_TYPES`) | 1,260,275 / 1,116,391 |
| retain a dense `u32` type column over the tree | 11,106,264 B (+30.8%; 11.29 B per token in all) |
| retain accepted nodes sparsely (`u32` node, `u32` type) | 8,931,128 B (+24.7%) |
| retain `TYPE_NAME` anchors only (55,886 × 8 B) | 447,088 B (+1.2%) |
| recompute in lowering: the eager pass, `c_ast_types_type_body` in B | 329.9 M Ir (1.44% of B) |

Recomputing costs more than all of row 7's removable work (the 26 M above,
the 413.6 M `c_ir_query_execute` is mostly real evaluation), so it is
rejected. Retaining fits the 16 B per token budget, but no lowering consumer
measured here reads a per-node type: the negative answer needs only
`TYPE_NAME` anchors, which the kinds and tokens columns already hold, and a
positive answer must reproduce the probe's IR type. The decision is recorded in
[ast.md § Storage and lifetime](../agents/frontend/ast.md#storage-and-lifetime).
