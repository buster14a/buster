## Hypothesis and bounded prototype

At c_parse.c:982, `c_parse_diagnostic` validates capacity, increments the count and appends an unchanged CDiagnostic. The file has 88 textual call sites plus its definition. CSourceLocation contains five u32 fields, so an out-of-line call must also handle a 20-byte aggregate argument.

Hypothesis: producer inlining duplicates cold append/validation work in the historically hot type-parser state machine. Outlining only that body might improve instruction delivery. Strongest alternative: these tails already lie outside frequently fetched paths; repeated parse-state copies, data loads, branch recovery or startup/system work are the limiting costs. A final diagnostic count of zero does not distinguish those cases because speculative parsing can append and roll back diagnostics.

`tools/ifetch_census.c` provides four variants:

- A: unchanged Release binary.
- Q: separate population-only binary, private AtomicU64 increment at helper entry and one report after compilation joins. Counts attempts, including speculative ones. Never used for timing.
- N: `__attribute__((noinline))` on only this helper, ordinary ABI.
- C: `BUSTER_COLD` plus that noinline attribute, ordinary ABI.

The helper body, storage and callers' source logic are unchanged. Every temporary mutation is exact-anchor checked. Builds are serial in one configured root; original source bytes are restored before any compiler consumes the workload. Same input/output paths, source metrics path, generated headers and debug contract are used throughout. C versus N is not a pure placement control: cold also changes branch probabilities and optimization decisions. These are Clang diagnostic prototypes, not portable production patches.

## Hardware evidence, competing explanations and research

The old #1438 checkpoint reports 33.7% frontend-bound dispatch slots, memory pressure, bad speculation and approximately 52.7 million L1I misses on ade6ac4b with Clang 22.1.8. It is historical, not a verified current-source attribution; no speedup or bottleneck percentage is transported. Its approximately 21.4 MB generated code is not the trusted compiler's own text size.

Primary references were checked before interpreting those claims:

1. [Linux perf Zen 5 pipeline definitions](https://raw.githubusercontent.com/torvalds/linux/master/tools/perf/pmu-events/arch/x86/amdzen5/pipeline.json): total slots = 8 * non-halted cycles. Frontend-bound counts unfilled dispatch slots, not recoverable wall time. Its latency/bandwidth split is not an independent I-cache-capacity measurement.
2. [AMD uProf 5.3 IBS derived events](https://docs.amd.com/r/en-US/57368-uProf-user-guide/7.9.3.2.4.-IBS-Derived-Events), June 17, 2026: attempted, non-killed fetch samples are the denominator; completed fetches can be wrong-path, aborted fetches bound only part of speculative waste. Average fetch latency is not total stalled cycles. Do not combine ordinary event-sample and IBS-sample counts arithmetically.
3. [Linux perf-amd-ibs](https://raw.githubusercontent.com/torvalds/linux/master/tools/perf/Documentation/perf-amd-ibs.txt): ordinary sampling has skid, IBS gives precise sampled IPs. Validate installed formats/permissions; Zen 5 swfilt and Zen 6 fetchlat/hardware-filter examples are not interchangeable. Retain periods, lost samples and raw registers.
4. [LLVM HotColdSplitting](https://llvm.org/doxygen/HotColdSplitting_8cpp_source.html): profitability prices arguments, outputs, reloads and multiple exits. This is methodological precedent, not imported code or evidence of what Clang 18 emitted.
5. [Pepi et al., Exposing Shadow Branches](https://arxiv.org/abs/2408.12592), 2024 preprint / Skia ASPLOS 2025: branch-target misses and fetch-directed prefetching interact with cache pollution. No paper speedup is transferred to Buster or Zen 5.

The hosted VM exposes no cpu, ibs_fetch or ibs_op PMU; perf_event_paranoid is 4. No hardware events were accepted or synthesized. #1597's zero accepted cycle/instruction samples are unavailable evidence, not zero work; its watchdog/multiplexing explanation remains unverified without raw scheduling fractions.

The latest #880 closure records service dispatch disabled and leaves performance-recipe/ChatGPT-client work outside the smoke qualification. This session had no approved 9700X execution route. That does not mean the physical machine was offline. No SSH/runner bypass, watchdog change or acceptance-threshold relaxation was attempted.

Consequently this packet cannot rank current instruction delivery against data-cache misses, dependency latency, mispredictions or OS overhead. The strongest alternate mechanism is retained parse-state/data work and branch recovery, with startup/system effects especially on tiny inputs. The source still copies CParseResult at c_parse_expression_type_query; existing owners cover that work. Counters or aggregate text size alone cannot eliminate those alternatives.

A larger binary could still have a smaller hot working set: absence of the deciding measurement is not a proof of no benefit.

Accepted here: exact identities, bounded diagnostic attempts, removed inline instances, emitted sizes and stack reservations, secondary inlining, output equivalence, focused correctness and binary reproducibility. **Unmeasured:** 9700X runtime, retired instructions, fetch stalls/working set, data-cache stalls, dependency latency, misprediction, OS costs, peak RSS and runtime noise. **Not run:** full test_all, registered self-host, sanitizer/Debug/non-unity/supported-host matrices, alternative allocator modes and dense-error populations.
