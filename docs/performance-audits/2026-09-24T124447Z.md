Clang 21.1.8; **C frontend lookup-growth census and scalar counterexamples**).

## Decision

**No production optimization is proposed by this investigation.** Three
lookup mechanisms have demonstrable synthetic amplification, but they do not
establish a valuable whole-compiler optimization on the measured real inputs.
This is a bounded rejection of these leads as immediate implementation work,
not a claim that the mechanisms are linear, universally cheap, or impossible
to improve.

The strongest remaining observation is important: SQLite does execute
**2,368,721 qualified-type visits**. The instrumented routine totals a median
**2.948 ms** during an **840.476 ms** instrumented compile (about **0.351%**).
The complete routine includes validation, lookup and creation; the measured
share is neither a proven uninstrumented upper bound nor a promised saving.
A one-entry scalar replay would skip 38.1% of its visits, not all of them.
In self-compilation, the same routine examines only 247 entries despite the
final 48,836-type population. The other two probed lookup sites have zero
calls on all five real translation units in this capture.

No production cache, IR field, optimization switch, benchmark policy,
required check or parent-issue status is changed. No #36 work is performed.
The deliverable is the executed experiment, exact work models, counterexamples,
raw evidence and an offline replay check. A synthetic operation-count win is
not being promoted to a compiler-throughput win.

For a future implementation, qualified-type lookup must preserve invalid and
unresolved-layout retries, atomic layout promotion, GNU exact-layout access
views, and the earliest qualifying canonical ID. A cache cannot retain raw
pointers across type-table relocation, share mutable state between TUs, or
inject C identities into canonical IR. Constant lookup cannot cache a mutable
initializer result indiscriminately. Runtime-symbol lookup cannot bypass an
existing incompatible declaration's diagnostic. This experiment changes none
of those semantics: every diagnostic query still executes the original code.

## Exact growth and falsification populations

N is one of 0, 64, 256, 1024; Q is one of 1, 16, 64, 256. The following are
**actual counts**, not fits to wall-clock samples. The offline replay checks
all 64 grid points against the original captured records.

### Qualified types: eliminate the confounding function population

The first family puts N unrelated `struct PadNNNN { int x; };` declarations
before Q functions, each returning `__atomic_load_n(p, 0)`. Q function types
also grow the canonical table, so its exact model is
`visits = Q * (N + Q + 27) - 1`:

| N / Q | 1 | 16 | 64 | 256 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 27 | 687 | 5823 | 72447 |
| 64 | 91 | 1711 | 9919 | 88831 |
| 256 | 283 | 4783 | 22207 | 137983 |
| 1024 | 1051 | 17071 | 71359 | 334591 |

The follow-up keeps **one function** and repeats the load Q times inside it:

```c
/* Emit N distinct struct PadNNNN { int x; }; declarations first. */
unsigned f(unsigned *p)
{
    unsigned x = 0;
    /* Emit Q copies of the next statement. */
    x += __atomic_load_n(p, 0);
    return x;
}
```

Now the measured canonical population is exactly N+29 and the entity count
is always 3, independent of Q. The first lookup examines N+27 entries and
creates the type; subsequent lookups examine N+28. Therefore
`visits = Q * (N + 28) - 1`:

| N / Q | 1 | 16 | 64 | 256 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 27 | 447 | 1791 | 7167 |
| 64 | 91 | 1471 | 5887 | 23551 |
| 256 | 283 | 4543 | 18175 | 72703 |
| 1024 | 1051 | 16831 | 67327 | 269311 |

At Q=256 the object is 6,736 bytes and byte-identical across all N values.
Thus the additional N-dependent scan work is not necessary output growth.
Input/type parsing still necessarily grows with N; this experiment does not
attribute that work to the lookup or subtract it from elapsed compile time.

Prepending `_Atomic(unsigned) early;` before the same 1,024 padding structs
reduces the count to **5,719** visits despite the same 1,053 canonical types.
A plain-load control produces no qualified-type calls. First-match position,
not the final whole-ID-space population, is the relevant multiplier.

### Constant-global lookup

The family emits N ordinary globals, `const int needle = 7;`, and Q functions
returning `__builtin_constant_p(needle + 1)`. Each entity scan and each global
scan examines exactly `Q * (N + 1)` entries:

| N / Q, for each of the two scans | 1 | 16 | 64 | 256 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 1 | 16 | 64 | 256 |
| 64 | 65 | 1040 | 4160 | 16640 |
| 256 | 257 | 4112 | 16448 | 65792 |
| 1024 | 1025 | 16400 | 65600 | 262400 |

At N=1024/Q=256 this is 524,800 total visits. Moving `needle` before the
unrelated globals reduces each scan to 256 visits, or 512 total. This grid
varies the unrelated population and query count independently, but E and G
grow together; it does **not** establish a separately varied E/G response.
Because all real-input calls are zero, a more elaborate E/G study or index
implementation was not justified for this packet.

### Runtime imports: the first reproducer did not reach the candidate

The initial family used ordinary `__int128` division. All 16 inputs compiled,
but none called `c_ir_emit_runtime_call_source`. That **falsifies the proposed
input-route hypothesis**, not the compiler and not the existence of the scan.
It is not counted as positive evidence about frontend runtime-import cost.

The corrected family emits N globals and one function containing Q copies of
`x += __c11_atomic_load(p, __ATOMIC_RELAXED)` for an `_Atomic(unsigned __int128)`
pointer and unsigned wide accumulator. With CX16 disabled, the frontend
runtime helper is reached exactly Q times. Its first search examines N+1
symbols; reuse examines N+2. Actual symbol visits are `Q * (N + 2) - 1`:

| N / Q | 1 | 16 | 64 | 256 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 1 | 31 | 127 | 511 |
| 64 | 65 | 1055 | 4223 | 16895 |
| 256 | 257 | 4127 | 16511 | 66047 |
| 1024 | 1025 | 16415 | 65663 | 262655 |

Enabling CX16 for the Q=256 control gives zero frontend runtime-helper calls.
Unlike unused struct padding, N emitted globals necessarily grow the object;
the claim is the avoidable product of lookup requests and symbol population,
not that all N-dependent compile work or output should disappear.

SQLite must not be hidden behind the other workloads' near-zero counts. Its
queries are volatile qualification, not atomic qualification. There are nine
distinct queried keys, 824 existing-type hits and 13 invalid/retry results
with zero visits. A scalar observer only updates on a valid result; caching
failed lookups would be a different and unproved algorithm.

The one-entry alternative remembers `(base ID, atomic, volatile) -> result ID`
and replays the actual stream while still executing the reference. Its
predicted successful hits return the same IDs in every observed query:

| Population | Actual visits | Visits the one-entry replay could skip | Remaining visits |
| --- | ---: | ---: | ---: |
| One body, N=1024/Q=256 | 269311 | 268260 | 1051 |
| Same padding, alternating two base-type keys | 269822 | 0 | 269822 |
| Frozen unity | 247 | 200 | 47 |
| SQLite | 2368721 | 903390 | 1465331 |

This is a counterexample to treating a last-value cache as a solution to the
unwanted asymptotic growth: alternating keys preserve the scan cost. SQLite
also leaves 61.9% of visits untouched. The replay is **not** a tested cache
implementation, a memory/lifetime proof, or a measured 38.1% speedup. A full
index would need additional state, maintenance and correctness evidence;
none is introduced to optimize a sub-millisecond-to-few-millisecond lead.

## Validation and limitations

**PASS:** initial hosted workflow; 112/112 compilations and 56 paired object
identities; existing baseline `test_self_host --config Release`, including
byte-identical 46,281,120-byte stage1/stage2 fixed point; follow-up hosted
workflow; 378/378 compilations; all repeated outputs within each of 93 cases
have one identical object hash; 88 generated-input Clang syntax checks; all
64 exact work-model grid points; all 56 shared counter populations across the
two captures; per-query totals and scalar ID replay; artifact/member SHA-256
checks; offline replay rejection of missing observations, altered object
identity, altered counters and a scalar mismatch; `new_audit.py --check` (zero problems), its self-test,
and Python syntax compilation of the archived scripts/replay.

**FAIL (hypothesis, not compiler):** ordinary i128 division as a reproducer
for the frontend runtime-import helper. Replaced with the verified atomic
route; the failed hypothesis remains in the evidence.

**NOT RUN:** a production optimization; uninstrumented optimized A/B;
ordinary `bench_throughput` performance acceptance; 9700X/PMU/RSS experiments;
full `test_all`, sanitizer, Debug/non-unity/all-target matrix; external
library execution oracles; post-change self-host for an optimized compiler.
No production compiler change exists to claim those gates against. The
baseline fixed point does not validate hypothetical cache code. Hosted counts
and object equality are not universal semantic/diagnostic equivalence proofs.

This narrows the next search without creating another assignment: total
canonical type count is a poor predictor of this cost in unity; the two
other lookup sites cannot explain its measured lowering time; SQLite retains
a small real volatile-qualification lead, not an accepted optimization.
Existing semantic attribution ownership (#1028) remains untouched. Reopening
these leads should require a real workload with a larger attributable cost,
or an actual minimal implementation with matched uninstrumented evidence;
the synthetic NQ formula alone is not enough.
