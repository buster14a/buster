## Scope and implementation

Baseline `fe892a803737d0debcbabdb94403e472f1f84967` rejects ordinary Clang
AArch64 ELF ADRP/ADD references with object error 2. Candidate
`c85ab3222bad15d79fa51144de79e4be6625e9d5` (tree
`10d4cc99ce74e0adf7283514af67b83c9647724e`) implements the focused gap in
GitHub #355. This is a compatibility repair, not a generated-code optimization.

Object relocation kinds preserve ordinary ELF page/high and ADD/low identities.
The reader validates the instruction and site before clearing its immediate,
retaining RELA's explicit addend or REL's instruction addend. AAELF64's REL
ADRP addend is an unscaled signed 21-bit literal; its architectural displacement
is page scaled. The shared A64 decoder and generated ADD operand plan own the
bit layout. The address helper checks S+A, page range and alignment.

Both native ELF writers and in-memory linking use that helper. The dynamic
writer omits page sites from its x86 layout stage, avoiding unrelated rel32
range restrictions, then resolves local addresses, PLT addresses or data copy
slots in the A64 overlay. Dynamic data aliases retain their assigned copy-slot
address. Exported untyped AArch64 text labels can be assembly entry points;
explicit STT_OBJECT symbols remain data.

ObjectSymbol and ObjectRelocation gain no fields. There is no new per-symbol
allocation or instruction pass. Existing Mach-O, PE and TLS kinds retain their
separate format contracts. The new forms add constant work per affected ELF
relocation; no SIMD throughput improvement is claimed.

The addend contract follows the primary
[Arm AAELF64 specification](https://github.com/ARM-software/abi-aa/blob/main/aaelf64/aaelf64.rst).

## Compiler-throughput measurements

The dedicated [PR throughput job](https://github.com/buster14a/buster/actions/runs/34503468568/job/102959936900)
compared the immutable baseline and candidate above on one ubuntu-26.04
x86-64 runner. Both Release compilers were built sequentially with Clang
21.1.8, tests/unity/allocation instrumentation disabled, before measurement.
The candidate-owned `ci` profile supplied identical generated inputs and flags
to both compilers: six synthetic workloads, each in `none`, `mir-stack`,
`fast` and `quality` allocator modes (`cc -c -g0 -O0`).

Two predeclared rounds each used twenty adjacent, balanced AB/BA pairs per
case/mode after two warmups per variant/case, with a 120-second invocation
deadline and automatic CPU selection. Every progress record reports valid=1.
Measurement ran from 16:42:19 to 16:44:25 UTC on 2026-09-10. The job ended:

```text
THROUGHPUT_RESULT confirmed_regressions=0 inconclusive=19 guard=1 exit=0
```

This passes the repository guard; it does not establish equivalence or a
speedup. Nineteen measurements remain inconclusive. The guard requires both
a 15% and 2 ms wall-time increase, or both a 20% and 16 MiB peak-RSS increase,
with the same series significant in both rounds under its corrected paired
sign test. Shared-runner noise and serial correlation limit that inference.
The job retains its [result bundle](https://github.com/buster14a/buster/actions/runs/34503468568/artifacts/10163001640)
with raw samples, metadata and commands. Its summary line was verified from
the job log; per-series medians were not independently inspected locally.

The own-source self-host elapsed times (baseline 3.103097 s, candidate
2.554953 s for the trusted first stage) are correctness diagnostics only:
the sources differ and other local validation was active. No local timing
comparison or retired-instruction measurement is claimed, and this run
provides no Zen 5 or AArch64 throughput conclusion.
