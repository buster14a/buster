`2026-08-22a` (Linux x86_64, Zen 4 7940HS; **delete the allocator's
free-register loop, not just its skip branch**).  A stage-1 branch-miss
survey put one line of `machine_fast_free_candidates` — the
`if (!active) continue;` guarding the AVX-512 chunk loop `2026-08-20a`
reshaped — at 0.98% of all stage-1 branch misses (~245 K of 25.17 M), the
largest single source line inside `machine_fast_placement_build_prepassed`
(7.96% of all misses).  The obvious reading is that the skip is a
data-dependent branch bought to save one memory-folded VPCMPEQD, on a loop
that runs one to three iterations.  That reading is wrong, and the wrong fix
was measured first.

**Dropping only the `continue`** — computing the mask unconditionally and
letting `active` zero the lanes, which is semantically exact — does remove
the branch from the object code.  Eleven order-alternated, CPU-pinned,
same-source pairs (both compilers building the identical pre-change tree,
outputs byte-identical) say it does not pay: instructions rise
10,588,823,845 -> 10,590,076,556 (**+0.0118%**, candidate loses 11/11) and
branch misses are flat, 25,294,795 -> 25,299,831 (**+0.02%**, 6/11).  A
`branch-misses:u` profile explains why.  In the baseline the function's
hottest miss site is `kmovw %k0,%r10d`, the instruction after the skip's
`je`, at 6.15% of the symbol's misses; in the candidate it is
`shrx %rdi,%rcx,%r9`, the target of the loop's back-edge, at 6.17%.  The
misses relocate one for one.  The entropy was never "is this chunk empty" —
it is the chunk count itself, which is the target's full file for a function
with a vector virtual register and one past the top general bit for one
without, so it flips at function boundaries whichever branch closes the
loop.  **Order the pairs**: an unordered first run, always baseline-first,
had made the branch misses look 272 K *worse* rather than flat.

The loop therefore goes.  The chunk count becomes
`MACHINE_TARGET_REGISTER_LIMIT`, so the query is three straight-line
compares with no loop and no data-dependent branch at all; clang folds it to
three memory-folded `vpcmpeqd`, a `kunpckwd` fusing two 16-bit masks, one
shift/or and one `and` — twelve instructions, zero branches.  Two facts
license reading past `active_register_count`, and the comment at the kernel
now records both: `owner` is declared `MACHINE_TARGET_REGISTER_LIMIT` lanes
wide (already statically checked against every target's `register_count` in
`machine_x86_64.c`, and a new `BUSTER_CT_CHECK` pins it to a multiple of
sixteen), and `candidates` never carries a bit at or above
`active_register_count`, because that count is either the full file or one
past the highest bit of `allocatable_mask | callee_saved_mask`, a superset
of the only class mask a function with no vector virtual register can ask
about.  The second fact is the load-bearing one: the reduced-count case
leaves the lanes above it holding the free sentinel, since the reset loop
runs to `description->register_count`, so masking is what makes them
contribute nothing.  The non-AVX-512 scalar walk is untouched and still
compiles clean at `-march=x86-64` under the full warning set with `-Werror`
(verified by rebuilding the unity TU with the real command line; the object
contains `simd512_equal_word_fallback` and no AVX-512 instruction).

Fifteen order-alternated pairs, outputs byte-identical, are unanimous on the
honest carrier: instructions fall 10,588,743,366 -> 10,576,804,385,
**-11,938,981 (-0.1128%)**, candidate wins 15/15, and eleven earlier pairs
put branches at 1,965,466,192 -> 1,961,179,842, **-4,286,350 (-0.2181%)**,
11/11.  The cost is real and is reported rather than buried: L1d loads rise
3,831,343,525 -> 3,839,109,418 (**+0.2027%**) and lose 0/15, which is
exactly the two extra 64-byte reads on the chunks the skip used to avoid.
They stay in L1 — L1d misses move 129,434,735 -> 129,576,585
(**+0.11%**, mixed signs, 4/15) — so three extra L1 hits per query buy the
removal of the loop.  Cycles do not resolve: **+0.52%**, 5/15, against a
baseline whose own cycle median drifted 4.09 G -> 4.18 G -> 4.43 G across
three runs of this same measurement on this same idle host.  As in `19c` and
`20a`, retired instructions are the number to read.

The final `test_self_host` reaches a byte-identical 35,394,712-byte fixed
point.  Measured against the same gate on the same tree with the change
stashed (35,394,688 bytes), stage 1 retires 10,578,013,605 instructions
versus 10,589,097,639, **-11,084,034 (-0.1047%)**, agreeing with the pairs.
The full local CI combination matrix (`test_all_combinations_ci`) is green
across its three `test_all` runs, every module passing, 309,196 assertions
on the fullest; remote a64/Windows coverage stays pending on CI as usual.
The lead the survey handed over was worth about a fifth of what the branch
attribution promised and none of it came from branch misses, which did not
move: what actually paid was the ~4.3 M loop-control branches the unroll
stopped executing.  A branch-miss survey names a line, not a fix — confirm
where the misses go before believing the line is the cause.

The pairs above were taken on `b2c52677`, before `2026-08-21d` landed from
the same survey, so their absolute baselines predate it; each is an A/B over
one fixed tree and is unaffected as a delta.  The fixed-point gate was
remeasured after rebasing onto `21d`, both sides in one session on the
merged tree: base 10,537,567,235 (35,384,984 bytes) against candidate
10,526,766,462 (35,385,016 bytes), **-10,800,773 (-0.1025%)**, reproducing
the -0.1047% taken on the older base and confirming the two changes stack.
**Revert the file with `git checkout HEAD~1 -- <path>` for that comparison,
never `git stash push -- <path>`**: once the change is committed the push
has nothing to save, is silent under `-q`, and the matching `pop` then
applies whatever unrelated stash sits on top — both self-host runs measure
the same tree and agree to 48 K, which reads exactly like a real null
result.
