## Census method

The census build changes no answer:
- **Wrappers.** Each lowering query that takes a token range, and each
  expression frame at its first step, goes through a `noinline` wrapper.
  The wrapper resolves the range through two maps, then calls the unchanged
  query.
- **Hit, gate and miss.** The call is routed through one of three
  trampolines, so Callgrind splits the query's Ir:
  - **miss:** neither map resolves the range;
  - **gate:** the map resolves it, and the range holds no candidate token at
    all. A per-body token count answers these ranges without a tree;
  - **hit:** the map resolves it, and only a tree can answer.
- **The tree's answer.** For each yes/no query, the wrapper derives the
  tree's answer and compares it with the scan's. It found **0
  disagreements** among about 1.97 M compared answers.
- **Body scope.** Both maps are built lazily, on the first query in each
  function body, in a private arena that each body rewinds.

**Span rules.** The census uses the tree typer's rules (`c_ast_types_span`
and `c_ast_types_locate`): a node's token span is widened over the
parentheses that wrap it exactly, and a query strips balanced outer
parentheses before looking up. Each node also gets two masks:
- **The root region:** the `,`, assignment, `?:` and `&&`/`||` operators
  that lie outside every parenthesis, bracket and brace of the node. These
  are the operators the token scans see at depth 0. An assignment in a
  conditional's second or third operand is dropped, as the scans drop it.
- **Anywhere:** those operators anywhere in the subtree. Statement
  expressions, compound literals, initializer lists, `_Generic` and
  `sizeof`/`alignof` of a type mark it opaque. The first census run
  disagreed on 21 group facts inside such constructs; the opaque mark hands
  them back to the scan.

**The designs:**
- **A, dense.** Per body: `first`, `end` and `link` per node, a `head` per
  token, and the two masks. A lookup follows the chain of nodes that start
  at the range's first token.
- **B, sparse.** The same pass into transient columns. Then a table, sorted by
  first token, of only the nodes whose root region holds a split operator.
  A lookup is a binary search. B cannot prove a negative: a range missing
  from its table may still be a node.
- **C, reuse.** No separate build. Analysis's tree typer already computes the
  same spans and start chains for every typed body, but in validator scratch
  released before lowering. C is costed from counts, not run.

**A token gate takes most of the predicates' share.** A per-body count of
candidate tokens refuses a range that holds none, and needs no tree. The
gate-answerable ranges of the five predicates cost 71.76 M over 703,748
calls.
- **What is left for the tree:** the hit rows, 9.60 M in all.
- **What the map would cost there:** 15.65 M of lookups over the 323,981
  calls the gate does not answer.
- So after the gate, the map loses on every predicate.
- A gate test at about 8 Ir would cost about 5.6 M. That makes the gate worth
  about **66 M on both paths**, before any new prefix columns (a comma count;
  possibly an assignment-only count), which are not measured.

**The pilot's root conditional costs more than the default path's.**
- **Under the pilot,** `c_ir_root_conditional` goes to the records' path for
  all 892,999 calls. That path costs 79.11 M, about 86 Ir a call.
- **On the default path,** an inline O(1) `?` count (#3467) refuses the
  ranges first. Only 61,938 reach the scan, which costs 18.15 M.
- B already builds the token prefix table for every body, so testing the
  `?` count before the records under the pilot costs no new table. It would
  refuse 93.1% of the calls first. The saving is not measured.

## Design C and slice 5

**C's build cost is already paid.** It moves 34 MB of span and chain
arrays, about 4.7% of peak RSS, from analysis's per-body scratch to unit
lifetime. In exchange, the consumers above net roughly:
- 68 to 76 M before the token gates;
- 40 to 50 M after them (type-name negatives and the root conditional).

The masks' cost in the typer's pass is not measured.

**Every evaluator core resolves to one node.** A therefore satisfies the
range-to-node index that `ast.md` makes the precondition for slice 5a.
- **5a's ceiling** is about 280 M, from the 2026-10-11 census, net of #3445.
- **Against a lowering-built A,** 189.5 M of build plus about 20 M of core
  lookups leaves at most about 70 M for the walk.
- **Against C,** it leaves at most about 260 M.

## Limits

- Callgrind counts instructions, not time, on v3 builds. The census covers
  one input on one host.
- The census build adds `noinline` wrappers around inlined queries, which
  moves some of their Ir. The base's own numbers are used wherever the base
  shows the query.
- The consumer estimates assume a 48.3 Ir lookup and a mask test as each
  query's whole answer cost. Anything a real consumer adds lowers the net
  further.
- The design C, slice 5 and token-gate figures are estimates from these
  counts, not measured candidates.
- No 9700X request is made. Zen 5 validation stays **incomplete** (#2761),
  and the pilot-default switch stays on owner hold.
