**#56 closing acceptance report, a6705764 vs 7d0762e5, x86-64/AArch64
FAST/QUALITY with per-merge attribution**).

Diagnostic evidence only. It is not 9700X acceptance (#2761), and it claims
no generated-program speedup. It is the closing report for #56 ("reduce
values and live ranges before redesigning register allocation"). It measures
the cumulative effect of the #56 slices on one frozen input, attributes it to
merges, and audits the correctness coverage for criterion 4. Raw files are in
[`evidence/2026-10-12T224512Z/`](evidence/2026-10-12T224512Z/), pinned by
`SHA256SUMS`.

## Identities

- **Baseline:** `a67057643a40c0ab99931849eb30053a2b870fcc`, main on
  2026-10-11. This is the revision of the #56 IR census, and it predates every

  #3868 (`dea6497b`). That is the last #56 slice.

- **Compilers:** Release `ide`, one `git worktree` per revision, built with
  `./build.sh generate` and then `./build.sh build --config Release -t ide`.
  - `build.c` was bootstrapped with TinyCC 0.9.28rc
    `0fb54300b56512754221d80adda85ddb9815bceb`, built from source.
  - Applications were built with Ubuntu Clang 18.1.3, CMake 3.28.3 and
    Ninja 1.11.1.
  - Binary SHA-256: baseline `f48dd0a1ca2c3cab5e83ea52a4673dc6d5b52b7a9f0528eaadaa03c87f50702e`,
    candidate `f1ed532723f9f677724b4196e29d7b0635c4441266dccd00dd48aaea00a21262`.
- **Host:** 4-vCPU Intel Xeon @ 2.80 GHz with AVX-512 but no VBMI, a shared
  KVM guest running Linux 6.18.44.
  - AArch64 headers come from Ubuntu `libc6-dev-arm64-cross`.
  - There is no qemu, so nothing AArch64 was executed.

**Command**, from the frozen root:

```sh
ide cc -Isrc -Igenerated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g0 \
    <target flags> -fregister-allocator={fast,quality} \
    -c src/buster/apps/ide/ide.c -o <obj> -v
```

The target flags are `-march=native` for x86-64, and
`-target aarch64-linux -isystem /usr/aarch64-linux-gnu/include` for AArch64.
Counters come from the `CODEGEN` and `CODEGEN_ALLOCATOR` lines. "Code" is
`CODEGEN code_bytes`. No function fell back in any run.

**Reproduction check.** The baseline's x86-64 FAST counters are 69,970

## Compile time

The compile CPU is user plus system time of the `ide` child, from
`getrusage(RUSAGE_CHILDREN)`.
- Ten base/head pairs per cell, alternating which compiler runs first, after
  one warm-up compile each.
- The ratio is the geometric mean of the per-pair head/base ratios, with a
  95% t-interval (t = 2.262, n = 10).
- Raw samples are in `timing.json`.

| Cell | Compile CPU head/base [95% CI] | Median CPU base → head | Median wall base → head |
|---|---|---|---|
| x86-64 FAST | 0.9988 [0.9796, 1.0183] | 6.04 s → 5.94 s | 6.10 s → 6.01 s |
| x86-64 QUALITY | 0.9642 [0.9410, 0.9881] | 7.46 s → 7.17 s | 7.57 s → 7.27 s |
| AArch64 FAST | 0.9988 [0.9792, 1.0188] | 5.97 s → 5.94 s | 6.04 s → 6.04 s |
| AArch64 QUALITY | 0.9539 [0.9349, 0.9732] | 7.15 s → 6.89 s | 7.27 s → 6.97 s |

- No material regression was detected in these hosted samples. The FAST
  point estimates are neutral, but their 95% intervals still allow increases
  of up to about +1.8% (x86-64) and +1.9% (AArch64). This is not a
  categorical no-regression result.
- These are whole-compiler comparisons. The candidate also carries
  unrelated frontend and IR changes made between the two revisions, so the
  QUALITY improvement is not attributed to #56.
- On a shared VM this is not a speed claim. It shows only the absence of a
  visible regression.
- The routine 9700X compiler comparisons for the individual merges are
  summarized in the #56 thread (2026-10-11, for #3337, #3351 and #3367).
  This audit adds no 9700X evidence.

## Correctness coverage (criterion 4)

The audit read `src/buster/tests/compiler/driver/driver_test.c`,
`src/buster/tests/compiler/codegen/` and the mode matrix in `build.c`.

| Category | Executed coverage, FAST and QUALITY |
|---|---|
| Control flow | The #56 driver fixtures cover joins, swapped and rotated loop parameters, `continue`/`break`, switch state machines, and more loop values than registers:<br>`_join_parameter_registers`, `_join_carried_values`, `_loop_parameter_registers`, `_back_edge_dead_stores`, `_liveness_dead_stores`, `_deferred_edge_stores`, `_parameter_contract_carry_lanes`, `_parallel_edge_moves`, `_recreated_edge_sources`.<br>The mode matrix adds `tests/basic_c_fast_ra_cfg.c`. |
| Calls | `_fixed_register_vacate`, `_call_crossing_callee_saved` (#3868), `_frame_address_rematerialization`, `_preferred_reload_registers`, `_many_native_arguments`.<br>The mode matrix adds `basic_c_call_abi.c` and `basic_c_x86_64_i128_stack_abi.c`. |
| Wide integers | `_i128_block_parameters`: `__int128` through joins, loops, switch and computed goto.<br>`_native_i128_divide` with `basic_c_i128_shift_edges.c`: 128-bit values across calls in a loop.<br>The `i128_binary` block in `compiler_driver_tests`. |
| Vectors | Before this audit: `_native_frame_vectors` (`basic_c_vector_joins.c`, 128-bit, low pressure) and the 256/512-bit arithmetic fixtures (no calls, no pressure).<br>**Gap:** no executed test held more vectors than registers, or kept vectors wider than 16 bytes across a call. `tests/basic_c_vector_register_pressure.c` has a body only under AVX-512 VBMI/VBMI2. | Constrained registers | `_fixed_register_vacate`: x86-64 divide (RDX:RAX), variable shifts (CL), widening multiply and fixed ABI registers.<br>`_call_crossing_callee_saved`: a quotient carried across a call, then shifted by a variable count. |

**Closing the vector gap.** This PR adds
`compiler_driver_test_vector_call_pressure`; the program is
`vector_call_pressure.c` in the evidence directory.
- `narrow_loop` carries 38 vectors of 16 bytes around a loop that makes two
  calls per iteration. That is more than 16 XMM or 32 V registers.
- `wide_calls` keeps eight 32-byte and six 64-byte vectors live across two
  calls in straight-line code.
- Every target selects without fallback under both allocators and both
  frontend forms (20 object configurations), and the host runs the program
  under each (4 native runs).
- Host GCC and Clang agree on the expected values at `-O0`, `-O2` and
  `-O2 -march=native`.
- Changing one expected value makes the program exit 1.

**New issue, #3886.** Writing the test found a pre-existing refusal: a 32- or
64-byte GNU vector reaching any join or loop header is refused with
`reason=selection-other`, on both targets, under both allocators and both
frontend forms, even with `-march=native`. The baseline refuses it
identically, so it is not a #56 regression. Wide vectors stay out of joins in
the new test until #3886 is fixed.
