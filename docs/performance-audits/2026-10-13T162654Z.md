`2026-10-13T162654Z` (Linux x86_64, Ryzen 9 7940HS, Callgrind 3.25.1;
**self-host capture: reuse promotion proofs and project scalar layouts**).


The final candidate removes repeated work while preserving generated bytes:
strict validation proofs survive an unchanged local-promotion body, and scalar
layout queries project one property instead of rebuilding the complete ABI
record. The evidence supports an instruction/work reduction. Native elapsed
time remains inconclusive; there is no Zen 5 or cache/predictor speed claim.

## Implemented structural changes

### Retain the exact proof that remains valid

`ir_prepare_canonical_module` already validates functions containing LOCAL
rows before local promotion in checked builds, so it can distinguish a
pre-existing invalid body from a transformation defect. Previously it threw
away successful proofs and validated those same bodies after promotion even
when they were unchanged.

A preparation-scoped byte per function now records input validity, whether
promotion changed the body, and output validity. An unchanged, strictly valid
input is also a valid output. A changed body still receives its strict output
check. A legacy-invalid neighbor does not erase a valid function's proof;
FAST can reuse that individual output proof while still checking shared
scope and retaining its output validation. The scratch allocation outlives
promotion and FAST admission, and is released before preparation returns.
It is not a persistent cache and cannot certify a later mutation.

On the frozen replay, promotion-output function walks fall from 6,435 to 727:
**5,708 duplicate walks removed**. The walk cost on that edge falls from
698,256,335 to 12,308,102 instructions. The entire promotion-output check
falls from 700,742,767 to 14,806,785 in the first combined diagnostic build.
The remaining bodies include the ones actually changed and those without
an earlier per-function proof. Canonical input, shared ownership/scope,
changed-output and FAST-output validation are retained.

The regression exercises both function orders, a legacy-invalid neighbor,
an unchanged address-taken local, an actually promoted function, promotion
disabled, and corruption followed by a second preparation. Diagnostic
counter assertions prove both kinds of reuse and the absence of a stale
proof on the second call. The original strict validator remains the rejection
oracle; the tests do not substitute a more permissive validator.

### Ask the target policy for the requested scalar

`target_scalar_type_layout(Target, TargetScalarKind)` returns one 12-byte
layout. `target_plain_char_is_signed` answers the separate signedness policy.
The complete `target_data_layout` API and the scalar API share one policy;
there is no extra mutable target cache, epoch, warmup, or invalidation rule.

C builtin layout and IR scalar properties use the narrow projection. The
full ABI API remains for consumers that actually need the record. This keeps
LLP64, i386 alignment, x87/binary64/binary128 long double, wasm pointers,
AArch64 varargs, plain-char overrides, GNU void size, and complex storage
rules in their existing ownership boundary.

Complete layout constructions fall from 2,556,761 to 206,739 on the frozen
replay: **91.91% fewer**. Full-constructor work falls from 493,454,873 to
38,866,932 instructions in the first combined diagnostic build. Some of the
removed work reappears as the much smaller scalar projection; therefore the
454.6-million reduction in that one symbol is not itself the net speedup.
The whole-workload measurements include the replacement work and any code
layout effects.

An independent ABI probe compiles the old and new target implementation
separately and compares all 280 bytes of each result over 1,512 combinations
of architecture, OS, char policy and stack-boundary settings, including
sentinel architecture/OS values. All 423,360 bytes match. Existing numeric
ABI expectations also pass. This is stronger than checking the new scalar
API only against a complete API that calls the same helper.

### Negative experiment retained

The first change only retained promotion-output proofs for FAST admission.
That was a plausible interpretation of the 5,722 calls charged directly to
preparation, but a fresh profile showed these calls were the *pre-promotion*
attribution checks. FAST already reused the successful whole-module proof
on this unity workload. Instructions were 28,481,091,118 versus
28,481,356,737: effectively neutral, with identical output. That result is
retained as `proof.cg`; the issue was corrected before the input-proof reuse
was implemented. The mixed-invalid fixture still justifies the narrower
output-proof path, but it does not explain the measured unity improvement.

The supplied and repeated simulation uses 32 KiB, 8-way, 64-byte-line I1 and
D1 caches, and a **16 MiB, direct-mapped** last-level cache. This is the
capture's model, not the host's LLC geometry. Valgrind describes its cache
and branch models as basic and recommends hardware counters for modern CPU
behavior; see its [simulation documentation](https://valgrind.org/docs/manual/cg-manual.html#cg-manual.simulation)
and [Callgrind manual](https://valgrind.org/docs/manual/cl-manual.html).

The original instruction validator accounts for 5,370,839 indirect
mispredictions, 28.66% of that simulated event. This is a reason to inspect
how often validation runs; it does not establish that rewriting its switch
will help a modern predictor. The implemented change removes repeated visits
without regrouping instructions or changing diagnostics.

The simulation's reduced branch misses do **not** reproduce as a demonstrated
native branch-prediction benefit. Native production branch misses change
+0.40%, inconclusively, while retired instructions improve 1.93%. Total
writes fall substantially in the checked profile while D1 write misses barely
change: many eliminated stores were already hot. The supported explanation
is less repeated work, rather than an asserted cache-footprint breakthrough.

## Highest-value remaining work

These are measured cost pools and proposed experiments, not promised savings.
Nested rows overlap their enclosing phases and must not be added together.
Current issue ownership was inspected before choosing the implemented slice.

1. **Move semantic checks onto typed facts, one diagnostic family at a time.**
   [#2607](https://github.com/buster14a/buster/issues/2607) remains relevant:
   the fresh baseline spends 5,243,830,877 instructions, 18.41% of the whole
   compile, in `c_parse_validate_lowering_constraints`. Its direct children
   put 1,945,413,333 instructions in assignment/const checks (6.83% of the
   whole compile) and 1,178,574,020 in initializer-shape checks (4.14%).
   `c_parse_validate_const_assignments` scans body tokens, reconstructs
   assignment bounds/scopes, resolves entities and asks the expression typer
   again. A bounded next experiment is an assignment-node worklist with
   retained destination/source types and value-category/qualifier facts.
   Keep diagnostic precedence, locations, unevaluated operands, GNU forms
   and malformed-source refusal identical. Compare existing facts versus
   re-derivation on the same nodes before removing a walk. Reject a design
   that buys instruction savings with unbounded retained memory.

   The current AST is a pilot: the default profiled command does not build
   it. [#4062](https://github.com/buster14a/buster/issues/4062) retained facts
   under `-fc-ast-pilot`, with unresolved fact gaps; it is incorrect to say
   that all facts are still discarded or that normal lowering consumes them.
   [PR #4103](https://github.com/buster14a/buster/pull/4103) owns statement-node
   lowering. No competing AST/frontend migration was started here.

2. **Replace remaining whole-table layout scratch with a dependency closure.**
   [#1457](https://github.com/buster14a/buster/issues/1457) already owns this.
   The fresh baseline calls `c_parse_type_layout_passes_run` 176 times at
   874,251,641 instructions (3.07%). The scalar projection reduces that
   inclusive pool to 571,315,251 in the diagnostic candidate, but it still
   allocates arrays indexed by the complete type count, copies committed
   rows, and snapshots pending work. The machineless uncached closure path
   already landed in #1463; reimplementing it would be duplication. The
   remaining machine/cache path needs a census of requested dependency
   closure versus seeded rows, then a transaction-local overlay or
   generation-stamped sparse state with explicit rollback/retraction.
   Validate nested sizeof/alignof queries that append types, incomplete
   arrays, member offsets and qualifiers. A 10x reduction in this residual
   pool alone has only a roughly 1.8% whole-compile instruction ceiling on
   this input; the semantic family above is a larger opportunity.

3. **Preserve bounded per-function parallel backend work under its owner.**
   [#54](https://github.com/buster14a/buster/issues/54) already has an active
   selection/allocation/encoding implementation. Native codegen is 20.23%
   of the supplied capture, so infinite acceleration of the entire phase
   would cap the instruction-proportional model at about 1.254x. Actual
   runtime ceilings require native phase timings; Callgrind serializes the
   workload and cannot validate scaling. Useful follow-up evidence is
   worker-budget scaling, private scratch/RSS, one-worker overhead and
   deterministic ordered publication. This change touches preparation and
   scalar policy, not that owner's scheduling/publication work.

4. **Price the remaining debug index by events, not by repeating its old fix.**
   The fresh baseline still charges 841,885,686 instructions (2.96%) to
   `codegen_record_machine_locations`, including 574,516,454 in index build
   and 147,714,093 in timeline lookup. [#1723](https://github.com/buster14a/buster/issues/1723)
   already records merged #3803/#3849, their reduced event count and a
   completed linearity census. The current capture includes those source
   changes. A next design would need to eliminate another complete event
   representation or construct final ordered location facts directly, while
   preserving object bytes and debug semantics. This is a retained cost
   pool, not evidence that the prior fix regressed or that a quadratic remains.

5. **Repair scoped event matching in the evidence tool.**
   [#4140](https://github.com/buster14a/buster/issues/4140) records a new,
   reproduced issue: `instructions:u` is present in raw `perf stat` CSV but
   `pe_parse_perf` strips the modifier only from the observed name, then
   compares against the qualified request and reports it missing. The
   initial control is retained as incomplete. A separate control/comparison
   uses supported unqualified request names; every raw CSV retains its
   observed `:u` scope. No counter-denial workaround or host policy change
   was used. This reporting-tool fix remains unimplemented.

## Core dumps and reproducible profiling environment

The supplied ELF core notes name one `ide` and two `true` processes. All three
stop on `vmovdqu8 %zmm0,0x30(%rsp)`. A fresh host
`valgrind --tool=none /usr/bin/true` stops at the identical address in
`_dl_start (rtld.c:563)`. This is an AVX-512 loader incompatibility before
application code, not a demonstrated Buster failure.

There was a second environmental obstacle: the host startup object gives a
v2-compiled executable a GNU ELF v4 ISA requirement. A generic runtime then
correctly refuses it. The measured profile executables relink the unchanged
Clang compiler objects with the generic Arch runtime's `Scrt1.o`, `crti.o`
and `crtn.o`, using `clang -B<runtime-directory>/ ... -lm`, and run against
that same generic runtime in a network-disabled container. Both arms use
identical startup objects and libraries. Native binaries use the host runtime.
No feature note or machine instruction is patched. Raw rejected attempts,
core triage (without uploading the cores), image identity and startup-object
hashes are retained. [#4138](https://github.com/buster14a/buster/issues/4138)
and the benchmarking guide document the distinction.
