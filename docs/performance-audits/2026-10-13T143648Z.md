## Method

Each workload ran from the repository root under
`valgrind --tool=callgrind --cache-sim=no --branch-sim=no` with the same
command line for both binaries, `ide cc -march=znver3`:

- `int main(void){return 0;}` for `-target x86_64-pc-windows` and for
  `-target x86_64-apple-macos`;
- a program with two constructors, two destructors and calls to `puts`, for
  both targets; on Windows it links with `-L` naming the stand-in DLL;
- a program that takes the address of the imported `helper_data` in a
  `noinline` function and calls two imported functions, for both targets,
  with the same `-L` on Windows; the PE writer rewrites that address load into
  its GOT load;
- controls: `tests/differential/observables.c` as a dynamic ELF link, and
  `tests/basic_c_operations.c` with `-c`.

Inclusive costs come from `callgrind_annotate --auto=no --inclusive=yes`,
read from this checkout.

The writers are `link_native_executable_pe64` and
`link_native_executable_mach_o64`; the PE entry stub, the Mach-O destructor
runner and the import-stub encodes are inlined into them. In the base, every
`buster_x86_metadata_encode` call in these workloads came from those writers
(`link_x86_emit`, `link_x86_emit_zero`, or the inlined stub builders). The
candidate makes no `buster_x86_metadata_encode` call in any of the eight
workloads. About 2.0 M of the Mach-O writer's remaining cost is code-signature
hashing, unchanged. The macOS `int main(void)` link runs none of these
writers: it has no import and no destructor.

The Windows `int main(void)` link saves the most because nothing before it
had warmed the selector. The selector normalizes a mnemonic's candidate forms
on its first query and keeps them, and in the larger programs codegen's own
shape resolutions had already normalized some of the forms the linker later
queried. That reading fits the counts (14 linker queries cost 6.0 M there,
24 cost 4.9 M in the constructor link) but was not instrumented.

**What remains.** Every remaining `buster_x86_metadata_select_form` call in
these workloads comes from `machine_x64_metadata_shape_resolve`: three to
five codegen shape-cache resolutions, 2.5–4.6 M Ir, unchanged from the base.
Those are the input-dependent shapes #3796 left to the selector, the
mechanism `2026-10-13T114733Z` recorded for `observables.c`. No linker writer
reaches the selector.

## Limits

- Counts come from `-march=x86-64-v3` builds, whose SIMD kernels run their
  fallbacks; the removed work is scalar selector and normalization code, so
  the deltas should carry over, but no native-build count was taken.
- The Windows workloads with imports depend on the stand-in DLL's export
  table. A real `ucrtbase.dll` exports far more names, which costs more to
  read but does not change the stub, thunk or GOT-load encodes.
- No PE or Mach-O output was executed: this host has neither Windows nor
  macOS, and `test_mode_matrix` checks those legs structurally.
