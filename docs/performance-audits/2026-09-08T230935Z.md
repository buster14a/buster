## Changes and correctness boundaries

1. Reuse the resolved sparse current-value slot when creating a provisional
   parameter. Value and parameter allocation do not grow the slot table, so the
   caller's pointer stays valid. This removes a second hash lookup.
2. Grow the sparse table only for a missing-key insertion. Existing-key queries
   no longer trigger a rehash at the insertion threshold. The hash, capacity
   sequence, zero initialization and load factor are unchanged.
3. Record when an owner has exactly one initializing entry store. Once every
   write is known, forward reachable pending reads to that definition without
   predecessor discovery. A later write revokes the fact; an escaped owner
   follows the existing whole-owner memory recovery. Disconnected reads retain
   the previous path. Store RHS roots still expose copies of uninitialized
   owners before alias substitution. The new flag fits existing structure
   padding (`sizeof(CIrSsaLocal)` remains 24).
4. Skip the initialization dependency walk only when every retained owner has
   the existing entry-initialization proof. Restored loads become independent
   definitions first. Any retained owner without that proof retains the full
   store/instruction work queue and conservative recovery.

Focused tests cover a read-only entry value through loops and diamonds, a later
reassignment, copying an uninitialized owner, late address escape, and a
multiple-entry loop. Raw canonical tests check memory ownership, complete CFG,
source/debug provenance and the independent promotion operation census across
x86-64, AArch64, Wasm64 and eBPF layouts. Undefined input is checked structurally,
not executed as a semantic oracle.

## Why one output changes

The two lookup changes preserve byte-identical outputs for all four frozen
workloads. Entry-definition forwarding can remove a group of mutually dependent
trivial parameters that single-parameter simplification previously retained.
A two-entry loop with one immutable `seed` has seven LLVM phi nodes before this
change and five after: the two redundant `seed` nodes disappear, while mutable
counter and sum nodes remain. This explains a real code-generation difference;
byte identity is not asserted across that change.

For the frozen full-compiler source, direct-SSA telemetry changes from 455,769
parameters created / 427,841 removed / 27,928 retained to 373,828 / 347,331 /
26,497. Functions (4,232), locals (36,140), reads (134,587), writes (58,286),
private temporaries (9,079), recovered locals (1,849) and the eight owners still
promoted by the shared pass are unchanged. The fixed point and independent
execution comparisons below validate the changed output.

## Reproduction

Configure once and then build incrementally; `generate` destroys its chosen
build directory.

```sh
./build.sh generate
./build.sh build --config Release -t ide
./build.sh build --config Release -t test_all
./build.sh test_self_host --config Release
./build.sh test_mode_matrix --config Release
```

Generate the two synthetic inputs with the exact following contents. This is
corpus construction, not production build orchestration:

```python
from pathlib import Path
out = Path('build/ssa-corpus')
out.mkdir(exist_ok=True)
(out / 'functions.c').write_text(''.join(
    f'int f{i}(int x) {{ int value=x+{i}; for(int j=0;j<5;j++) '
    '{ if(value&1) value+=j+3; else value^=j+7; } return value; }\n'
    for i in range(1280)))
(out / 'diamonds.c').write_text('int diamonds(int x) { int result=x;\n' +
    ''.join(f'if ((x >> {i % 16}) & 1) result += {i % 29 + 1}; '
            f'else result ^= {i+1};\n' for i in range(700)) +
    'return result; }\n')
```

For each source, invoke the same trusted executable twice with only
`-ffrontend-ssa` versus `-fno-frontend-ssa` changed. For small sources:

```sh
taskset -c 2 build/Release/ide cc -ffrontend-ssa -c tests/basic_c_operations.c -o build/ssa-corpus/result.o
```

For the complete compiler:

```sh
taskset -c 2 build/Release/ide cc -ffrontend-ssa -Isrc -Ibuild/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g src/buster/apps/ide/ide.c -lm -o build/ssa-corpus/ide
```

Use the same output path for both modes. Count user instructions/cycles with a
separate `perf stat --no-big-num -x , -e instructions:u,cycles:u,task-clock`
invocation. Independently time a direct child process with a monotonic clock and
collect its CPU time/RSS with `wait4`; process startup, object writing and linking
are included. Discard two warm-up pairs. Balance which mode runs first and shuffle
the pair order with Python `random.Random(34)` before collecting the measured
pairs. No `perf duration_time` value is used (it reports zero on this host).
