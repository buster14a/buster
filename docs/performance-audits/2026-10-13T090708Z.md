## Result

**The wall gap is the IR phase, and within it the inliner's cold sweeps over
the instruction rows. It is not page faults, kernel time, branch prediction or
codegen.**

|---|---:|---:|---:|---|
| total phase time | 1547.6 ms | 1588.3 ms | +40.8 ms | 1.0264 [1.0243, 1.0301] |

What the counters rule out:
- **Kernel time.** The user-mode cycle delta is 216 M cycles, or 40.6 ms at the
  measured 5.33 GHz. That accounts for the whole +41.3 ms wall delta.
- **Page faults and `os_discard`.** Page faults are flat; the host backs the
  arenas with large pages (about 5k faults per compile, against 273k in the
  VM).
- **Branch prediction.** Branch misses rise only with instruction count.

What remains is an IPC loss, 92.7 M cycles (17.4 ms) beyond what A's IPC
predicts for the extra instructions.

Per-phase instruction ratios come from callgrind on this VM (below): `ir`
×1.147, `codegen` ×1.0148, `object` ×1.031. Scaling each phase's 9700X A time
by its own instruction ratio gives:

| Phase | Predicted Δ | Measured Δ | Excess | Bound by |
|---|---:|---:|---:|---|
| `ir` | +21.8 ms | +34.2 ms | +12.4 ms | memory stalls |
| `codegen` | +5.7 ms | +6.2 ms | +0.5 ms | instructions |
| `object` | +1.1 ms | +1.3 ms | +0.2 ms | instructions |

So codegen and object track their instruction growth. The wall-over-instruction
gap sits in the IR phase.

## Where the IR phase stalls (callgrind, diagnostic)

The compiler was the same source compiled `-march=x86-64-v3` for valgrind,
tests off. The workload was the unity command with `-march=x86-64-v3`. The
cache geometry was Zen 5-like:
`--D1=49152,12,64 --I1=32768,8,64 --LL=33554432,16,64`. Callgrind models no
L2, TLB or prefetcher, so its misses show *where* cold data is touched. They
are not cycle counts.

| Inclusive, B − A | ΔIr | Ir B/A | ΔLL data misses | LLd B/A |
|---|---:|---:|---:|---:|
| whole compile | +385.3 M | 1.0149 | +3.673 M | 1.0637 |
| `ir_prepare_canonical_module` | +281.5 M | 1.1470 | +3.408 M (93%) | 1.2794 |
| — `ir_inline_module` | +225.5 M | 5.17 | **+3.180 M (87%)** | 2.44 |
| — `ir_validate_canonical_function` (all callers) | +113.1 M | 1.168 | +0.209 M | 1.064 |
| `codegen_generate_canonical_module_with_trace` | +89.2 M | 1.0148 | +0.084 M (2%) | 1.013 |
| `object_from_canonical_codegen_module` | +12.8 M | 1.031 | +0.113 M | 1.025 |

The instruction ratio (1.0149) matches the 9700X's 1.0148. LL data misses rise
four times faster than instructions, and almost all of the extra misses are in
the inliner.

`ir_inline_module`'s self cost is +57.7 M Ir with +2.32 M LL misses: one
miss per 25 instructions. Its per-line diff (`callgrind-ir_inline-line-diff.txt`)
pins them down:
- **`ir_inline.c:706`** (`call->opcode`), in the optional phase's per-caller
  tiny screen: +1.53 M LL misses on +3.07 M Ir. That is one miss per row
  visited.
- **`ir_inline.c:904`**, the per-caller planning walk that follows: +0.45 M.
- **`__memcpy_avx_unaligned_erms`**, the copy of relocated caller tables: +0.55 M.

`IrInstruction` is 64 bytes, a whole cache line per row. The module has about
2.06 M rows, which is about 132 MB, four times the 9700X's 32 MB L3. The dense
required-call scan in `ir_inline_plan_graph` (`ir_inline.c:345`) already makes
one cold sweep of those rows in **both** modes: 2.00 M LL misses with tiny
inlining off (`callgrind-ir_inline-lines-tiny-off.txt`). By the time the
optional phase runs, the rows have been evicted. The tiny screen then makes a
second cold sweep of nearly every caller, and the planner a third partial one.

## Local phase timers (diagnostic)

These timers come from a scratch patch that is not proposed for merge
(`diagnostic-timers.diff`, at the evidence anchor). It adds `timestamp_take`
spans around the inliner's parts and around every strict validation in
`ir_prepare_canonical_module`.

The timed compiler is a CMake-flag Clang Release `ide` with
`-DBUSTER_INCLUDE_TESTS=0`, which matches the 9700X stage-1 compiler. Each run
used ABBA order, was pinned to one vCPU, and had one warm-up. 20 pairs give
`abba-diag4-summary.txt`. The `ir` and `codegen` rows pool 60 pairs from three
such sets.

| B − A, median of paired deltas | Δ ms | Note |
|---|---:|---|
| `ir` phase (60 pairs) | +114.9 [101.3, 125.1] | ratio 1.284; 9700X 1.230 |
| — `ir_inline_module` | +86.1 | ×5.17 |
| — — tiny screen (`ir_inline.c:680`–`747`) | **+33.6** | memory-bound: +21 M Ir, +1.55 M LL misses |
| — — table relocation (`ir_inline_cfg_reserve_tables`) | +19.9 | 31.4 MB copied; 9,109 extra first-touch faults in the VM |
| — — caller planning, without strict validation | +15.5 | |
| — — strict validation inside the pass | +12.5 | required before FAST reads a caller |
| — — `os_discard` (1,640 `madvise` calls) | +3.7 | |
| — — splices and predecessor rebuilds | +4.6 | |
| — promotion, FAST and publication of the extra rows | about +25 | noisy, rows-proportional |
| — FAST input-guard validation | +5.6 | deferred callers are proven there (−11.8 / +17.4); net small |
| `codegen` (60 pairs) | +49.3 [27.4, 73.3] | the flag-independent `analysis` control moved +30.2 [−15.4, 63.9] |

The VM inflates fault-bound items. Here, 10,540 extra minor faults per compile
(86% inside the inliner) cost about 1 µs each. On the 9700X, faults are flat.
So the relocation's 19.9 ms is mostly a VM artifact, and only its +0.55 M LL
misses from the copy carry over. The screen has no fault component, so its
cost does carry over.

An earlier run with the default CMake Release `ide` (tests on) is kept as
`abba-tests-on-summary.txt`. Its `BUSTER_IR_TRANSFORM_CHECKS` validation adds
about 200 ms of module-wide output checks per compile in **both** modes, so
it is the wrong compiler for this question.

## Conclusion and proposal

- **Dominant avoidable cost: the second cold row sweep.**
  - The optional phase's tiny screen re-reads each caller's 64-byte rows after
    `ir_inline_plan_graph`'s required-call scan has already streamed all of
    them.
  - Fold the screen's per-caller predicate into that existing dense scan. The
    predicate is "has a direct call to a linkage-allowed tiny leaf other than
    itself", plus the recursive-site count. This needs a per-symbol tiny/linkage
    byte table built from function headers before the scan. The optional phase
    would then read only that byte per caller.
  - Locally this removes the screen's 1.55 M LL misses and about 34 ms (≈23%
    of the local wall delta).
  - Estimate for the 9700X, unverified until a run there:
    - the screen holds 45% of the IR phase's extra simulated misses, so about
      5.6 ms of the 12.4 ms IR excess;
    - its 21 M instructions add about 1.4 ms;
    - together about 7 ms, ≈17% of the +41 ms delta, or 0.45% of stage-1
      wall.
  - Constraints: keep the per-caller `IR_FAST_WORK_BUDGET` exhaustion and the
    `visits`/`candidates`/`recursion_skips` statistics. Keep output
    byte-identical.
- **Stronger variant.** Have C lowering record each function's direct-call rows
  while they are hot. Both the required-call scan (2.0 M LL misses on *every*
  compile that has an `always_inline` symbol, about 14 ms locally in
  `ir_inline_plan_graph`) and the planning walk (+0.45 M) would then visit only
  call rows. This also speeds the default path.
- **Inherent.**
  - Codegen and object of the extra rows (+7.5 ms on the 9700X, proportional to
    instructions).
  - Strict validation before FAST.
  - Promotion and FAST over 1.6% more rows.
  - The splices themselves.
- **Not a factor on the 9700X.** Page faults, `os_discard`, kernel time and
  branch prediction.

Unverified:
- the 9700X split *inside* the IR phase (the receipt has no inliner timer);
- TLB behaviour (no counters here);
- the codegen excess seen locally, which the 9700X does not show.
