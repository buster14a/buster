`2026-10-13T085334Z` (Linux x86_64, hosted Intel Xeon (4 vCPU), callgrind on
x86-64-v3 builds; **x86-64 first-touch form normalization parses each pattern
once (#124)**).

## Scope

This audit records one [#124](https://github.com/buster14a/buster/issues/124)
slice. It follows the handoff in
[2026-10-12T223825Z](2026-10-12T223825Z.md), which named first-use shape
resolution through `buster_x86_metadata_select_form` as the largest x86 cost
left in small compiles. Every number is a callgrind instruction count from a
hosted container. None of it is timing, Zen 5 evidence or acceptance
evidence; #124's 9700X acceptance stays open.

## Method

- **Base:** main `446f742e`.
- **Builds:** the base and candidate builds were configured with
  `./build.sh generate -DBUSTER_NATIVE_TARGET=x86-64-v3` (candidate in a
  separate `--build-directory`), then built with
  `./build.sh build --config Release -t ide`. The driver was bootstrapped
  with the host Clang (hosted-CI style), because fetching TinyCC was not
  permitted in the container.
- **Profiler:** `valgrind --tool=callgrind --cache-sim=no --branch-sim=no`.
- **Small workloads:** frozen copies, compiled with `ide cc -Isrc -c` and no
  `-march`:
  - `tests/basic_c_operations.c`;
  - a one-function file `int f(int a, int b) { return a + b; }`;
  - `tests/basic_c_constructor_order.c` (compiled with `ide cc -c`).
- **Self-compile workload:** a frozen `git archive` copy of the base's `src/`
  plus its `build/generated`, compiled with
  `ide cc -Isrc -Ibuild/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g -march=znver3 src/buster/apps/ide/ide.c -o OUT -lm`.
- **Output identity:** every compared pair of outputs was checked with `cmp`.

## Census on base

In `ide cc -c tests/basic_c_operations.c` (55,579,766 Ir):
- `buster_x86_metadata_select_form` ran 32 times for 13.52M Ir inclusive.
- `buster_x86_metadata_normalized_form` normalized 665 forms for 10.27M Ir,
  about 15.4K Ir per form.

Each normalized form's pattern was tokenized twice:
- `buster_x86_metadata_copy_form` parsed it to normalize the row's prefix and
  family fields (665 calls, 2.60M Ir);
- `buster_x86_metadata_prepare_form_facts` parsed the published row again
  (665 calls, 2.68M Ir), because the row did not yet exist when the first
  parse ran, so the first parse was not cacheable.

The rest of `prepare_form_facts` (2.14M Ir in `buster_x86_metadata_operand`)
is the first touch of the form's operand views, which the selector also
reads.

## Change

`copy_form` writes only `field_flags`, `prefix_kind` and `encoder_family`
after its parse. When those three fields are unchanged, the published row is
the struct the first parse read, so the parse is a pure function of
identical input. In that case `buster_x86_metadata_normalized_form`
publishes the first parse to the pattern-semantics cache right after the
row, and the facts read it back from the cache.

The pattern claim (level 7) ranks above the row claim (level 6), so the
store follows the row's publication. It runs where the facts claim (level 8)
already ran, so it adds no new nesting. Selection, candidate order and
diagnostics are untouched.

## Results

| `ide cc -c` | base | candidate | change |
|---|---:|---:|---:|
| one-function file | 12,021,875 | 11,624,062 | −3.31% |
| `tests/basic_c_operations.c` | 55,579,766 | 53,149,995 | −4.37% |
| `tests/basic_c_constructor_order.c` | 19,556,012 | 17,891,858 | −8.51% |
| stage-1 self-compile | 27,389,440,824 | 27,384,863,193 | −0.02% |

On `basic_c_operations.c`, the facts' parse fell from 2.68M Ir to 0.16M Ir.
All 665 calls are now cache copies, so every normalized form reused its
first parse. The self-compile is neutral, as expected: it is dominated by
work other than first-touch normalization.

## Considered and not taken

- **Cheaper tokenization.** The first parse still costs about 3.9K Ir per
  form. A line-level profile spreads that across the ~150-comparison token
  chain, and no single line exceeds about 0.3M Ir over the whole compile.
  A dispatch rewrite of `buster_x86_metadata_emit_parse_pattern` would be a
  large change for a diffuse gain.
- **Pre-filtering candidates or resolving shapes by exact token.**
  - A pre-filter risks the source-assembly diagnostic order.
  - Pinning keys for the per-compile shapes is already proposed in
    [PR #3796](https://github.com/buster14a/buster/pull/3796).
  - This slice is complementary to both: it makes every first touch cheaper,
    including source assembly's.
