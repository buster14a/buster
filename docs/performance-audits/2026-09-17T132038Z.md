**Disposition: retain the sequential owner-row clear and do not add a generation
stamp.** On the current unity self-compile, `ir_function_instruction_owners` runs for
4,896 lowered functions, clears 5,349,372 bytes and performs exactly 1,337,343
successful-path `owners[]` reads. That is 0.25 reads per clear byte: one 4-byte owner
read for every 4 bytes cleared. The small input independently reports one function,
four reads and 16 clear bytes.

A separate lossless `u32` epoch does not reduce successful-path logical traffic. It
replaces each 4-byte clear store plus 4-byte owner read with a 4-byte epoch read plus
4-byte epoch write, while retaining the 4-byte owner write. Both designs move
16,048,116 logical bytes over the unity population. The epoch also adds a compare and
second stream, requires explicit wrap handling and doubles peak scratch from 276,908
to 553,816 bytes. A packed lossless `u64` owner+epoch row moves 21,397,488 bytes,
33.3% more. Stealing epoch bits from the current `u32` row is not representation-neutral:
`IrBlockId` uses the full `u32` underlying type and `UINT32_MAX` invalid value, so that
design narrows the owner id or needs masks plus a large-function fallback/dynamic split.
The screen supplies no byte-traffic case that pays for the added protocol.

This is the successful no-patch outcome permitted by #566. No validator invariant,
error result, production mode, test expectation or compiler source changes.

## Representation arithmetic

| representation | successful-path logical row traffic | unity bytes | peak scratch |
|---|---:|---:|---:|
| current `u32 owners[]` | `4N` clear + `4N` read + `4N` write = `12N` | 16,048,116 | 276,908 B |
| separate `u32 owners[]` + `u32 epoch[]` | `4N` epoch read + `4N` epoch write + `4N` owner write = `12N` | 16,048,116 | 553,816 B |
| packed `u64` owner+epoch | `8N` read + `8N` write = `16N` | 21,397,488 | 553,816 B |

This is logical byte accounting, not a cache-line, wall-time, PMU or retired-instruction
claim. It gives the epoch its best successful-path case by suppressing a separate owner
read when the epoch is stale. Duplicate/cyclic invalid chains require the owner read
after a current epoch, and the unowned error path still requires a full epoch scan.
