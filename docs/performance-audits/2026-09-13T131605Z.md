### 1.1 Encoding decisions and ownership

The x86 metadata owner exposes `BusterX86MetadataExactPlan` (16 bytes) and `BusterX86MetadataMachineExactToken` (4 bytes). The token is opaque; its representation is not a license for a second decoder or handwritten opcode logic. `buster_x86_metadata_machine_exact_token_for_plan` prepares an existing plan token. `BusterX86MetadataMachineExactQuery` still supplies physical operands, output and relocation capacity, `force_disp32`, `force_lock`, mask-register selection, and zeroing policy. `BusterX86MetadataEmitResult` retains status, actual/required byte and relocation counts, diagnostic operands/values, and `value_field_count`. **Only a result with no value fields is a candidate for value-independent byte reuse, and its complete physical shape and policy must also match.** See [metadata declarations][metadata].

The shared authority owns legal forms, prefixes, opcode maps, ModRM/SIB rules, immediate/displacement widths, decorators, and feature constraints. A fast consumer may reuse a proven result; it must not silently reinterpret the opcode or register encoding. Instruction encoding is not merely copying a mnemonic's opcode. Intel's [XED guide][xed] describes the 1–15-byte instruction envelope and the prefix/opcode/ModRM/SIB/value-field structure; Buster's currently supported subset, not every extension listed in that document, remains the scope.

The current machinery already performs important bulk work:

* `machine_x64_metadata_shape_cache_prepare_predicates` prewarms predicate shapes, including KMOV widths and register-class directions. This is existing work, not a proposed new cache. [Predicate prewarm][predicate-prewarm].
* `machine_x64_emit_exact_movabs` already uses the prepared GPR population: it validates register, variant, table policy, trailing eight-byte field and capacity, copies the authoritative two-byte prefix, then patches the eight-byte value. It deliberately retains the ten-byte MOVABS form even when a shorter encoding could represent the value. The fallback is `machine_x64_emit_exact_form`, not handwritten bytes. [MOVABS and variable memory][prepared-copy].
* `machine_x64_emit_variable_memory_encoding` classifies displacement as zero, signed byte, or full width, accounts for the frame-base offset, and indexes the prepared register/base population. It calls `machine_x64_encoder_copy_encoding`, then patches the value field. Its documented wide-copy strategy uses unwritten reservation slack and an exact-copy tail near capacity. It is **not** a proof that adjacent final-output slices may be written concurrently. [Same source][prepared-copy].

Consequently, “add plans,” “replace a per-byte MOVABS loop,” and “use a single displacement store” are not new research findings at this SHA. Additional plan retention is useful only where the producer and consumer census finds a surviving lookup or reconstruction cost. A possible narrow continuation is to retain existing KMOV tokens by width/direction at their existing owner; do not add a permanent per-instruction plan array just to bypass a cache already hit once. Twelve four-byte tokens would be 48 payload bytes, before validity state/alignment, but neither the need for that table nor its benefit was established here.

### 1.2 Reservation, rows, and final publication

`machine_encode_x86_64` first rejects invalid placement. It makes a capacity pass using `machine_opcode_row_table()` and each row's `encode_budget`, with side-data additions for switches, aggregate work, inline assembly paths, frame probes and placement edits. The checked final capacity is limited to `UINT32_MAX`. This is already a table-based bounded reservation, not repeated allocator growth per instruction. [Reservation and row ownership][machine-start].

It then emits the prologue, stable callee-save order, stack probing, blocks, placement edits and machine rows. `result.block_offsets` and `result.row_offsets` are consumers of the layout. An important boundary visible in the source: a row offset is recorded **before** its before-edit run; a packet must preserve that convention, not redefine a row offset as the first opcode byte. Call sites, inline-assembly relocations, unwind-related prologue offsets and after-edit positions also depend on exact byte positions. A MIR row may expand to several native instructions; “one 16-byte record per MIR row” is invalid in general.

The terminal fixup walk uses `MachineX64BranchFixup`, `machine_x64_block_displacement`, final block offsets and `patch_offset + 4`. It validates signed-32-bit range and writes the four-byte displacement. Failed fixups prevent a valid result. Only afterwards are call-site and inline-assembly-relocation streams flattened and the byte slice marked valid. [Fixups and result publication][machine-finish]. The switch path uses the existing JZ/JMP rel32 templates. Small recipe-local branches elsewhere have their own fixed widths; they are not automatically eligible for a generic relaxation algorithm.

### 1.3 Object, linker, metadata, file

The driver guide documents the boundary above this emitter: native C workers own private translation-unit state and diagnostics; the caller consumes compact objects and diagnostics in input order. Workers do not independently write output files. Assembly input goes through `assembly_unit_encode`/`assembly_encode` into an `ObjectFile`. Constructor priorities, ordered linking and first-failing-input behavior belong to the driver. The present assembly-unit handling accepts and drops `.cfi_*`; this report does not invent emitted assembly CFI. [Driver contracts][driver-guide].

For the inspected ELF tail path, `link_elf_section_table_append` computes debug offsets, section-name positions, eight-byte table alignment and total size; it retains a bump-on-top path and a copying path. Debug sections are copied, their relocations patched, names and headers written, ELF header fields patched, and the executable slice length finally published. In particular, DWARF location/range-list relocations into text may remain section-relative while other address attributes use image addresses. Treating all debug relocations as `image_base + symbol` would corrupt required semantics. [Tail layout][elf-tail] and [relocation/header publication][elf-publish].

`link_elf_eh_frame_header_write` independently resolves function addresses, uses an eight-pass stable byte-radix ordering, validates relative differences and writes the unwind search table. That ordering is real required work, not a memcpy to remove. [Unwind header source][eh-header].

CodeView/PDB already have the bounded, non-owning `byte_writer` contract: append/patch/align are whole-operation-or-fail; patches target the written prefix; failures are sticky; CodeView streams and the final PDB container have publication gates. It is currently a CodeView/PDB utility, not a mandate to migrate all emitters. Reuse its tests and lessons without replacing artifact construction with a new writer framework. [Byte-writer contract][byte-writer].

Coverage limitation: the detailed implementation trace here is the MIR x86 emitter and common/ELF linker tail and unwind header. PE/Mach-O serialization and AArch64 instruction selection are not claimed to have received equally exhaustive source inspection. Their required invariants and acceptance coverage are specified below; optimizing them needs a focused source pass first. Completed-artifact experiments must include object construction, linker work, debug/unwind generation, ordered driver consumption and file completion, rather than stopping at `result.byte_count`.

## 3. Low-risk metadata candidate: copy-owned ELF debug bytes need no initial clear

### 3.1 Baselines and limited disposition

At `5217113`, the ELF tail is fully cleared before copying the debug section images over its initial contiguous prefix. At the verified #572 merge, its own allocation is dirty-aware instead. The latter is the baseline for any new implementation: preserve #572's unzeroed copied prefix and contiguous tail reservation. Do not resurrect the unconditional fill to make a candidate appear faster. [Merged implementation][elf-572].

Define offsets within the new image:

```
L = existing executable length
S = string_offset, after all debug section images
H = header_offset, after names and alignment
T = total_size

[0,L)   existing image (copied only on the existing copy path)
[L,S)   complete debug section images, each copied in the existing order
[S,H)   names, NULs and table-alignment padding
[H,T)   null header, descriptor headers and string-table header
```

The inspected loop starts its debug cursor at L and advances it only by each section's data length. Empty/skipped DWARF 5 sections contribute zero length. Therefore the nonempty debug-copy intervals are disjoint and exactly cover `[L,S)`. No gap or padding inside that range needs zero initialization under this layout. The existing code later patches relocations only after those copies. This is a D proof from [the current layout source][elf-tail], not an executed byte-equality result.

### 3.2 Proposed algorithm, using existing allocation primitives

The following is design pseudocode, not a patch or a new API:

```c
// Keep all existing layout computation, overflow refusal, and path selection.
L = result->executable.length;
S = string_offset;
T = total_size;
require(L <= S && S <= T); // follows the existing layout; assert in tests

bytes = result->executable.pointer;
if (!link_arena_block_on_top(arena, bytes, L)) {
    bytes = arena_allocate(arena, u8, L);
    memcpy(bytes, old_image, L);
}

// Byte-aligned allocations, no intervening allocation or published pointer.
if (S != L) {
    copied_debug = arena_allocate(arena, u8, S - L);
    require(copied_debug == bytes + L);
}
remaining_tail = arena_allocate_zeroed(arena, u8, T - S);
require(remaining_tail == bytes + S);

// Exactly the existing copies, relocation validation/patches, names, headers,
// ELF-header patches and successful executable-slice publication follow.
```

This saves only the dirty-aware clear of the copy-owned debug prefix. It does not save a debug copy, a relocation, zero-dependent terminator, null header or padding byte. It requires neither SIMD nor another pass over debug bytes. The scalar allocator operations still have a cost, and a fresh arena already performs no explicit tail clearing after #572: **there is no fresh-arena fill saving to claim**.

Let `D` denote dirty storage in allocation-address coordinates, and translate image intervals to that address space. Relative to #572, removed initialization writes are exactly:

```
Q = bytes( [L,S) intersect D )
0 <= Q <= S - L
```

All logical bytes and allocation extent remain T. The copying path still copies exactly L bytes. Do not use `arena_allocate_zeroed(T)` before copying the old prefix: that would reintroduce redundant dirty-prefix clearing, which #572 already avoided.

### 3.3 Byte-ownership and failure proof obligations

The old prefix is preserved except for the same explicit ELF-header patches. Debug section source spans must retain their existing lifetime and non-overlap contract with destination copies. Every byte of `[L,S)` receives its source byte before any relocation consumes it. Every byte in `[S,T)` receives dirty-aware zero initialization before the unchanged name/header writers, leaving all existing zero-dependent fields deterministic. No consumer sees a complete artifact until existing publication succeeds.

The two tail allocations must remain adjacent, alignment one, in a reservation that does not move; assert pointer adjacency, final arena position and unchanged dirty tracking. Capture the same allocation-failure behavior and preserve the same layout-overflow and relocation refusals. Merely proving successful output equality is insufficient if a split allocation changes externally observable failure reporting or publication. No new parallel writer is needed.

The design applies only while `[L,S)` has complete copy ownership. If a future layout inserts gaps, rederive the partition or retain the conservative clear; do not assume a symbol named `string_offset` proves coverage.

### 3.4 Break-even and validation

Let `a` be extra allocation/check work and `c_clear(Q)` the avoided dirty clear, including its cache effects. The extension wins only when `c_clear(Q) > a + added downstream cost`. A bandwidth approximation `Q / effective_clear_bandwidth > a` is a hypothesis for selecting an experiment, not a result. Fresh arenas and no-debug inputs have Q = 0 and are mandatory regression controls. Reject or defer the extension if dirty reuse is rare in actual completed compilations, or the extra allocation/check work costs more than it saves.

Reuse #572's `link_test_elf_section_table_tail` and production ELF writer tests rather than creating a duplicate harness. Add dirty-mark boundaries immediately before/at/after S, all/no/sparse debug kinds, zero-length sections, both growth paths, all table-padding residues, repeated poisoned-arena replays, and exact prefix preservation on the copying path. Compare every output byte against the **post-#572** baseline. Include x86-64 and AArch64 ELF final writers, debug relocations, self-host linked output, and complete-link timing. These gates are U. This is a proposed follow-on assessment, not grounds to reopen #563 or claim #572 incomplete.

## 4. Aggressive alternative: bounded homogeneous packets inside the existing emitter

### 4.1 Eligibility and plan ownership

Start with one metadata-proven register/register family where each eligible MIR row emits exactly one instruction, physical registers are final, and form/policy identity is already available. Fixed-immediate and simple-memory families are later independent pilots; do not combine them into a universal packet on day one. Stop at a block boundary, before/after edit, label, call, relocation, source/unwind event, multi-instruction recipe, unsupported decorator, or policy change. Keep original order. Do not gather equal opcodes from distant rows or create another whole-function instruction representation.

The producer consumes existing placement operands and prepared authority. A packet-scoped family descriptor may retain its existing token/proven shape; it must not invent constant prefix/field masks by duplicating ISA knowledge outside `x86_64_metadata`. Features, REX/high-byte restrictions, register classes, immediate fit and special addressing cases remain validated. The initial scalar-batched prototype can call the existing checked exact bridge per record; vector field assembly is a separate experiment, not an assumed consequence of storing bytes in a vector.

### 4.2 Concrete temporary layout

For a register/register pilot, propose at most 32 instructions per tile, using one 768-byte, 64-byte-aligned scratch allocation. This is scratch only, not a public or persistent C ABI layout:

| Offset | Size | Meaning |
|---:|---:|---|
| 0 | 512 | `u8 raw[32][16]`: independently owned instruction-byte records |
| 512 | 32 | `u8 length[32]` |
| 544 | 66 | `u16 local_offset[33]` |
| 610 | 32 | `u8 dst[32]` |
| 642 | 32 | `u8 src[32]` |
| 674 | 32 | `u8 status[32]` for pilot pass/fail or eligibility, not replacement diagnostics |
| 706 | 62 | allocation padding; never serialized |

The payload is 706 bytes; the aligned allocation is 768. The packet descriptor and any existing full diagnostic result remain separately accounted for. This raw record is **not** a reinterpretation of `MachineX64GprEncoding`: its metadata fields are not instruction bytes. A fixed-immediate pilot needs additional immediate storage; charge it explicitly rather than pretending this layout contains it.

`u16` is sufficient only for the local 32-record sum (at most 480 valid instruction bytes). Global offsets retain the existing width and checked total limits. Scratch records are initialized before any wide load of their unused bytes; zeroing all 512 raw bytes costs real writes and may erase the packing benefit. A later full-record producer can prove every byte initialized instead, but cannot read indeterminate padding.

### 4.3 Producer, scan, output

Conceptual algorithm; named operations below are not claims of existing public APIs:

```text
find next maximal eligible consecutive run, capped at 32
if run below measured threshold: use current scalar emitter
otherwise:
    retain its authoritative family/form policy at the existing owner
    project only the physical operands needed by this family
    initialize raw records that will be read as full vectors
    produce checked encodings into raw[i][0..length[i])
    retain the existing diagnostic result for any failed lane
    on failure: follow the owning emitter's existing failure policy
    checked exclusive scan of lengths -> local_offset; compute B
    validate output capacity using B <= capacity - cursor
    copy/compact in original order into [cursor,cursor+B)
    publish row offsets with the existing before-edit convention
    advance cursor by B; preserve counters and publication behavior
```

Packet barriers mean there are no hidden edits to weave into this pilot. Validation cannot be removed to make a benchmark favorable. Any change in failure-time counter or private-buffer semantics required by existing tests must be resolved against the scalar owner, not dismissed because the final result is invalid.

AVX2 can vectorize field arithmetic and use lane-local byte shuffles plus explicit lane concatenation and exact stores. It has no native byte-compress store equivalent to VBMI2; count the glue operations and mask/table traffic. AVX-512 can load four 16-byte scratch records, make a 64-bit keep mask with each record's low `length[i]` bits, and use byte compaction through the existing SIMD abstraction. Four short records per vector, not 64 arbitrary variable-length instructions, is the first manageable packing unit. Tail groups must not load uninitialized/unallocated rows.

An x86 byte-compress path requires the actual supported feature set, notably **AVX-512 VBMI2**, not a check for AVX-512F alone; [Clang's intrinsic definitions][vbmi2] identify that operation family. Follow `<buster/lib/simd.h>`, its scalar/host/self-host implementations, and existing masks. No vendor intrinsic header, new SIMD operation, or runtime feature-dispatch framework is proposed. If the current abstraction/build cannot select a legal AVX2-only variant, keep that arm an experiment rather than adding a new framework. Cross-host AArch64/MSVC/scalar builds must remain valid.

### 4.4 Destination-byte ownership

For lengths `l_i`, define `o_0=0`, `o_(i+1)=o_i+l_i`, and B=`o_n`. Checked arithmetic establishes `0 <= o_i <= B <= capacity-cursor`. Instruction i owns the half-open interval `[cursor+o_i, cursor+o_(i+1))`. Nonnegative lengths and stable prefix order make these intervals disjoint and exhaustive over the packet output. Nonempty accepted x86 instructions have lengths 1–15; n=0 must avoid pointer arithmetic and shifts with invalid widths.

A scalar exact copy writes only its interval. A compress-store group writes exactly the sum of that group's selected bytes, wholly within the packet interval. A full-width final store is legal only when its entire destination lies in that writer's owned interval; the final partial vector requires exact or properly masked storage. Capacity slack owned by another instruction, packet or worker is **not** padding permission. An unaligned store still needs full bounds and ownership.

The current serial overstore strategy is unsafe across adjacent final slices: its spare bytes may overwrite another worker's live output even when every address is allocated. Retain it only in its existing serial/unwritten-slack context. Parallel work uses exact final writes or genuinely private scratch, never “reserve 16 extra bytes globally” as a substitute for per-writer ownership.

Out-of-place scratch-to-output compaction is the initial design: source and destination do not overlap. In-place forward compaction needs an additional proof that the entire current source record/group has been loaded before any overlapping write and that writes cannot reach a future unread group. Do not select in-place compaction based only on `write_cursor <= read_cursor` at the start of a loop.

### 4.5 Reservation alternatives and actual cost

Let N be native instructions, B valid output bytes, K emitted tiles, and R the existing worst-case reserved byte count.

| Strategy | Passes and storage | Principal cost/risk |
|---|---|---|
| Current bounded reservation | Capacity pass, emission, fixups; reserve R | Already avoids per-instruction allocation. R is not all necessarily touched. Serial slack enables cheap bounded copies. |
| Exact sizing then direct write | Validating sizing pass, scan, emission, fixups; reserve B | Repeats decisions or needs retained plans/lengths; extra arrays and source reads can cost more than saved reservation. |
| Bounded records plus compaction | Existing producer plus record production, scan, compact; tile scratch | Separates variable writes but adds initialization, record traffic and a consumer pass. |
| Scalar-batched exact destination | Packet classification/scan, direct exact stores | Often the strongest low-complexity competitor; no obligatory 16-byte-per-instruction scratch traffic. |

For the initialized-raw-record design, each tile can cost 512 bytes of zero writes, up to B scratch encoding writes, 16N scratch read bytes for full records, and B final writes, plus field projection, lengths, offsets and status. A producer that fully initializes each 16-byte record can reduce this to approximately 16N scratch writes + 16N scratch reads + B final writes, but that is a different proven implementation. Do not advertise the latter traffic for a prototype that first clears and then overwrites its scratch. Cache residency can hide DRAM traffic while still consuming load/store bandwidth and cache capacity.

A general break-even model is:

```
N * (current_per_instruction - candidate_per_instruction)
  > K * packet_setup + projection + scans + scratch_initialization
    + scratch_read_write + compaction + added_validation
    + extra_prewarm + downstream_cache_penalty
```

All terms must be measured or explicitly modeled. An N threshold exists only when net per-instruction savings are positive. Derive thresholds by eligible family and host; there is no justified universal “four instructions is enough” threshold here. Charge producer toolchain compile time and compiler text/table size as well: a large population of specialized functions can trade emission dispatch for compiler-build and instruction-cache cost.

## 5. Layout dependence, branch decisions, and fixups

A prefix sum gives offsets **after lengths are known**. It does not resolve a branch whose selected length depends on its distance to another instruction whose length is still changing. It also does not decide section padding, literal pools, veneers, or compressed displacement eligibility.

The low-risk course is to preserve current layout decisions and scalar fixup logic. The inspected MIR x86 final block-fixup path uses existing rel32 forms; keep those exact encodings even when a shorter branch would work. Place packet boundaries around branch recipes. Local short branches and multi-instruction stack/atomic recipes remain scalar. This avoids introducing a relaxation problem merely to make a scan look parallel.

For a future independently justified relaxer, a valid model is finite monotone promotion: each branch starts in an allowed rank, recompute all offsets and alignment, promote every out-of-range branch to a larger allowed rank, and repeat. There can be at most the sum of rank increases; alignment may vary non-monotonically, so final range checks remain mandatory and demotion is not allowed in this proof. If maximal forms still do not fit, preserve the existing error or separately specified veneer/island policy. Inserting an unbounded number of islands is not covered by the finite-rank proof. Such a relaxer changes bytes and is **outside the byte-identical proposals here**.

AArch64's fixed-width instructions do not imply fixed whole-function or final-image layout: branch veneers and paired relocations still impose layout policy. The [AAELF64 specification][aaelf] is explicit about addends, instruction-field extraction, page-relative forms and permitted veneers. No x86 packet algorithm should be transplanted into AArch64 relocation handling merely because the byte width is regular.

## 6. Relocations, debug/unwind metadata, deterministic output

`BusterX86MetadataRelocation` carries offset, width, kind, addend and symbol; ABS32 sign-extended and zero-extended address forms are distinct. The exact query also has independent relocation capacity. Batching byte generation must preserve both relocation ordering and the meaning of the field, not just the resulting instruction length. [Metadata declarations][metadata].

A plausible bulk relocation pilot computes candidate values for consecutive, already resolved, same-kind relocations with independent destination fields. Keep field stores and error arbitration in the original order initially. Validate section/symbol indices, `offset <= section_size`, `width <= section_size-offset`, signedness, addend overflow, place bias and target alignment before each owner publishes a patch. Record the original index for any temporary projection; never sort the externally visible symbol/relocation stream to simplify a vector kernel.

Independence is not implied by equal width. The [ELF gABI][gabi-reloc] permits composed consecutive relocations at one location, and REL addends can come from the place being patched. AArch64 instruction relocations may modify fields of the same word or form semantic pairs. Stop a batch at possible overlap, composition, shared read-modify-write words, unresolved symbols, TLS/relaxation recipes or ordering-dependent evaluation. An implementation must prove its accepted subset; this report does not assert that Buster supports every general-ABI composition case.

Preserve the caller's stable symbol order and deterministic constructor/section order. In PE, an RVA is not generally a file offset, and file alignment is not virtual alignment; COFF symbol indexing and image base relocations cannot be conflated with ordinary object relocations. [Microsoft PE/COFF documentation][pe]. Equivalent virtual addresses are insufficient for a byte-identical artifact claim.

For metadata, compute counts and checked offsets only where independent, then assign record or block ownership. Keep DWARF value/base conventions and variable-length encodings; keep the existing unwind-table stable order; preserve CodeView/PDB all-stream validation and final-container gates. At a minimum, metadata timing includes precomputation, sorting, string handling, padding, copying and relocation application. No proposal obtains speed by omitting line tables, unwind records or required validation.

Parallel emission should first exploit the existing translation-unit lane ownership. Do not introduce nested parallel gangs within a small function. A future function-level design needs immutable prewarmed plans, private scratch, stable function/section order, one final checked layout allocation, disjoint function byte ranges, an ordered metadata merge and the same failure/publication policy. Workers must not race on caches, symbol insertion, diagnostic order or the final file handle.

## 7. Comparison and experiment contract

### 7.1 Required implementations and controls

| Arm | Producer | Consumer and expected tradeoff |
|---|---|---|
| Baseline | Current prepared metadata, reservation and scalar paths | Actual current-main behavior after overlapping changes, not an artificially slow generic encoder. |
| Improved scalar | Existing token reuse where a census proves remaining lookup; post-#572 dirty-debug ownership candidate separately | Direct exact field/copy operations; smallest added code/scratch. |
| Scalar-batched | Same eligibility, plans, validation and packet boundaries as vector arms | Measures the benefit/cost of amortization before crediting SIMD. Include direct exact output and scratch variants separately. |
| AVX2 | Same family semantics; legal vector field operations | Lane shuffle/concatenation and exact tails; packing glue is charged. |
| AVX-512 | Same semantics, existing abstraction and actual subset gates | Byte compaction and masked exact tails; initialized scratch, mask production, register pressure and frequency/cache effects are charged. |

Test the low-risk linker change independently from encoding changes, then any combined arm. Otherwise a linker improvement could conceal a slower vector encoder. Keep generated encodings/target features identical across arms even when the **compiler producer** ISA differs. A host-native compiler build can change target defaults; pass the same explicit target options rather than assuming equal command text guarantees equal target configuration.

### 7.2 Reproducible completed-artifact measurements

Use an explicitly authorized dedicated runner/remote experiment with the existing harness, no laptop run and no new CI workflow in this research session. Before execution, record a manifest containing compiler source SHA/tree, candidate patch SHA, producer compiler/version/binary hash, complete build flags, generated metadata snapshot hashes, host CPU/microcode/ISA/OS, worker affinity/count, memory configuration, and exact workload archive/hash and argument vectors. Pin tool versions for independent decoding and linking too.

Measure cold one-shot builds (including plan preparation), warmed repeated invocations, tiny functions, many small translation units, large homogeneous candidates, branch-heavy mixed functions, representative self-host translation units, debug-heavy links, and fresh/dirty arena replays. Include single-worker and existing multi-worker driver modes without oversubscription. Keep files, target, diagnostics, debug level, output location and durability policy constant.

The acceptance clock covers input loading through the **completed requested artifact**: frontend, lowering, selection/placement, reservation, encoding, fixups, metadata construction, object merge/link, ordered joins and successful file-write/close return. Do not add an fsync to only one arm or call normal close a durability guarantee. Object-only timing is useful for attribution but cannot validate the ELF tail proposal; #563's own implementation discussion already records that the object-only throughput guard does not enter this linker path.

Use paired alternating/interleaved baseline-candidate runs after separately declared warmups; retain raw samples, failures, hashes, medians and uncertainty, plus any meaningful tails. Fix the run count and noise/regression threshold before examining the result. Hardware counters, when available, supplement completed time with cycles/instructions, branch misses, cache misses, RSS and faults. Callgrind v3 measurements must be separate: they do not observe the AVX-512 arm and are not a substitute for it. Do not cherry-pick the minimum of noisy host runs.

A change is accepted only if complete-artifact improvement is repeatable on the intended workload/host, controls do not regress outside the declared noise bound, added code/build/scratch costs remain acceptable, and all correctness gates pass. “The emitter kernel is faster” is insufficient. An inconclusive or negative result is a valid disposition; preserve it with the measured traffic/run-length evidence rather than adding more speculative machinery.

## 8. Validation and unrun gates

### 8.1 Exact bytes and independent interpretation

For every changed path, compare baseline and candidate **whole artifacts**, including text, data, relocation records, section/symbol order, deterministic padding, debug/unwind bytes and header offsets. Repeat production over poisoned/reused arenas and different supported worker counts. Use fixed inputs, target/features and existing deterministic metadata settings; do not hide differences by broadly stripping headers or debug information. Any unavoidable normalization must be narrowly documented, with raw artifacts retained.

Use an independent decoder to verify instruction lengths, operands and branch targets across packet boundaries. Existing XED/LLVM tooling may serve as external oracles where the repository already provisions it; do not add a production dependency. Because Buster's metadata has XED provenance, byte comparison against the same prepared table is not an independent ISA test; an additional LLVM decode or runtime check reduces common-mode risk. A decoder does not prove relocation, unwind or ABI correctness: independently parse objects, apply/inspect relocations, link with an existing independent linker where supported, and execute the resulting native regression programs on the appropriate runners.

### 8.2 Boundaries and failure cases

Exercise zero and one item; packet/group/ISA widths minus one, equal and plus one; non-multiple tails; lengths 1–15; exact output capacity and one byte short; relocation capacity and one short; guard pages and output canaries; unaligned source/destination; initially dirty scratch and arena reuse. Check zero-item paths for null arithmetic and all-ones masks for undefined shifts. Prove full-vector reads and writes remain within their owner.

Cover immediate and displacement signed/unsigned boundaries, zero displacement, rbp/rsp and SIB cases, RIP-relative addressing, register extension/high-byte restrictions, mask/zeroing policy and compressed-displacement rules for any later vector family. Include forward/backward branch range edges, alignment boundaries, many fixups to one target, out-of-range targets, malformed indices, absolute32 signed versus unsigned semantics, and relocation overlap/pairs. Ensure cold and prewarmed cache states, unsupported feature subsets and every fallback yield the same required status and diagnostics.

For the ELF extension, add dirty boundaries at L/S/T, both growth paths, original-image canaries, empty and sparse debug arrays, all alignment residues, repeated resets and independent debug-relocation checks. The existing #572 tests are a foundation, not a claimed pass for this different allocation split.

### 8.3 Supported-target and self-host coverage

Run the repository's registered test, sanitizer, compatibility and artifact suites on the maintained target/host matrix. Native coverage must include x86-64 System V and Win64, AArch64 Linux/Darwin/Windows, and supported UEFI/unwind paths; ELF, PE/COFF and Mach-O debug/nondebug outputs must remain unchanged outside an intentionally scoped change. An object emitted for another target is not evidence that it executes there. Preserve build/regression coverage for LLVM, Wasm and eBPF and existing GPU-facing builds without adding a GPU implementation or assuming these paths use the x86 packet.

Run the existing self-host stages and fixed-point comparisons, plus the supported allocator modes and strict machine-fallback gates at the implementation revision. Do not silently restore the direct backend after #36/#522 retirement, weaken a gate, or treat a mode spelling change as missing coverage. Verify all SIMD abstraction implementations compile, including scalar/AArch64 and partial AVX-512 hosts; feature legality is a correctness gate, not just performance tuning.
