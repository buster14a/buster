## Workload

Every arm compiles the same input, the base revision's unity self-host source,
from a checkout of the base:

```sh
ide cc -Isrc -Ibuild/perf/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 \
  -target x86_64-unknown-linux -march=znver5 -g0 -fsyntax-only \
  [-fc-ast-pilot] src/buster/apps/ide/ide.c
```

There are four arms:
- A: base, default flags;
- B: base with `-fc-ast-pilot`;
- C: candidate with `-fc-ast-pilot`;
- D: candidate, default flags.

C − B is the read's own effect, and D − A is its cost to the default path.
Callgrind ran with `--cache-sim=no --branch-sim=no`. No arm passed `-v`;
coverage counts come from a separate `-v` run of C.

**C − B: −13.80 M (−0.154%).** Semantic analysis (`c_analyze_semantics_core`)
falls from 5,624.3 M to 5,610.5 M; the whole difference is there.
- `c_parse_tree_specifiers_type` gains 9,812 calls (114,281 → 124,093), one
  per member run that reaches its specifier stage: the 9,691 reads and the
  121 runs handed back. Its inclusive cost grows by 4.84 M (63.17 M →
  68.02 M), about 494 Ir a call, the rows it appends included.
- `c_type_parse_machine_run` runs the same 79,866 times, for 14.74 M fewer
  instructions inclusive (145.06 M → 130.32 M): the scalar and core frames
  the reads replace, net of the reads inside it. The largest self-cost falls
  are the machine loop (−4.29 M), `c_parse_skip_attributes` (−3.95 M),
  `c_parse_skip_alignment_specifiers` (−2.14 M), `c_parse_qualified_typedef_type`
  (−1.93 M) and `c_parse_storage_classes_valid` (−2.38 M).
- The root runs (`c_parse_scalar_type_in_scope_attempt`) are the same 4,748
  calls, 14.86 M cheaper inclusive: tag definitions are typed inside them.

**D − A: +4.99 M (+0.046%), inside the band.** The default path builds no
index and makes the same calls as A: `c_parse_scalar_type_in_scope_attempt`
163,449 and `c_type_parse_machine_run` 941,814 in both. The whole difference
is self cost in `c_type_parse_machine_run` (1,905.07 M → 1,910.02 M
inclusive, +0.26% of the machine), where the segment frame's new branch is
inlined into the frame loop. That is code generation in the loop, not more
work; it is the largest share of the band any recent slice has used.

## Negative and unproven parts

- **Casts are not read.** Plain casts typed by a scalar frame inside a
  parenthesized expression leaf cost 5.39 M over 3,445 runs; a read there
  would remove about 3.5 M, below the gate, and would need its own code in
  the expression leaf. They stay with the machine.
- **Most of a tag definition stays with the machine.** The read removes the
  members' specifier frames only. The segment frames with their result
  checkpoints, the alignment frames, the declarators, bit-field widths and
  layout attributes are unchanged. No census here splits that remainder.
- **The 2,243 root runs the declaration read hands back** (2,221 `input`, 22
  `specifiers`) are unchanged by this slice: tags, `typeof` and attributes in
  the list. Of them, 494 are tag definitions and 1,324 tag references.
- Declarator derivations stay below any useful gate (audit
  [`2026-10-11T145510Z`](2026-10-11T145510Z.md)); no new evidence was taken.

## Validation and limits

- Callgrind counts instructions, not time, on `-march=x86-64-v3` builds whose
  AVX-512 kernels are compiled out.
- One input, one host, single process, no pinning and no `perf` counters. Wall
  time was not measured; on this host it cannot resolve an effect of this size
  in the whole compile.
- No 9700X comparison is requested for this slice. Zen 5 validation stays
  **incomplete** (#2761), and the hook stays opt-in; the owner has put the
  pilot-default switch on hold.
- Correctness of the measured candidate is in the pull request's validation
  record: `c_ast_tests`, `test_all` and `test_self_host --config Release`.
