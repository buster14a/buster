The refill proportions normalize the three source-specific events counted

It is **not total memory-controller bandwidth**: it does not include all

results do not establish DRAM bandwidth saturation, nor do they establish
that memory latency is unimportant.

On this host, generic `cache-misses` maps to `event=0x64,umask=0x09`, the
combined instruction/data **L2** miss event. Calling it an LLC or DRAM miss
counter would be incorrect. Explicit AMD events and their installed `perf`
descriptions are retained. See AMD's
[performance metric definitions](https://docs.amd.com/r/en-US/57368-uProf-user-guide/4.6.3.-Performance-Metrics-for-AMD-EPYC-Zen-4-and-later-Core-Architecture-Processors).

IBS provides precise instruction-pointer and memory-source attribution
([Linux perf documentation](https://linux.googlesource.com/linux/kernel/git/torvalds/linux/+/e34a79b96ab9d49ed8b605fee11099cf3efbb428/tools/perf/Documentation/perf-amd-ibs.txt)).

samples. Both highlight the dependent `local_places -> values -> definition

## Data populations and vectorization constraints

The retained IR contains 6,609 functions, 210,577 blocks, 1,705,147 live
canonical rows, 1,442,633 values and 1,822,953 operands. Results exist on
82.17% of rows. The current 64-byte canonical rows occupy 109,129,408 bytes
for this live population, before operands, values and other metadata.

- **96.64% of rows have zero, one or two operands.** Common inline operand
  storage or dense operand columns can address most rows; calls and larger
  aggregates need an out-of-line tail.
- **88.11% of blocks have fewer than 16 rows.** Independent classification
  should batch across block boundaries while carrying stable row/block IDs.
  Restricting every 16-lane kernel to one block would often underfill it.
- Canonical rows are 64 bytes, machine rows 24 bytes, virtual-register
  records 16 bytes and operand-use records 16 bytes. Smaller is not
  automatically better: the four operand-use fields are often updated
  together, where their current interleaving can avoid separate cache lines.
- The trusted selector body is 39,287 bytes of machine code, larger than
  this host's 32 KiB L1 instruction cache even before its helpers. This is
  a footprint observation, not proof of an instruction-cache bottleneck.

The scoped interval retires about 1.189 billion instructions and 4.90 million
branch mispredicts per complete warm selection. That includes its helpers;
it is about 697 host instructions per canonical row. There is substantial
bookkeeping to examine, but a low-level counter is not a removable-work budget.

## Rejected SIMD experiment

Before measurement, the exploratory retention floor was set to a 2% warm
selection-time improvement, output equivalence, and no observed whole-compile
regression. The candidate batches four machine rows during the virtual-
register reference scan, packs their sixteen operands with a permutation,
applies opcode-arity and virtual-reference masks, validates payload bounds,
compresses valid IDs, and performs the idempotent reference-byte stores.
The existing scalar loop handles tails and unsupported targets. Duplicate
IDs are safe here because every write is the same `1`; this does not justify
conflict-unsafe vector scatter-adds for use counts.

The compiler emits AVX-512 permutation, comparison and compression operations.
It also materializes the compressed IDs in a stack array before individual
stores. Source patch, assembly and immutable subject identity are retained:
SHA256 `67d9924d36137369f24a22ebdd44a46b416334195aaef4bf232403a52d7c5951`.

Each comparison uses one warmup per arm. Work counts are repeatable and not
multiplexed, but below the exploratory 2% floor configured for this study.
The timing pairs ran after an observed external compiler build ended; the
normal desktop remained active. Counts and identity checks do not claim an
isolated runtime environment. No statistically supported speedup emerged,
so there was no resampling to seek a favorable outcome.

A separate oracle passes 200,000 differential four-row cases with mixed
arity, repeated IDs, inactive operand garbage and invalid opcodes/references,
both normally and with ASan/UBSan. Warm replay's MIR verification passes.
Ordinary frozen self-host outputs are byte-identical in FAST and QUALITY.
No full suite, self-host fixed-point, backend matrix or 9700X qualification
was run for the discarded prototype. None is claimed. Both the diagnostic
hook and the SIMD production edit were removed; the prior qualified source
tree is preserved.

## Recommended representation work

These are hypotheses for subsequent measured implementation, not established
speedups. The architectural target is **contiguous facts -> masks -> stable
compaction -> homogeneous work -> ordered publication**.

1. **Publish sparse local facts once.** Explore a compact, producer-owned
   live-local population carrying value/type/definition facts at the immutable
   canonical boundary. Preserve live-definition identity and invalidation
   after every canonical rewrite. This directly targets the sampled dependent
   chain, without another value-wide discovery scan.
2. **Separate canonical hot columns from uncommon payloads.** Opcode, result,
   type and common operands should be accessible as dense streams; large call
   and aggregate operand lists belong in explicit tails. Build the authoritative
   representation at publication rather than copying a new whole-function
   projection inside selection. Account for construction, mutation, validation,
   debug consumers and small functions. The old all-result projection already
   failed to deliver a 9700X gain ([#132 audit](2026-10-10T170504Z.md)).
3. **Batch classification and allocation with stable IDs.** Classify independent
   rows across blocks, retain masks, compact active indices in order, and
   reserve output spans in bulk. Preserve existing virtual-register numbering,
   origins and block layout. Exact use-count updates remain a conflict-aware
   reduction: two SIMD lanes can name the same value.
4. **Evaluate separate MIR operand and header streams.** The current 24-byte
   rows interleave sixteen operand bytes with eight header bytes. Separate
   streams could eliminate the prototype's packing permutation while retaining
   total row payload size. Measure scalar consumers and serialization too;
   widening every row to 32 bytes merely to simplify SIMD would add 33% storage.
5. **Batch only independent lowering work.** Begin with regular fixed-shape
   operations and explicit output ranges. Preserve memory/call order, control
   dependencies, debug positions and relocations; keep rare or dependent forms
   on a scalar path. Reordering instructions by opcode is not a valid general
   transformation.

Any retained cache/SIMD implementation needs the approved 9700X experiment in
addition to local Zen 4 validation, complete-path timing and output checks.
This diagnostic study makes no Zen 5 claim and requests no target-host run
for a locally rejected kernel.
