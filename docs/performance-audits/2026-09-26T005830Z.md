## Disposition

**High-frequency source-level policy resolution confirmed; a performance
benefit is neither confirmed nor falsified. No production specialization is
implemented.** This is a tested, branch-only diagnostic experiment, not a
completed performance change or a claim that fewer source calls imply a win.

The tempting replacement of every target query with the existing TU layout
record is not behavior-preserving by inspection: that record can contain a
caller-provided layout, while the investigated helpers derive their answers
from `Target`. A process-global target record is also ruled out by the actual
cross-target census, which visits both target and host layouts. A correctly
scoped, target-derived immutable record remains a candidate, not a tested
replacement.

## The experiment actually run

`tools/policy_resolution_census.c` temporarily wraps exactly
`target_data_layout(Target)` and `ir_abi_convention_for_target(Target)` in the
hosted checkout. Unique source anchors must match before a write. The original
bodies remain behind direct wrappers; each observation records target CPU/OS
and a result tuple. There is no global cache, callback or shared mutable
counter. The trace goes to a private stderr prefix.

The documented hosted Clang bootstrap exception builds `build.c`. The driver
configures Release with `--cc clang --ci --linker DEFAULT`, builds `ide`, and
freezes the baseline. It then instruments and incrementally rebuilds in the
same configured path, freezes the diagnostic compiler, and restores both
production files **before either compiler reads the workload source**.
Both receive identical input paths, flags, target, output paths, source-metrics
paths and debug contract. The workload source is never the instrumented source.

The complete argv and raw `system()` statuses are in `commands.txt`.
`host-and-source.txt`, both build logs, source snapshots and
`instrumentation.patch` retain provenance. This setup was used for diagnostic
work counts only. It does not meet a complete matched-build performance
receipt and has no timing, RSS, prewarming or cache-effect interpretation.

## Optimized-host falsification

The uninstrumented trusted binary, not the trace build, was inspected with
GNU `objdump` and `nm` offline. This is static binary inspection, not execution
on another host.

In this exact binary:

- `target_data_layout`: address `0x585080`, size `0x28a` (650 bytes).
- `ir_abi_convention_for_target`: address `0x703800`, size `0x3f` (63 bytes).
- `c_parse_builtin_type_layout`: address `0x759250`, size `0x1a1` (417 bytes).

In `c_parse_builtin_type_layout`, target CPU/OS comparisons and selection of
pointer, long, long-double and va-list properties remain before the builtin
kind dispatch at `+0xe6`. The host optimizer therefore has **not eliminated
all target policy decisions in this caller**. It has, however, inlined layout
resolution and eliminated most unused full-record writes. Treating the source
as 4,407,111 materializations of a 280-byte struct would be false.

The census wrappers add observable I/O and can prevent inlining, dead-call
removal and hoisting. Their counts are **source-execution counts**, not the
number of production calls, branch mispredictions, instructions or cache misses.
No dynamic caller attribution was collected. In particular, this experiment
does not establish that `c_parse_builtin_type_layout` accounts for most of the
4,407,111 observations. Its residual code is evidence of a mechanism, not a
whole-compiler cost attribution.

To reproduce the relevant inspection from the raw artifact:

```sh
objdump -d --disassemble=c_parse_builtin_type_layout ide-baseline
objdump -d --disassemble=target_data_layout ide-baseline
objdump -d --disassemble=ir_abi_convention_for_target ide-baseline
nm -S --size-sort ide-baseline
```

## True scope and exclusions

| Decision | Boundary that must be preserved | Current evidence / disposition |
| --- | --- | --- |
| Host capabilities | Executing host and its initialized runtime tables, not requested target ISA | Not measured; no new host cache or prewarming |
| Default target data layout | Explicit `Target`; at this pin the helper reads CPU architecture and OS | High source-call population; candidate selected |
| Caller-provided layout | Accepted `CPreprocessOptions.data_layout`, retained in `CPreprocessDetail` | Not interchangeable with recomputing the target default |
| Default ABI versus effective function ABI | Target default plus explicit calling convention and function/call-site context | Default helper counted; exceptions not specialized |
| Output kind | Validated invocation action and effective object/link job | Inspected driver boundary; no cost claim |
| Language / extensions | Per-input `input_languages`, dialect and frontend's scoped state | Current `-x` snapshot already exists; old #536 premise rejected |
| Debug policy | Requested debug contract and backend/output job | Tiny `-g0` and `-g` controls run; no debug work removed |
| Compilation mode | Effective per-job/backend choice, with existing per-function exceptions | No lane, allocator, validation or fallback change |
| Packing and alignment | Declaration/type attributes, pragma state and actual aggregate members | Must remain outside target-only primitive facts |

The complete source archive exposes the important caller family omitted by the
initial code-search excerpts:

- `c_parse_builtin_type_layout`, used by primitive layout, type promotion,
  arithmetic common-type and semantic validation paths;
- `c_ir_scalar_type_properties`, used by scalar lowering, literal fit,
  enum/typed-constant checks and conditional character handling;
- target-wide floating-representation queries in `c_gen.c`.

`CPreprocessDetail` already owns a layout; it lives with the TU arena, while
`CPreprocessResult` is copied through many hot call chains. Enlarging that
by-value result would undo an existing representation improvement. Null
`detail` is supported for hand-built evaluator inputs. Copies can also retain
a detail pointer while changing the target. Any target-derived record would
need an explicit owner/key or an API contract that excludes these states.
A fallback must preserve the existing diagnostics and exact target semantics.

A valid supplied layout may differ from `target_data_layout(options.target)`;
`c_preprocess` accepts it after structural validity checks. Meanwhile the
primitive helper signatures accept `Target`, not that supplied layout. Simply
passing `detail->data_layout` into those helpers could change current behavior.
This is a source-derived obstacle to that specific shortcut, **not an executed
custom-layout regression or a new correctness issue**.

## Costs, missing experiments, and next acceptance boundary

No immutable-record replacement or specialized consumer has been built.
Consequently **zero repeated policy decisions have been removed from the
production compiler by this PR**. There is no candidate footprint/RSS/setup
number to report. The trace build's size difference is instrumentation overhead,
not the cost of a proposed specialization.

Whole-compiler wall time, requested-artifact latency, peak RSS, generated-code
size/runtime regressions, prewarming, extra memory traffic and instruction-cache
effects: **UNMEASURED**. No desktop benchmark, ad-hoc SSH, protected runner
execution, lease request, deployment or performance-policy change occurred.

Same-process contrasting compilations, explicit per-function ABI exceptions,
custom-layout/null-detail fallback tests, full `test_all`, the registered
`test_self_host` gate, sanitizers and supported-host/platform matrix:
**NOT RUN** by this experiment. Separate CLI invocations do not satisfy the
same-process requirement. A direct fixed-point byte check is not the complete
registered gate.

The next discriminating experiment is caller-level attribution of this same
family, followed by one target-derived primitive record at a proven TU or
function boundary, if that attribution justifies it. Preserve custom-layout
behavior rather than opportunistically unifying it. Required counterexamples
are Linux -> Windows -> Linux and AArch64 -> x86-64 -> AArch64 in one process,
null/retargeted detail, pragma/attribute layout, a mixed default/explicit ABI
input, and a tiny compilation. Match baseline and candidate artifacts and
failure/diagnostic bytes before any performance conclusion. A record whose
setup or loads outweigh the eliminated work must be rejected.

Only approved, exclusively leased 9700X whole-compiler comparisons under the
existing ordinary measurement policy could establish a performance result.
No service/admission work is part of this research continuation.
