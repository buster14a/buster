## Inside the compile

These figures come from Clang's `-ftime-trace` with granularity 2000 µs, on the
same command. The trace is diagnostic only, and the nested totals below are not
additive.

| Clang phase | Seconds |
|---|---:|
| `ExecuteCompiler` | 256.7 |
| `Frontend`: preprocess, parse, IR generation | 13.0 |
| `Optimizer`: the `-O3` middle end | 113.1 |
| `CodeGenPasses`: x86 code generation | 130.6 |

- **Middle end.** The CGSCC inliner pipeline dominates it, at 78.4 s.
- **No dominant function.** The most expensive function to optimize,
  `c_lower_to_ir_reserved_run`, takes 8.6 s, which is 6.9 % of `OptFunction`.
  The next ones are:
  - `c_parse_validate_lowering_constraints`, 5.4 s;
  - `machine_encode_x86_64_into`, 4.0 s;
  - `c_preprocess_run`, 2.8 s;
  - `machine_encode_aarch64_into`, 2.5 s.

  2,352 functions exceed the 2 ms trace granularity, so optimizer time is
  spread across the compiler. No single source construct could be rewritten to remove a
  material share.
- **Code generation.** The largest recorded passes are:
  - `Live DEBUG_VALUE analysis`, 21.0 s;
  - `X86 DAG->DAG Instruction Selection`, 19.9 s;
  - `Greedy Register Allocator`, 9.3 s;
  - `Assignment Tracking Analysis`, 9.2 s;
  - `CodeGen Prepare`, 8.3 s.

## Debug-information variants

Three compiles ran concurrently on the 4 vCPUs. They contend with each other,
so compare them with each other only.

| Variant | Wall | User | Peak RSS | `.text` sha256 |
|---|---:|---:|---:|---|
| Release flags as built | 252.8 s | 242.3 s | 2.10 GB | `a5d71c0195f0d47c…` |
| plus `-Xclang -fexperimental-assignment-tracking=disabled` | 240.0 s | 230.9 s | 1.94 GB | `a5d71c0195f0d47c…` |
| `-g0` | 181.0 s | 176.4 s | 0.76 GB | `e4d8cc4a130e812e…` |

- **Disabling assignment tracking** keeps the object's `.text` byte-identical
  and saves about 4.7 % of user time.
  - It changes only the variable-location debug information of the production
    Release profile, and it is a Clang-specific `-Xclang` switch.
  - The issue forbids dropping debug flags, and a different production profile
    needs its own qualification route. This census therefore records the
    effect and does not adopt it.
- **`-g0` changes `.text`.** Debug information is not a pure side table for
  this build, so removing it would change the benchmark subject. It is
  inadmissible regardless of its 27 % saving.

## Conclusion

- **Necessary work.** Each of the two builds is one Clang `-O3 -g` compile of
  the unity TU. That is 98.9 % of the build's wall time, on a single core.
- **No repeatable waste.** The census found no repeated tool probe, no
  regeneration of byte-identical inputs and no repeated wrapper or driver start
  inside a build that costs a material share. Configure, generation and
  driver reuse together cost about 1 %.
- **No narrow repair.** No safe material repair exists that leaves the
  measured binaries and the Release profile unchanged.
- **Projection to the 9700X run.** #3911 reports two builds of about 72 s in an
  852 s run. If the shares above carry over, about 71 s of each build is this
  single compile, and about 15 of the host's 16 hardware threads sit idle
  while it runs. This projection is unverified on the 9700X.

The material opportunity that preserves the binaries is to overlap the two
independent baseline and candidate compiles. That would save up to one compile,
about 72 s or 8.5 % of that run, at the cost of a second working tree.

That change is not narrow:
- `compiler_owned_plan._commands` and `validate_plan` freeze a single
  `candidate_root` that both builds check out in turn.
- The baseline closure snapshot (#3211/#3906) is taken from that root
  between the two builds.
- Two concurrent 2.1 GB compiles must also stay clear of quiet measurement.

It therefore needs a separate bounded design and actual 9700X evidence, and is
left to that follow-up rather than bundled here.
