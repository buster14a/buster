`2026-10-15T081323Z` (Linux x86_64, Ryzen 9 7940HS; **Narrow constant fold
preparation with qualified work reduction for issue 4241**).

The x86-64 selector now collects CAST/INDEX row IDs during its existing fact
walk and retires folded reads after branch fusion. Two full instruction
walks and the zeroed value-wide folded-read table are removed. Selected MIR
and generated artifacts retain their identities. The measured claim is
**work reduction**: the frozen native unity compile retires 0.2763% fewer
user instructions in FAST and 0.2200% fewer in QUALITY. Elapsed-time and
Zen 5 benefits are not claimed.

## Candidate and bounded storage

Owning [issue #4241](https://github.com/buster14a/buster/issues/4241).
Baseline/current main at measurement:
`614353c082fe8fbc5fdaaa57e67d3fd5b106b4dd`; implementation:
`10926eb25978874c5f8d93f5474a72b60200eb61`.
The implementation commit includes the final independent lifetime fixture.
The frozen tests-off candidate was built before test-only fixture corrections;
its production source blob is identical to that implementation commit:
`e8d14cd438d9f6c8413e0192b39da13fc1d981a5`.

The existing `MachineX64CandidateRow` allocation has one entry per canonical
instruction. Alias/fusion rows occupy its prefix; CAST/INDEX rows use its
tail. Their opcode sets are disjoint, so the two populations cannot exceed
the number of visited rows. Only the tail entry's row ID is written/read.
The old marking order is preserved by consuming those tail IDs in producer
order. No new allocation, wider row or all-result projection is introduced.

Branch fusion is the last consumer of original `MachineX64ValueUse.use_count`.
Each recognized folded read then decrements its existing count; zero marks
the source `fused_dead`. Ordinary uses and CFG arguments remain counted.
The recognizers, virtual-register classification, aliasing, fusion,
compaction and emission policies remain unchanged. This is separate from
closed #132's rejected all-result classification projection and from
#4242/#4243/#4244/#4233.

The baseline production census contains 1,558,648 canonical rows, 118,007
CAST rows and 43,365 INDEX rows. Its two full prepasses visit 3,117,296 rows
and clear 5,191,548 logical bytes. On that same population, the new bounded
algorithm records and visits 161,372 candidate IDs and allocates/clears no
folded-read table. Candidate collection is included in the measured whole
compiler counts below. These operation counts follow from the retained
opcode census and the new loop bounds, rather than a second instrumented
candidate campaign.

Warm selector replay retains 6,550 functions, 1,692,109 IR rows and 2,215,078
MIR rows in both arms. Cumulative function scratch decreases from
1,109,950,312 to 1,104,219,432 bytes; the maximum single-function allocation
decreases from 4,315,424 to 4,250,480 bytes. Those are arena counters, not
RSS or heap allocation counts. The warm replay's population differs from
ordinary compilation because it omits ordinary canonical cleanup.

## Predeclared work screen and measurements

The issue claim declared at least 0.1% repeatable retired-user-instruction
reduction on the frozen native unity compile, no material instruction-count
regression on small/large and zero-hit/all-hit controls at the same 0.1%
screen, lower explicit work including candidate production, and identical
output. Failed/neutral attempts are retained.

Both trusted compilers were built serially in the same owned
`build/profile` path with Clang 23.1.1, tests disabled, Release `-O3`,
`-march=native`, debug information and frame pointers enabled, no LTO/PGO.
Measurements use native x86-64 code on Ryzen 9 7940HS, logical CPU 2.
The existing `tools/performance_evidence.c` compares alternating arms with
`--claim work-reduction --tool perf-stat --events instructions:u
--min-effect-percent 0.1`. All required counters are available and

discarded warmup pair.
