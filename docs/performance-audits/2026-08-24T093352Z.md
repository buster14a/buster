`2026-08-24T093352Z` (Linux x86_64, Zen 4 7940HS; **an absent array bound is
not a variable-length array either — main's argv and envp lose their layout,
and a null control puts a number on the build-shift floor that hid two
sites**).

A follow-up to `2026-08-24T085746Z`, which stopped the array-parameter layout
running for a **constant** bound and left the **absent** one as its second open
lead. This entry takes that lead and, in doing so, measures the thing that
makes a two-site population hard to audit at all: the build-shift floor.

**Budgets before** (clang Release `ide`, unity stage-1 compile, `main` at
`c39adbe6`, which is PR 551): 9.643.713.499 / 9.643.740.946 instructions — the
counter is bimodal on this host, see below — and 1.762.599.757 branches.

**The finding.** The parameter loop in `c_lower_to_ir` (the previous audit
calls it `c_ir_generate`; no function of that name is in the tree) now has two
escapes from `c_ir_prepare_vla_layout` — `fixed_inner_array` and the mapped C
type that audit added — and neither sees `unsigned char slots[]`. An absent
bound has no constant to detect, so a `[]` parameter still takes the layout,
and what it gets there is nearly nothing: in `c_ir_lower_vla_layout_step` the
absent bound hits the `if (!bound.token_count || bound.is_star)` arm, which for
`state->parameter && dimension == 0` just advances the dimension and leaves
`dimension_counts[0]` invalid. `suffix_sizes[0]` is then invalid too, so the
one thing emitted is the CONSTANT element size in `suffix_sizes[1]`. The rest
of the cost is the dispatch-machine round trip, the
`arena_allocate(builder->scratch_arena, CArrayBound, capacity)` sized at
`builder->parse.type_count`, the two arena arrays, and — because the local is
left flagged `is_vla_parameter` — every later subscript of the parameter going
through `c_ir_lower_vla_index_place_step` instead of the ordinary place path.

The escape is a third test beside the other two: an outermost bound that is
absent or `[*]`, over one dimension only, with a mapped element type. The
parameter is a pointer either way and every consumer reaches the same answer
through `local->type` — `sizeof slots` is the pointer's (which the `sizeof` arm
already refused to answer from `vla_suffix_sizes[0]` for an `is_vla_parameter`
local), `sizeof slots[0]` is the pointer's element's, and `slots[i]` lowers as
ordinary pointer indexing. One dimension is the whole of the care:
`u8 a[][n]` genuinely needs `suffix_sizes[1]` as its row stride and must keep
its layout, while `u8 a[][3]` is a pointer to a mapped array and already took
`fixed_inner_array`.

**The population, from a probe at the decision site.** The self-host unit's 17
array-syntax parameters split 15 constant-bound (already skipped) and **2
absent**, and the two are `argv` and `envp` on `main` in
`src/buster/lib/entry_point.c`. Neither is already mapped in `c_type_ir_map`,
which was worth checking — a shared C type could have been mapped through a
flexible array member or an inferred bound elsewhere in the unit, in which case
the previous audit's test would have caught them already and this one would
have had nothing to do. Neither is subscripted: on Linux `main` only casts them
to `StringOsList`.

**The isolated cost.** 1.000 functions per file, compiled by both binaries.
Two shapes, because the flag costs something per *use* as well as per
parameter:

    declaration only (main's shape)   665.989.593 -> 660.646.651   -5.342.942
      same file spelled `unsigned char* s`             control        -1.329
    declaration plus one `s[0]`       645.534.624 -> 635.061.104  -10.473.520
      same file spelled `unsigned char* s`             control        +6.645

So **5.343 instructions per `[]` parameter** and a further **5.131 per
subscript of one**, with the pointer-spelled control flat at well under a
thousandth of the signal in both files. 843 branches per parameter. Two
unsubscripted sites therefore predict **-10,7 K instructions** and **-1,7 K
branches** on the self-host unit: **0,00011%**. The same measurement on
`ba03ccd4`, before PR 551, gave 5.349 and 10.472 — PR 551 stops
`suffix_sizes[0]` being emitted for parameters that keep a layout, and an
absent bound never had one, so the two changes do not touch each other's cost.

**The aggregate cannot see it, and its sign is not even stable.** The audit
protocol is order-alternated CPU-pinned pairs over one frozen tree, both
binaries writing the same `-o`. Run against `ba03ccd4` it read **-334.070
instructions, 22/22, bands disjoint**. Run against `c39adbe6` one commit later,
the *same change* read **+438.163, 0/12, bands disjoint**. Both readings pass
every criterion an aggregate result is normally judged by — unanimous sign,
non-overlapping bands, reproducible — and they disagree in sign about a
mechanism that is worth -10,7 K either way.

A null control says the same thing without needing two bases. `ide-N` carries
this change's code in full plus one conjunct that is never true —
`&& parameter.type.value == IR_ID_UNDERLYING_INVALID` — so the escape can never
fire. It is behaviourally identical to the baseline: compiling
`tests/basic_c_vla.c` with it produces a **byte-identical object**. On
`ba03ccd4`, twelve pairs each:

    baseline -> null control   +317.947  (+0,00330%)   0/12   bands disjoint
    null control -> change     -652.016  (-0,00676%)  12/12   bands disjoint
    baseline -> change         -334.070  (-0,00346%)  22/22   bands disjoint

A source edit that provably changes no behaviour moves the stage-1 instruction
count by **+318 K**, thirty times the mechanism's prediction, unanimously and
with disjoint bands. That is the floor for a one-line edit inside
`c_lower_to_ir` in a 300 K-line unity translation unit: clang re-optimizes the
whole thing and the retired-instruction count of unrelated hot code moves with
it. Retired instructions are architectural, so this is not sampling noise and
more pairs will not average it away — which is exactly what makes it dangerous.
Disjoint bands and a 22/22 sign say a difference is reproducible between
*those two binaries*; they say nothing about which line caused it.

**No aggregate number is claimed for this change.** The isolated per-site
figure is the only measurement of the mechanism here, and by it the change is
worth 10,7 K instructions.

It is not the bimodality either, which `2026-08-24T092849Z` found on this host
independently and which every sample here shows: each binary's counts fall into
clusters about **27,3 K** apart, and a mean that mixes them invents a delta of
that size. Matching mode to mode leaves the reading unchanged, which is what
rules it out — the shifts are twelve times the gap:

    binary        low mode           high mode          gap
    baseline      9.643.665.886      9.643.693.200      27.314
    null control  9.643.983.959      9.644.011.020      27.061
    change        9.643.331.819      9.643.359.129      27.310

    mode-matched  baseline -> null control   +318.073   +317.820
                  baseline -> change         -334.067   -334.072

The floor is worth carrying forward. `2026-08-24T085746Z`'s 15 sites predicted
-137 K and its aggregate read -148 K, agreeing to 8%. That agreement is better
than a +-318 K floor entitles it to; read it as fortunate rather than as
evidence that the aggregate resolves a 137 K signal. The conclusion there
rested on its isolated measurement, which is the right way round. Below roughly
half a million instructions, measure the mechanism, count the sites, and do not
read the aggregate at all.

**The generated code.** Under `-fregister-allocator=none` a `[]` parameter now
emits *exactly* what the pointer spelling emits: 24 rows to 21, and the
disassembly of a `take_unspecified(unsigned char s[])` is identical to
`take_pointer(unsigned char* s)` line for line, with 16 bytes less frame. The
neighbouring shapes are untouched, PR 551's included — `take_vla` stays at the
30 rows that commit brought it down to, and `take_constant` and
`take_unspecified_two` do not move. In `tests/basic_c_vla.c` that is
`check_constant_bound_parameter`'s frame going `0x550` to `0x540` and losing
the dead `movabs $0x1` that was `open[]`'s element size, which is the proof the
fixture reaches the changed path; it is the only function in that file whose
instruction stream moves at all, PR 551's `check_one_dimensional_parameter`
included. Under
the default FAST allocator and under QUALITY the row count does not move at
all — the difference is a register-materialization shuffle and less trailing
padding — so this is a compile-time change and not an artifact-quality one.

**Verification**, all of it re-run on `c39adbe6` after PR 551 landed under this
branch. `SELF_HOST deterministic bytes=35068608` — stage 1 and stage 2
byte-identical. Unit tests 309.683/309.683. `test_all_combinations_ci` green
(exit 0), `clang --analyze` clean. `tests/basic_c_vla.c` gains the `[]` and
`[][3]` parameters beside the existing constant-bound ones, and a
`check_unspecified_bound_over_vla` for `cells[][columns]` — the shape the
one-dimension clause must *not* reach. That clause holding is exactly what the
fixture shows: `check_constant_bound_parameter` is the only function in the
file whose instruction stream moves at all, and `check_parameter`,
`check_unspecified_bound_over_vla` and PR 551's
`check_one_dimensional_parameter` all come out identical.

A throwaway differential over eight shapes — `u8 a[]`, `char* argv[]`,
`u8 a[][3]`, `u8 a[][n]`, `u8 a[n]`, `u8 a[2]`, `u8 a[const]`, and a struct
element — agrees with clang exactly in all three allocator modes both before
and after, and both fixtures still cross-compile to Win64, aarch64-linux and
aarch64-macos objects.

**The other lead was taken concurrently, and the two do not overlap.**
`2026-08-24T092849Z` / PR 551 took the first lead — a parameter's outermost
product is dead in *every* case, so the dimension walk now stops at index 1
when `state->parameter`. For an absent bound `suffix_sizes[0]` was already
invalid, so that change and this one neither help nor hinder each other: PR 551
stops suffix 0 being emitted for the parameters that keep a layout, and this one
stops two parameters having a layout at all. They touch different functions,
this branch is rebased on top of PR 551, and every gate above was re-run there.
The `ba03ccd4` numbers are kept only where they are labelled as such, because
the null control and the sign reversal are both statements about that base.

What that entry lists as still open after both: a parameter emits its element
size even when no `sizeof a[0]` reads it — a dead-value question rather than a
layout one — and it names two pre-existing bugs its differential found in
parameter bounds, a call inside one and a global read from one. This change
closes the element-size emission for `[]` parameters, since they no longer take
a layout at all; the `[n]` shapes still emit it.
