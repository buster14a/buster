`2026-10-04T111831Z` (Linux x86_64, Zen 4 Ryzen 9 7940HS desktop, diagnostic
only; **minimum-work model of the C pipeline at 94976ecc: per-stage lower
bounds against Buster's passes, traversals and memory; ranked removable work;
a provisional-SSA-parameter census says the SSA finish pool is mostly inherent
to the deferred design**).

## Decision

No production change. This audit derives a per-stage model of the minimum work
a compiler of Buster's feature set must do for its supported C programs,
measures what Buster does at `94976eccad9c31776cf264a33dcda960dd8ed51a`
against it, ranks the removable work with Amdahl-adjusted estimates, and runs
one decisive census experiment on the second-largest pool (the IR that is
built and then rewritten). The semantic half of the largest pool was measured
the same day by #2607 / #2606; this audit does not repeat that probe.

Three results carry the ranking:

1. **The stage-1 self-compile retires 21.51 G instructions for 3.76 M
   preprocessed tokens (5,720 per token, 637 per lexed byte).** A per-stage
   lower bound for the same feature set sums to about 0.6 G; a one-pass
   compiler without DWARF or a verifier (TinyCC 0.9.28rc) spends 750 per
   token on the pinned SQLite amalgamation. The genuine headroom is therefore
   about 4-5x of design, not the 30x the information-theoretic floor suggests.
2. **Each function body is typed three times and each IR row is visited about
   eleven times.** Bodies are walked by binding, by the lowering-constraint
   validator (19.3% of cycles; 1.06x the whole token stream re-walked by
   uncached type queries) and by lowering; IR rows pass through construction,
   SSA finish (4.17 M value-row remaps), promotion, three FAST passes,
   compaction, validation, CFG publication and selection.
3. **The decisive census says the SSA finish pool is mostly inherent to the
   deferred-placeholder design, not to eager creation.** Of 500,552
   provisional block parameters (93% later removed), 71% are created by the
   finish-time resolution walk itself; only 24% are created in blocks that
   were already sealable when the read ran. Sealing at construction cannot
   remove the 6.6% `c_ir_ssa_finish` pool; removing it needs use lists or
   deferred patch lists so trivial parameters never materialize.

The fsync of every published artifact (7-8 ms per object on this btrfs home)
is the cheapest finding: 0.4% of the self-compile but 27% of a per-file Lua
compile. It is a durability choice, not compilation work.

## The workload, in expanded units

Costs scale with what the frontend reads and expands, not with source bytes.
The stage-1 self-compile (W1) is 33.76 MB in 400 lexes of 364 files (include
amplification 54 KB), 3,384,362 lexed tokens, **3,762,000 tokens to the parser**
(111% of lexed), 26.5 MB of token spelling (37.0 MB retained), 141,694 macro
expansions and 3,925 `#define`s. 39% of its code bytes are literals (13.2 MB,
generated metadata tables), and initializer walks visit 2.6 M tokens, 69% of
the stream: W1 is literal-heavy. It lowers 5,657 functions (2.08 M body
tokens) to 1,627,306 IR rows and 1,400,665 values before FAST (1,425,857 and
1,199,216 after), selects 1,971,400 machine rows, encodes 1,824,010
instructions into 16,096,400 code bytes, and links a 41,270,216-byte image.
Of the encoded instructions, 676,480 (37%) are allocator edits: 222,559
spills, 203,606 reloads, 195,322 copies, 54,993 rematerializations.

SQLite `sqlite3.c -g0`: 708 K preprocessed tokens, 4.05 G instructions,
0.44 s, 259 MB peak; `-g` 4.40 G, 306 MB. Lua 5.4.8 per file: 33 processes,
559 K preprocessed and 1.47 M lexed tokens in total.

Three columns are kept apart. *Lower bound* is work any correct compiler of
this feature set (C17/GNU, full diagnostics, canonical IR validated before the
backend, DWARF, deterministic output) must do, counted in units it cannot
avoid: bytes classified, tokens produced, rows written, decisions made. The
instruction figures beside them are rough prices of those units (10-50
instructions per unit, stated per row) and are estimates, not measurements.
*Buster* is the measured cost: inclusive cycle share of the phase root on W1
times 21.51 G, so each row carries the phase's IPC error (about ±20%).
*Hardware* is the speculative time of the bound on this machine. Shares are in
[`self-host.perf-children.txt`](evidence/2026-10-04T111831Z/self-host.perf-children.txt).

Two calibrations bound what the design, as opposed to the arithmetic, can
reach. TinyCC compiles `sqlite3.c` in 532 M instructions (750 per token,
57 ms, 13 MB) with no SSA, no verifier and stabs; Buster takes 4.05 G
(5,720 per token, 0.44 s, 259 MB), Clang 23 `-O0` 0.67 s. Scaling TinyCC's
per-token cost to W1 gives about 2.8 G instructions, and adding a verifier
and DWARF realistically 4-5 G: **the achievable design floor is about 4-5x
below today, the arithmetic floor about 30x.** Generated code sizes are
2,039,847 / 1,377,406 / 1,113,473 `.text` bytes for Buster / TinyCC / Clang
`-O0` on `sqlite3.o`, so Buster's backend also processes 1.5-1.8x the rows a
one-pass design would.

## Cold start, warm cache, and reusable state

- **Process floor.** `ide help` 0.8 ms (0.79 M instructions);
  `cc -fsyntax-only empty.c` 2.9 ms (1.35 M); `cc -c empty.c` 15.3 ms and
  65.96 M instructions (2.6 ms user, 6.8 ms sys): the x86-64 table prewarm
  (#1295, #1125) plus arena reservation and first touch. Writing the object
  adds the publish `fsync` (below). Per Lua file the floor is 20 of 25.6 ms:
  prewarm ~6.5, sys ~6, fsync+exec ~8. TinyCC compiles `lapi.c` in 5.6 ms
  total.
- **Durability.** `file_publish_slices_checked` fsyncs every staging file
  before its rename (`file.c`, `os_file_flush`). On this btrfs home that is
  7-8 ms per object: `lapi.c` 29-33 ms to btrfs against 22 ms to tmpfs; the
  33-file Lua build 846 ms serial to btrfs against 611 ms to tmpfs. `os.h`
  states "ordinary artifact writes promise completion, not crash durability",
  so the flush contradicts the documented promise. Neither Clang nor GCC
  fsync objects.
- **Warm page cache.** Evicting the 368 opened files plus the compiler and
  its libraries (115 MB) raised W1 from 2,203 to 2,227-2,237 ms (364 major
  faults, 24 MB read back): cold I/O is at most ~1.5% of a large unit on
  NVMe here. 3,645 failed `openat` probes resolve 400 includes (579 per Lua
  file), worth ~0.3% of W1 and 2-3% of a small file.
- **Explicitly reusable state.** (a) The x86 tables are content-independent
  (65 M instructions per process). (b) Header state: the 20-header glibc
  preamble costs 56.5 M instructions to preprocess and 87.5 M to analyze, and
  the Lua build lexes 2.6x the tokens it hands to the parser because every
  process re-reads the shared headers; W1 has no comparable header share
  (364 project files, 54 KB re-read). (c) Function-granular reuse across
  edits is #1470's subject and was not measured. One process compiling the
  33 Lua inputs takes 554-606 ms against 846 ms for 33 processes; 33
  processes eight at a time take 200 ms, `-fcompile-jobs=8` 165 ms with
  689 MB.
- **Kernel time.** W1 spends 68-86 ms (4%) in the kernel with THP active,
  essentially zero-filling the 1.07 GB it touches; the hosted run of this
  revision without THP (run 37194571306, #2606) took 304,021 four-KiB minor
  faults, about 1.19 GB first-touched for a 34 MB input.

## The decisive experiment: are provisional SSA parameters avoidable at construction?

**Uncertainty chosen.** Item 3's largest member is `c_ir_ssa_finish`
(6.6% of W1 cycles, 1.42 G instructions): the body lowering creates a
provisional block parameter at every read of a local whose value is unknown
in the current block, because predecessor lists do not exist until the
function is complete (`c_ir_ssa_current`, `c_ir_ssa_parameter`); finish then
builds predecessors, resolves, simplifies and remaps. If most of the 500,552
creations happen in blocks that were already sealable when the read ran (all
final predecessors' terminators already emitted), tracking predecessors
during construction and forwarding eagerly would remove most of the pool. If
most are created by the resolution walk itself, the pool is inherent to the
algorithm and only a different fix-up mechanism removes it.

**Method.** The census binary records, per provisional parameter, the
function's instruction count at creation (or "created by finish"), and at
the end of simplification classifies it by: created during construction or
finish; local fell back to memory; zero predecessors; whether every final
predecessor's terminator row id is below the creation count ("sealed");
predecessor count 1 or ≥2; removed or kept. The probe reads state only; its
outputs are byte-identical to the timed subject. Lines are in
[`measurements.txt`](evidence/2026-10-04T111831Z/measurements.txt).

| Workload | Created | By finish walk | By construction | …in sealed single-pred block (removed) | …in sealed merge, removed / kept | …unsealed merge, removed / kept | memory-owned | preds 0 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| self-host | 500,552 | 353,727 (70.7%) | 146,825 (29.3%) | 107,312 | 14,700 / 9,826 | 3,019 / 5,191 | 6,777 | 617 |
| `sqlite3.c` | 80,580 | 35,604 (44.2%) | 44,976 (55.8%) | 27,558 | 7,068 / 1,566 | 739 / 1,290 | 6,754 | 706 |
| `lvm.c` | 691 | 165 | 526 | 385 | 66 / 31 | 4 / 5 | 34 | 2 |

**Verdict.** On W1, 71% of all provisional parameters are created by the
finish walk propagating unresolved reads through merge blocks (Braun-style
intermediate phis, created then found trivial); the predecessor-tracking
intervention cannot touch them. Of the 29% created during construction, 73%
sit in already-sealable single-predecessor blocks and 10% are trivial merges,
so eager forwarding would avoid 122,012 creations (24% of the total) and
their incoming rows, but not the remap: read placeholders (183,509) still
need replacement, and without use lists any replacement is a whole-function
renumbering. SQLite shifts the split (56% construction-created, 77% of those
eagerly avoidable) but reaches the same conclusion. **Sealing at construction
is not the lever for item 3; the lever is a fix-up mechanism that never
materializes trivial parameters and read placeholders as value rows** (use
lists on parameters, or deferred operand patch lists resolved at seal time),
which is a design change of the SSA builder, not a pass cut. #1321's dominated-
definition shortcut remains valid for its slice. This is a no-go for the
narrow intervention and a redirect, not a measurement of any speedup. The
census is recorded on [#1321](https://github.com/buster14a/buster/issues/1321#issuecomment-5979417415).

## Limits

- Phase shares are sampled cycles with frame-pointer unwinding on one
  binary; instruction figures per phase are shares times the exact total
  and inherit the phase's IPC error. Lower-bound prices are stated
  assumptions, not measurements.
- The desktop was shared with two concurrent compiler builds; the quiet
  W1 figure (2.06 s) and the contended one (2.35 s) are both reported.
- The hosted fault attribution is the prior session's ledger of this
  revision (#2606), not a run made here.
- No sanitizer, self-host fixed-point, mode-matrix or harness gate ran; the
  only source change is the diagnostic probe in a private worktree, never
  in the primary checkout or a branch.
