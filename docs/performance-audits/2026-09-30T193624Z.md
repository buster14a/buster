# Issue #59: current run population and two batch controls

## Decision and source boundary

**Reject the tested SIMD encoding prototypes; retain the existing scalar
emitter.** A current-source census found long runs for two displacement-patched
frame forms, so a bounded SIMD experiment was warranted. Both SIMD candidates
produced byte-identical complete objects, but neither demonstrated an
end-to-end improvement. On the measured Zen 4 host, each increased retired
instructions and compiler `.text` size. Direct scalar batching was at least
as good on instruction count, and neither scalar control demonstrated a wall
improvement. The A/A wall spread makes a sub-percent speed claim untenable.
This is a no-go for this measured experiment, not a claim that every future
x86 encoding design is impossible.

Source anchor: main `a947bc1d0e0050e516743b9a51253645dd805345`, tree
`ee577bb2cbfa7a3fbac0a8fd5c5db311a91ca218`. Only the temporary
patches in [`tools/research/x86_encode_runs`](../../tools/research/x86_encode_runs/)
and this audit/evidence are proposed for publication. No production encoder,
MIR layout, dispatch, default, build gate, or generated identity changes.
The compiled input was restored to this exact source before every diagnostic
and paired run. `git status` was clean apart from the research files.

Issue [#59](https://github.com/buster14a/buster/issues/59) owns the batching
question. [#124](https://github.com/buster14a/buster/issues/124) owns

encoder path, not that portfolio audit. The prior arbitrary-row gather and

## Method and evidence

The trusted host build was Clang 22.1.8, Release, `-march=native`, on an AMD
Ryzen 9 7940HS (Zen 4). Linux `perf stat` recorded user-mode cycles and retired
instructions. The host was shared with other active builds, with no dedicated
9700X, isolation receipt, governor pin, or trustworthy wall-time acceptance
envelope. A/A, source/path matching, alternating order, complete object hashes,
and raw PMU rows are therefore kept separate from any speedup claim.

Before instrumentation, `./build.sh generate --cc clang` and
`./build.sh test_self_host --config Release` passed; the fixed point reported
47,050,232 byte-identical stage executables. A temporary diagnostic was then
built in the same tree. Its binary SHA-256 was
`6c45ed646d6369aa00bb84738295bb4012c35a80bff5b721eeb5fc37b0390897`.
The diagnostic source was restored without rebuilding the copied binary; it
compiled the unchanged unity source with the command in the [research README](../../tools/research/x86_encode_runs/README.md).
The strict native compile succeeded with 5,410 verified MIR functions and zero
machine fallback. A preliminary `-march=baseline` strict invocation stopped at
the existing `xgetbv` inline-assembly feature boundary; it is excluded from
the census. The first narrow diagnostic also excluded a row immediately after
an edit; that boundary was corrected before the retained run and no initial
counts enter this decision.

The corrected diagnostic counts actual completed x86 machine functions after
placement. It saw **1,886,793 machine rows** and 423,016 before-edit sites.
The broad same-opcode count is an upper bound for SIMD: it requires one valid
exact variant, one emitted instruction of 1–15 bytes, no new call/fixup, and
no edit or block boundary inside a run. It does not assert equal register or
displacement bytes. The narrower ready GPR-table count requires two register
operands and excludes dynamic patch fields. Block boundaries and before/after
edit runs close both classes;
a row after a before-edit can start a new run.

The register ALU rows have no four-row same-form runs in the retained data;
the only narrow four-plus populations are `MOV32_RR` (176 rows) and
`MOVZX8_RR` (4 rows). The frame-store and frame-push populations are the two
distinct high-volume shapes that clear the issue's first gate. Other form
counts and every per-function histogram are in the raw diagnostic and JSON
summaries. The exact emitted object SHA-256 in all experiments was
`48e9414ef423dbb597e3fb2f8124378f9f4acaa2e04f35df64bf63cfa3458675`.

The two prototypes each take at most 32 consecutive rows within one block,
after confirming the prewarmed exact table, fixed byte length, stack-slot and
register bounds, no placement edit, and output capacity. `STORE_FRAME64` is
seven bytes with a register-selected prepared prefix and a disp32 patch;
`PUSH_FRAME` is six bytes with a fixed prepared prefix and a disp32 patch.
Temporary arrays hold row displacements and prepared encoding pointers. The
AVX-512/VBMI2 arms fill private eight-byte records, load eight records, and
`vpcompressb` exactly the seven or six owned bytes per record into output.
Non-multiple tails use exact scalar copies. The direct scalar controls bypass
scratch and patch final bytes in source order. All preserve row offsets,
before-edit positions, exact counters, and existing scalar fallback.
The compiled host `machine_encode_x86_64_into` contains `vpcompressb` in both
SIMD builds. All 170 A/B and A/A compiles (five families × 34 runs, including
two warm-up pairs per family) succeeded; every full object hash
matched. These are temporary research patches, not a production change.

## Paired complete-object result

All five comparisons used the same restored input and argv, compiled through
`-c` to a complete ELF object, and alternated A/B then B/A for 15 measured
pairs. Baseline host binary SHA-256:
`e7ef590574de827b99a37e76153d236e212d402aa9cf921961d5f2ec4c81676c`.
The no-change A/A control uses that one binary in both arms. The table reports
the median of *within-pair* differences; wall signs use candidate minus
baseline. Instruction deltas were stable across pairs; the wall results were
not. Executable `.text` is from `size` on the compared host binaries.

A/A paired wall differences ranged from −8.34% to +6.10%; its paired
instruction differences ranged from −5,022 to +1,724 around about
19.213 billion baseline instructions. The push SIMD wall estimate falls
inside A/A variation, while its instruction increase is far beyond the
counter's no-change variation. Direct scalar push reduces instructions but
also has no demonstrated wall gain. The store class increases instructions
materially in either batch design. Since the SIMD arms do not meet the
complete-workload improvement gate and add code, none is retained. This does
not assert a statistically proven wall-time regression.

The existing `<buster/lib/simd.h>` has a legal VBMI2 byte-compress store but
no AVX2 byte-compaction operation. An AVX2-only arm was not built: the direct
scalar output control already avoids compaction scratch and has better total
instruction economics than both tested SIMD arms. Adding an AVX2 abstraction
after those no-go results would expand the experiment without an acceptance
path. Zen 5 timing/PMU, sanitized and cross-platform builds, randomized
encoding/relocation tests, mode matrix, and a production self-host test of a
batch candidate were not run because no candidate was admitted. The baseline
self-host gate and byte-identical full-object tests are the gates actually
completed.
