`2026-10-06T112455Z` (Linux x86-64, shared 4-vCPU cloud VM; **Distinct-key GPR
encoding-table prewarm, issue #2017**).

Matched timing of the recovered distinct-key GPR encoding-table preparation
(candidate `e1cd8979`, rebased) for
[issue #2017](https://github.com/buster14a/buster/issues/2017) in
[PR #2759](https://github.com/buster14a/buster/pull/2759).
`machine_x64_exact_prepare_gpr_encoding_table` now queries the metadata
authority once per distinct register key (1, 16 or 256 per table) and replicates
the rows. Before, it queried all 256 keys of every table. The dense table
layout and its consumers are unchanged.

## Controls

- Base: main `3bf9d004`. Candidate: `b2ccfaa5`, which is that base plus this
  one change.
- Both binaries are tests-off Clang 18.1.3 Release `ide` builds made in one
  detached worktree and one build path, with
  `./build.sh generate --cc clang --no-include-tests` and
  `./build.sh build --config Release -t ide`. The driver was bootstrapped with
  pinned TinyCC `0fb54300`. Rebuilding the base after the candidate reproduced
  the base binary byte for byte.
- SHA-256: base `067b6c6a2e62de78f9beeb2c1802f03e0cc1e3dc70c805a9b61867930b466e1b`,
  candidate `f959664a9bd5ecbfaa85d505aadef408816ce175719ef3cccba34826cb71f79b`.
- Host: a shared 4-vCPU cloud VM (`Intel(R) Xeon(R) Processor @ 2.10GHz`),
  not the dedicated Zen 5 host. The VM exposes no hardware counters, so
  instructions, cycles and IPC are unavailable. Timed runs were pinned to
  CPU 2.

## Results

**Per-process floor, which is where prewarm dominates.** Workload:
`ide cc -c tiny.c` on a one-line function
`int f(int a, int b) { return a * b + 3; }`. The run used 400 pairs in
alternating AB/BA order. Each pair ran the binaries in place under
`taskset -c 2`, timed by an ad hoc `perf_counter_ns` loop with a sign-test
95% CI. The objects were byte-identical.

| variant | median | min |
|---|---|---|
| base | 15.450 ms | 13.281 ms |
| candidate | 14.471 ms | 12.597 ms |

Median per-pair B/A is **0.9329**, 95% CI [0.9270, 0.9425]. That is about
1 ms less startup work per process.

**Stage-1 self-compile.** Command:

```sh
python3 tools/uarch_lab.py compare --perf /usr/lib/linux-tools/6.8.0-146-generic/perf \
    --baseline ide-base --candidate ide-cand --repo-root <frozen base worktree> --cpu 2 \
    --output ab-attempt-3 --pairs 50 --require-identical-output --seed 2017
```

The run used fresh binary copies and ABBA order, completed 50 of 50 pairs
with no warnings, and produced deterministic, byte-identical outputs with
14,225,130 code bytes on both sides.

> NO DETECTABLE DIFFERENCE: wall time B/A 0.9906, 95% CI [0.9798, 1.0016]
> includes 1.0 over 50 pairs; any real change is within about +/-2.02%.

The medians are 4.6063 s for the base and 4.5334 s for the candidate. A
saving of about 1 ms is about 0.02% of a stage-1 compile, far below what this
host resolves. The stage-1 run is not evidence for or against the change.

## Reading

The change removes a measurable piece of the fixed per-process prewarm cost
(#1295) without changing any output. It has no measurable effect on a large
translation unit. Repeat it on the dedicated Zen 5 host before using it as a
precise number.
