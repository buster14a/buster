## Decision

No production change. The census looked for a hot loop-carried recurrence
`s[i+1] = F(s[i], item[i])` whose dependency is an artifact of how it is
written and which has a small, exactly composable block summary. It excluded the
already-studied lexer, hash, allocator, bitset and encoder work. Only one
candidate is both warm and has such a summary: the digit loop of
`c_conditional_number`, `parsed = parsed * base + digit`. Its block summary is
the affine map `x -> x * b^k + v`, which composes associatively with constant
size.

The summary is exact, and every tested formulation of it agrees with the
incumbent on all inputs checked. It still loses on the population that
actually reaches it:

- The stage-1 compile makes 2,512,840 calls with 2.33 digits on average.
- 75.1% of calls have at most two digits, and 96.3% fit in one eight-byte
  block.
- Constructing one block summary costs more than the short Horner chain it
  replaces.
- Literals are independent across calls, so the out-of-order core already
  overlaps their chains.

On the recorded call stream, the safe blocked form took 14.9 ns per call
against the incumbent's 8.2–8.4 ns. A blocked form that assumes an 8-byte
over-read, which production spellings do not guarantee, took 6.4–6.6 ns. The
best simple scalar loop took 5.2–5.4 ns. The blocked formulation is therefore
rejected. The incumbent's exact contract gains adversarial regression vectors
so that any later attempt must preserve it.

Removing the recurrence entirely has a hard ceiling: 5,857,749 digit steps at
the measured 4 cycles per step. That is about 23 M cycles, or 0.13% of the
container's 4.36 s stage-1 compile. The realized value was negative.

The canonical-frame recurrence has a constant-size summary as well. With
power-of-two alignments, every step is a member of the family
`F(p, A, q)(x) = align_up(x + p, A) + q`, and that family is closed under
composition:

- if `A2 <= A1`, the composition is `(p1, A1, align_up(q1 + p2, A2) + q2)`;
- otherwise it is `(p1 + align_up(q1 + p2, A1), A2, q2)`.

`alignadd.py` checks all element pairs with `A` in {1,2,4,8,16} and `p, q < 20`
at every `x < 64`, plus 200,000 random triples for associativity: 258,000,000
checks, all passing. The loop still has only ≈3 cycles of carried latency
against a body of 30 Ir per value and 0.14% of the compile, so there is
nothing to win.

## The selected recurrence

**Population (measured).** The census recorded 2,512,840 calls, all of them
valid literals, with 5,857,749 digits in total.

- By base: decimal 2,118,503, hexadecimal 384,321, octal 10,016.
- Digit separators: none.
- Suffix length: 0 bytes in 2,151,827 calls, 1 in 327,679, 2 in 31,970 and 3
  in 1,364.
- Cumulative share by digit count:

  | Digits | 1 | 2 | 3 | 4 | 5 | 6 | 8 | 10 | 16 | 20 |
  |---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
  | Share of calls | 59.1% | 75.1% | 80.8% | 88.0% | 91.6% | 93.6% | 96.3% | 98.8% | 99.9% | 100% |

- Only 92,109 calls, 3.7%, need a second eight-byte block.

The preprocessed translation unit holds 640,181 integer pp-numbers, so each
literal is converted about 3.9 times. Callgrind's caller counts under valgrind
(2,512,636 calls, because valgrind's CPUID hides AVX-512 and the conditional
source differs slightly) break the calls down as follows:

| Caller | Calls |
|---|---:|
| `c_parse_expression_leaf_without_cast` | 1,198,588 |
| `c_parser_validate_integer_token` | 640,176 |
| `c_ir_constant_initializer_fold_integer_leaf` | 520,098 |
| `c_ir_lower_expression_core_step` | 84,180 |
| `c_integer_expression_evaluate_with_features` (`#if`) | 23,299 |
| Others | 46,295 |

**Exact algorithm and validity argument.** For base `b` in {2, 8, 10, 16} and
a digit block `d1..dk`, the summary is `T = (m, v)` with `m = b^k` and
`v = Σ d_i b^(k-i)`. That is the composition of the step maps
`x -> x*b + d_i`, namely `x -> x*m + v`.

- **Composition and identity.** Composing `(m1, v1)` then `(m2, v2)` gives
  `(m1*m2, v1*m2 + v2)`. This is associative because it is function
  composition. The identity `(1, 0)` is the empty block.
- **Ordering.** Composition is not commutative: blocks compose in spelling
  order, most significant first.
- **Overflow.** The incumbent rejects a spelling when any prefix would exceed
  `UINT64_MAX`. Every step is monotone non-decreasing for `b >= 2`: the value
  of a prefix `P` extended by `r` digits `V` is `P*b^r + V >= P`. So some prefix
  overflows if and only if the whole run's exact value is at least `2^64`.
  Overflow is therefore a sticky bit that is decided exactly at each
  composition by a 128-bit product and sum. A digit count alone is not enough,
  because leading zeros are legal: `000…001` has 30 octal digits and the value
  1.
- **Separators.** A separator is the identity element of the value algebra. Its
  validity is a local predicate: a digit has already been accepted, and the
  next byte is a digit of the base.
- **Empty input and suffix.** The "any digit" flag is an OR monoid. Base
  selection and suffix acceptance depend only on the prefix and on the bytes
  after the run, so they are unchanged.
- **Reconstruction.** None is needed. Callers observe only the success bit and
  the final value, so there are no per-item outputs, no extra pass and no
  storage beyond a 4×9 power table.
- **Block construction.** Construction works on eight bytes:
  1. SWAR range tests on `x | 0x80…`, which cannot borrow across bytes, give a
     digit mask and per-byte digit values.
  2. `k = tzcnt(~mask) / 8`.
  3. The `k` digits are left-justified, so the unused bytes act as leading
     zeros.
  4. Three multiply/shift/mask pair reductions with constants `b·2^8+1`,
     `b²·2^16+1` and `b⁴·2^32+1` produce `v`.
  5. `v` is composed into the running value by one 128-bit multiply with `b^k`.

  A separator inside a block falls back to the scalar path. None occurs in the
  census.

**Verification (measured, zero failures).** `harness.c` checks the incumbent
(a verbatim copy), the best simple scalar loop, the safe blocked form and the
over-reading blocked form against each other. It also checks them against an
oracle that is structurally different: it enumerates the valid suffixes,
classifies digits with `memchr` and accumulates in 128 bits.

- **Exhaustive.** 3,368,421 strings of length 0–5 over a 20-symbol alphabet
  that reaches every branch (`0178afgxXbB'uUlLi64` plus space).
- **Byte sweep.** Every byte value, including high-bit bytes, at each of 12
  positions after the prefixes `1`, `0x1`, `0` and `0b1`, in both full and
  truncated spellings.
- **Digit runs.** Runs of 1–70 digits in each base, with four fills and ten
  suffix or separator tails. These cover every eight-byte boundary phase.
- **Extremes.** 27 vectors covering `2^64 ± 1` in each base, leading-zero runs,
  and malformed separators.
- **Random.** 2,000,000 random spellings.
- **Summary algebra.** 12,048,972 composition and three-part associativity
  checks. These are exhaustive up to 10 binary, 5 octal, 4 decimal and 3
  hexadecimal digits at every split, and random up to 69 digits.
- **Census replay.** All 2,512,840 recorded calls reproduce their recorded
  result and value.

## Incumbent, strongest scalar, blocked

All timings below are measured in this container and are **diagnostic only**:
the host is not Zen and not an admitted benchmark host. Each figure is
ns per call over the recorded call stream in call order (4 passes per
sample), through the same indirect call for every variant. The table gives
the minimum of 7 interleaved samples in each of three processes; all raw
samples are in `harness-run{1,2,3}.txt`.

| Variant | Run 1 | Run 2 | Run 3 |
|---|---:|---:|---:|
| Incumbent (`clang -O3 -march=native`) | 8.191 | 8.284 | 8.429 |
| Strongest simple scalar (table digit, constant cutoffs, check-free below the safe length) | 5.211 | 5.268 | 5.400 |
| Blocked, safe partial loads | 14.997 | 14.875 | 14.908 |
| Blocked, 8-byte over-read (not legal in production) | 6.429 | 6.478 | 6.645 |

**Crossover (measured, run 1, fixed digit count, perfectly predictable
branches).**

- *Decimal, over-reading blocked form:* it overtakes the scalar loop at 4
  digits (5.03 against 5.54 ns). At 1 digit, where 59% of calls sit, it takes
  4.96 ns against 3.11.
- *Hexadecimal, over-reading blocked form:* it overtakes the scalar loop at 7
  digits.
- *Safe blocked form:* it wins only when a spelling fills whole blocks, at
  exactly 8 or 16 digits. For example, 8-digit decimal takes 5.10 ns against
  the scalar's 8.49.

Weighted by the census, the fixed-length table models these per-call costs:

| Variant | ns per call |
|---|---:|
| Incumbent | 8.84 |
| Strongest scalar | 4.25 |
| Safe blocked | 14.43 |
| Over-reading blocked | 5.51 |
| Hybrid: scalar below 8 digits, over-read from 8 | 4.12 |

The hybrid saves 0.33 ms per compile over the scalar loop in this container
(about 0.008% of stage 1). It also needs a padding guarantee that production
spellings do not have.

**Instruction properties (measured on this host, not Zen).** `latency.c`
measures dependent chains:

- `imul r64, r64` is 2.97–3.02 dependent-add latencies.
- The Horner step `imul` + `add` is 3.96–4.05.
- A register-register `add` takes about 0.24 ns, so the core runs at about
  4.1 GHz.

Checking these against primary Zen 4 and Zen 5 documentation was not
possible: uops.info and the AMD guides are blocked by this environment's
egress policy. Zen-specific latency figures are therefore **unverified**.

**Assembly (inspected).**

- Clang `-O3` keeps a runtime `div` in the incumbent for
  `UINT64_MAX / base`: one `div` supplies both `/` and `%`, per call.
- The trusted Release `ide` compiles `c_conditional_number` without
  optimization: every local lives in an `%rbp` slot, and there are two `div`
  instructions (`trusted-release-c_conditional_number.s`). See the side
  findings.
- The scalar variant has no `div` and one `imul` per digit.
- The blocked variant has three dependent `imul` pair reductions, one `mulx`
  compose, `tzcnt` and `shlx`, plus per-call `imul`s for `b²` and `b⁴` that a
  production form would take from a table.

**Removed dependency chain and new limiting resource.**

- *What the blocked form removes:* the `k`-step loop-carried chain
  `parsed <- parsed*b + d`, measured at about 4 cycles per digit, and the
  per-digit loop-exit control dependency.
- *What it adds (modeled):* a per-block critical path of about 25–30 cycles:
  - load;
  - about 6 ALU operations of classification;
  - `tzcnt` and `shlx`;
  - three (`imul`, `shr`, `and`) stages;
  - `mulx` and `add`/`adc`.

  This path is constant for `k <= 8`.
- *Net effect:* the census mean chain is 2.33 × 4 ≈ 9.3 cycles, and the
  median literal has one digit. The new constant path is therefore longer
  than what it removes for most calls.
- *Where time actually goes:* successive calls are independent, so their
  short chains already overlap. The limiting resource is per-call work:
  - instruction count;
  - prefix and suffix classification;
  - call overhead;
  - prediction of the variable-length loop exit;
  - for the incumbent, the 64-bit divide.
- *In the safe production form:* the partial-tail load becomes the limiter,
  with branches plus a store-forwarded stack buffer. 96.3% of calls end in a
  partial block.

The blocked summary buys nothing a SIMD or multi-lane version could scale.
There is no eligible independent work inside a call, and the calls come from
unrelated parser and lowering sites. SIMD and lane evaluation were therefore
not pursued, and no scheduler or parallel-codegen change is proposed.

## Registered regressions

`c_test_integer_spelling_consistency` gains vectors that a compositional
implementation is most likely to get wrong.

Valid:

- a 30-digit octal `1` with leading zeros;
- `0x` followed by 32 hex digits whose significant digits equal `UINT64_MAX`;
- the in-range 20-digit decimal `18446744073709551614`;
- exactly one decimal block (`12345678`) and one block plus a digit
  (`123456789`);
- one and two full hexadecimal blocks (`0x12345678`,
  `0x123456789abcdef0`).

Invalid:

- `99999999999999999999`;
- `0001844674407370955161`, where the leading zero selects octal and `8`
  ends the run;
- `0x1'g`.

## Side findings, not pursued here

1. **The trusted Release `ide` compiles production functions without
   optimization.** In the unity build, test code is included inside
   `#pragma clang attribute push (__attribute__((optnone)), apply_to=function)`
   in `ide.c`. Test sources include production internal headers there, so a
   production function first declared in that region keeps `optnone` when it
   is defined later.
   - *Extent:* re-emitting the Release unity TU as LLVM IR shows 1,157
     `optnone` definitions among 3,716. Of these, 156 are outside
     `src/buster/tests/` (`optnone-production-functions.txt`); some are test
     hooks that live in production files. Examples: `c_conditional_number`,
     `c_parse_scope_for_token`, `c_parse_lookup_entity`, `c_type_from_id`,
     `machine_schedule_frame_access`, `debug_variable_add_location`,
     `byte_writer_*` and `buster_hash_64`.
   - *Measured cost:* in the two callgrind profiles above, which differ only
     in tests included or excluded and produce the same object:
     - `c_conditional_number` falls from 449.6 M to 247.1 M Ir;
     - `c_parse_scope_for_token` falls from 284.8 M to 130.1 M Ir.
   - *Effect on earlier profiles:* profiles and shares taken with a trusted
     binary that includes tests carry this penalty.
   - *Unaffected:* the self-hosted stages.
   - *Fix:* this needs its own change, for example including the production
     headers before the push, plus a guard.
2. **Each literal is converted about 3.9 times.** Two non-recurrence levers
   exist: cache the value, or use the strongest simple scalar loop, which was
   measured 36% faster per call in this container. Neither is a recurrence
   result.
3. **`c_type_parse_core_step` searches every type linearly** for each
   aggregate definition. `c_parse.c:9729` and `c_parse.c:9731` carry 206 M Ir
   (0.87%). This belongs to the #1028 census.
4. **Materializing the ranges of `machine_fast_close_live_ranges`** costs
   about 0.85 G Ir including `trailing_zeroes_u64`. This is bitset and
   allocator work that belongs to #54; it is not a recurrence.
