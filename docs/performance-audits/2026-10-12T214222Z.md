## Question

[Canonical CFG publication](../canonical-cfg-publication.md) promises that
"Instructions occupy one contiguous span per block, in block ID order". The
proposal relaxes this to one contiguous span per block, in any order. A
function with no split block would then skip the row permutation. On SQLite
`-c -g0 -O0` that covers 1,110 of the 1,565 functions whose rows move.

**Verdict: keep the contract. No code change.** The best case saves about
0.1% of instructions, and detecting a split block eats most of that. Meanwhile
consumers in four backends and the DWARF builder depend on the order.

## Consumers that depend on span order

These were found by reading the code at the base revision. "Linear" means a
loop over rows `0..instruction_count` whose output follows the global row
order. Under the current contract, that order equals walking blocks in ID
order over their spans.

| Consumer | File and symbol | Dependency | Effect if spans are unordered |
|---|---|---|---|
| Published-shape validator | `ir/ir_cfg.c` `ir_validate_published_cfg` | Requires `first_instruction == rows`, a running sum in block-ID order, for both the span and the builder block | Rejects every unordered function. Must become a coverage check. |
| DWARF definition-to-end range | `codegen/machine.c` `machine_debug_values_build` (and `machine_debug_values_build_dense`) | The range is `[definition, instruction_count)` in row space, and likewise from `local_first_store_after` | A different set of blocks falls after the definition. |
| Row-to-machine range mapping | `codegen/codegen.c` `codegen_machine_debug_span_range`, `codegen_machine_debug_span_dense_range` | Sorts line marks by IR row and takes min/max over a row interval | Location-list rows change, and so do `.debug_loc` / `.debug_info` bytes. |
| Debug place choice | `codegen/machine.c` `machine_debug_values_build` (`local_places`) | Picks the first row, by linear order, that carries a `canonical_local` | A different row's result can win, changing register vs frame locations. |
| Debug facts | `codegen/machine.c` `machine_debug_facts_build` (`argument_results`, `wide_places`) | Linear first-seen choice | Order-dependent if a key repeats. |
| Wasm data and frame layout | `wasm/wasm.c` `wasm64_collect_data`, `wasm64_fe_initialize` | Linear | String data offsets and frame offsets change. `wasm64_string_record_find` binary-searches records appended in ascending row order. |
| eBPF stack and rodata | `ebpf/ebpf.c` `ebpf_fe_allocate`, `ebpf_fe_emit_prologue`, `ebpf_collect_strings` | Linear | Stack slots, prologue order and `.rodata` change. `ebpf_string_find` relies on ascending rows. |
| LLVM bitcode | `llvm/bitcode.c` `llvm_bc_collect_entities`, `llvm_bc_collect_instruction_constants`, `llvm_bc_plan_value_spills` | Linear | String global names, type/constant record order, intrinsic declaration order and spill alloca indices change. |
| Fallback diagnostic | `codegen/codegen.c` `codegen_generate_canonical_module_attempt` (`failed_instruction`) | First row with the failing opcode, by linear order | The reported instruction, and hence its source location, can change. |
| IR validation error text | `driver/driver.c` `compiler_driver_execute_c_single` | Prints the row number | Only the number changes, and only on an error. |
| Bootstrap IR trace | `codegen/bootstrap_trace.c` `bootstrap_trace_ir_function` | Prints block first/last, rows linearly, definitions and extras | The `.ir` trace differs from the base. It stays deterministic. |

Consumers that do **not** depend on the order:

- **Selection.** `machine_select.c` (`machine_selection_canonical_layout`,
  `machine_selection_finish_canonical_edges`,
  `machine_selection_validate_function`) and both canonical selectors,
  `machine_select_canonical_function_x86_64` and
  `machine_select_canonical_function_aarch64`. They walk blocks by ID or in RPO
  layout, over each block's span. Their ordinals are walk counters, not row
  indices.
- **Register allocators, scheduler and predicate passes.** They see only
  machine IR.
- **Debug initialized ranges.** `machine_debug_initialized_build` uses
  per-block spans.
- **Edge lookup.** `ir_function_cfg_edge` searches the predecessor slice.
- **Extras.** The `ir_instruction_extra` lookup is re-sorted by
  `ir_cfg_remap_extras`.
- **Reopen.** `ir_function_reopen_cfg` walks spans per block.
- **Validator row walks.** `ir_validate_block_rows` and the parameter checks in
  `ir/ir.c`.
- **SPIR-V.** `spirv_check_rows` admits only one block.
- **Mid-pipeline passes.** `ir_promote.c`, `ir_inline*.c` and `ir_fast.c`
  reopen before mutating, or only sum counts.

Most linear consumers could be made order-independent by walking blocks in ID
order over their spans. That walk reproduces today's order exactly. The Wasm
and eBPF string lookups would then also need a different key, since their
records would no longer ascend by row. The debug ranges would need row-to-rank
translation, or the permutation kept for any function with debug locals. So
"any order" is not a free relaxation: it puts a hidden obligation on every
future linear consumer.

## Upper bound on the benefit

The prototype measures what skipping the permutation can save, without paying
for any consumer fix. It detects a split block during the existing ownership
walk. If there is none, it publishes each block's span at its original rows
and skips the moves, the value-definition remap and the extras re-sort. Only
the validator is relaxed:

```diff
@@ ir_cfg_publish_instruction_rows
     bool moved = false;
+    bool split = false;
@@
                 moved |= id.value != cursor;
+                split |= last.value != IR_ID_UNDERLYING_INVALID && id.value != last.value + 1;
@@
+        if (!split)
+        {
+            for (u32 index = 0; index < function->block_count; index += 1)
+            {
+                blocks[index].first_instruction = function->blocks[index].first_instruction.value;
+            }
+            moved = false;
+        }
         for (u32 index = 0; index < count; index += 1)
         {
-            if (inverse[index] != index)
+            if (split && inverse[index] != index)
@@ ir_validate_published_cfg
-        valid = block->first_instruction == rows && block->instruction_count && ...
+        valid = block->instruction_count && block->first_instruction <= cfg->instruction_count - block->instruction_count && ...
-                original->id.value == index && original->first_instruction.value == rows && ...
+                original->id.value == index && original->first_instruction.value == block->first_instruction && ...
-            valid = original->last_instruction.value == rows - 1;
+            valid = original->last_instruction.value == block->first_instruction + block->instruction_count - 1;
```

Builds: tests-off Release `ide` built twice, in separate worktrees, with
`generate --build-directory build/cg --cc clang --no-include-tests -- -DBUSTER_NATIVE_TARGET=x86-64-v3`
(Clang 18.1.3). Valgrind 3.22.0 cannot decode EVEX, hence x86-64-v3. Input:
SQLite 3.50.4 amalgamation, `sqlite3.c` sha256
`90b7189566ea710ee18361b25d893f5cda3fcf43033223a16384762f53e99a85`, taken
from the `better-sqlite3@12.4.1` npm package. SQLite is public domain. The
self-host unit is the base revision's `src/buster/apps/ide/ide.c`.

```sh

ide cc -I<base>/src -I<base>/build/cg/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g0 -c <base>/src/buster/apps/ide/ide.c -o ide.o
```

Line-level counts on SQLite `-c -g0 -O0` show where it goes. Skipping the work
saves about 4.2M instructions:

- row moves: 2.94M → 1.58M;
- canonical-source moves: 1.87M → 1.01M;
- the value-definition remap loop: 1.93M → 0.89M;
- the extras re-sort.

That is the whole prize: under 0.1% of the compile. The per-row `split` test
costs 3.16M of it. At `-c -g -O0`, 1,562 of the 1,791 moved functions have a
split block, so almost nothing is skipped. The test's 3.56M and a
code-layout change in the loop make publication 5.1M **more** expensive.
A cheaper test cannot fall below the per-row walk that already exists. The
ceiling stays about 4M at `-g0` and near zero at `-g`. That is before paying
for the consumer fixes above, which add block-ordered walks to every Wasm, eBPF
and LLVM function, and a rank map or a forced permutation for debug locals.

Every compile above produced byte-identical objects between the arms
(`cmp`: SQLite `-c -g0 -O0`, `-c -g0`, `-c -g -O0`, and the self-host
`-c -g0` unit). For the `-g` object that is luck, not evidence of safety. The
definition-to-end dependency is real by reading, and the native `-g0` path
simply does not reach it. The prototype was not run through `test_all` or the
Wasm, eBPF and bitcode tests, which the table predicts it would change.

Instruction counts are not time. No 9700X evidence exists for this proposal,
and none was requested, because the hosted upper bound is too small to justify
the consumer work.

## Remaining publication work

The permutation stays, under the block-ID-ordered contract. The larger lever
named in the previous audit is unchanged: reuse the validator's ownership walk
by publishing each function right after FAST (#1406 part B, waiting on the
#1424 timing decision). A prerequisite for any future "spans in any order"
change: first convert the linear consumers listed above to block-ordered span
walks. That conversion is behavior-preserving on its own and can be tested
under the current contract.
