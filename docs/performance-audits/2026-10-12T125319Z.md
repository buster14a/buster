## What placement does per row

These counts are read from the source at the baseline. One "walk" visits every
machine row of the function once.

| Stage | Row walks | Notes |
|---|---:|---|
| `machine_predicate_placement_build` inspection | 0–1 | Only when no MASK value exists and predicate absence is not certified. |
| `machine_fast_prepass_build` classification | 1 | Forward, one 16-byte opcode row per row. |
| prepass successor/escape walk | terminators only | It falls back to every row when a block reference appears outside a terminator. |
| prepass next-call walk | 1 | Backward over the 4-byte `operand_masks`, not the instructions. |
| `machine_fast_value_liveness` gen/kill | 1 | Only when there are at least 2 blocks and some tracked value. |
| placement block scan | 1 | The register decisions. |
| home row tiling (`row_blocks`) | 1 | |
| `machine_fast_certify_frame_addresses` | 3 | Only while slots are coalesced. The third walk decodes `machine_schedule_frame_access`. |
| slot touch census | 1 | Only while slots are coalesced; decodes a frame access per row. |
| `machine_fast_close_slot_ranges` | 2 | Only with at least 1 shareable slot; each walk decodes a frame access per row. |

Three bitset liveness solves run per function: values in the prepass, allocator
homes, and shareable slots. On these inputs the widest plane is 7 words.

| Input | Liveness word updates (values / homes / slots) | Rows |
|---|---|---:|
| SQLite | 230,609 / 185,375 / 53,232 | 312,024 |
| self-host | 761,534 / 743,533 / 0 | 2,330,153 |

That is under 1.5 word updates per row.

Nothing is repeated from instruction selection. Selection calls
`machine_schedule_frame_access` only on rows covered by a volatile line mark,
which is the slot memory flags in `machine_select.c`. The repetition is inside
placement: a coalesced function decodes every row's frame access 2 times, or 4
when a shareable slot exists. It also walks its rows 4 or 6 more times.

## Phase attribution and scaling

The timings cover the whole `machine_predicate_placement_build` call. The
slope is the log-log fit of a phase's cycles against rows, over functions of
at least 128 rows: 544 SQLite functions and 3,084 self-host functions.

| Phase | SQLite cyc/row | share | slope | self-host cyc/row | share | slope |
|---|---:|---:|---:|---:|---:|---:|
| prepass classification walks | 79 | 15.9% | 0.96 | 62 | 26.7% | 0.91 |
| edge index + value liveness | 50 | 10.1% | 0.97 | 29 | 12.5% | 0.91 |
| block scan | 169 | 34.0% | 1.02 | 98 | 42.3% | 0.89 |
| home census + block close/color | 55 | 11.1% | ≤1.03 | 23 | 10.1% | ≤0.86 |
| slot certify + census | 77 | 15.5% | 0.98 | 1 | 0.3% | 0.28 |
| slot closure | 29 | 5.8% | 2.03* | 0 | 0.0% | — |
| everything else | 32 | 6.2% | ≤1.12 | 16 | 6.5% | ≤0.83 |
| **total** | **497** | 155.2 M cyc | | **231** | 537.5 M cyc | |

The SQLite unit has 2,620 functions, 43,434 blocks and 183,983 virtual
registers. The self-host unit has 6,322 functions, 202,477 blocks and
1,082,132 virtual registers. Raw output is in `analysis-*-baseline.txt`.

\*The slot closure only runs in the 331 SQLite functions that have a
shareable slot, and those are the larger ones. Within that population the
slope is 0.95 (`slots-sqlite-baseline.txt`), at 64–74 cycles per row in every
size bucket. The apparent quadratic is a selection effect.

**No super-linear term was found on either unit.** Every phase is linear in
rows within a function population. Cycles per row fall slightly with function
size on the self-host unit, from 421 below 64 rows to 182 above 16k rows. On
SQLite they are flat, between 440 and 544. The largest SQLite function
(13,120 rows and 1,925 blocks) costs 506 cycles per row. Its widest liveness
plane is 4 words. Dense block × object planes would become quadratic if the
tracked objects grew with function size. `MACHINE_FAST_LIVENESS_WORD_LIMIT`
and `MACHINE_FAST_BLOCK_COLOR_PLANE_LIMIT` bound that case, and neither unit
comes close.

The self-host unit barely pays for slots because `-g` sets
`distinct_frame_objects` (`pin_debug_locals`). That disables slot coalescing
for every function, so stage-1 throughput cannot show the slot findings below.

## Repeated scans and their disposition

1. **Frames without slots still certified and censused their rows (fixed).**
   1,893 of the 2,620 SQLite functions have `stack_slot_count == 0`. They
   still ran the 3 certification walks and the census walk, at 8.63 M of
   155.2 M cycles. Slot coalescing is now gated on `stack_slot_count != 0`.
   With no slot to name, every one of those walks wrote nothing that layout
   reads, and the group count is 0 either way. After the change, that
   population spends 0.32 M cycles there, and SQLite placement falls from
   155.2 M to 144.4 M cycles (`analysis-sqlite-candidate.txt`,
   `slots-sqlite-candidate.txt`). The whole-compile effect is about 4 ms of a
   0.89 s compile at nominal clock. That is an estimate, not a measurement.
2. **Coalesced frames with no shareable slot (named, not fixed).** 396 SQLite
   functions spend 5.87 M cycles certifying and censusing slots, and every
   slot ends up fixed. The census has to run before a slot is known to be
   unshareable. A static pre-filter could skip it: volatile memory flags, the
   outgoing area, and inline-assembly and `va_arg` ownership are known before
   any row walk. This probe did not record which reason fixed each slot, so
   the next step is to count those reasons before writing the filter.
3. **The frame access is decoded 2 or 4 times per row (named, not fixed).**
   The census and both walks in `machine_fast_close_slot_ranges` call
   `machine_fast_slot_touches` on the same rows. Recording at most 2 touches
   per row in the census, for the 331 functions with a shareable slot, would
   remove 2 walks and 2 decodes per row. Those walks dominate the 8.9 M-cycle
   slot closure, since its liveness solve is only 53 k word updates. The three
   certification walks could also become one: LEA definitions precede their
   uses in layout order, and MOV propagation already depends on that order.
   That needs its own proof for MOV chains that run against layout order.
4. **Prepass classification and value liveness (inherent as structured).**
   The backward gen/kill walk cannot fold into the forward classification. It
   needs `live_index`, which depends on escapes, and escapes are only final
   once every defining block is known. It reads the 4-byte classification
   words and the operands, not the descriptors.
5. **Block scan (inherent).** It visits each row once and does each row's
   register decisions. This audit found no repeated scan in it. The earlier
   minimum-work audit (`2026-10-04T111831Z`) attributed its cost to the
   algorithm and the volume of edit rows, and that is a separate question
   from the scaling asked about here.
