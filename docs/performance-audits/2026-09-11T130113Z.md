## Mechanism

The same compile command with `-emit-llvm` produced the optimized module;
`llvm-extract --func=codegen_generate_canonical_module_attempt` isolated the
function. It has 5,815 basic blocks, 41,042 instructions, 141 switches and a
single `ret`. Its 543 `return result;` sites fold into that one exit with 48
`memcpy` calls in the whole function, so return copies do not explain the cost.
`llc` 22.1.8 takes 2.3 to 3.2 s on the function alone, about half of it in
CodeGen Prepare.

CodeGen Prepare repeats a whole-function walk until an iteration makes no
change. LLVM limits that only for functions with more blocks than
`-cgpp-huge-func` (default 10,000 in the LLVM 16.x, 18.x and 22.x sources); for
those, later iterations visit only changed blocks. At 5,815 blocks this
function receives full rescans. The
[ablation](2026-09-11T130113Z-evidence/cgp-ablation.txt) confirms it: a
threshold of 5,000 cuts the function's CodeGen Prepare time from 1.05 s to
0.20 s and its `llc` total from 2.33 s to 1.51 s, below the 1.77 s with the pass
disabled. None of the pass's eleven individual transform switches reduces it.

Size alone is not the trigger. The [block census](2026-09-11T130113Z-evidence/block-census.txt)
shows `assembly_tests` (9,160 blocks), `compiler_driver_tests` (8,552) and
`x86_64_metadata_tests` (6,421) are larger, yet together contribute little
CodeGen Prepare time; this function's structure keeps the fixed point
iterating.

A separate `-gline-tables-only` module attributed each block to the source
region of its first instruction, following inlined locations to their outermost
call site. The [build guide](../agents/build.md) records that debug information
does not change code generation.

## Limits and disposition

The flag is not applied. It is a hidden LLVM option without a stability
guarantee, Apple Clang's copy was not exercised, and it changes generated code
for every function over the threshold — at this revision the module driver and
the three test functions above. Adopting it would need a Clang-only
configuration, matched builds on the CI runner, `test_all`, the self-host fixed
point and the throughput guard on the resulting compiler, for a gain of about 2%
of object-compile instructions.

Moving the direct emitter into a coarse helper was not attempted: the helper
would inherit its roughly 4,700 blocks and the same transform chains, #36
restricts that backend to correctness fixes until retirement, and #90 asks for
splits at documented semantic boundaries rather than moves. Deleting the direct
emitter under #36 is the change that would remove most of this function's cost,
and it remains gated by #36's coverage, differential and budget criteria. At
recording time GitHub showed #36 closed: the closing phrase "close #36" in
`bc69d279`'s message ("This does not retire the direct backend or close #36")
closed it on merge, while its latest comment says it stays open.

After this function, no single function exceeds 3.3% of the traced compile, and
the optimizer is 43% to 54% of it. #413's remaining cost is a long tail, not a
second outlier. This is documentation only: compiler tests and the self-host
fixed point were not run because no compiler input changed.
