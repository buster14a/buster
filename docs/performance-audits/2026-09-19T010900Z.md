## Outcome

This closes #792 through its explicitly allowed audit path. No compiler source
changes are proposed here.

The cache survey attributes 51.61% of the stage-1 compile's DRAM fills to the
six symbols named by the issue, but those symbols own only 15.17% of cycles.
Deleting all six symbols outright would therefore save at most 15.17% of the
measured run, or 175 ms at the 1.151 s median wall time. Function-at-a-time
ordering does not delete their validation, rewriting, CFG construction or
selection work, so 15.17% is an impossible-extinction ceiling, not an expected
speedup.

The current semantics tighten the useful bound further. Local promotion runs
before the FAST input guard, and that guard validates the *post-promotion
module* as one unit. Without changing which legacy accepted modules FAST may
touch, the first function cannot enter FAST until every function has completed
promotion and the unit guard has inspected the whole module. The directly
reorderable row-consuming suffix is therefore:

```
FAST -> CFG publication -> target selection -> allocation -> encoding
```

The four measured leaf symbols in that suffix — `ir_fast_function`,
`ir_cfg_publish_instruction_rows`, `ir_function_publish_cfg` and
`machine_select_canonical_function_x86_64` — total **8.19% of cycles and 31.24%
of DRAM fills**. Even if locality made all four free, the wall-time return is at
most **94 ms**. The codegen attempt's whole-module capacity/layout work adds
0.84% of cycles and 2.27% of DRAM fills; charging its *entire* self time to the
rewrite, although only part is the prewalk, raises the deliberately loose bound
to **9.03% / 104 ms**.

The 250-cycle-per-DRAM-fill model gives 1.016 G cycles for the suffix's 4.06 M
attributed fills, or 17.28% of the complete run. That already exceeds the
suffix's own 8.19% of measured cycles. The phase-time bound is therefore the
binding one and confirms that most miss latency overlaps; multiplying fills by
latency is not a speedup prediction.

Issue #791 remains open and is the stated prerequisite. It removes four
whole-row scans whose work would otherwise merely be moved into the proposed
function-local loop. Those changes must land and be remeasured before accepting
the risk and maintenance cost of a pipeline decomposition whose present hard
ceiling is 94–104 ms and whose actual locality-only return must be smaller.

## Why the whole pipeline cannot simply be interleaved

### The FAST decision is module-wide in the state after promotion

`ir_prepare_canonical_module` first applies `ir_promote_function` to every
lowered function. If the current rows are not already covered by a strict
validation, it then calls `ir_validate_canonical_module` once and either runs
FAST over every lowered function or records one module-level
`validation_skips`. That is an observable contract: optional rewrites decline
legacy accepted shapes as a unit.

Moving the guard before promotion changes the state it validates. A certified
module that is strict-invalid before promotion but strict-valid afterwards can
currently enter FAST; a pre-promotion guard would decline it. Starting FAST on
function 0 before the guard has seen function N changes the all-or-none decision
more directly. Preserving the contract therefore requires all promotion and the
whole-module guard to complete before the reorderable suffix starts, unless a
separate proof establishes that changing the decision is harmless for every
accepted producer, not just the measured unity unit.

The conditional transform checks are another ordering boundary. Debug,
sanitizer and explicit verification builds validate promotion and FAST outputs
before publication. Letting selection consume function 0 while the eventual
whole-module output validation can still reject function N violates the
repository rule that invalid canonical IR never reaches a backend. A real
function-local path needs a validator split into a module preamble plus an exact
per-function form, or it needs to retain the old module path in checked builds;
the latter would leave the new ordering least tested where its mutation logic
is most observable.

### Codegen deliberately pre-touches the module and retries it as a unit

`codegen_generate_canonical_module_with_trace` prepares ABI state and the x86
f80/type caches outside a temporal attempt, then calls
`codegen_generate_canonical_module_attempt` in a capacity-doubling loop. Before
emitting function 0, the attempt walks every function/value to derive frame,
stack-probe, over-aligned argument, inline-assembly and debug/relocation
capacity. An exhausted code buffer rewinds the attempt arena and regenerates
the complete module.

Putting mutable preparation inside that loop is not transactional: promotion,
FAST statistics and published CFG storage live in the program arena, while the
attempt arena is rewound. Keeping preparation outside the retry restores
correctness but loses the intended locality. The structural implementation
therefore also needs one of these code-buffer ownership changes:

1. independently sized per-function fragments followed by a deterministic
   source-order merge;
2. a growable stable-offset buffer plus growable relocation/debug arrays; or
3. a retained first attempt whose already-emitted functions survive capacity
   growth.

All three are broader than moving a loop. They must preserve source-order
function descriptors, relocations, unwind rows, debug locations, assembly
entries and byte-identical object layout. The f80 cache and
`ir_prepare_program_abi` are hoistable and are not blockers; the whole-module
capacity scan and retry ownership are.

### Statistics and deterministic order are solvable, not blockers

`IrLocalPromotionStatistics` and `IrFastStatistics` are additive. They can be
zeroed before a serial source-order loop, accumulated per function, and
published with `local_promotion_complete`/`fast_complete` only after the last
function. Keeping the same source order also preserves deterministic function,
relocation and debug publication. No lane, task queue, callback or new parallel
path is required, and none should be introduced for #792.

## Smallest safe implementation sequence after #791

1. Land and measure #791's producer-known facts first. Do not hide the four
   scans inside a new loop.
2. Split canonical preparation into an explicit module-begin/unit-admission,
   per-function FAST/publication, and module-finish contract. Keep local
   promotion and the post-promotion FAST guard before the per-function suffix
   unless a stronger compatibility proof is added.
3. Split strict validation so checked builds validate each transformed
   function before selection while module-global invariants remain one serial
   preamble/finalization.
4. Replace the codegen whole-module capacity prewalk/retry with deterministic
   per-function fragments or another ownership model that does not read later
   functions before the current one is encoded.
5. Run `test_self_host`, `test_all`, `test_mode_matrix`, compare all
   `IR_LOCAL_PROMOTION`, `IR_FAST` and `CODEGEN` census rows, then repeat the
   pinned `perf stat` and `tools/cache_miss_survey.py --dwarf` experiment.

Until #791 has reduced the row work and a prototype demonstrates a material
fraction of the 8.19% ceiling, the wide preparation/codegen ownership rewrite
is not justified by the measured return. #792 is therefore complete as a
priced negative result; it does not claim that a later, smaller decomposition
cannot win.
