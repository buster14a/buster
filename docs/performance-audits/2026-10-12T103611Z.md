## Allocation regression

`compiler_driver_test_dependency_target_scaling` measures the real parser's
arena-position delta, excluding fixture construction. It parses 128 and 2,048
repeated `target $name#.o` values as raw, quoted and alternating options, with
and without response-file expansion. The checked limits are 4,096 bytes per
target plus 65,536 bytes of slack, and at most 16 times the smaller population's
allocation plus the same slack. There is no process timing gate.

On baseline production code the 2,048-target populations retain 35,192,202 to
41,699,976 bytes; all twelve large-population assertions fail. The candidate
passes all bounds and byte assertions. The regression bounds every retained
parser allocation, rather than counting a newly introduced helper alone.

## Process and build-system controls

Each child compiles `tiny.c` containing `#include "tiny.h"` and `int x = VALUE;`,
with a generated header defining `VALUE`. The command is
`ide cc @targets.rsp -c tiny.c -o tiny.o`; the response file specifies
`-MMD -MF tiny.d` followed by the targets. Raw/quoted families use the distinct
names `target0000000.o`, etc. The mixed family cycles through raw
`raw$target.o`, quoted `quoted $target#.o`, raw `repeat.o`, and quoted empty
strings. Byte comparisons use the unchanged relative paths in separate output
directories. All generated inputs are original to this probe.

One sequential trial per cell, **unpinned**, on a shared local desktop. RSS is
Linux `os.wait4(pid, 0).ru_maxrss` for the individual child in KiB. These are
resource diagnostics, not controlled performance acceptance or latency data.
