## 2. What a defensible leadership claim says

A finite experiment cannot establish dominance over every compiler, program,
machine, language, and output contract. A useful claim is nevertheless testable:

> At exact revision and binary identities, on admitted host H, Buster has the
> lowest measured time for operation O over frozen corpus C among the named
> compiler versions, subject to declared functionality, correctness, artifact
> quality, memory, and uncertainty constraints.

Publish that full qualification wherever the result is advertised. A corpus
leader is not automatically a per-program leader. A C result is not a C++ or
all-language result. A native Linux result does not generalize to every ABI.
A throughput result does not establish the lowest cold-start latency.

Use two claims with different tests. **Portfolio leadership** compares a
predeclared, family-weighted geometric mean of paired time ratios, with all
per-cell results visible and no unacceptable required-cell regression.
**Pointwise leadership** requires a simultaneous upper confidence bound below
one against every admitted competitor in every required cell. Neither claim is
supported merely by a regression test returning zero. Publish ties and
inconclusive outcomes instead of selecting the smallest observed median.

The comparison contract is a versioned manifest, not a collection of flag names.
It must bind: corpus and dependency closure; compiler source, executable and
producer identities; language and extensions; target triple and ABI; requested
artifact; optimization/debug/runtime-support policy; concurrency/cache/I/O
policy; independent oracle; resource budgets; statistical design; and admission
status. Freeze it before candidate results are inspected. Amendments create a
new version and retain the old results.

### Language, ABI, and quality lanes

Start with native C on Linux x86-64, ELF, System V ABI, LP64, a fixed sysroot,
and an explicitly selected baseline target ISA. The host compiler may use Zen
5 AVX-512 to implement compilation while emitting that baseline ISA: **host
implementation ISA and generated-program target ISA are different axes**.
Never let a producer's `-march=native` silently change the subject's target.
Add a separate explicit Zen 5 output-ISA lane only after all compared subjects
and oracles support it. AArch64, Darwin, and Windows are separate contracts.

For portable controls use the common supported C language subset and valid,
defined programs. For real projects preserve the exact dialect and extension
requirements in their existing recipes, rather than pretending every workload
is strict C17. Record implementation-defined choices including char signedness,
integer widths, long double, layout, and calling conventions. Buster's build
policy (`-fwrapv -fno-strict-aliasing -funsigned-char`) must be preserved when
building Buster; benchmark-program semantics must also be matched explicitly.
Do not silently use different programs selected by compiler-specific macros.

Create distinct output-quality lanes:

| Lane | Required output contract | What it does not imply |
|---|---|---|
| Minimum-latency correct artifact | Complete valid artifact, supported semantics/ABI, named optimization policy; ordinary debug-off | `-O0` across compilers does not mean identical passes or code quality |
| Debuggable artifact | Named debug format/version, line and symbol requirements, relevant unwind behavior, debugger checks | `-g` alone does not prove equivalent debugging information |
| Quality-constrained artifact | Predeclared generated-program runtime and code-size envelopes on held-out valid tests, with compile time measured separately | Buster QUALITY and another compiler's `-O2` are not interchangeable labels |

For each lane specify PIC/PIE, relocation/code model, TLS, vector ABI, fast-math,
FP contraction, stack protector, sanitizers, LTO, PGO, exception/unwind support,
and linked runtime libraries. Disable optional features symmetrically only when
that is the declared requested work. A feature that a compiler cannot supply
is an unsupported cell, not a reason to weaken the contract after timing.
Record all actual switches and inspect artifacts and behavior to verify them.

Treat Buster NONE, MIR_STACK, FAST, and QUALITY as separate series. Do not select
a different winning allocator for each workload after looking at measurements.
Likewise predeclare competitor optimization choices or a bounded tuning budget
on training inputs, then evaluate held-out inputs. Generated-program runtime
and code size constrain a quality lane; they never replace compiler-time data.

### Phase accounting without changing the requested work

Report end-to-end uninstrumented time first. In separate diagnostics attribute
startup/loader/argument handling; source and header I/O; preprocessing including
lexing; parsing/semantics/lowering; canonical preparation/validation; selection,
allocation and encoding; and object/debug/link/output work. Define disjoint
phase intervals or an explicit nesting tree. Report unassigned time and
observer overhead rather than forcing every inclusive sample into a partition.

Preprocessed-input comparisons are useful for isolating frontend work only when
all subjects consume the same validated token/spelling stream and the adapter
actually bypasses preprocessing. They are not source-to-object scores. Likewise,
`-E`, syntax-only, `-S`, and `-c` differences are not exact phase subtractions:
they may change control flow, optimization, I/O, and initialization. A separate
empty-input or launch control estimates overhead, not a universally subtractable
constant. Keep the raw full-process score in the headline.

## 8. Necessary-work models and bottleneck migration

Models are conditional bounds or experiment-selection tools, never performance
measurements. First census source bytes, meaningful token/IR populations,
actually touched bytes, cache-line traffic, loop/dependency depth, function-size
and queue-size distributions, and output bytes. Separate logical capacity from
resident/touched storage. In particular, clearing all allocated capacity is not
necessarily required semantic work.

For a stage whose necessary work has been justified, define B_k as its traffic
through memory level k, BW_k as an independently calibrated effective bandwidth,
U_r as required operations using execution resource r, R_r its effective service
rate, and D as critical dependent steps at latency L. A conditional optimistic
bound is:

```text
T_stage >= max_k(B_k / BW_k), max_r(U_r / R_r), D * L
T_total >= mandatory serial startup/I/O/output + critical path of stage work
```

The first line means the maximum of those terms, not their sum. Stages that
cannot overlap contribute sequentially; genuinely pipelined work follows its
critical path. State cache residency, line utilization, dependency and overlap
assumptions. Peak advertised bandwidth or instruction throughput is not an
achievable mixed-workload rate. IR traffic is a bound for the chosen
representation, not a universal requirement for all possible compilers.
Output writes and required source observation remain part of the declared work.

For a staged vector candidate model the complete cost:

```text
T_vector = producer/extraction + classification + partition/compaction
         + vector kernel + tails/fallback + scalar state publication
         + downstream consumption + extra allocation/traffic
```

Compare with the scalar path producing the same consumed result. A prepacked
benchmark can identify a kernel limit but cannot establish end-to-end gain.
If batch setup costs F and the useful per-item saving is d, a first crossover
estimate is n > F/d, only when d is positive and traffic/fallback costs are
already included. Measure around that crossover; do not round every small
function into a full-width batch or call masked-off lanes productive work.

For cumulative changes, use nonoverlapping baseline components and an
interaction-aware residual ledger:

```text
T(S) = T_fixed + sum_j T_j * residual_j(S) / acceleration_j(S)
     + setup(S) + merge(S) + extra_memory(S) + interactions(S)
```

Each eliminated operation belongs to one residual population. Two changes that
remove the same decoding, clear, or traversal cannot both claim its full saving.
Re-measure the integrated subset and refresh the partition after each accepted
change. Cross-cutting page clearing is already inside phase time, not a new
Amdahl fraction to add on top of lowering and codegen.

An illustrative, non-measured 100-unit compiler has fixed/other 40, lowering 40,
and backend 20. A layout/work-elimination change removes 20 lowering units;
a second change doubles the remaining lowering work. The combined result is
70, or 1.43x, not the product of two independently quoted 1.25x whole-compiler
speedups. If both changes eliminate the same 20 units, they still leave 80.
After the 70-unit result, fixed/other is 57% of the remaining time: the bottleneck
has migrated. Additional SIMD on the remaining ten lowering units has a small
ceiling even if its kernel is spectacular.

For the historical native capture only, lowering plus codegen is about 73.1%
of the compiler lane. Halving both, with everything else unchanged and zero
new overhead, models about 1.58x lane throughput. It is not a current-main wall
forecast. A workload-specific Amdahl model becomes invalid when output policy,
corpus, runtime-quality requirement, ownership boundary, or memory behavior
changes. For threading also bound makespan by the largest indivisible function
or TU, total work divided by workers, and bandwidth; include joins, imbalance,
private scratch and deterministic publication.

## 9. Ablations that distinguish SIMD from cheaper work

Use an ordered ladder plus selected factorial cross-checks. Changing five things
at once and labeling the result "AVX-512" does not identify the winning cause.
All implemented variants must preserve C, canonical IR validation, diagnostics,
ordering, supported ABIs and deterministic output. No variant in this report is
implemented or benchmarked.

| Variant | Change relative to its parent | Question |
|---|---|---|
| A0 | Current trusted scalar/available baseline, one worker | What is paid today? |
| A1 | Remove demonstrably unnecessary work; otherwise same representation and scheduling | Does deletion win before vectorization? |
| A2 | Compact/SoA or tiled layout with scalar kernels and unchanged useful work | Is the gain layout/traffic rather than SIMD? |
| A3 | Stable homogeneous batching/active lists, still scalar | Does grouping repay construction and publication? |
| A4 | Vectorize the same batch at narrower width | What is the gain at matched work and layout? |
| A5 | AVX-512 on that same contract | Does width add net benefit after frequency, tails and traffic? |
| A6 | Bounded thread scaling of the winning single-worker path | Does concurrency add benefit after bandwidth and scratch costs? |

Keep matched scalar/batched/width controls, because the simple ladder alone
cannot estimate all interactions. Cross A2 layout with scalar versus vector and
A3 batch size with width; test combined accepted changes against the original
and their immediate parent. For the producer-controlled study inspect generated
host code: a "scalar" C loop may auto-vectorize. A globally disabled-vector build
is a broad producer ablation, not attribution to one explicit kernel. Bind the
actual instructions and algorithm selection rather than trusting a switch name.

Candidate algorithm shapes should be local to measured residual work: stable
active-block lists and touched-entry resets; explicit place-versus-value demand
to avoid construction/retraction; compact opcode/operand projections;
classification-mask-compaction pipelines; and private function results merged
in stable source order. The [priority synthesis][priorities] already identifies
which compact metadata and active-block changes exist: do not implement them
again as though they were missing. Census production of every sidecar and its
reuse/invalidation before proposing another pass.

The [SIMD guide][simd-guide] documents `c_lex_compact` versus `c_lex_scan_one`,
item-aligned 64-byte windows, masks, tails, and differential boundary testing.
Use those existing differential gates for lexer experiments. SIMD vocabulary
remains `simd.h`, with feature/compiler guards and supported fallbacks; avoid
vendor-header-only paths that break self-hosting. Preserve validation and the
platform/ABI gates, including independent producer/consumer exchanges motivated
by the Darwin audit. The large `c_gen.c` contents response was empty through
this interface despite returning a blob identity; no fresh line-level audit of
that entire file is claimed here.

On verified Zen 5 and separately verified Zen 4, record useful lane occupancy,
bytes per item, compacted fraction, fallback rate, mask/permute and gather/scatter
cost, spills, code footprint, branch/cache behavior and effective frequency.
Guide statements about ideal native width are architectural intentions, not a
universal promise that 512-bit code doubles application throughput. Prefer
scalar or narrower paths below an empirically established crossover. Preserve
portability correctness even where fallback performance is not the headline.

## 10. Ranked experiment queue and acceptance dependencies

The ranking combines decision value, measured historical opportunity, cost and
existing ownership, not an unsupported prediction of speedup.

| Rank | Experiment / existing owner | Evidence required and architectural decision |
|---|---|---|
| 0, admission prerequisite | Immutable A/A and whole-job host proof, #422/#426/#437 | Establish useful noise resolution and enforce non-oversubscription; without it dedicated performance decisions stay blocked |
| 1 | Frozen real-source cross-compiler object/linked baseline, #423/#46 | Admit the exact corpus and operation adapters; expose where Buster is competitive and which failures/quality requirements prevent the claim |
| 2 | Current-main lowering/validation/memory census plus one deletion-vs-layout control, #447/#306/#52/#525 and #564 | Re-establish where time/work actually goes after merged changes; choose elimination, layout or no-change before wide kernels |
| 3 | Complete-path scalar/batched/narrow/512-bit residual, #131/#122/#132 as current attribution warrants | Measure staging and downstream cost on large and small inputs, Zen 5 and Zen 4; decide whether pervasive width is justified or selective |
| 4 | Function-body ownership census and bounded function-backend/lowering versus TU scheduling, #54/#531/#424 | Compare single-TU and project critical paths at equal total workers and memory; decide the appropriate parallelism boundary |
| 5, independent control | Trusted-producer PGO on held-out corpus, #55 | Separate host-code layout/optimization benefit from SIMD source architecture; include startup and compiler text size |

Every experiment begins by rechecking current main and active ownership. Preserve
its exact source, producer, workload and output contract; prohibit simultaneous
unrelated implementation changes. Acceptance needs mechanism counts, complete
uninstrumented paired timings and uncertainty, resource/quality budgets,
independent correctness, platform/ABI coverage, determinism and reproducible raw
artifacts. A negative or inconclusive result is a valid disposition. Do not wait
for a new dashboard, GPU backend, representation rewrite or universal service
framework to obtain the first useful admitted pair.

### Trusted, self-built, and generated-program scoreboards

Maintain three explicitly labeled populations. (1) A trusted Clang-built Buster
compiling frozen work is the principal implementation-throughput scoreboard.
(2) A self-built Buster compiling that work has its own stage, executable digest,
feature path and fixed-point/correctness evidence; its host machine code can
change because the predecessor generated different code. (3) The runtime of
ordinary generated programs is a separate quality scoreboard. Compilation of
Buster by Clang is a fourth build-engineering cost when reported, not Buster's
source-to-artifact throughput. No scoreboard's improvement cancels another's
correctness or required-functionality failure.

## 12. Three experiments most likely to change architecture

**1. Eliminate work before widening the lowering path.** On frozen current-main
Buster, SQLite and small controls, census remaining lowering/SSA/validation
costs, then compare current code, one bounded work-elimination change, and a
matched scalar compact-layout path. Include every added census-free production
walk, queue, allocation and canonical validation. Favored hypothesis: avoiding
construction and memory touching is a larger near-term lever than vectorizing
the same waste. **Falsifier:** the qualified native profile shows that residual
work is small, or the proposed elimination/layout path fails to lower complete
compile time within approved uncertainty/resource limits despite fewer visits
or fills. Fewer counters alone do not rescue the hypothesis.

**2. Test the full producer-to-consumer width crossover.** Choose one dense
residual actually hot after experiment 1, such as backend operand classification
under its existing owner. Compare matched scalar, batched scalar, narrower
vector and AVX-512 paths over measured small/large/low-occupancy populations on
Zen 5 and Zen 4, with packing, tails, fallback, scalar publication and downstream
consumption timed. Favored hypothesis: a SIMD-friendly layout yields a net
AVX-512 gain over the best scalar/batched/narrow control at useful populations.
**Falsifier:** the complete path is neutral or slower after staging/frequency/
traffic, the crossover lies above real batch populations, or required Zen 4 and
small-input bounds fail. The disposition is selective width or scalar batching,
not a claim that an isolated kernel multiplier justifies pervasive SIMD.

**3. Locate the profitable parallelism boundary.** Inventory function-body
ownership and distribution, then compare admitted single-worker execution,
bounded existing TU cohorts, and separately authorized function-backend or
function-lowering prototypes at equal total worker/memory budgets. Use a huge
single TU, balanced projects and deliberately imbalanced projects; include
prewarm, scratch, deterministic merge, link and cleanup. Favored hypothesis:
function-local work exposes useful parallelism that TU scheduling alone cannot
reach on unity inputs. **Falsifier:** shared-state serialization, largest-function
dependency, bandwidth, imbalance, memory multiplication or merge costs erase
whole-artifact gains, or stable diagnostics/ABI/canonical behavior cannot be
preserved within the bounded design. Retain the simpler scheduling boundary
when that is what the evidence supports.
