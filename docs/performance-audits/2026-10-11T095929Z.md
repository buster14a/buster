## What the leaf already reuses

`c_parse_string_literal_expression_type` passes `result->string_literals` to
`c_ir_count_string_literal_range_for_target`. That argument is a
`CStringLiteralMemo`: a per-unit table, keyed by final-stream token index, of
every narrow fragment's decoded bytes and length. It is allocated in the parse
arena. That arena is never rewound, so speculative rollback, which restores
`CParseResult` wholesale, keeps a valid pointer, and lowering reads the same
bytes. A narrow fragment is therefore already decoded once per unit.
- The decode in the leaf is not repeated for the same token. Only a token's
  first sight decodes it, and that first decode records the bytes that
  lowering reads under `-c`.
- A count cache keyed by token could skip only a repeat call's range shape:
  the parenthesis trim, the string-literal kind check, the encoding scan, and
  the fragment loop around the memo probe.
- Wide fragments are never recorded, so each wide call decodes again. On this
  input the leaf saw none.

## Census (base, before any candidate)

A throwaway build of the base (binary `20887ab2927b8e6f`, not committed) sent
each leaf call through one of two no-inline wrappers around the count:
- **repeat**, when after the trim every fragment is already in the memo;
- **first sight**, otherwise.

It also counted the leaf's fragments and the decodes made under it. The
classifying probe was charged to the leaf, outside both wrappers (2.10 M).

This build compiled its own instrumented tree, not the pristine input. That
tree adds one string literal, a `fprintf` format, so the census shows 32,708
leaf calls where the arms below show 32,707. The two arms gave the same
counters:

| Leaf calls | Calls | Count inclusive Ir |
| --- | ---: | ---: |
| repeat | 5,477 | 1,384,369 |
| first sight | 27,231 | 48,467,684 |
| of which the first decode (`c_ir_decode_quoted`, 27,822 fragments) | | 38,412,970 |
| **total** | **32,708** | **49,852,053** |

- There were 33,707 fragments, 70 multi-token calls and no wide literal.
- 83% of the leaf's calls are the first time any consumer sees the token. Of
  the 26 M "decode" the earlier audit named, nearly all is this first decode,
  which every design must keep: it is the decode lowering reuses.
- The repeat half, 1.38 M Ir, clears the 1 M floor, so a candidate was built.
  That bound includes what a cache cannot remove: the call itself, the
  wrapper's by-value `CPreprocessResult`, and the probe. The skippable shape
  is a fraction of the roughly 250 Ir per repeat.

## The candidates

The memo is already the per-token cache, so the candidates add no second
table. A second table would add an insert to each of the 27,231 first sights
on top of a probe. Both versions put a fast path at the top of
`c_ir_count_string_literal_range_for_target`.

When the range is one token, the memo answers for this token array and holds
that token, and the spelling begins with `"`, the result is built directly:
width 1, `C_TYPE_CHAR`, ordinary encoding, and the recorded length as the
count. An unprefixed narrow literal is a plain `char` array on every target.
Every other range, including `u8`, wide, parenthesized and concatenated
ranges, takes the existing walk unchanged.
- **Version 1** probes the memo in the fast path and, on a miss, probes it
  again in the walk.
- **Version 2** reuses the fast path's probe for the walk's one fragment, so
  a first sight probes once, as base does.

The fast path answered 7,991 calls in all: the leaf's repeats and
`c_parse_validate_initializer_shape`'s 2,531 calls.

## Reading

- The premise that the leaf decodes the same tokens again does not hold on
  this base. `result->string_literals` already caches each narrow token's
  decoded bytes and length, and the leaf is the first consumer of 83% of the
  tokens it types. Its 38.4 M of decoding is first-sight work that lowering
  reuses under `-c`.
- What a count cache can skip on a repeat is the range shape, a few tens of
  instructions. There are only 5,477 repeats. Even version 2, which adds no
  probe to a first sight, makes the leaf 0.25 M dearer: the extra branch on
  all 32,707 calls and the changed code of the inlined shape cost more than
  the skipped shape saves. A separate side table would also add an insert to
  every first sight.
- The array bound and row the leaf appends were left alone, as required: each
  row lowers to its own IR array type, and `-g` describes every IR type.
- Not pursued: under `-fsyntax-only` nothing reads the recorded bytes, so a
  first sight could count (`c_ir_count_quoted`) instead of decode. That would
  move the decode to lowering under `-c`, which is the endpoint this compiler
  optimizes, and would add a count there. The larger first-sight cost is
  outside the leaf. The count's other callers decode 2,938 fragments for
  272.4 M Ir, about 93 K Ir a fragment, and nearly all of it is under
  `c_parse_infer_initializer_array_count_core` (273.3 M over 2,531 calls).
  Neither lead was measured here, and both are unverified.
- Hosted wall time was not measured, and these counts are diagnostic.
  Performance validation is incomplete (#2761).
