## Mechanism

`c_ast_types_operand_width` returned `C_AST_TYPE_NONE` for an operand that ends
in `. name` or `-> name` but is not a member node. The parent (a binary
arithmetic operator, a shift, a unary operator or a `?:`) then declined.
For such a range, `c_parse_expression_bit_field_width` re-types the tokens
before the final `.` with `c_parse_direct_expression_type`, and reads a
bit-field width only if that probe succeeds on a struct or union.

The candidate answers width 0 exactly when the probe provably fails without
appending a row (`c_ast_types_probe_fails`). It mirrors the probe's
normalization (enclosing parentheses, leading `*`/`&`, the `++`/`--` it
treats as type-preserving), then takes the base before the first `[`, `.` or
`->` outside parentheses:
- **Leading identifier.** The machine walks the postfix steps after it and
  fails at the first token that is not a step. The candidate requires those
  steps to span an accepted `INDEX`, `MEMBER` or `MEMBER_ARROW` node. The
  tree accepts those only over an unqualified array or aggregate, which are
  the only cases where the walk's `c_parse_add_qualified_type` would append.
  Example: `prefix.length + 1 + modrm.length` as a shift's operand.
- **Any other base.** It must hold no `,` or `{` outside parentheses, so the
  descent stops there. It must not start with a string literal, `(` or a
  call's callee. `c_parse_direct_expression_base` then returns invalid
  before making any row, and nothing unwinds. Example: `a + s.f`,
  `c ? x : s.f`.

Everything else declines, even when the probe would also fail: casts
(`(u32)operands[0].index`), commas (`x, s.f`, where the probe succeeds through
the comma and reads the real width), and postfix chains over qualified
aggregates.

## Proof before code (census build of the base)

The census build marks, in the eager pass, every node that declined because
of a `C_AST_TYPE_NONE` width, and whether the candidate's predicate holds for
it. It records each predicted range, and checks every bit-field probe the
machine makes against it. Over the whole pilot `-fsyntax-only` compile:

| Bit-field probes on a member-tail range | Probes | Succeeded | Rows appended |
| --- | ---: | ---: | ---: |
| predicted to fail by the candidate | 546 | 0 | 0 |
| not predicted (member nodes, casts, commas, qualified chains) | 3,938 | 3,423 | 150 |

**Every predicted probe failed and appended nothing.**

Declines whose first refusing operand is the width rule (the census's
descent, from the query's node to its first unaccepted child): 1,440 runs,
against 1,424 in the census on `a6705764`. The base has moved since then:
24,919 declines here against 24,759 there. The runs split as follows:
- 512 where every `NONE` width is a predicted failure;
- 908 with an unpredicted width;
- 20 with both.

**The rows these runs append.** The 1,440 runs append 162 rows, against 120
in the census on its older base. A per-run log (`CENSUS_LOG`) prints each
appended row, and all 162 are const-qualified copies from
`c_parse_add_qualified_type`:
- 158 come from the machine typing *another* operand of the same query: a
  member or element step over a const aggregate, the census's qualified-member
  shape (row 1). Examples are `(u32)operands[1].index << 5` with `operands`
  pointing to const, and `preprocess->tokens` with `preprocess` a pointer to
  const. The census charges these runs to the width rule only because its
  descent stops at the first refusing operand.
- 4 come from bit-field probes on unpredicted ranges: successful probes
  through a qualified chain.
- 0 come from a predicted probe.

Three of the 512 predicted runs append one such row each, from a qualified
operand elsewhere in the query, so those queries still decline after the
change. That matches the arms: 508 fewer declines, not 512.

## Correctness

- **Objects.** Byte-identical across A, B, C and D: `-g0` sha256
  `7102b68d95125e0e…`, `-g` sha256 `da615f0174fe797c…`. No arm prints a
  diagnostic.
- **Corpus verify gate** (`c_ast_tests`, tests-on Release, Linux x86-64):
  0 mismatches. Tree answers checked against the machine went from 58,322
  on base to 58,365 on the candidate, all compared. Every floor passes.
- **Mutation check.** Handing the parent width 3 where the predicate says
  the probe fails gives verify mismatches:
  - 18 tree answers in `c_parse.c` and 26 in `c_gen.c`;
  - more in fixtures such as `tests/basic_c_local_aggregate_copy.c` and
    `tests/basic_c_packed_layout_callee.c`;
  - failures in the new `CAstTypeCase` probes.

  A wrong width therefore fails the gate.
- **New `CAstTypeCase` probes.**
  - Answered as `unsigned`: `(a + s.bits) << 1`, `-(a + s.bits)`,
    `(c ? a : s.bits) + 1u` and `(t.n + s.bits) << 1`.
  - Declined: `(x, s.bits) << 1` (the probe succeeds and reads width 3) and
    `(t->n + s.bits) << 1` over `struct S const*`.
