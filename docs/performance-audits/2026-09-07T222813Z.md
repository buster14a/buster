The one isolated copy-bound experiment had a small local selector improvement

## What actually selects instructions

`machine_select_generated.c` contains ten named declarative rules, but the
call-site search for `machine_selection_rule_select` finds only the definition,
declaration, and tests. Production native selectors do not dispatch through
that matcher. Packing those rows or indexing them by opcode would optimize a
diagnostic/test path, not current compiler throughput.

The diagnostic matcher has meaningful behavior that should not be casually
changed: FAST picks the first eligible rule in table order; QUALITY continues
the ordered scan and retains at most four additional alternatives. Candidate
cost is static rank plus a side-effect flag, not a measured target cost model.
The fallback row is QUALITY-legal but not FAST-legal; the no-match result has
`UINT16_MAX` estimated cost and sets the legacy-fallback flag. An attractive
microbenchmark must not erase these distinctions or masquerade as production
selection timing.

Production entry points are `machine_select_validated_canonical_function`,
`machine_select_canonical_function_x86_64`, and the AArch64 selector. The native
selectors directly dispatch canonical opcodes and selected operand forms.
There is no general production DAG-covering search to accelerate by indexing
this diagnostic rule table. Existing direct selection is the baseline, not a
proposed new abstraction layer.

## Requested optimization directions, against the inspected implementation

| Area | Existing mechanism and decision |
| --- | --- |
| Compact/predecoded patterns | Diagnostic rule rows are not on the production path. Production already consumes compact type/opcode facts. No new matcher table is justified by this audit. |
| Opcode-indexed candidates | Main selection uses direct opcode dispatch. x86 prepasses already retain `MachineX64CandidateRow {row, ordinal}` populations and use opcode-summary masks. Narrow a demonstrated remaining scan; do not add a second general dispatch table. |
| Operand predicates | `MachineTypeClass` is four bytes, carrying kind, flags and size/width logarithms; `place_kinds` avoids repeated definition decoding. Keep inexpensive pure flag predicates together, but preserve short-circuit guards around bounds, feature-specific operations and expensive shape decoding. |
| Feature filtering | Baseline vector capability is cached in selector setup; operation-specific checks use the requested target feature set. Do not replace target legality with host capability or blindly evaluate an unsupported SIMD path. |
| Batched legalization | ABI records and module type facts are already prepared outside per-instruction emission; signature plans are cached by module/type and filled lazily. Separate pure classification from stateful argument materialization, memory effects and emitted ordering. |
| Common canonical forms | Scalar operations, loads/stores, address forms, calls and branches already have direct target paths. Changing canonical preparation must include its own cost, not simply move work outside the selection timer. |
| Temporary allocation | Per-value x86 scratch is grouped into zero/none regions; atomic-success maps are conditional. Builder streams use chunks, cursor writes and same-arena single-chunk materialization without flattening copies. Further capacity changes need measured allocation and full-function evidence. |
| Metadata access | `MachineInstruction` is 24 bytes; `MachineOpcodeRow` is a 16-byte hot projection. Keep rare metadata cold and respect existing metadata-layout work rather than duplicate it. |
| Repeated traversal | Repeated operand prewalks and address-definition recovery remain candidates, tracked by #132 and #44. Build shared compact facts only when they replace enough consumer work to pay for construction and memory. |
| Cost and fallback | Production QUALITY decisions include placement spill/reload and callee-saved-register cost, not the diagnostic rule rank. Preserve whole-function unsupported, verifier, placement and encoder fallback attribution. |
| Abstraction removal | Remove measured duplicate fact construction or lookup, not necessary target/ABI boundaries. A shared caller/callee eligibility bit would be a correctness regression. |

The x86 setup already combines its per-value planes, stores co-read use facts
in a 16-byte `MachineX64ValueUse`, records row and ordinal together, and selects
dense layout traversal when available. These facts explain why a broad
"replace pointer-rich selector with SoA/SIMD" proposal would repeat work already
paid for rather than identify the present bottleneck. The earlier audit history
also records negative broad layout/branch-reduction experiments; they are not
new wins merely because a different instruction vocabulary is available.

## A correctness boundary in ABI cache reuse

`machine_x64_signature_plan` classifies a *call*. Its
`arguments_supported` can be false when an aligned stack argument opens a gap
that the caller's push machinery cannot emit. It also rejects certain variadic
vector arguments. The function-definition signature path separately computes
incoming placements and does not impose that caller push-gap restriction.

Therefore reusing the caller's eligibility result to accept or reject a callee
would incorrectly narrow the supported target subset. Share immutable shape
facts only after distinguishing caller and callee legality. Preserve hidden
results, aggregate parts, register classes, stack alignment, extension rules,
variadic AL/Windows conventions and the target-specific limit of the applicable
path. Cache lifetime must survive function-arena rewind without crossing the
module/target ownership boundary.

## Measured, unshipped experiment

At the inspected x86 selector entry, fixed-size signature shape and placement
arrays have 24 entries. After classification the code copies all 24 into the
zero-initialized selector even when the function has fewer parameters. The
experiment changed only that copy loop's bound from the array length to
`function_type->parameter_count`. It did not replace the arrays or change
signature legality. The experimental patch is preserved in the evidence bundle
as `isel-narrow-copy.patch`, not included in PR #254.

Nine outer A/B rounds alternated binary order, each invoking the same 30-sample
warm-IR benchmark. The first version of this replay used its untimed warmup to
populate ABI caches. The final implementation makes eager ABI preparation
explicit and, on updated main, invokes canonical module preparation first.
This difference is another reason to keep the historical numbers tied to the
actual prototype binaries rather than attach them to the submitted head.

| Workload | Functions | MIR rows | Baseline ns/MIR | Narrow-copy ns/MIR | Selection delta | FAST compile baseline ms | FAST compile candidate ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| many-small | 257 | 7271 | 52.465 | 51.083 | -2.633% | 21.559 | 21.653 |
| one-large | 2 | 5647 | 40.163 | 40.089 | -0.186% | 17.641 | 17.211 |
| abi-and-memory | 29 | 1985 | 42.748 | 42.531 | -0.508% | 15.780 | 15.653 |

The many-small selection reduction was 10.045 microseconds per replay, or about
1.382 ns per emitted MIR row. Its FAST fresh-process object compilation median
was slightly worse, not better. NONE also moved despite bypassing the selector:
this control prevents assigning every wall-time movement to the changed copy.
All compared objects remained byte-identical per allocator, and the generated
programs passed native execution under NONE, FAST, MIR_STACK and QUALITY.
This is insufficient evidence for shipping a production optimization.

A separate full-compiler translation-unit experiment compiled the same source
and include closure 40 times: five outer rounds, four allocators, two binaries,
with alternating A/B order. Source-closure hashes before/after agreed, and all
object hashes agreed within each allocator. The observed distributions were
highly variable:

| Allocator | Baseline median s (min–max) | Candidate median s (min–max) |
| --- | ---: | ---: |
| none | 2.399 (1.993–3.610) | 2.075 (1.990–2.464) |
| fast | 1.508 (1.446–2.241) | 2.065 (1.456–2.215) |
| mir-stack | 1.617 (1.536–2.450) | 2.088 (1.497–2.292) |
| quality | 1.814 (1.768–2.378) | 2.349 (1.721–2.544) |

Do not hide the apparent large regressions in the selecting modes or the large
NONE improvement. These noisy measurements do not establish an attributable
win or quantify the copy's effect. A dedicated Zen 5 A/B rerun and instruction
counters are required before making a throughput claim. The ad-hoc runner's
final JSON serialization failed on an `st_size()` typo after measurements and
the source-closure assertion completed; the JSON was reconstructed from all
40 preserved raw log rows and explicitly records that provenance.

The replay also reports supplied-arena consumption. For the historical
many-small workload, summed function deltas were 17,539,080 bytes, maximum
function delta 348,264 bytes, and module delta 47,288 bytes. Those are not peak
RSS, committed memory, or total malloc bytes: function scratch is rewound after
each attempt. Stream capacity and repeated setup deserve measurement, but
these counters alone do not prove that smaller chunks improve compile time.

## Benchmark and regression contract

PR #254 adds `ide bench-select` and `tools/selection_benchmark.py`. The C command
validates/prepares canonical input, freezes ABI records, verifies one untimed
MIR replay, then measures module preparation separately from function selection.
A stable numeric row records functions, selected IR/MIR counts, fallbacks,
timings and arena deltas; a second row records target identity/features.

The denominator is **emitted MIR rows before placement and encoding**, not
encoded ISA instructions or retired host instructions. Timed selection includes
its outer function walk, small counters, lazy module plans and arena rewind;
it is not cycle attribution to the selector body alone. Frontend work,
canonical preparation, eager ABI preparation and verification are excluded;
fresh-process time to an object is measured separately, including frontend,
backend and object writing but excluding linking.

The Python runner stores raw inner-summary rows, source/compiler/object
SHA-256 values, host/affinity/build description and outer medians. It refuses
changed target/work counts, fallback, malformed rows, stale/missing/empty
objects, changed object bytes, and sources/binaries changed during a run.
The execution oracle preserves raw stdout/stderr separately; replacement UTF-8
decoding cannot accidentally make distinct byte outputs compare equal.

Generated programs cover 256 small noinline functions, a 512-step unsigned
chain with independently calculated modulo-2^64 checksums, zero through 24
arguments, register/stack passing, mixed integer/floating aggregate
arguments/results, signed extension, indexed memory and branches/loops.
`--check` runs them under every requested allocator and exercises malformed
CLI/source, declaration-only and unsupported-signature rejection. Five Python
unit tests cover report validation, additive numeric fields and byte-output
identity. The 25-argument rejection fixture is explicitly the current selector
limit, not a permanent language restriction; update it when support expands.

The benchmark intentionally prints no success timing row on a verifier or
coverage failure. On the old recovered snapshot, raw frontend output from
`basic_c_operations.c` failed MIR dominance verification in `main`, with a
selected function containing zero CFG edges. This may be a preparation/verifier
contract mismatch; it is not asserted as a current-main miscompilation. The
newly merged canonical preparation path must be checked separately. Suppressing
that rejection just to populate a timing table would invalidate the benchmark.

## Completed prototype validation and unrun gates

The unchanged recovered baseline and the later benchmark prototype each passed
323,783/323,783 unit assertions across 39/39 modules. Baseline self-hosted stage
binaries were byte-identical at 36,348,448 bytes. Benchmark-prototype stages were
byte-identical at 36,376,856 bytes; its stage-2 frontend and selector benchmarks
also succeeded. These are separate fixed points within each source revision,
not an assertion that baseline and benchmark binaries have identical bytes.
Generated native regression runs and A/B object identity checks passed under all
four allocators. The latest Python runner's five self-tests passed.

The exact rebased head, TCC bootstrap gate, full sanitizer/compiler/platform
matrix and dedicated Zen 5 PMU validation were not completed at audit recording.
The PR is draft for these disclosed reasons. Its live checks, not this historical
paragraph, govern subsequent merge readiness. No generated-code correctness or
Zen 5 speed claim is inferred from a warm replay alone.

## Reproduction and next work

Run from the repository root, using the supported build driver and the same
host-compiler policy for both binaries. The detailed measurement contract is
in `docs/instruction-selection-benchmark.md` in PR #254.

```sh
./build.sh test_self_host --config Release
python3 tools/selection_benchmark.py --self-test
python3 tools/selection_benchmark.py --compiler build/Release/ide --samples 8 --allocators none fast mir-stack quality --check --output build/selection-benchmark/smoke.json
python3 tools/selection_benchmark.py --compiler /absolute/base/ide --candidate /absolute/candidate/ide --samples 12 --allocators none fast mir-stack quality --check --cpu 0 --build-description 'Record commits, compiler/version, flags, host and configuration' --output build/selection-benchmark/ab.json
```

Select an allowed CPU for affinity; preserve raw samples, not just a best run.
For the historical non-unity workaround the build driver was compiled with
Clang, followed by `generate --cc clang --linker DEFAULT
-DBUSTER_UNITY_BUILD=OFF -DBUSTER_DEBUG_INFO=OFF` and
`build --config Release -t ide -- -j1`. Unit tests used
`BUSTER_TEST_JOBS=1 <binary> test --verbose=1 --ci=1`. Manual self-host stages
used `cc -Isrc -Ibuild/generated -DBUSTER_UNITY_BUILD=1
-DBUSTER_INCLUDE_TESTS=0 -g -v -lm <compiler-source.c> -o <stage>` and `cmp`;
`-lm` matches the Linux build-driver dependency. This workaround does not
replace the repository's canonical bootstrap requirement.

The highest-value continuation is to profile current-main production selection
on the intended Zen 5 host, then revisit the already tracked operand-fact
population in #132 and address recovery in #44, with #42 owning selector
boundary cleanup. Include row/operand visits, scratch traffic, retained
instructions and whole-compile cost. Preserve target-feature, ABI, volatile,
atomic, TLS, relocation, signedness and pointer-width cases. A new fact stream
must remove more work than it adds; an unchanged NONE control, unchanged
selected work and unchanged object bytes make attribution substantially more
credible. Do not start by optimizing the test-only rule table.
