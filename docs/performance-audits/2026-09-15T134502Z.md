`2026-09-15T134502Z` (Linux x86_64, 4-vCPU Intel Xeon @ 2.10GHz KVM guest, no
PMU; **Per-value block fill screening for the x86-64 selector: negative
disposition**).

## Disposition

**Negative. Neither half of [#560](https://github.com/buster14a/buster/issues/560)
is worth implementing, and the premise under both — that the per-value block's
two fills are a compiler-throughput cost — does not survive measurement.** The
filing's fill byte counts are confirmed and have grown with the tree. What the
filing did not establish, and what this screen measures, is that those bytes
are 0,069% of the compile's instructions and no measurable time at all; that
the proposed present bitmap would spend more instructions on the read side than
the fill spends in total, losing outright on the array it most obviously aimed
at; and that the zero half's capacity hypothesis is false on this workload. No
code change is made. This is recorded so the screen is not repeated silently.

## Method

Revision `c96696e41329ca3b62b06e9b2d441d8ddf30ca49`, branch
`claude/issue-560-l7h8dk`. Workload: one frozen `git archive` of that commit,
compiled as the unity translation unit

```sh
ide cc -c -I<frozen>/src -I<frozen>/generated \
    -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 -g \
    <frozen>/src/buster/apps/ide/ide.c -o out.o
```

Freezing the input is what makes the comparison a comparison. The instrument
and the probes live in `machine_x86_64.c`, which the live tree's unity build
feeds to the compiler under test, so an unfrozen workload has candidate and
baseline compiling different source. Every compiler here — baseline, both
sizing probes, both `-march` variants — produces the byte-identical object
`7feb46b8dde965d40745fda3a8ee0f60b626dfb16edff7eb90671efcaf7d3dd5` from the
frozen tree, which is the selection-output identity check for all of it.

The workload allocates the block 4.793 times; 4.791 selections then run to
completion, so the two counts differ by the functions that allocate and are
rejected before finishing. Read and sentinel counts below come from the
instrument, present populations from the 4.791 completed selections.

Selection runs single-threaded here: the compiler's only `lane_run` splits
translation units, and this is one unit.

The screening instrument was temporary and is **not committed**. It rewrote the
100 read sites of the six `UINT32_MAX`-initialized arrays to a counting
accessor and added a per-function shadow map; it reproduces the baseline object
through that rewrite, so the rewrite is semantics-preserving. The existing
`BUSTER_BENCH_ALLOCATIONS` census and `-fsource-metrics` were read first and
carry neither per-array read populations nor sentinel-versus-value reads; no
metrics path was added to the tree.

## What the fill actually costs

Callgrind, on an `-march=x86-64-v3` build so the AVX-512 kernels appear as their
`simd.h` fallbacks and Valgrind 3.22 can decode the binary — the `-march=native`
build this machine otherwise produces aborts on EVEX:

| site | Ir a compile | calls | share of compile |
|---|---:|---:|---:|
| the zero region | 34.803.581 | 4.793 | 0,045% |
| the "none" region, `0xff` | 17.997.545 | 4.793 | 0,023% |
| **both fills** | **52.801.126** | | **0,069%** |
| every `memset` in the program | 948.842.866 | | 1,24% |
| PROGRAM TOTAL | 76.712.366.767 | | 100% |

This confirms the filing's figures (33.949.578 and 17.551.853 over 4.755
functions; the tree now selects 4.793). It also reframes them. The filing's
"15,2% of the 338.167.692 the whole compile writes through `memset`" is a share
of fill *bytes*, and all fill bytes together are 1,24% of the compile. The two
fills are 5,6% of the compile's `memset` instructions and **0,069% of the
compile**.

## The fill is not memory traffic that not filling would avoid

Priced in situ with behavior-identical probes — the block's two fills repeated
verbatim, so selection results, the single-allocation layout, region ordering
and arena ownership are untouched and the frozen object still matches:

| build | fill bytes a compile | median | min | user median | peak RSS |
|---|---:|---:|---:|---:|---:|
| baseline (`native`) | 56.846.304 | 7,320s | 7,039s | 6,541s | 1.027.344 KB |
| 8× fill (`native`) | 454.770.432 | 7,110s | 6,919s | 6,484s | 1.027.344 KB |
| baseline (`v3`) | 56.846.304 | 7,212s | 6,845s | 6,660s | 1.027.352 KB |
| 8× fill (`v3`) | 454.770.432 | 7,117s | 6,835s | 6,576s | 1.027.352 KB |

Nine interleaved samples each. **Multiplying the block's fill by eight — an
extra 398 MB a compile — is invisible on both ISAs**, and lands inside noise in
the faster direction on every estimator: median, minimum and user time. A 2×
probe run earlier over seven samples behaves the same way.

Two structural reasons, and they are why the byte count misleads:

1. The block is about 12 KB per function (7,7 KB zero, 4,2 KB none) and the
   selector's arena is reset for each of the 4.793 functions. The 56,8 MB is
   the same handful of pages written 4.793 times. It stays resident in L1/L2,
   and the passes that read it run immediately after, so the fill largely
   warms lines those passes were about to fetch anyway.
2. For the same reason **no fill change can move peak RSS**, which is identical
   to the kilobyte across all four builds. The 51,5 MB is not comparable to the
   53,8 MB of whole-stream per-token arrays PR #559 removed: those were live
   simultaneously and took peak RSS down 18.784 KB; this is one small block
   reused. The filing's "for scale" comparison is the part that does not
   transfer.

## Why the present bitmap loses, in the filing's own currency

The fill costs 0,893 Ir a byte here, so each "none" array's fill is about
3.599.509 Ir a compile. A present bit costs at minimum a byte load, a test and
a branch on every read; two Ir a read is generous to the proposal, and ignores
that the present byte is a second line, not the one the value lives in:

| array | fill Ir saved | reads | added Ir at 2/read | net |
|---|---:|---:|---:|---:|
| `value_virtual_registers` | 3.599.509 | 2.708.980 | 5.417.960 | **−1.818.451** |
| `value_stack_slots` | 3.599.509 | 787.843 | 1.575.686 | +2.023.823 |
| `value_indirect_slots` | 3.599.509 | 139.423 | 278.846 | +3.320.663 |
| `value_def_blocks` | 3.599.509 | 173.106 | 346.212 | +3.253.297 |
| `load_aliases` | 3.599.509 | 162.010 | 324.020 | +3.275.489 |

Applied to all five as filed the bitmap nets 10.054.821 Ir, **0,0131% of the
compile**, and it is a net loss on `value_virtual_registers` — the densest
array, 90,4% present, where nine reads in ten want the value and would now pay
to be told so. Applied only to the four that win, it nets 0,0155%. Against
that, 3.971.362 reads a compile move from one load to a load, a test and a
branch, in the selector's hottest path, across 100 read sites — and the
wall-clock probes say the fill side of the trade is worth nothing to begin
with. No version of this trade pays.

## Why the capacity hypothesis for the zero half is false here

The zero half rests on "the block is sized by `function->value_count`, the whole
value id space, and the selector visits the values a function actually defines".
On this workload those are the same set. `value_def_blocks` is present for
**1.007.264 of 1.007.264 entries** — every value id in `[0, value_count)` is
defined, as a block parameter or an instruction result — and the per-function
high-water mark of touched ids sums to exactly `value_capacity`. There is no
capacity to reclaim without changing what the IR hands the selector, which is
outside this issue and belongs to #52.

Sparse id spaces do exist: `tests/basic_c_atomic_pair_contention.c` selects 49
value ids of which 24 are defined. They are not what the unity self-compile
looks like, and they occur in small functions where the absolute bytes are
trivial.

## Measurements not available

- **No PMU.** `perf` is absent and the guest exposes no counters, so cycles,
  cache misses and stalls are unmeasured. Ir and wall clock are the whole
  currency here, as in the filing.
- **No per-array read populations for the seven zero-region arrays.** They were
  not instrumented individually. The zero half was screened on its stated
  premise, capacity, which `value_def_blocks`' 100% density refutes directly,
  and on the fill-cost probes, which cover both regions together.
- **Ir on `-march=x86-64-v3`; timings on both `v3` and `native`.**
  Architecture-neutral byte counts transfer, Ir totals do not.
- **No self-host, `test_all`, `test_mode_matrix` or sanitized run.** This audit
  changes no code, and the documentation row of the validation table in
  `AGENTS.md` does not require them. The tree was rebuilt clean afterwards and
  reproduces the frozen object above.
- **Uninstrumented paired measurements exist only for the probes**, not for a
  candidate implementation, because none was written. That is the finding.

## One defect noticed while screening, not fixed here

[`machine_x86_64.c`](https://github.com/buster14a/buster/blob/c96696e41329ca3b62b06e9b2d441d8ddf30ca49/src/buster/lib/compiler/codegen/machine_x86_64.c#L6703-L6704)
stores `atomic_success_registers[instruction->result.value] = success_register`
twice in a row, identically, on the `CMPXCHG16` path. The second store is dead.
It is harmless and unrelated to this screen's subject, so it is left to a
focused change rather than folded into an audit.

## If this is revisited

Do not re-screen the fill. The result to overturn is not the byte count, which
is confirmed, but the 0,069% and the invisible 8× probe. A revisit needs a host
where the fill is not L1/L2-resident — a far larger `value_count` per function,
or a PMU showing the fill's stores actually stalling — and it must price the
read side, because that is where the proposed fix spends. On this tree and this
workload the per-value block's initialization is not a throughput problem.
