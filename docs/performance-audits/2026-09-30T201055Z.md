## Source observation, hypothesis and measured mechanism

The historical successful ARM job 110038480978 in run 36759465982 records
398.190s for the nine behavior cases. Sixteen serial wrapper children have
observed lifetimes 22.183–24.070s; the deliberate six-writer batch takes 35.531s.
Cold/warm reuse, corruption, flag/compiler/dependency invalidation and error cases
are distinct ordered scenarios, each creating its own repository/cache/environment.

Hypothesis: overlap independent scenarios without changing their work or reducing
publication contention coverage. The eight regular cases contain sixteen serial
wrapper launches. Admit two of those cases concurrently; keep the publication
case's six launches exclusive. The useful-work count stays 22; only case admission
changes. Both serial and parallel arms use the same loader, original assertions,
per-child owner, scenario ordering and added timing records.

The ARM case durations remain broadly similar between arms: two- and three-launch
scenarios still cost about 45s and 68s; publication remains about 35s. Phase time
falls by overlap rather than making each wrapper fast. For example, pair 2:
serial dependency/compiler invalidation 67.488s versus parallel 68.178s, serial
publication 35.125s versus parallel 35.205s.

Constructor and cleanup clocks are separately retained. x64 pair-2 launch sums
are 0.000s serial / 0.063s parallel at the clock's resolution; collection sums
are 13.390s / 14.529s and cleanup sums round to zero. These sums are not CPU work
and overlapping collection intervals are not phase latency. Scripted child work
and waiting are not separately observable with these clocks. No diagnosis of
PowerShell internals, Defender, emulation or storage follows.

## Counterargument and disposition

The strongest counterargument is that an unchanged analyzer or another later
lane can leave whole-workflow latency unchanged, while the new scheduler adds
ownership/cancellation code to maintain. CPU and RSS were not measured, and
three pairs on one machine do not cover every future hosted-image variation.
That prevents a global CI-speed claim.

The bounded phase win is nevertheless large on the reproduced ARM bottleneck and
positive on x64, with useful work and existing contention coverage preserved.
Adopt only the measured two-case budget in the existing Windows Release owner,
retain serial reproduction and the unchanged deadlines, and continue end-to-end
CI evidence in #709. No extra full-matrix job is justified by these measurements.
