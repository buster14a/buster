## Scope and method

This is a monorepo audit for hidden superlinear behavior, pinned at
`cf12953cd7c9cf2cb217ed28e47ad0179ce7f146` (tree `8b3781547ace5cde4b0988dc4425874cd97f0ffe`). It covered:

- repeated string processing
- growing-buffer copies
- symbol resolution
- graph traversals
- sorting inside iteration
- relocation processing
- archive extraction
- diagnostic aggregation
- recomputation after small mutations

Candidates were kept only if three things held:

1. A real caller reaches them.
2. Their input dimensions can grow independently.
3. No current issue or PR already tracks them.

Each kept candidate was measured with a C generator that varies one dimension
at a time, with the expected scaling written down before measuring. Each was
then compared against an alternative algorithm.

Measurement setup:

- Release `ide` from `./build.sh build --config Release -t ide`.
- Run on a Devin cloud VM (8 vCPU Xeon Platinum 8559C).
- The metric is `perf stat -e instructions:u`. Repeat runs varied by less than
  0.001%. Wall time was not used, and nothing here is a wall-clock claim.
- `perf record`/`annotate` attributes the cost. The relevant helpers are
  inlined, so hot loops were matched by record stride and field offsets.
- AArch64 output was checked with `llvm-objdump-18` and not executed.

No Python and no new dependency were added. Generators, runners, raw counts,
the measurement-only prototype and test-site summaries are in
[`evidence/2026-10-04T110828Z/`](evidence/2026-10-04T110828Z/).

## Findings

**[#2615](https://github.com/buster14a/buster/issues/2615): C
prepared-control-expression lookups.** These cost Θ((G + C) · P) per function.

- **Variables:** P is prepared control expressions, G is paren/bracket groups,
  C is call candidates.
- **Mechanism:** `c_ir_prepared_control_expression_find`, `_contains` and
  `_contains_range` scan the whole function's list for every group and every
  call candidate.
- **Scaling:** with C = 0, cost goes from 222.8 M instructions at P = 1,000 to
  6,949.9 M at P = 16,000. The increase per doubling of P is 2.9× to 3.3×.
- **Cross term:** 27 instructions per (call, prepared expression) pair. This
  predicted the per-call slopes at P = 2,000 and 8,000 to within 1%.
- **Alternative:** an indexed prototype uses an `open_index` hash, a LIFO
  lowering stack and verified per-token marks. It is linear, cutting P = 16,000
  to 2.09 G and removing the cross term.
  - Objects stay byte-identical on the generated input, the SQLite 3.46.1
    amalgamation and Lua 5.4.7 `lparser.c`.
  - The C frontend test failure sites are identical to the pinned build.
  - Extra memory is at most about 24 B per body token of per-function scratch.
  - Constant factor on real files ranges from −0.13% to +0.035%.
- **Realistic impact:** negligible. SQLite and Lua show no samples in these
  loops.

**[#2616](https://github.com/buster14a/buster/issues/2616): AArch64 branch
relaxation.** This costs Θ(K · (R + N + F)).

- **Variables:** K is branch expansions, R is machine rows, N is code bytes, F
  is fixups.
- **Mechanism:** after every expansion, `machine_a64_relax_branches` restarts
  its fixup scan. Each expansion then memmoves the code tail and rewrites every
  metadata stream.
- **Trigger and control:** a switch with K sparse cases jumping over an
  M-statement case 1 placed first. The control places that case last.
- **Measured excess over the control:**
  - About 3.0 M instructions per relaxation at 1.15 MB of code. K = 8,000
    costs 31.6 G extra in total.
  - Per-relaxation cost scales 1.50× when M grows 1.5×.
  - Zero below 1 MiB.
- **Profile:** 64.9% of samples are in `machine_a64_relax_expand_fixup` and
  13.8% in memmove.
- **Alternative:** a C model that applies all of a pass's expansions in one
  backward sweep plus a prefix-sum merge. It produces identical layout hashes.
  - It is 117× to 676× cheaper (20.5 M against 2.40 G instructions at
    K = 1,000).
  - Memory cost is 4 B per pending insertion. Because tiers only grow, it needs
    at most 3 passes.
- **Realistic impact:** low. It needs a single AArch64 function larger than
  1 MiB with long-range switch compare chains.

## Side findings

- [#2617](https://github.com/buster14a/buster/issues/2617): switch-case
  `b.cond` relaxes to the 32-byte long transfer even when a 4-byte `B` tier
  would reach. Disassembly shows this at a displacement of about 1.07 MiB. The
  tier-1 range test reads the existing word at P+4, which is the next compare's
  `mov`. A fix is not validated.
- [#2618](https://github.com/buster14a/buster/issues/2618): `gen_a64sw 1000
  80000 1` exits through `arena.h:240` validation in `c_ir_ssa_finish` instead
  of a diagnostic. Straight-line bodies of the same size get the structured
  diagnostics from #2487.
- [#954](https://github.com/buster14a/buster/issues/954): I added a
  lowering-side switch measurement. Frontend cost is superlinear in the number
  of sparse case labels: each doubling of K raises the increase by 2.7× to
  3.4×. Exclusive attribution to the prior-pair loop is not established.
