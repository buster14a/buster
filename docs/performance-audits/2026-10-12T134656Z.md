## Census that chose the design

This census uses a throwaway build of the base, which is not committed. It
puts the settlement, the per-mark check and the file-scope lookup in
noinline functions, and counts each path. Over the same input with
`-fc-ast-pilot`, the typer reports 132,116 settled checks and 179 walks.

| Census count | Value |
| --- | ---: |
| Settlements (regions settled) | 6,022 |
| Flag bytes scanned | 1,932,162 |
| Lookup marks checked | 125,907 |
| Marks recorded as "other" | 106 |
| Regions checked per query (more than 16 others) | 0 |
| Table builds (`c_ast_types_locals_build`) | 1 |
| File-scope lookups answered by the binding array | 125,801 of 125,801 |

Every file-scope lookup already takes the one-load binding path, because the
binding array stands for the file scope while the typer answers. So the
"no lookup at all" idea saves the call and its gates, not a chain walk. Most
of the cost is around the lookup, not in it.

The census's Callgrind split of `c_ast_types_lookups_settled`, inclusive
(the noinline wrappers add their own call costs):

| Part | Ir |
| --- | ---: |
| All of it, over 132,295 calls | 40.03 M |
| The query-time checks (generation, use count, others, rooted scope) | 6.47 M |
| The flag scan, eight bytes at a time, and the byte loop in groups with a mark | 11.87 M |
| The per-mark checks, of which: | 19.40 M |
| — the file-scope lookup call, with its gates | 6.79 M |
| — finding a call's callee through `c_ast_types_first_child` | 3.78 M |
| — the binding, its entity, and the entity's scope | about 7.5 M |
| The one table build | 2.28 M |

The design follows from that split:
- **A per-symbol file answer.** `c_ast_types_locals_build` already clears a
  byte per symbol and marks the symbols that an entity outside the file scope
  has. The candidate widens that to a `u32` per symbol (`CAstTypeSymbol`):
  - unseen;
  - local;
  - the file scope answers nothing;
  - the file scope answers entity `e`, stored as `e` + 3.

  The first mark of a symbol in a lookup generation calls
  `c_parse_lookup_entity_token` at the file scope and stores the answer. Later
  marks of that symbol read it.
- **The callee token from the call's own token.** `c_ast_types_call` marks a
  call only when its callee is the identifier directly before the `(` that is
  the call node's token, and `c_ast_types_builtin_call` is reached only from
  there. So the callee token is `tokens[call] − 1`. The new
  `c_ast_types_mark_token` reads it, in the settlement and in
  `c_ast_types_lookups_agree`.
- **The marks from each word's mask.** Each 8-byte group's mask of mark bits
  is walked with `mask64_first_set`, so a group visits only its marks, not
  every byte up to the last one. The tail group is assembled bytewise into
  the same word.
- **One scope load fewer.** An entity the file scope answers is a file-scope
  entity, so only an answer of nothing still needs the binding's scope.

## The change

All of it is under `-fc-ast-pilot`, in `c_ast_types.c`. The query-time check,
the "other" marks, the generation stamp and the walk are unchanged. So is
every rule.

**Why it is exact.**
- **The memo.** The file-scope lookup reads only what the lookup generation
  stamps (`c_parse_lookup_generation`).
  - The symbol table is used only while its build generation is current.
  - While that holds, one symbol looked up at the file scope gives one answer.
    The lookup path is `c_parse_lookup_entity_token` with the token's interned
    symbol, which ignores the spelling once a symbol is set.
  - A token that cannot spell a word is answered "nothing" by that function
    whatever its symbol. It is looked up each time and never stored.
- **The scope test it drops.** The test dropped from the entity case is implied:
  - the chain lookup answers only an entity whose scope is the one walked;
  - the binding array equals the chain under `BUSTER_REFERENCE_CHECKS`.
- **The callee token.** It is the token the old walk found, for every call
  that carries a mark.

## Correctness probes

`c_ast_test_type_lookups` gains two sources, each analyzed with the tree and
again with every answer verified against the machine:
- **One callee in three function bodies.** The bodies after the first settle
  on the answer the first looked up. Expected: settled, never walked.
- **A callee declared, then defined between its uses.** Expected: settled,
  never walked.

**Mutation check.** The mutation makes the memo store "local" in place of the
looked-up answer. A tests-off build of it walks the new cases' later regions:
- the first case: 0 settled and 4 walked, against 4 settled before;
- the second case: 1 settled and 1 walked, against 2 settled.

Both cases expect no walk, so both catch it. The existing shadowing cases
still cover the local-symbol condition.

I could not write a valid source in which a name's file-scope answer differs
from a file-scope binding while no local spells it:
- a block-scope `extern` is an entity outside the file scope, so it takes the
  walk;
- a callee used before its declaration is a diagnostic.

So the entity comparison is covered by the verify differential, not by a
probe that settles wrongly under a mutation.
