`2026-09-12T224432Z` (Linux x86-64 KVM guest, 4-vCPU Intel Xeon Emerald
Rapids, no PMU, callgrind Ir; **the four whole-stream per-token arrays and the
constant-initializer images move onto the zeroed-arena path: 69,6 MB less fill
a compile, byte-identically**).

The brief was an audit of the compiler, with no subsystem named. The
instrument decided the ranking, so it is decided first, as
`2026-09-07T013544Z` asked the next audit to do: this host has **no
performance counter**. `perf` is not installed, `perf_event_paranoid` is 2,
and no self-host stage printed a `STEP_INSTRUCTIONS` line in any run recorded
here. That leaves callgrind's Ir, which
[benchmarking.md](../agents/benchmarking.md) names as the currency in exactly
this case, and which counts the one thing `instructions:u` cannot see: a libc
ERMS fill costs one Ir a byte, so **a fill's Ir number is the bytes it moved**.
Every item below is a memory-traffic item, and every figure for one is stated
as bytes.

## Host and method

A 4-vCPU Intel Xeon (family 6, model 207, stepping 2 — Emerald Rapids) at
2,10 GHz under KVM, 15 GB, AVX-512 F/DQ/BW/VL/VBMI/VBMI2/VNNI/BITALG/VPOPCNTDQ
plus AMX, shared with whatever else the host is running. Clang 18.1.3, glibc
2.39, valgrind 3.22.0.

Every A/B compiles **one frozen tree** — `git archive` of
`5dab18af0208cfa7fa65673b6884d5c253fda85b`, the `main` this branch left — with
two saved compiler binaries and the same argument vector, under
`valgrind --tool=callgrind --cache-sim=no --branch-sim=no`, and `cmp`s the two
produced executables before the delta is read. The vector is the one
`self_host_compile_arguments` in `build.c` builds for stage 1:

```sh
ide cc -Isrc -I<build>/generated -DBUSTER_UNITY_BUILD=1 -DBUSTER_INCLUDE_TESTS=0 \
    -g -v -fsource-metrics=<out>.metrics src/buster/apps/ide/ide.c -lm -o <out>
```

A measurement is one run: callgrind is deterministic, so the alternating pairs
a timing method needs buy nothing. Freezing the tree matters here more than
usual, because the change is in the compiler's own source — compiling the live
tree would move the workload underneath the measurement.

**Valgrind 3.22 cannot decode EVEX**, so the measured binary is
`-march=x86-64-v3`: the configured Release compile command for the unity TU
with `-march=native` replaced and the same link line, which is the only
difference from `build/Release/ide`. Every AVX-512 kernel in the tree is
compiled out of it and appears as its `simd.h` fallback, so the Ir totals below
sit above what an AVX-512 build would retire and **an AVX-512 item is invisible
to this instrument** and would have to be priced by census. Nothing in this
audit is one. The `-march=native` build was gated separately, as
`2026-09-07T013544Z` requires: the two builds do not produce the same output,
because the host build's feature set reaches the compiler's own target
defaults.

TCC is not installed in this image, so the build driver was
bootstrapped with the documented Clang exception
(`clang -Isrc -Wall -Werror -Wno-unused-function -Wno-unused-variable -g build.c`),
exactly as `ci.yml` does. This is not a local TCC bootstrap claim.

## What landed

**The four per-token arrays store their value plus one (-57.181.953 bytes,
-51.657.501 Ir).** The bias is already this codebase's spelling for the same
problem — `CEntity.declaration_token_plus_one` is read as `- 1` a few lines
from one of these arrays — and it is free at every reader, which is the whole
reason it is worth doing rather than adding a present-bitmap: **`0 - 1` is
`UINT32_MAX` in unsigned arithmetic**, so a decode that subtracts one turns the
unwritten zero back into exactly the sentinel every reader already tests, and
no reader grows a branch. `c_parse_matching_delimiter_indexed` returns
`... [open] - 1`; `c_parse_identifier_use_index` returns
`... [token_index] - 1`; `c_ir_matching_delimiter_cached` subtracts one and
lets its existing `match < end` test reject the result; the two
`== UINT32_MAX` owner tests become `!` and `- 1`. The fields are renamed to
`_plus_one` so the encoding cannot be read past: an array whose name does not
say it is biased is a bug waiting for its next reader. `token_entities` changes
type with its encoding, from `CEntityId*` to `u32*`, and the three registered
oracle seams and the position-index oracle's expectation array move with it —
they assert the production array element for element, so they assert the new
encoding too. `token_classes`, one byte a token beside
`identifier_use_by_token_plus_one` and already zero-sentinelled, takes the
zeroed path in the same edit (3.363.657 bytes).

**The constant-initializer images are allocated zeroed (-12.445.545 bytes,
-12.393.144 Ir).** Five `arena_allocate` + `memset(bytes, 0, size)` pairs in
`c_gen.c` that build a global's or a compound literal's byte image in
`builder->arena` and then overwrite the part the initializer names. That arena
is the lowering's forward-growing result arena, so the fill was writing zeros
over pages that were already zero. This is the general form of the change
`2026-09-07T013544Z` made for six other single allocations; these sites were
left then and are not a scratch arena.

**Both together.** On the frozen tree, byte-identical output at every step:

| | pristine | this head | delta |
|---|---:|---:|---:|
| stage-1 total | 13.749.246.043 Ir | 13.685.195.398 Ir | **-64.050.645 (-0,466%)** |
| `memset` | 338.167.692 B | 268.540.194 B | **-69.627.498 (-20,6%)** |
| `memcpy` | 180.282.159 B | 180.282.429 B | +270 |
| total less libc's fill | 13.411.078.351 | 13.416.655.204 | **+5.576.853 (+0,042%)** |

The last row is the honest price and the reason the headline is in megabytes:
the compiler's own instruction count goes **up** by 5,58 M — the `+ 1` at every
store, the `- 1` at every load, and two loads and a compare inside each zeroed
allocation — and that buys 69,6 MB it no longer writes. On this instrument the
fill is 1 Ir a byte; on the machine the same `rep stosb` retires one
instruction and costs only bandwidth, so a counter-based audit would see this
change as a small regression and be wrong about it. Which of the two numbers
matters is a property of the machine, not of the diff, and this host cannot
settle it: 69,6 MB is a few milliseconds of one DDR5 channel at its peak
against a compile that takes about 1,7 s of user time here, but a store that
never leaves the write-combining path costs less than that and a cold one
costs more, and the 5,58 M added instructions are predicted, dependency-free
and spread over 3,36 M tokens. What the change does establish is that the
compile writes 20,6% less memory for the same bytes out.

**Peak resident memory falls with the fill, and repeats.** A fill is not only
bandwidth: a page that is written is a page that must be resident, and these
arrays were being touched end to end for a sentinel the reader could infer.
Three runs of each native compiler, peak RSS and page faults from the child's
own `rusage`:

| native stage-1 | pristine | this head |
|---|---:|---:|
| peak RSS | 1.029.800 / 1.029.968 / 1.030.024 KB | 1.011.184 / 1.011.260 / 1.011.176 KB |
| minor faults | 255.740 / 255.896 / 255.889 | 254.046 / 254.052 / 254.050 |

That is **-18.784 KB of peak RSS (-1,82%)** and **-1.839 minor faults
(-0,72%)** on medians, and both series repeat to within 200 KB and 6 faults —
a spread two orders of magnitude below the delta, which is what makes this the
one end-to-end result this host can actually support. It is smaller than the
69,6 MB of fill removed, and it should be: some of those bytes were being
written over pages the compile then uses anyway, and only the pages nothing
ever touches leave the resident set.

The tiny compile (`ide cc -c` of `int main(void){return 0;}`) is
118.337.339 -> 118.337.377 Ir, which is the expected shape: the arrays are
sized by token count and a four-token unit has nothing to fill either way.

Wall time on this host does not support a claim and none is made. Min-of-four
user time on the native stage-1 compile is 1,641 s pristine against 1,680 s
here, medians 1,936 s against 1,772 s — the two orderings disagree, which is
what a shared 4-vCPU guest looks like. `ide bench` is 1.618.246 ns min /
1.691.373 ns median pristine against 1.653.755 / 1.707.248 here, on a 21.042-byte
input that allocates none of these arrays at a size worth measuring.

## Left standing, ranked

Shares are against 13.685,20 M, where 1% = 136,9 M. Fill figures are bytes
written a compile, which this instrument reports directly.

- **`c_ir_ssa_grow_slots` writes 70,8 MB a compile, the largest single item
  left**, and it is not a sentinel problem: the direct-SSA slot table doubles
  from 64 entries and is cleared whole at every doubling, so 8.172 grows for
  4.755 functions pay for the same table several times over. It is a
  per-function scratch arena, so the zeroed path cannot help; what would is a
  first capacity taken from the body's local count, which the builder already
  knows before the first insert.
- **The selector's per-value block is 51,5 MB** (33,9 zero + 17,6 "none"), the
  item `2026-09-07T013544Z` ranked second and which has grown with the tree. The
  "none" half is five or six `u32` arrays set to `UINT32_MAX`; the bias that
  landed here does not apply, because the block is a per-function scratch arena
  that is dirty by construction — a one-byte present bitmap beside them would,
  at the cost of a load and a test on each read.
- **`CIrExt80Big shifted = {0}` is 8,65 MB over 2.101 calls** (`c_gen.c:8634`),
  which is a 4 KB `u32 limbs[1024]` zeroed on the stack for a shift that then
  writes `value->count + limb_shift` of them. Clearing to the used length is a
  two-line change; it is left here only because it is not a fill of the class
  this audit was working.
- **`ir_validate_canonical_module` is 1.181 M Ir, 8,6% of the compile.** The
  validation is required before backend consumption and is not a candidate for
  removal, but nothing has ever measured what inside it costs, and 8,6% is
  larger than the whole of `machine_encode_x86_64`.
- **`ir.c:4404`'s instruction-owner map, 9,9 MB over 14.265 calls.** It looks
  like the same `0xff` shape as the four arrays above and is not: the buffer
  is one scratch array sized to the largest function and reused for every
  function in the module, so the fill is already only
  `function->instruction_count` entries (692 bytes a call) and it is *load
  bearing* — without it the previous function's owners would read as this
  one's. Biasing the sentinel would not remove a byte. The only form that
  would is a generation stamp compared on each read, which trades 9,9 MB of
  fill for a compare in the ownership walk and has to be measured rather than
  assumed.
- **`link.c:2885`, 5,5 MB in one call**, fills the tail of an image whose head
  is a `memcpy`. Allocating the whole image zeroed and dropping the tail fill
  is the same trade, with a branch above it that hands `bytes` from elsewhere.

`-I` the vector names, and run the stage-1 vector quoted at the top from

`valgrind --tool=callgrind --cache-sim=no --branch-sim=no`. Read the total from
valgrind's own `I refs` line and the per-site fill ranking from the
`calls=`/`cfn=` records of the callgrind output, which carry the caller's
source line; `callgrind_annotate --tree=caller` gives the same attribution per
function. Compare only same-`march` binaries for byte identity.
