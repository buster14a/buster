Compilation: 7 alternating/rotating round samples, one untimed warmup.
End-to-object commands use -O2 -std=gnu17 -fno-pic -c. Buster additionally

Buster default-target profile reports cpu=znver4 vector_bits=512; CCC and

Timing: monotonic perf_counter around compiler subprocess from fresh Python
wrapper, excluding wrapper interpreter startup, including compiler process
spawn/startup and object writing. Initial Python wrapper resource RSS had
approximately 10MiB pre-exec memory floor on tiny CCC processes. RSS was
therefore corrected with 3 extra compile samples in a small C fork/exec/wait4
timer (ru_maxrss KiB). Those separate RSS samples and original floor-affected
values are retained in raw_results.json; accepted compile WALL times and
runtime times were not replaced. Current harness uses the C helper for new
reproductions. This small wrapper-method change can alter spawn overhead
slightly. cJSON and all synthetic cells compiled under all 4 variants.

Runtime: the same compiler-generated objects linked through clang20 -no-pie,
common libc; cJSON additionally common libm. Thus speed results concern
generated code, not bundled linkers. Arrays fit in small caches, so these do
not measure cache-miss behavior, SIMD512 throughput, multi-threading or I/O.
8 header-free synthetic kernels use unsigned defined wraparound arithmetic
and FP powers of two, avoiding signed overflow and FP reassociation alarms.
Seed and repetition input come from argv. Checksum is printed and consumed.
All 72 seed/repetition/kernel cases per BusterFAST/BusterQUALITY/CCC matched
Clang20 stdout. Stock cJSON parse/print/free driver matched Clang for reps
1/3/19. Every timed run and full warmup also matched the oracle. This proves
only these checked cases, not general compiler or cJSON-suite correctness.

Runtime repetitions are common across compilers per kernel, calibrated on
Clang20 to approximately 35-65ms. 5 rotating/alternating samples follow
warmup. Runtime wall includes process startup and array initialization.
Raw min/max ranges are retained. FP FAST/CCC ranges do not overlap in this
capture (FAST minimum184.317ms; CCC maximum180.431ms), while QUALITY/CCC

Disassembly-supported optimization opportunities:
1. helper inlining: Buster inlining kernel retains two call relocations to
   helper per inner iteration (runtime_buster_fast.disasm.txt offsets e75,
   ec8), while CCC inlining kernel has no calls. CCC also hoists helper
   invariants. Measured whole-kernel gap1.907x, not attributable solely to
   calls because allocation/instruction selection differ too.
2. LICM: CCC computes x*y at2e8, x+y at2f0, and seed&15 at303 before loops.
   Buster repeats invariant multiply at8b3, addition at8e0, mask at92c in
   inner loop. Whole-kernel gap2.483x. Add safe loop-invariant hoisting with
   dominance, trap/side-effect/alias legality; test unsigned/floating cases
   separately to preserve language semantics.
3. if conversion: CCC branches kernel uses cmovne at8e3; Buster uses a
   conditional jump at10cc and stack-mediated branch merges. Clang uses
   conditional branches too. CCC3.651x faster than Buster and1.598x faster
   than Clang here. Add costed diamond-to-select lowering for safe small
   arms; do not infer that unconditional branchless code always wins.
4. constant division: Buster uses two div rcx per element at649/68a, including
   /37. CCC retains variable divide at17b but lowers /37 to unsigned magic
   multiplication and >>5 around1a1-1e9 (not especially compact!). Gap1.525x.
   Add unsigned and signed exact division/remainder-by-constant algorithms,
   with high-product lowering and boundary/differential tests.
5. GVN/CSE: CCC GVN kernel has a single x*y computation at4cf and reuses
   x*y+seed. Buster repeats multiplications and stack traffic. Whole-kernel
   gap2.231x. Add value numbering before allocation, with memorySSA/alias
   reasoning only where needed, plus dirty-function scheduling/budgets.
6. register/value placement and addressing: Buster spills/reloads even f0:
   166-byte body vs CCC73-byte body; scalar_4 total.text694vs295B. Constant
   shifts use CL in Buster vs immediate encodings in CCC, *3 uses imul plus
   constant register in Buster vs lea in CCC. Reduction accumulator and
   counters use stack homes in Buster; CCC keeps key values in registers
   though still has needless moves/spills. Improve live-range persistence,
   copy coalescing, immediate operand selection, fold scaled addressing and
   removable jump/mov chains before introducing a broad vectorizer.
   Scalar frontend SSA was active: profile says fallback_locals=0.
   All profile runs report codegen fallback_functions=0; gaps are actual
   current native FAST behavior, not fallback path measurement.
7. startup/small-TU compilation: Buster15-21ms vs CCC2.8-6.2ms on tiny scalar
   inputs. Profile CLI/OS/arena/target initialization and fixed per-module
   work, add lazy setup or persistent compile batch service as evidence
   warrants. Do not assert a specific root cause without startup profiling.
